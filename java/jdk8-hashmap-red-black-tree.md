# JDK8 中 HashMap 为什么要转成红黑树

> 类型:Java 基础 / 集合框架
> 提问频率:⭐⭐⭐⭐⭐

---

## S (Situation) — 背景

JDK7 及以前的 HashMap 采用「数组 + 链表」解决哈希冲突:

- 计算 key 的 hash 值 → 定位到数组的桶 (bucket) → 多个 key 冲突时用链表串联
- 当 hash 冲突严重时,链表会变得非常长
- 链表查询需要从头遍历,**最坏情况时间复杂度退化为 O(n)**
- 一旦遇到恶意构造的 hash 值(比如已知 hashCode 规律的 key),HashMap 会退化成一条长链表,查询性能灾难性下降,甚至引发 DoS 攻击(历史上真实发生过的漏洞场景)

## T (Task) — 要解决的问题

在**不显著增加内存和写入成本**的前提下:

1. 把极端情况下 HashMap 的查询性能从 **O(n) 提升到 O(logn)**
2. 同时保证常规场景仍然是 O(1),不能因为防御极端情况拖累正常性能

## A (Action) — 解决方案与原理

### 1. JDK8 的核心改动:链表 → 红黑树

JDK8 中,HashMap 的存储结构变为「数组 + 链表 + 红黑树」:

- 当**链表长度 ≥ 8** 且 **数组长度 ≥ 64** 时,链表树化为红黑树
- 红黑树是自平衡的二叉查找树,**插入 / 删除 / 查找的时间复杂度都是 O(logn)**

### 2. 为什么选红黑树,而不是 AVL 树或跳表?

| 方案 | 比较 |
|---|---|
| **AVL 树** | 平衡更严格,查询更快,但维护平衡需要**频繁旋转**,插入删除开销大;HashMap 以插入为主,不划算 |
| **跳表 (SkipList)** | 需要多级索引,每个元素要存多级指针,**空间开销大**;Redis 用跳表是因为 ZSet 需要范围查询,HashMap 不需要 |
| **红黑树** | 允许局部不平衡,**旋转次数少**,插入删除效率高,查找 O(logn),综合最优 |

### 3. 为什么树化阈值是 8?

源码注释基于**泊松分布 (Poisson Distribution)** 计算:

- 负载因子为 0.75 时,某个桶中恰好出现 k 个元素的概率服从泊松分布
- 链表长度达到 **8 的概率约为 0.00000006(千万分之六)**,几乎不可能发生
- 所以:**超过 8 意味着 hash 分布严重异常**,此时树化才值得(红黑树节点 TreeNode 是普通 Node 的 2 倍大小,占用更多内存)
- 8 是「性能 + 空间」的平衡点:正常情况下永远不会树化,异常时兜底

### 4. 为什么退化阈值是 6,而不是 8?

- 如果退化阈值也是 8,元素数量在 7、8 之间反复横跳时,链表会**频繁树化 / 退化**,白白浪费性能(称为「抖动」)
- 阈值设 6,与 8 之间留出缓冲区间,避免频繁转换

### 5. 树化的第二个条件:数组长度 ≥ 64

- 即使链表长度 ≥ 8,如果**数组长度 < 64**,也不树化,而是**先扩容**
- 扩容后数组变长,原有冲突的 key 会重新散列分布,**链表自然变短**,比直接树化更划算

### 6. 补充细节

- 扩容时,红黑树会被**拆分**成两个链表,若长度 < 6 则退化为链表(UNTREEIFY_THRESHOLD = 6)
- 红黑树节点 `TreeNode` 继承自 `Node`,额外持有 parent / left / right / red 等字段,内存约为普通节点的 2 倍——这也是不轻易树化的原因

## R (Result) — 效果

- 极端哈希冲突场景:查询从 **O(n) 降为 O(logn)**
- 常规场景:仍然是 **O(1)**,性能无损失
- 通过「8 / 6 / 64」三个阈值的组合设计:正常情况不树化(省空间),异常情况有兜底(保性能),同时避免树与链表的频繁抖动

---

## 💡 追问点速背

1. **为什么不是 7 或 9?** → 泊松分布,概率 0.00000006 说明 8 是正常分布的极限
2. **为什么有 64 的限制?** → 数组太小时扩容比重建树更划算
3. **红黑树 vs AVL?** → AVL 查询快但旋转多,红黑树平衡要求宽松、写入快
4. **JDK7 有什么问题?** → 头插法 + 并发扩容成环导致死循环(JDK8 改尾插法解决)
5. **HashMap 不是线程安全的,并发怎么办?** → ConcurrentHashMap(JUC 包)
