Redis可以用来做什么？

联想记忆法

记忆口诀/联想

口诀：缓存提速、计数统计、锁控并发、队列解耦、排行定位、状态托管。

也可以把 Redis 想成一个“高频临时状态中心”：

  • 访问太快，数据库扛不住，用它做 缓存
  • 数据要不断加减，用它做 计数器
  • 多个服务抢同一资源，用它做 分布式锁
  • 请求不想同步硬顶，用它做 消息队列
  • 数据要排序比较，用它做 排行榜
  • 用户在线、Token、会话这类临时状态，用它做 状态存储

记忆原理

这个口诀不是按数据类型记，而是按业务目标记。面试官问“Redis 能做什么”，本质是在考你有没有把 Redis 真正放到系统设计里用过。按“加速、统计、控制、解耦、排序、托管状态”这六类场景回答，会比单纯背 String/Hash/List 更像工程思维。

关联知识

  • 会关联到 数据类型：不同场景要匹配不同结构
  • 会关联到 缓存一致性：缓存不是用了就完，还要考虑更新策略
  • 会关联到 高可用：做核心链路时要考虑主从、哨兵、Cluster
  • 会关联到 消息队列边界：轻量场景能用 Redis，重事务场景更适合 Kafka/RabbitMQ

深度解答

1. 核心概念：Redis 最擅长的是“高频、低延迟、状态型”场景

Redis 是内存数据结构数据库，它最大的优势不是“会存数据”，而是能用极低延迟管理大量高频状态变化。
所以判断能不能用 Redis，通常看三个条件：

  1. 访问是不是很频繁
  2. 数据是不是可以接受驻留内存
  3. 业务是不是更关心读写速度，而不是复杂查询

如果这三个条件基本满足，Redis 往往就是很强的候选。

2. 实践应用：Redis 常见使用场景

场景一：缓存热点数据

这是最常见的用途。把数据库里访问频率高、变化频率相对可控的数据放到 Redis 里，减少数据库压力。

请求 -> Redis
       -> 命中，直接返回
       -> 未命中，再查 MySQL 并回填 Redis

典型例子：

  • 商品详情页
  • 用户基础信息
  • 首页推荐列表
  • 配置字典、区域信息

如果没有 Redis，这些请求每次都打数据库，高并发时很容易把 MySQL 压垮。

场景二：计数器与实时统计

Redis 的自增、自减命令非常适合做高频计数。

INCR article:1001:view_count
INCRBY product:88:sales 10
DECR stock:sku:9001

常见业务包括：

  • 阅读数、点赞数、收藏数
  • 秒杀库存扣减
  • API 调用次数统计
  • 登录失败次数限制

这类数据的特点是“更新比查询更频繁”，如果每次都落数据库，成本很高。

场景三：分布式锁

当多个服务实例可能同时修改同一份资源时，可以用 Redis 做一个轻量的分布式锁。

SET order:lock:1001 uuid123 NX EX 10

如果返回成功，说明当前线程拿到锁；如果失败，说明已有其他线程正在处理。
典型应用：

  • 防止重复下单
  • 防止重复执行定时任务
  • 控制同一用户短时间重复提交

但这里要补一句：Redis 分布式锁能用，但要处理锁超时、误删、续期等细节，生产上通常会结合 Lua 或 Redisson。

场景四：消息队列和异步削峰

Redis 可用 List、Pub/Sub、Stream 做消息传递。

用户下单 -> 先写 Redis Stream
         -> 订单服务异步消费
         -> 扣库存 / 发通知 / 记日志

适合：

  • 异步发短信
  • 下单后发积分
  • 操作日志异步落库
  • 削峰填谷

不过如果业务要求消息堆积能力很强、可靠投递、长时间积压不丢失，那往往会转向专业 MQ。

场景五：排行榜和排序系统

Redis 的 ZSet 天然支持按 score 排序：

ZADD game:rank 100 userA
ZADD game:rank 95 userB
ZREVRANGE game:rank 0 9 WITHSCORES

典型场景：

  • 游戏积分榜
  • 热搜榜
  • 播放量榜单
  • 用户活跃排名

用数据库也能做排序，但在高并发和频繁更新下，Redis 会更轻快。

场景六：会话、Token、临时状态管理

很多系统会把登录态、验证码、临时令牌、分布式 Session 存到 Redis。

例如：

  • 登录 Token 过期控制
  • 短信验证码 5 分钟有效
  • OAuth 授权状态
  • 用户在线状态

这类数据都有一个共同点：天然带过期时间，很适合 Redis 的 TTL 模型。

场景七：限流、防刷和风控

Redis 对“单位时间内做了多少次”这类问题很擅长。

key = user:1001:login:count
1 分钟内超过 5 次 -> 拒绝

适合：

  • 接口限流
  • 短信发送频率控制
  • 登录错误次数控制
  • 秒杀入口防刷

3. 数据类型和场景怎么对应

一个很容易拿分的回答方式，是把业务场景和 Redis 类型对应起来：

场景 常用类型
缓存对象 String / Hash
计数器 String
消息队列 List / Stream
排行榜 ZSet
去重、标签 Set
地理位置 GEO
UV 统计 HyperLogLog
用户签到 Bitmap

这会让面试官感觉你不只是知道“能做什么”，还知道“该怎么落地”。

4. 深入思考：Redis 的边界在哪

1. Redis 不是万能数据库

它不适合复杂联表、强事务、大规模历史数据分析。
如果把一切都塞进 Redis，后期不仅贵，而且会因为内存成本和数据治理变得困难。

2. Redis 特别适合“状态型”数据

像库存状态、登录状态、排行榜、热点数据，本质都不是重分析型数据，而是需要被快速读取和快速更新的状态数据，这正是 Redis 的主场。

3. 用 Redis 做缓存时，要顺手想到三个追问

  1. 缓存一致性怎么保证
  2. 缓存穿透、击穿、雪崩怎么处理
  3. Redis 宕机后系统怎么兜底

所以面试时不要只说“能做缓存”，最好顺带提一句这些风险点，会更完整。

回答思路

答题逻辑框架

建议这样回答：

  1. 先给总定义：Redis 是高性能内存数据结构数据库
  2. 再按业务目标展开：缓存、计数、锁、队列、排行榜、会话状态、限流
  3. 然后补充“不同场景对应不同数据类型”
  4. 最后说边界：复杂事务和复杂查询不是 Redis 强项

重点得分点

  • 说出 缓存 是基础分
  • 补上 分布式锁、消息队列、排行榜、限流 是加分项
  • 能把 业务场景和数据类型匹配 是高分项
  • 能主动提到 Redis 不是万能替代数据库，说明你有边界意识

常见误区

  • 误区 1：Redis 就是缓存
    正解：缓存只是最常见用途，它还是状态和结构型数据工具

  • 误区 2：Redis 可以直接替代 MQ
    正解：轻量异步可以，复杂消息语义通常还是专业 MQ 更稳

  • 误区 3：Redis 可以替代 MySQL 存核心业务全量数据
    正解：核心持久化和复杂查询仍然更适合关系型数据库

面试话术

“我一般把 Redis 理解成一个高性能状态中心。最常见的是做缓存，其次还能做计数器、分布式锁、异步队列、排行榜、会话存储和限流。不同场景会对应不同数据类型，比如排行榜常用 ZSet，去重常用 Set，计数器常用 String。它非常适合高并发低延迟场景，但不适合替代数据库做复杂查询。”
