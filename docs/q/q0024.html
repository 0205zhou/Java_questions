接口和抽象类的区别

接口和抽象类的区别

接口与抽象类的区别

联想记忆法

记忆口诀/联想

口诀:"抽象类是'是什么'(IS-A),接口是'能干什么'(CAN-DO);抽象类单继承、可有状态,接口多实现、纯约定;JDK8 后接口也能写 default"

三句话对应三个维度:

  • 语义维度:抽象类回答"你是什么"(一辆车、一只动物),接口回答"你能做什么"(能跑、能飞、能比较)
  • 继承维度:一个类只能继承一个抽象类,但能实现多个接口(单继承 vs 多实现)
  • 能力维度:抽象类可以有构造器、字段、普通方法(有"实装"能力);接口在 JDK8 前只能有抽象方法,JDK8 后增加 default/static 方法,JDK9 后还能有私有方法

记忆原理

用"名词 vs 动词"的语法联想:抽象类是名词(人、动物、车——描述身份),接口是动词(跑、飞、比较——描述能力)。名词只能有一个(单继承),动词可以有一堆(多实现)。这个语言学的锚点非常稳——面试时先说出"名词/动词"的定位,再对比语法差异(构造器、字段、多继承),逻辑自然展开。JDK8 的 default 方法再单独记:它是"给动词加默认姿势"的妥协设计。

关联知识

  • 与设计模式关联:抽象类 + 模板方法模式(骨架逻辑在抽象类,子类只填钩子);接口 + 策略/适配器模式(能力注入)
  • 与多态关联:接口是"多态的实现载体",面向接口编程(依赖倒置原则 DIP)是 Spring IoC 的基石
  • 与 Comparable/Cloneable 关联:标记接口(Marker Interface)没有方法,纯粹声明"我能做什么"
  • 与 JDK8 函数式编程关联:接口配 Lambda + 函数式接口(Functional Interface),是 Stream 流式编程的基础

深度解答

第一层:核心概念

两者是什么

  • 抽象类(Abstract Class):用 abstract 修饰的类,可以包含抽象方法(只有声明没有实现)和具体方法。它是"部分完成的类",定义一类事物的骨架和共性
  • 接口(Interface):用 interface 声明,是完全抽象的约定(契约)。它定义"能力清单",不关心实现细节

核心区别一句话

抽象类描述"是什么"(IS-A 关系,复用代码与状态),接口描述"能做什么"(CAN-DO 关系,约定能力);一个类只能有一个"身份",但可以拥有无数"能力"。

第二层:底层原理

语法层面对比

对比项 抽象类 接口
继承限制 单继承(extends 一个) 多实现(implements 多个),接口可多继承接口
构造器 有构造器 无构造器
字段 可有实例字段(有状态) 只能有 public static final 常量
方法 抽象方法 + 具体方法(可全具体) JDK8 前全抽象;JDK8+ 有 default/static,JDK9+ 私有方法
访问修饰符 任意 JDK8 前方法隐式 public abstract
实例化 不能 new(但可被继承) 不能 new 
// 抽象类:可以"有实装"
public abstract class Animal {
    protected String name;              // ① 可以有实例字段(状态)
    public Animal(String name) {        // ② 可以有构造器
        this.name = name;
    }
    public abstract void eat();         // ③ 抽象方法:子类必须实现
    public void sleep() {               // ④ 具体方法:直接继承使用
        System.out.println(name + " 在睡觉");
    }
}

// 接口:纯"契约"
public interface Flyable {
    int MAX_SPEED = 100;                // 只能是常量(隐含 public static final)
    void fly();                         // 抽象方法
    // JDK8+:默认方法,提供"默认姿势",实现类可覆盖
    default void refuel() { System.out.println("加油中..."); }
    // JDK8+:静态方法,接口自己的工具方法
    static void info() { System.out.println("能飞的生物"); }
}

设计层面对比

  • 抽象类 = 模板:把"同类事物的共性逻辑"沉淀在父类,子类只补充差异(钩子方法)。如 AbstractList 已实现 addAll、iterator,ArrayList/LinkedList 只需实现核心方法
  • 接口 = 契约:声明"调用方可以依赖的能力",实现方负责细节。如 JDBC 的 Connection、Statement 接口,数据库厂商各自实现

JDK 官方代码中的应用对比

// 抽象类:骨架实现 → 子类补差异
abstract class AbstractList<E> {
    public boolean add(E e) { ... }         // 已实现
    public abstract E get(int index);       // 待子类实现
}

// 接口:能力声明 → 实现方自由发挥
public interface Comparable<T> {
    int compareTo(T o);                     // "我能比大小"
}

public interface Cloneable { }              // 标记接口:无方法,声明"我能克隆"

为什么 Java 只允许单继承类?

多继承会带来菱形问题(Diamond Problem):两个父类有同名方法时,子类继承谁的?C++ 用虚继承等复杂机制处理。Java 选择类单继承,彻底规避;但多实现接口没有冲突(接口无实现),JDK8 的 default 方法重新引入冲突,于是规定:类中实现优先于接口 default,多个接口 default 冲突必须显式覆写:

public interface A { default void run() { System.out.println("A"); } }
public interface B { default void run() { System.out.println("B"); } }

public class C implements A, B {
    @Override
    public void run() { A.super.run(); }    // 冲突时必须自己决定调哪个
}

第三层:实践应用

选择标准(面试必答点)

优先级:接口优先,抽象类兜底。

场景 选择
表达"能力/行为",不同类差异大 接口(如 Comparable、Runnable)
多个类有相同的实现代码需要复用 抽象类
需要非静态、非 final 的字段(状态) 抽象类(接口做不到)
需要构造器参与初始化 抽象类
对外暴露 API、系统间解耦 接口(面向接口编程)
希望 JDK8 的默认方法提供基础行为 接口

代码示例:模板方法模式(抽象类的典型应用)

public abstract class DataParser {
    // 模板方法:流程固定
    public final void parse(String file) {
        readFile(file);          // 固定步骤
        processData();           // 抽象:子类自定义
        writeResult();           // 固定步骤
    }
    protected abstract void processData();   // 钩子方法
    private void readFile(String f) { ... }
    private void writeResult() { ... }
}

public class CsvParser extends DataParser {
    @Override
    protected void processData() { /* CSV 解析逻辑 */ }
}

代码示例:策略模式(接口的典型应用)

public interface PaymentStrategy {
    void pay(double amount);
}

public class AlipayStrategy implements PaymentStrategy {
    public void pay(double amount) { /* 支付宝逻辑 */ }
}

public class WechatStrategy implements PaymentStrategy {
    public void pay(double amount) { /* 微信逻辑 */ }
}

// 调用方只依赖接口,换实现不改业务代码
public class OrderService {
    private final PaymentStrategy strategy;   // 接口注入(依赖倒置)
    public OrderService(PaymentStrategy s) { this.strategy = s; }
}

最佳实践

  • 面向接口编程:变量、方法参数、返回值尽量声明为接口类型(如 List 而非 ArrayList)
  • 抽象类做"骨架",接口做"契约":很多框架两者配合——抽象类实现接口,提供公共实现,再让具体类继承抽象类(如 Spring 的 AbstractApplicationContext implements ApplicationContext)
  • default 方法慎用:它弱化了接口的纯粹性,主要用于向后兼容(给已有接口加方法而不破坏实现类),不要当作常规功能设计

第四层:深入思考

追问 1:JDK8 给接口加了 default 方法,那接口和抽象类的界限是不是模糊了?

没有。界限依然清晰:

  • 抽象类可以有状态(实例字段)和构造器,接口始终不能
  • default 方法的动机是兼容性(List 加 sort 而不破坏所有实现类),不是"接口要变成抽象类"
  • 设计语义不变:抽象类表达"身份+骨架",接口表达"能力+契约"

追问 2:为什么 Java 8 之后默认方法能解决"接口新增方法破坏实现类"?

接口新增抽象方法 → 所有实现类都必须实现 → 第三方实现类全部编译失败。default 方法提供"默认实现",老实现类无需改动就能编译运行,只有需要新能力时才覆盖它——这是演进式设计的经典手法。

追问 3:什么时候抽象类优于接口?

当多个子类共享同一段状态/逻辑时。例如 JDK 的 AbstractMap 给 Map 接口的实现者提供公共实现;再如模板方法模式——流程骨架写死在抽象类,子类只填空。如果纯靠接口,每个实现类都要重复实现公共逻辑,违反 DRY 原则。

回答思路

答题逻辑框架(约 1.5 分钟)

  1. 先给定位:抽象类回答"是什么",接口回答"能做什么"
  2. 语法对比:继承限制(单继承 vs 多实现)、构造器/字段(有 vs 无)、方法形态(JDK8 前后变化)
  3. 设计对比:模板复用 vs 契约能力,举 JDK 例子(AbstractList vs Comparable)
  4. 给出选择标准:默认接口优先,需要状态/代码复用时用抽象类
  5. 收尾升华:面向接口编程 + JDK8 default 的兼容性设计

重点得分点

  • 准确说出"IS-A vs CAN-DO"的语义定位
  • 准确说出接口无构造器、无实例字段、抽象类可以有
  • 准确说出 JDK8 default/static、JDK9 私有方法 的演进
  • 说出选择标准:优先接口,需要状态/复用实现时用抽象类
  • 顺带提一句菱形问题与单继承的取舍(资深加分项)

常见误区

  • ❌ 说"接口的方法全是抽象的"——JDK8 后 default/static 方法破坏了这个说法
  • ❌ 说"接口可以定义变量"——接口字段一定是 public static final 常量,没有实例变量
  • ❌ 认为"接口和抽象类随便选"——两者语义不同:一个表达身份(单继承),一个表达能力(多实现)
  • ❌ 忽略 JDK8 默认方法的冲突解决规则(类优先、必须覆写)

过渡话术

  • 开头定调:"两者最本质的差别不是语法,而是设计语义——抽象类是'身份',接口是'能力'……"
  • 从语法到设计:"语法差异背后是设计取舍,Java 的类只能单继承,就是为了避免多继承的菱形问题……"
  • 收尾:"所以实践上有个共识——能接口就接口,实在需要复用状态和骨架实现,再用抽象类。"
