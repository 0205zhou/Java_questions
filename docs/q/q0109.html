B+树的缺点是什么？

联想记忆法

记忆口诀/联想

口诀："写入要维护，空间要付出；低选择性不划算，大范围不一定快；全文高维另选结构。"

这句话对应 B+Tree 的主要缺点：

  • 写入要维护：插入、删除和更新索引列都需要维护树结构。
  • 空间要付出：索引需要额外占用磁盘空间和内存。
  • 低选择性不划算：匹配记录太多时，走索引可能不如全表扫描。
  • 大范围不一定快：范围过大、深分页或回表过多时，性能收益会下降。
  • 全文高维另选结构：全文检索、相似度搜索和复杂空间查询不适合只依赖 B+Tree。

记忆原理

B+Tree 的优点是“有序、稳定、适合磁盘页和范围查询”，缺点也正是由这些特性带来的：为了保持有序，写入时要调整结构；为了提高查询速度，需要额外维护索引；当查询结果覆盖大量数据，索引定位的优势就会被扫描和回表成本抵消。

深度解答

第一层：核心概念

B+Tree 不是没有缺点，而是一种针对结构化数据和磁盘页访问优化后的折中方案。它通过有序节点、较高扇出和叶子节点链表，降低等值查询、范围查询和排序的成本，但需要付出额外的存储、写入和维护开销。

面试中回答时要强调：下面说的多数是相对缺点，并不意味着 B+Tree 不适合数据库。对于 InnoDB 这类以 OLTP 为主的关系型存储，B+Tree 仍然是非常通用的索引结构。

第二层：主要缺点

1. 写入、更新和删除成本更高

建立索引后，插入一行数据不再只是写入数据页，还需要把索引记录插入对应的 B+Tree。删除和更新索引列也要同步维护索引。

INSERT INTO user(id, name, age) VALUES (100, 'Tom', 20);
UPDATE user SET name = 'Jerry' WHERE id = 100;
DELETE FROM user WHERE id = 100;

如果表上有多个索引，一次写操作可能需要修改多棵树。更新索引列时，通常可以理解为先删除旧索引项，再插入新索引项，因此维护成本更高。

2. 可能发生页分裂和写放大

B+Tree 的节点通常对应数据库页。向已经接近容量上限的中间页插入数据时，可能触发页分裂：

原页面已接近满页
        ↓ 插入中间位置
拆分为两个页面，并移动部分记录
        ↓
必要时继续更新父节点，甚至导致树向上分裂

页分裂会带来额外的数据移动、日志记录和磁盘写入。随机主键或随机索引值更容易在索引中间位置插入，通常比递增键更容易产生页分裂和碎片。

3. 占用额外的存储空间和内存

每个索引都需要保存索引列、页结构和指针等信息。索引越多，占用的磁盘空间越大，加载到 Buffer Pool 后也会消耗更多内存。

InnoDB 的二级索引叶子节点通常还要保存主键值。主键越长，所有二级索引的记录可能越大，索引占用空间和维护成本也会随之增加。

因此，索引不是越多越好，应围绕真实查询建立，删除长期不用或重复度较高的索引。

4. 低选择性字段的收益可能很低

选择性低表示一个索引值对应很多记录，例如性别、是否删除、状态等字段：

SELECT * FROM user WHERE gender = '男';

如果条件命中了表中很大比例的数据，数据库即使先扫描索引，也需要读取大量记录，甚至还要大量回表。此时优化器可能认为全表扫描成本更低。

所以“字段有索引”不等于“查询一定走索引”，是否使用还取决于数据分布、统计信息、回表成本和查询条件。

5. 大范围查询可能退化为大量扫描

B+Tree 很适合找到范围的起点，但如果范围本身很大，仍然需要顺着叶子节点扫描大量记录：

SELECT * FROM orders
WHERE create_time >= '2026-01-01'
  AND create_time < '2027-01-01';

如果一年内大部分订单都符合条件，索引只能帮助定位起点，不能消除后续的大量数据读取。范围查询的性能取决于范围大小、返回列、是否需要回表以及数据是否已经在缓存中。

6. 深分页效率较差

SELECT id, name
FROM user
ORDER BY id
LIMIT 1000000, 20;

数据库通常需要先扫描或跳过前面的 1000000 条记录，再返回后面的 20 条。即使使用了 B+Tree，偏移量很大时也会产生较多扫描成本。

更适合大数据量分页的方式通常是基于上一页最后一个有序键做“游标分页”：

SELECT id, name
FROM user
WHERE id > 1000000
ORDER BY id
LIMIT 20;

7. 联合索引受最左前缀限制

对于联合索引：

CREATE INDEX idx_a_b_c ON t(a, b, c);

它按照 (a, b, c) 的字典序排列。因此下面的查询缺少最左列 a，通常无法充分利用这棵联合索引的有序结构：

SELECT * FROM t WHERE b = 10 AND c = 20;

联合索引不是任意字段组合都能高效匹配，需要结合查询模式设计索引顺序。索引顺序设计不合理时，索引可能无法覆盖主要查询，或者只能使用部分前缀。

8. 不适合全文检索和复杂相似度查询

B+Tree 主要解决结构化字段的等值、范围、排序和前缀匹配问题，不擅长：

  • 根据词频、相关性和语义进行全文检索。
  • 计算向量相似度或推荐相似内容。
  • 处理多维空间中的近邻搜索。
  • 对多个字段做复杂的模糊匹配。

例如，商品标题的分词搜索、相关性排序通常更适合 Elasticsearch 等倒排索引系统；向量相似度检索则应评估专用的向量索引结构。

9. 二级索引可能产生回表成本

InnoDB 二级索引叶子节点通常保存索引列和主键值，而不是完整行数据：

二级索引定位记录
        ↓
拿到主键
        ↓
回到聚簇索引读取完整行

如果查询返回很多行，或者需要读取大量不在索引中的列，回表次数会增加。此时可以考虑覆盖索引，但覆盖索引也会增加索引宽度和写入维护成本，不能无条件堆叠。

第三层：实践中的权衡

1. 什么时候 B+Tree 仍然是合适选择

B+Tree 适合以下场景：

  • 主键等值查询。
  • 有明确范围的时间、数值和排序查询。
  • 需要按照索引顺序读取数据。
  • 事务型系统中的高频结构化查询。
  • 查询条件具有较好选择性，且返回数据量适中。

2. 如何降低 B+Tree 的缺点

  • 只为真实、高频且有收益的查询建立索引。
  • 设计合适的联合索引顺序，遵循最左前缀原则。
  • 尽量使用稳定、有序的主键，减少随机插入导致的页分裂。
  • 通过覆盖索引减少回表，但控制索引宽度。
  • 避免无意义的深分页，改用基于有序键的游标分页。
  • 使用 EXPLAIN 检查访问类型、扫描行数和回表情况。
  • 对全文、空间和向量检索选择更匹配的专用索引。

3. 不要把所有问题归咎于 B+Tree

查询慢可能来自 SQL 写法、数据量、统计信息、锁等待、磁盘 IO、缓存命中率或网络传输，而不一定是 B+Tree 本身的问题。排查时应结合执行计划、慢查询日志和实际数据分布判断，不能只看到“用了索引”或“没有使用索引”就下结论。

回答思路

答题逻辑框架

  1. 先说明 B+Tree 的缺点是相对的，核心代价是空间和维护成本。
  2. 重点讲写入维护、页分裂、索引空间和回表。
  3. 再讲低选择性、大范围查询和深分页为什么收益下降。
  4. 补充联合索引最左前缀以及不适合全文、向量等复杂检索。
  5. 最后给出优化方法，说明如何在实际项目中权衡。

面试简答版

B+Tree 的主要缺点有：第一，索引需要额外占用磁盘和内存，插入、删除、更新时还要维护索引，可能发生页分裂和写放大；第二，低选择性字段、大范围查询和深分页场景下，索引扫描和回表成本可能很高，收益甚至不如全表扫描；第三，联合索引受最左前缀限制；第四，B+Tree 适合结构化的等值、范围和排序查询，不适合全文相关性、向量相似度等复杂检索。因此索引要根据实际查询建立，不能越多越好。

常见误区

  • ❌ 说 B+Tree 只能做等值查询；它也非常适合范围查询和有序扫描。
  • ❌ 说建了索引就一定比全表扫描快；低选择性和大范围查询可能相反。
  • ❌ 把页分裂说成查询缺点；页分裂主要影响写入和维护。
  • ❌ 认为索引越多越好；索引会增加空间、写入和更新成本。
  • ❌ 认为 B+Tree 不适合模糊查询；前缀匹配在合适条件下仍可使用索引，复杂全文检索才不适合。
