双亲委派机制

类加载 JVM

双亲委派机制

联想记忆法

记忆口诀/联想

口诀:"儿子不干活,层层问爸爸;爸爸干不了,层层往下传"

把类加载想成家族企业找负责人:

  • 三个层级的加载器:启动类加载器(太祖)、扩展类加载器(爷爷)、应用类加载器(爸爸),用户自定义加载器是"儿子"
  • 加载请求从最底层的儿子发起:先问爸爸,爸爸问爷爷,爷爷问太祖——太祖有就太祖干,没有传回爷爷,爷爷没有传回爸爸,爸爸没有才轮到儿子自己干
  • 一句话:自下而上委托,自上而下加载,谁都不干才自己干

记忆原理

"层层上报、逐级下发"是中国人最熟悉的请示汇报流程,用父子关系比类加载器层级,动作天然有顺序:先"往上问"(委派),再"往下干"(加载)。记牢两个方向,面试时先画三层结构,再讲委派方向,逻辑就完整了。重点强调安全性(防止自己写一个 java.lang.String 把核心类调包)和避免重复加载,这是"为什么要这么设计"的得分点。

关联知识

  • 与类加载过程关联:双亲委派发生在加载阶段的"获取字节流"之前——先决定"由谁加载",再执行五阶段流程
  • 与 JVM 内存结构关联:不同加载器加载的类,其元信息都进方法区,但类身份 = 全限定名 + 加载器,同名不同加载器是两个类(Class 对象 !=)
  • 与 SPI/框架关联:JDBC、Tomcat、Spring 都要打破双亲委派——这是必问的进阶考点
  • 与 OOM 关联:热部署框架(如 Spring Boot DevTools)通过新加载器实现类隔离与重载

深度解答

第一层:核心概念

是什么

双亲委派模型(Parents Delegation Model)是 Java 类加载器的默认协作规则:除启动类加载器外,任何类加载器收到加载请求时,先委派给父加载器,逐级向上,只有父加载器加载失败才自己加载。

┌────────────────────────────────────────────────┐
│  Bootstrap ClassLoader 启动类加载器(C/C++ 实现)    │
│  加载:JDK/lib 下的核心类(java.*)                  │
├────────────────────────────────────────────────┤
│  Extension ClassLoader 扩展类加载器               │
│  加载:JDK/lib/ext 扩展包(javax.*)                │
├────────────────────────────────────────────────┤
│  Application ClassLoader 应用类加载器             │
│  加载:classpath 下的用户类                        │
├────────────────────────────────────────────────┤
│  Custom ClassLoader 用户自定义加载器(可选)        │
└────────────────────────────────────────────────┘
        请求方向:从下往上委派
        加载方向:从上往下兜底

核心代码逻辑

// java.lang.ClassLoader#loadClass 简化版 —— 双亲委派的实现核心
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // ① 先查缓存:该类是否已被本加载器加载过
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            if (parent != null) {
                c = parent.loadClass(name, false);   // ② 委派给父加载器
            } else {
                c = findBootstrapClassOrNull(name);  // 没有父 → 启动类加载器
            }
            if (c == null) {
                c = findClass(name);                  // ③ 父都加载失败 → 自己加载
            }
        }
        return c;
    }
}

第二层:底层原理

为什么设计双亲委派——两大理由

① 安全性(防篡改核心类)

如果用户写一个自定义的 java.lang.String 并让它先加载,JVM 中的 java.lang.String 会被"调包",整个语言体系崩溃(黑客可通过伪造核心类窃取信息)。双亲委派保证 java.* 的类永远由启动类加载器加载,用户写的同名类永远没机会加载——同名不同源的类被"毙掉"。

② 避免重复加载

同一个类由同一条委派链加载,结果只会加载一次,内存中只存在一份 Class 对象,保证类型一致性与 == 比较的正确性。

类身份的三要素

JVM 中区分两个类是否"相同"看:全限定名 + 加载它们的类加载器。两个加载器分别加载同一个 com.x.Foo(即使字节码一模一样),也是两个不同的类,互相不能转型,instanceof 为 false——这是"类隔离"的理论基础,也是打破双亲委派后必须理解的代价。

启动类加载器为什么特殊

Bootstrap 由 C++ 实现(HotSpot 中即 JVM 自身),没有 Java 对应的 ClassLoader 对象,getParent() 返回 null。它是委派链的终点——"太祖没有能力"就宣告失败。

为什么不能重写 loadClass 来"增强"父加载

loadClass 是委派逻辑本身,规范建议自定义加载器只重写 findClass(加载失败后的兜底动作),这样委派链完整保留。若重写 loadClass 直接 findClass,就是打破双亲委派——需要时(SPI 场景)才这么做。

第三层:实践应用

哪些场景必须打破双亲委派

① JDBC 的 SPI(服务提供者接口)——经典必考题

  • 问题:JDBC 的接口 java.sql.Driver 在 rt.jar(启动类加载器管辖),但实现类(MySQL 驱动 com.mysql.cj.jdbc.Driver)在 classpath(应用类加载器管辖)。启动类加载器反向要加载子加载器的类——双亲委派是"父←子"单向的,天然做不到
  • 解决:DriverManager(启动类加载器加载)用线程上下文类加载器(Thread Context ClassLoader,默认为应用类加载器)去加载实现类——把委派方向倒过来
// ServiceLoader 加载驱动实现 —— 本质是"父加载器借子加载器的能力"
Class.forName(driverClassName, true, Thread.currentThread().getContextClassLoader());

② Tomcat 的 Web 应用隔离

每个 Web 应用一个 WebAppClassLoader,优先加载自己 WEB-INF/classes 下的类(打破父优先)——目的是多个应用可以部署不同版本的同一个库,互不冲突。

③ 热部署/热替换

框架加载"新版本"类时 new 一个全新加载器,旧类的 Class 对象留在旧加载器空间,配合加载器可达性,旧版类随加载器一起被回收,实现不重启替换。

如何自定义加载器(保留委派 vs 打破委派)

// 保留双亲委派:只重写 findClass
class SafeLoader extends ClassLoader {
    protected Class<?> findClass(String name) { ... }
}

// 打破双亲委派:重写 loadClass,自己优先
class BreakerLoader extends ClassLoader {
    protected Class<?> loadClass(String name, boolean resolve) {
        // 先自己 findClass,失败再走委派 —— 顺序颠倒
    }
}

第四层:深入思考

追问 1:双亲委派是强制规定吗?

不是。它是推荐的默认实现,由 ClassLoader.loadClass() 默认逻辑承载,规范并未强制。打破它有两种方式:重写 loadClass(自定义优先);SPI 的线程上下文类加载器(父借子)。Java 9 的模块化(JPMS)也调整了委派规则(平台类加载器替代扩展类加载器,模块间依赖可绕过委派)。

追问 2:两个加载器加载同一个类,能强转吗?

不能。会抛 ClassCastException——"全限定名 + 加载器"共同决定类身份。框架里常遇到:Spring 容器用容器类加载器,业务代码用应用类加载器,某些反射对象就转不过去。

追问 3:为什么 SPI 不干脆破坏 JDK 的委派链?

破坏 rt.jar 的加载逻辑代价太大、风险太高;线程上下文类加载器是最小侵入方案:只在"跨加载器需要"时,由标准库把"用哪个加载器"的决定权交给运行时。这是设计权衡——规则可以破,但要破得"局部、可控"。

追问 4:加载器之间是什么关系(继承吗)?

不是继承关系,是组合关系:子加载器持有父加载器引用(parent 字段)。"双亲"里的"亲"是逻辑委派关系,不是 Java 继承的"父类"。

回答思路

答题逻辑框架(约 2 分钟)

  1. 画三层结构:启动 → 扩展 → 应用 → 自定义
  2. 讲委派方向:自下而上问,自上而下干,父失败才自己加载
  3. 讲为什么(两大理由):安全性(防调包核心类)+ 避免重复加载
  4. 看源码:loadClass 三步走——查缓存、委派父、自己 findClass(体现深度)
  5. 讲打破:SPI/JDBC 的线程上下文类加载器 + Tomcat 隔离 + 重写 loadClass(体现广度)

重点得分点

  • 准确说出三层加载器名称及各自加载范围(java.、javax. 扩展、classpath)
  • 准确说出"向上委派、向下兜底"两个方向
  • 说全两大理由:安全性 + 避免重复加载
  • 能说出 loadClass vs findClass 的区别——重写哪个是保留/打破委派
  • 说出 JDBC 打破双亲委派的完整链路(启动类加载器 → 上下文类加载器 → 应用类加载器)——这是最高频的追问,说出来即加分

常见误区

  • ❌ 说"启动类加载器负责加载 ext 目录"——那是扩展类加载器的职责
  • ❌ 说"双亲委派是 JVM 规范强制规定"——它是默认实现,不是强制
  • ❌ 说"打破双亲委派就是重写 loadClass"——SPI 用线程上下文类加载器也能"借道"打破
  • ❌ 说"子加载器继承父加载器"——是组合,持有引用

过渡话术

  • 开场:"双亲委派可以概括为八个字——层层上报,逐级兜底。先说三层加载器……"
  • 从机制到源码:"这个机制在源码里的落点就是 loadClass 方法,三步:先查缓存、再委派父类、最后才自己加载……"
  • 引出打破:"但注意,双亲委派不是万能规则,JDBC 驱动加载就必须打破它,原理是线程上下文类加载器……"
