Redis的哨兵集群？

Redis Sentinel 高可用 主从复制

Redis的哨兵集群？

联想记忆法

记忆口诀/联想

口诀：哨兵不存数，专门盯主库；发现主挂了，投票换新主。

把哨兵（Sentinel）想成一组“值班监控员”：

  • 它们不负责存业务数据
  • 它们专门盯着主节点和从节点
  • 一旦发现主节点真挂了，就会投票
  • 投完票之后，选一个从节点升级成新的主节点

记忆原理

这个口诀把哨兵最容易混淆的地方先切开了：哨兵不是数据分片集群，也不是普通从库，它是高可用控制平面。 面试时先把这点说清楚，后面再讲监控、下线判断、故障转移，逻辑会很顺。

关联知识

  • 会关联到 主从复制：哨兵建立在主从架构之上
  • 会关联到 故障转移：核心价值在于自动切主
  • 会关联到 脑裂问题：网络分区下可能出现双主风险
  • 会关联到 Redis Cluster：哨兵解决高可用，Cluster 同时解决高可用和分片

深度解答

1. 核心概念：哨兵是 Redis 的高可用方案，不是分片方案

如果 Redis 只是一个单机主节点，那么一旦主节点宕机，服务就不可用了。
即使你做了主从复制，也只是“有备份数据”，并不代表系统会自动切换到从节点继续对外服务。

这时候哨兵模式就派上用场了。
Sentinel 的目标很明确：监控 Redis 主从实例，发现故障后自动完成主从切换，并把新的主节点信息通知客户端。

所以一句话概括：

主从复制解决“有备份”
哨兵解决“能自动切换”

2. 哨兵到底负责什么

哨兵主要有三大职责。

第一，监控（Monitoring）

哨兵会定期向主节点和从节点发送命令，检查它们是否还活着，网络是否可达，响应是否正常。

第二，通知（Notification）

当 Redis 实例状态发生变化时，哨兵能通过配置的通知方式告诉运维或其他系统。

第三，自动故障转移（Automatic Failover）

当主节点不可用并被多个哨兵确认后，哨兵会从从节点中挑选一个新的主节点，并让其他从节点去复制它。

3. 哨兵架构长什么样

一个典型架构如下：

                Sentinel1
                   |
客户端 -> Sentinel2 ---- Sentinel3
                   |
                Master
                /    \
             Slave1  Slave2

这里有两个关键点：

  1. 哨兵一般至少部署 3 个，避免单点判断失误
  2. Redis 数据节点还是主从结构，哨兵只是“旁路管理者”

4. 主观下线和客观下线

这是哨兵高频考点。

主观下线（SDOWN）

某一个哨兵自己认为主节点不可达，比如连续多次心跳失败，它会先做出“我觉得它挂了”的判断，这就叫主观下线。

客观下线（ODOWN）

如果不止一个哨兵都认为主节点挂了，并且达到配置的法定票数（quorum），那就会把主节点判定为客观下线。

为什么要分两层？

因为单个哨兵有可能误判，比如它自己网络抖动了。如果只靠一个哨兵就切主，系统会非常不稳定。
所以哨兵采用“个人怀疑 + 集体确认”的机制，降低误切换风险。

5. 故障转移流程

哨兵自动切主大致经历以下步骤：

  1. 发现主节点疑似不可用
  2. 多个哨兵确认，形成客观下线
  3. 哨兵之间选举出一个 leader
  4. leader 从可用从节点里挑选一个最合适的从节点
  5. 把这个从节点提升为新的主节点
  6. 通知其他从节点改为复制新的主节点
  7. 通知客户端新的主节点地址

可以记成：

“先确认，再选主，再重挂复制链路。”

6. 新主节点是怎么选的

哨兵不会随便挑一个从节点，它会综合考虑一些因素，例如：

  • 从节点和主节点的复制偏移量，谁的数据更接近主节点
  • 从节点是否在线、是否稳定
  • slave-priority 配置
  • 网络连接情况

简单理解就是：尽量选最新、最稳、优先级合适的从节点。

7. 哨兵配置示例

典型配置如下：

sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1

几个常见参数含义：

  • monitor：监控哪个主节点，以及法定票数是多少
  • down-after-milliseconds：多久没响应算主观下线
  • failover-timeout：故障转移超时时间
  • parallel-syncs：切主后允许多少个从节点同时重新同步

8. 实践应用：哨兵适合什么场景

哨兵模式适合：

  • 数据量还不需要分片
  • 主要诉求是主从高可用
  • 希望 Redis 故障切换自动化

例如：

  • 中小型业务缓存集群
  • 订单状态、Token、会话等状态型数据
  • 单节点写压力还可接受，但不能容忍长时间不可用的场景

9. 哨兵的局限

1. 它不解决分片扩容问题

哨兵模式下还是一个主节点负责写，多个从节点负责读。
如果数据量特别大、写流量特别高，哨兵并不能横向分散写压力。

2. 故障切换期间会有短暂不可用

从发现故障、达成共识、选举 leader、切主到客户端感知新主节点，中间会有一个窗口期，不可能完全无感。

3. 可能存在脑裂风险

如果网络分区导致旧主节点和哨兵集群失联，但旧主节点自己还活着，就可能出现“客户端还在写旧主，新哨兵又切了一个新主”的风险。
所以生产中会搭配：

  • 合理的 quorum
  • 主节点最小从库确认
  • 网络稳定性保障
  • 客户端正确接入哨兵

10. 哨兵和 Redis Cluster 的区别

这也是特别高频的追问。

对比项 哨兵模式 Redis Cluster
目标 高可用 高可用 + 分布式分片
数据分布 不分片 按槽位分片
写入节点 单主写 多主写
适用场景 中小规模、高可用优先 数据量大、扩容要求高

所以可以这样总结：

  • 哨兵：解决“主挂了怎么办”
  • Cluster：解决“主挂了怎么办 + 数据太大怎么办”

回答思路

答题逻辑框架

建议这样回答：

  1. 先说哨兵是基于主从复制的高可用方案
  2. 再说三个职责：监控、通知、自动故障转移
  3. 然后讲主观下线和客观下线
  4. 最后补充故障转移流程和它与 Cluster 的区别

重点得分点

  • 一定要先说清 哨兵不存业务数据
  • 能解释 SDOWN / ODOWN
  • 能讲出 故障转移流程
  • 能区分 哨兵模式 和 Redis Cluster

常见误区

  • 误区 1：哨兵就是 Redis 集群
    正解：哨兵是高可用方案，不是分片集群

  • 误区 2：有主从就等于高可用
    正解：没有自动切换能力时，主从只解决备份，不解决故障恢复流程

  • 误区 3：哨兵切主完全无损无感
    正解：切换期间通常会有短暂不可用窗口

面试话术

“Redis 哨兵是建立在主从复制之上的高可用方案。它本身不存业务数据，而是负责监控主从节点状态。当主节点发生故障时，多个哨兵会先确认主观下线和客观下线，再选出 leader 哨兵执行故障转移，把某个从节点提升成新的主节点，并通知其他从节点和客户端更新连接。它解决的是高可用问题，但不解决数据分片问题，这一点和 Redis Cluster 不一样。”
