JVM如何调优

调优 GC

JVM如何调优

联想记忆法

记忆口诀/联想

口诀:"先定目标,再看数据,最后改参数;改完必须验证,线上逐步灰度"

把 JVM 调优想成给汽车调校发动机:

  1. 定目标:先明确要什么——省油(吞吐量)?安静(低停顿)?还是别熄火(不 OOM)?
  2. 看仪表盘:上数据——GC 日志、堆使用、线程快照(jstat/jmap/jstack 就是仪表盘)
  3. 改参数:根据数据改配置(-Xmx/-Xmn/GC 收集器就是调旋钮)
  4. 验证:改完测效果,不行就回滚

最忌"上来就调参"——没有数据支撑的调优都是玄学。

记忆原理

用"调车"流程建立方法论骨架:调优是数据驱动的迭代过程,不是背参数。面试时先讲方法论(定目标→量化→改参→验证),再展开常用参数和工具,显得有工程思维。核心锚点:先监控、后调参、必验证。参数记不住没关系,记住"三个 X"(-Xms/-Xmx/-Xmn)和"一个收集器"(G1)就能撑起大半回答。

关联知识

  • 与 GC 机制关联:调优本质是调整 GC 行为(频率、停顿、内存分配),GC 原理是调优的底层依据
  • 与 OOM 排查关联:调优和排查是同一套工具链(jmap/jstat/jstack),一个面向预防、一个面向救火
  • 与内存结构关联:-Xmx 管堆、-Xss 管栈、-XX:MetaspaceSize 管元空间——调参落在具体区域上
  • 与线程模型关联:线程过多/锁竞争导致的 CPU 飙高,也属于"JVM 层面问题",用 jstack 分析

深度解答

第一层:核心概念

是什么

JVM 调优是通过监控工具量化 JVM 运行状态,针对性调整内存参数与 GC 策略,使应用在吞吐量、停顿时间、稳定性之间达到目标平衡的过程。三个经典目标:

目标 指标 对应手段
高吞吐量(不卡顿地干活) 总吞吐时间占比 Parallel 收集器、增大堆
低停顿(响应快) GC 停顿时间 G1/ZGC、控制堆大小
稳定性(不 OOM/不假死) 无 OOM、GC 频率稳定 内存泄漏治理 + 合理堆大小

吞吐量 vs 停顿时间天然矛盾:堆越大 GC 次数越少但单次停顿越长;堆越小停顿短但次数多。调优就是在这个跷跷板上找平衡点。

调优的正确姿势(方法论)

① 明确目标(吞吐/停顿/稳定性,量化指标)
② 部署监控(GC 日志、堆监控、线程监控)
③ 采集数据分析(发现问题根因,而非症状)
④ 制定并实施调整(每次只改 1~2 个参数)
⑤ 验证效果(对比调优前后指标)
⑥ 不理想 → 回滚,重新分析

铁律:一次只改一个变量,改动可回滚,数据说话。

第二层:底层原理

核心参数体系(对应内存结构)

参数 作用 默认/建议
-Xms 初始堆大小 建议 = -Xmx,避免堆伸缩(扩容缩容有开销和停顿)
-Xmx 最大堆大小 一般 ≤ 物理内存的 50%~60%(留出元空间/线程栈/直接内存)
-Xmn 新生代大小 一般占堆的 1/3~1/2,-XX:SurvivorRatio=8 时 Eden:S0:S1 = 8:1:1
-Xss 单线程栈大小 默认 512K~1M,线程多的系统可调小(如 256K)防"线程栈撑爆内存"
-XX:MetaspaceSize 元空间初始大小 动态生成类多的应用需显式设置上限 -XX:MaxMetaspaceSize
-XX:MaxDirectMemorySize 直接内存上限 NIO 场景必设,默认等于 -Xmx,易被忽略
-XX:MaxTenuringThreshold 晋升老年代年龄阈值 默认 15,短生命周期对象多可调小
-XX:MaxGCPauseMillis G1 停顿目标 如 200ms,G1 会为达成目标调整 Region 回收策略

为什么 -Xms 要等于 -Xmx

堆从初始值动态扩容到最大值会触发 Full GC(扩大堆前必须重新整理),线上频繁出现"没理由的 Full GC"往往就是堆在伸缩。初始直接给足,避免运行时扩容。

GC 日志与分析指标

java -Xlog:gc*:file=gc.log:time,uptime,level,tags   # JDK9+ 统一日志

看日志抓三个数:

  • GC 频率:Minor GC 间隔过短 → 新生代太小;Full GC 频繁 → 老年代不足或泄漏
  • GC 时间:单次停顿超目标 → 换收集器或调大堆;总 GC 时间占比高 → 吞吐量受损
  • 晋升情况:晋升失败(Promotion Failed)/ 老年代连续满 → 大对象过多或晋升阈值不合理

常用工具(命令级)

工具 用途 典型命令
jps 查看 Java 进程 jps -l
jstat 监控 GC/类加载/编译数据 jstat -gc <pid> 1000(每秒一行)
jmap 堆转储、内存统计 jmap -dump:format=b,file=heap.hprof <pid>
jstack 线程快照(查死锁/线程卡死) jstack <pid>
jcmd 综合诊断 jcmd <pid> GC.heap_info
MAT / VisualVM / Arthas 堆分析、在线诊断 图形化或 agent 方式

第三层:实践应用

实战案例一:响应慢 + 频繁 Full GC

现象:接口 P99 上涨,GC 日志显示每小时多次 Full GC,老年代持续接近满。

排查步骤:

jstat -gc <pid> 5000      # ① 确认 Full GC 频率与堆各区占用
jmap -dump:format=b,file=heap.bin <pid>   # ② 老年代快满时抓堆
# ③ MAT 打开 heap.bin → Histogram 看对象大小 Top10 → Dominator Tree 找泄漏链
# ④ 定位到静态 Map 缓存对象只进不出 → 修复为带过期策略的缓存
# ⑤ 同时把 -Xmx 从 512m 调到 1g(业务确实增长),-Xms 同步

结果:Full GC 从每小时多次降到每天 1~2 次,P99 恢复。

实战案例二:启动后频繁 Minor GC

现象:Minor GC 每秒好几次,Eden 秒级打满。

排查:业务本身创建了大量短生命周期对象(如循环内 new 大列表)——先优化代码(对象复用、批量处理),代码优化后仍高,再调 -Xmn 加大新生代。

实战案例三:CPU 100% 排查(顺带经典)

top -Hp <pid>         # 找占用 CPU 最高的线程 TID
printf '%x' <TID>     # 转十六进制
jstack <pid> > dump.txt   # 在 dump 里 grep 该 nid,看它在干什么

常见根因:死循环、GC 线程风暴(内存不足时 GC 线程疯狂工作)、锁竞争自旋。

标准启动参数模板

java -Xms4g -Xmx4g -Xmn2g \
     -XX:SurvivorRatio=8 -XX:MaxTenuringThreshold=15 \
     -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
     -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m \
     -XX:MaxDirectMemorySize=512m \
     -Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags \
     -jar app.jar

第四层:深入思考

追问 1:调优前需要监控多久、看哪些指标?

至少覆盖一个业务峰值周期(如大促前的小高峰),采集:堆各区占用曲线、GC 频率与单次时间、Full GC 次数、吞吐量/响应时间、CPU/内存。用数据回答"瓶颈到底在 GC 还是代码",避免盲目调参。

追问 2:什么情况下"调参解决不了问题"?

代码层面的内存泄漏、对象设计不合理、线程模型缺陷(如每请求新建线程)靠调参只能延缓不能根治——参数调大只是推迟 OOM。所以面试要强调:先查代码与设计,再谈参数。

追问 3:线上堆设多大合适?

取决于应用特性,没有万能值。经验法则:堆上限约为物理内存的 50%~70%(留足元空间、线程栈、直接内存、系统缓存);缓存类应用可大些,计算密集可小些;最关键的是用 GC 日志验证:Full GC 次数可控、单次停顿达标即为合适。

追问 4:JDK8 上想低停顿但不想升 JDK,怎么选收集器?

JDK8 可用 G1(-XX:+UseG1GC),它能达到毫秒级停顿目标,是 JDK8 上"不升级就低停顿"的主流答案;JDK15+ 再考虑 ZGC。

追问 5:为什么调优强调"一次只改一个参数"?

多个参数相互影响(堆大小影响晋升、晋升影响老年代、老年代影响 Full GC),同时改多个无法归因——调优必须可归因、可回滚,否则变成了碰运气。

回答思路

答题逻辑框架(约 3 分钟)

  1. 先讲方法论(加分点):定目标 → 监控采集 → 分析根因 → 改参 → 验证,强调"数据驱动、一次改一个"
  2. 讲目标与矛盾:吞吐量 vs 停顿时间的跷跷板
  3. 讲核心参数:-Xms/-Xmx(相等防伸缩)、-Xmn(新生代)、-Xss(栈)、Metaspace、G1 停顿目标
  4. 讲工具链:jstat(GC 统计)/ jmap(堆转储)/ jstack(线程快照)/ MAT(分析)
  5. 讲一个真实案例(如 Full GC 频繁 → jmap 抓堆 → MAT 找泄漏 → 修代码 + 调参),体现完整闭环

重点得分点

  • 说出"先监控后调参"的方法论,而不是背参数(这是和普通背题者的分水岭)
  • 准确说出 -Xms 与 -Xmx 要相等的原因(堆伸缩触发 Full GC)
  • 准确说出各工具用途:jstat 看 GC 统计、jmap 转储堆、jstack 看线程、MAT 分析泄漏
  • 说出吞吐量与停顿的矛盾取舍
  • 举一个"调参无效、修代码根治"的例子(体现认知深度)

常见误区

  • ❌ 上来就背参数,没有目标和方法论——面试官想听"怎么思考",不是"会多少参数"
  • ❌ 说"堆越大越好"——会撑爆物理内存,且单次 Full GC 停顿变长
  • ❌ 说"jstack 能看内存泄漏"——jstack 看线程,看堆用 jmap + MAT
  • ❌ 只说调参不提 GC 日志——没有数据支撑的调优面试里站不住
  • ❌ 忽略直接内存/元空间——NIO 场景的 DirectBuffer OOM 常被忽视

过渡话术

  • 开场:"JVM 调优我把它拆成四步:定目标、看数据、改参数、做验证。先说目标……"
  • 从参数到工具:"参数怎么定?靠工具看数据——jstat 看 GC 统计,jmap 抓堆快照,MAT 做泄漏分析……"
  • 收尾:"最后强调一点:如果根因是代码泄漏,调参只是拖延,先修代码再调参,这才是我理解的调优。"
