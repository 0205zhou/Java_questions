HashMap的长度为什么是2的N次方

哈希 HashMap

HashMap的长度为什么是2的N次方

联想记忆法

记忆口诀/联想

口诀:"位运算当取模,又快又均匀;低位全 1 保哈希,扩容搬家两选一"

把"计算元素放哪个桶"想成电影院找座位:

  • 朴素做法:取模 hash % 16,算 1 次除法
  • 2 的 N 次方做法:hash & 15,与运算——CPU 上一个时钟周期搞定,比除法快得多,而且结果和取模一模一样(当 n 是 2 的幂时,hash & (n-1) ≡ hash % n)
  • 为什么均匀:16-1=15 的二进制是 1111(低位全是 1),哈希值的低 4 位被完整保留——每个低位组合都对应一个桶,散得开
  • 附加红利:扩容时元素要么原位要么原位+老容量,一次位运算判断,不用重新哈希

记忆原理

三个钩子:① 性能(位运算 vs 除法)、② 均匀性(低位全 1)、③ 扩容迁移红利(两选一)。其中"hash & (n-1) ≡ hash % n"这个等式是核心,把"为什么是 2 的 N 次方"的三层理由(快、匀、迁移)都串起来——记住等式,理由自然推导出来。

关联知识

  • 与 HashMap 扩容关联:扩容翻倍 = 保持 2 的 N 次方,是迁移"两选一"的前提(配 hash & oldCap)
  • 与哈希函数关联:扰动函数(JDK8 的 (h = key.hashCode()) ^ (h >>> 16))配合低位全 1,进一步提升均匀性
  • 与 ConcurrentHashMap 关联:同样要求容量是 2 的幂(JDK8 的 tableSizeFor 也是取大于等于容量的最小 2 的幂)
  • 与数据结构对比关联:为什么不是质数容量——Hashtable 用 11(质数)直接取模,是另一派做法(牺牲性能求抗碰撞)

深度解答

第一层:核心概念

是什么

HashMap 的数组容量必须且始终是 2 的 N 次方:默认 16,扩容 32、64、128……构造时传入任意容量,内部也会用 tableSizeFor 修正为大于等于该值的最小 2 的幂(如传 17 → 实际 32)。

// 构造容量修正:返回 >= cap 的最小 2 的幂
static final int tableSizeFor(int cap) {
    int n = cap - 1;
    n |= n >>> 1;  n |= n >>> 2;  n |= n >>> 4;
    n |= n >>> 8;  n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}

定位桶的核心公式

// 元素放哪个桶:不是 hash % n,而是位运算
int index = (n - 1) & hash;
// 当 n = 2^k 时,n-1 二进制为 k 个 1,该式与 hash % n 完全等价

这是整个设计的基石:(n-1) & hash 替代 hash % n,是"2 的 N 次方"存在的意义。

第二层:底层原理

① 性能:位运算替代取模

  • % 取模指令在 CPU 上是慢指令(需要除法器,数十个时钟周期)
  • & 与运算一个时钟周期完成
  • HashMap 的每次 put/get 都要定位桶,这是全频段热点操作——用位运算,一次操作省下的量级不大,但整个 HashMap 生命周期累计的收益非常可观
  • 前提:(n-1) & hash 与 hash % n 等价,当且仅当 n 是 2 的幂(数学性质:n = 2^k 时,n-1 = k 个 1,与运算即保留 hash 的低 k 位,恰为模 2^k 的余数)

② 均匀性:低位全 1 保留哈希信息

  • 若 n = 2^k,n-1 的二进制是 k 个连续的 1(16 → 1111)——与运算完整保留 hash 的低 k 位,每个不同的低位组合都对应一个不同桶,哈希值均匀分布则桶位均匀分布
  • 若 n 不是 2 的幂,n-1 的某些位是 0——与运算后这些位的信息被丢弃,某些桶永远选不到,哈希冲突被人为放大
  • 配合 扰动函数(JDK8:key.hashCode() 的高 16 位异或到低 16 位),让高位的差异也能影响低位的取值,进一步降低碰撞——即使 hashCode 低位相同,扰动后也散开
// JDK8 扰动函数:让高位参与低位的计算
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

③ 扩容红利:迁移只需一次位运算判断

容量翻倍(16 → 32)后,n-1 从 1111 变成 11111,只多了一个 1。元素的新位置只取决于 hash 新增的哪一位:

if ((e.hash & oldCap) == 0) → 留在原位
else                        → 移到 原位 + oldCap
  • 不需要重新计算哈希、不需要逐个取模,O(1) 判断每个元素的位置
  • 元素只可能去两个地方(原位 / 原位+oldCap),可以拆成两条链表一次迁移,保持顺序
  • 如果容量不是 2 的幂,这个性质不存在,扩容必须全量重算——2 的 N 次方是扩容效率的设计前提

④ 为什么 Hashtable 用 11(质数)

Hashtable(遗留类)用质数容量 + 直接取模:质数容量下,取模结果的分布对某些"规律性"的哈希值(如都是 2 的倍数)更抗碰撞——这是牺牲速度换均匀的另一种哲学。HashMap 选 2 的 N 次方,是因为位运算 + 扰动函数已经解决了均匀性问题,且性能优势更大(现代工程的主流选择,ConcurrentHashMap 同样用 2 的幂)。

第三层:实践应用

构造时容量的正确写法

// 错误:传 1000,tableSizeFor 修正为 1024(2 的 10 次方),还算幸运
Map<String, Object> m1 = new HashMap<>(1000);

// 正确:结合负载因子反推,给出"够用且不浪费"的容量
// 目标存 1000 个元素不扩容:容量至少 1000/0.75 ≈ 1334 → 修正为 2048
Map<String, Object> m2 = new HashMap<>(1334);

// 或直接用:new HashMap<>(1000 * 4 / 3 + 1) 的常用写法

手推演示(面试画图)

n = 16 → n-1 = 15 = 1111(4 个 1)
hash = 1010_1101(hash 值示例,低 4 位 = 1101)
index = 1111 & 1101 = 1101 = 13

扩容后 n = 32 → n-1 = 11111
hash 新增位 = 第 5 位 = 1
index = 11111 & 10101 = 10101 = 21 = 13 + 16(oldCap)  ✓ 符合"原位 + oldCap"

工程启示

  • 自定义 key 时,hashCode() 的低 16 位尽量散开(扰动函数只保底,不兜底差哈希)
  • 不要依赖"扩容后位置不变"做任何顺序假设——HashMap 本就不保证迭代顺序
  • 容量给 2 的幂的整数倍记忆:2^4=16、2^5=32、2^10=1024、2^11=2048、2^20=100 万——预估容量时心里有数

第四层:深入思考

追问 1:如果容量不是 2 的 N 次方会怎样?

HashMap 内部不可能出现这种情况(tableSizeFor 强制修正),但假设不修正:

  • (n-1) & hash 退化为"丢位",某些桶永远空着,冲突加剧
  • 扩容时失去"两选一"性质,需要全量重新哈希,扩容成本大幅上升

追问 2:扰动函数为什么不直接把 hash 的 16 位全用?

(h >>> 16) 异或是一次性把高位"搅拌"进低位,成本极低(一次移位 + 一次异或)。足够的原因是:桶位索引只用低 k 位(k ≤ 30 但实际远小于),高位参与后,即使低位相同而高位不同的 hash,也能被区分开——用最小成本获得显著收益。

追问 3:JDK7 和 JDK8 的 hash 函数有区别吗?

有。JDK7:h ^= (h >>> 20) ^ (h >>> 12); return h ^ (h >>> 7) ^ (h >>> 4);(四次扰动,更复杂);JDK8 简化为一次 h ^ (h >>> 16)。原因:JDK8 有了红黑树兜底,对哈希质量的依赖下降,简化扰动换性能——工程上"兜底结构 + 简化主路径"的取舍。

追问 4:hash 为 0 的 key 会怎样?

JDK8 中 hash(null) = 0(HashMap 允许 null key),定位桶 index = 0,始终挂在0 号桶(JDK8 里 null key 固定放 table[0] 的链上)。Hashtable 不允许 null key,直接抛 NPE。

回答思路

答题逻辑框架(约 2 分钟)

  1. 先给核心公式:index = (n-1) & hash,当 n 是 2 的幂时等价于取模,但快得多
  2. 理由一:性能——位运算一个时钟周期,取模是慢指令,HashMap 每次访问都用
  3. 理由二:均匀性——n-1 低位全 1,哈希值低位被完整保留,配合扰动函数散得开
  4. 理由三:扩容红利——翻倍后 n-1 只多一个 1,hash & oldCap 一次判断,元素要么原位要么原位+oldCap,不用重新哈希
  5. 对比 Hashtable:质数 11 + 直接取模是另一派(抗规律性碰撞),HashMap 用位运算是性能派——体现对比深度

重点得分点

  • 写出公式 (n-1) & hash 并解释等价性(面试手写即加分)
  • 说出三个理由:性能 / 均匀 / 扩容迁移,一个不漏
  • 说出 tableSizeFor 强制修正容量(构造传 17 得 32)
  • 说出扰动函数 h ^ (h >>> 16) 的作用(高位参与低位)
  • 说出扩容迁移"两选一"与 2 的幂的关系(配"什么时候扩容"题联动)

常见误区

  • ❌ 只说"为了取模方便"——等价公式只说了一半,性能与均匀性才是核心
  • ❌ 说"HashMap 用取模运算"——用位运算,只是结果等价
  • ❌ 说"哈希值有多少位就参与多少位"——只有低 k 位参与桶定位,高位靠扰动函数参与
  • ❌ 说"Hashtable 也是 2 的幂"——Hashtable 用质数 11
  • ❌ 说"扩容重新算每个元素的哈希"——不重新哈希,位运算判断

过渡话术

  • 开场:"先说结论:因为索引公式是 (n-1) & hash,当容量是 2 的幂时它才等价于取模,而位运算更快——但好处不止性能……"
  • 展开:"第二,低位全 1 保证均匀;第三,扩容时元素只需一次位运算判断去留……"
  • 收尾:"对比一下 Hashtable 用质数 11 直接取模——那是抗规律碰撞的另一派设计,HashMap 是性能派,这也是它后来成为标准的原因。"
