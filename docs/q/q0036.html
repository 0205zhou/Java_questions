HashMap什么时候扩容

HashMap 集合

HashMap什么时候扩容

联想记忆法

记忆口诀/联想

口诀:"装到 75% 就搬家;容量翻倍,元素一半不动一半搬家"

把 HashMap 想成一家餐厅:

  • 餐厅有 16 张桌子(容量 capacity = 16),服务员领班觉得"桌子坐了 75% 就该准备加桌了"(负载因子 loadFactor = 0.75)
  • 超过 12 张桌有人(16 × 0.75 = 12)就扩容:桌子翻倍到 32 张
  • 搬家规则:每桌客人要么留在原桌号(新位置 = 原位),要么搬去"原桌号 + 老容量"的新桌(位置只可能两选一)——这就是扩容时元素分布的秘密

记忆原理

三个数字是记忆锚点:16(默认容量)、0.75(负载因子)、12(扩容阈值 = 16×0.75)。再用"餐厅加桌"的场景把"什么时候扩(超过阈值)、扩多少(翻倍)、怎么搬(两选一)"串成完整故事。最后记 JDK8 的新规则:链表要树化但容量小于 64 时,也会先扩容——这是"什么时候扩容"的第二个答案,不说会漏分。

关联知识

  • 与 2 的 N 次方关联:扩容翻倍正是为了保持"容量是 2 的幂",位置计算才能用位运算
  • 与红黑树关联:容量 <64 先扩容不树化——树化与扩容是"冲突缓解"的两条路
  • 与 JDK7 对比:JDK7 扩容多线程下链表成环死循环,JDK8 修复(尾插法)——经典演进故事
  • 与并发关联:HashMap 扩容非线程安全,并发场景用 ConcurrentHashMap(JDK8 也做了更细粒度的扩容处理)

深度解答

第一层:核心概念

是什么

HashMap 的扩容(resize)发生在两个场景:

  1. 元素数量超过扩容阈值:size > threshold,其中 threshold = capacity × loadFactor。默认容量 16、负载因子 0.75 → 阈值 12,元素数到 13(第 13 次 put)时触发扩容,容量翻倍为 32
  2. 链表树化但容量不足:某桶链表长度达到 8,但数组容量 < 64(即 MIN_TREEIFY_CAPACITY)时,先扩容把冲突散开,而不是树化
扩容触发条件(JDK8)
├── 场景一:size > capacity × loadFactor(默认 16 × 0.75 = 12)
└── 场景二:链表 ≥ 8 且 capacity < 64 → 先扩容(替代树化)

扩容做什么

  • 数组长度翻倍(16 → 32 → 64……始终是 2 的幂)
  • 重建整个表:新数组 + 重新计算每个元素位置(rehash)
  • 阈值同步翻倍:newThr = oldThr << 1

第二层:底层原理

① 为什么是 0.75(负载因子的权衡)

负载因子是"空间 vs 时间"的平衡旋钮:

负载因子 空间 冲突/性能 适用
0.75(默认) 浪费 25% 空间 冲突可控,兼顾两者 通用
更大(如 1.0) 空间省 冲突多,链表长,查找慢 内存紧张、可接受慢查
更小(如 0.5) 空间浪费大 冲突少,查找快 时间敏感、空间宽裕

0.75 的来源:JDK 源码注释给出的经验——泊松分布下,负载因子 0.75 时单个桶链表长度 ≥8 的概率约 0.00000006,在"空间浪费"和"冲突概率"之间取得统计平衡。工程上不要随意改,除非明确知道自己要什么。

② 扩容时的元素迁移(JDK8 的关键优化)

JDK8 扩容不再重新计算每个元素的 hash,而是利用"容量是 2 的幂"的性质:

位置公式 hash & (n-1):扩容后 n 变 2n,多出的那一位决定元素去哪——

// 判断规则:hash 的"新增最高位"是 0 还是 1
if ((e.hash & oldCap) == 0) {
    loTail.next = e;      // 留在原位置(低位链)
} else {
    hiTail.next = e;      // 移到 原位置 + oldCap(高位链)
}

例:老容量 16,元素 hash 后低位值 index=3:

  • hash & 16 == 0 → 新位置还是 3
  • hash & 16 == 16 → 新位置 3 + 16 = 19

每个元素迁移只可能落到两个位置:原位 or 原位+oldCap,用两条链表(低位链/高位链)一次遍历就完成迁移,复杂度 O(n) 且不丢顺序——而 JDK7 需要重新算 hash 逐个插入(还会反转链表)。

③ 为什么扩容这么重要(性能视角)

  • 扩容 = 全量重建数组 + 迁移全部元素,是最昂贵的操作之一
  • 频繁扩容的场景:预估容量,构造时直接给足:new HashMap<>(预估大小 / 0.75f),避免多次扩容
// 预估值 1000 个元素:直接给 1500 容量,让 threshold=1500*0.75=1125 > 1000,不扩容
Map<String, Object> map = new HashMap<>(1500);

④ JDK7 vs JDK8 扩容的差异(经典演进)

维度 JDK7 JDK8
插入方式 头插法(新元素插链头) 尾插法(新元素插链尾)
迁移 重新计算 hash,单链表逐个插 利用 hash & oldCap 高低位两条链,顺序保持
并发问题 多线程扩容可能链表成环 → get 死循环(经典事故) 尾插 + 顺序迁移,不再成环(但仍非线程安全,会丢数据)
数据规模 大数据量时新插元素直接进老年代 树化兜底

第三层:实践应用

代码验证扩容行为

// 观察扩容:打日志看 table 长度变化
Map<Integer, String> map = new HashMap<>(16);
for (int i = 1; i <= 13; i++) {
    map.put(i, "v" + i);
    // 第 13 次 put 后,数组长度从 16 变 32(threshold 12 → size 13 触发)
}

工程最佳实践

// ① 容量预估:避免扩容
int expectSize = 10_000;      // 业务预估
Map<String, Object> map = new HashMap<>(expectSize * 4 / 3 + 1);  // 按 0.75 反推

// ② 大 Map 的批量填充用 putAll,同样提前给容量
Map<String, Object> result = new HashMap<>(other.size() * 4 / 3 + 1);
result.putAll(other);

// ③ 不要在多线程场景用 HashMap(会丢数据/死循环历史)
// 并发读写 → ConcurrentHashMap

面试现场演示(口头 + 手写)

默认 HashMap(容量 16, 负载因子 0.75, 阈值 12):
put 1~12 → 不扩容(第 12 个元素后 size=12,尚未超)
put 13   → size=13 > 12 → 扩容 → 容量 32, 阈值 24

扩容迁移示例(老容量 16, 某元素 index=3):
hash & 16 == 0   → 新 index = 3
hash & 16 == 16  → 新 index = 3 + 16 = 19

第四层:深入思考

追问 1:为什么扩容后每个元素只可能"原位或原位+oldCap"?

因为容量翻倍后 n-1 的二进制只多了一个 1(16→32:1111→11111,多了第 5 位)。hash & (n-1) 的结果只取决于新增这一位:0 → 原位置,1 → 原位置 + 16。这就是"2 的 N 次方"设计的红利——扩容迁移是 O(1) 判断,不需要重新哈希。

追问 2:阈值为什么用"size > threshold"而不是"数组某个桶满了"?

HashMap 判断的是全局元素数量而非单桶负载:即使 16 个桶只有 1 个桶挂了 12 个元素,只要总 size 没到 12 也不扩容(冲突由树化兜底)。全局数量阈值 + 局部树化兜底是双保险设计。

追问 3:负载因子设成 0.5 或 1.0 会怎样?

  • 0.5:扩容更频繁(空间利用率 50%),但桶更空、冲突少、查询快——适合"读多、内存宽裕"
  • 1.0:空间用满才扩,冲突多、链表长,查询变慢——适合"内存紧张、写多读少"
  • 默认 0.75 是通用均衡,绝大多数场景不要改

追问 4:扩容后链表的顺序会变吗?

JDK8 不会变(尾插 + 高低位链保持原相对顺序);JDK7 会反转(头插法迁移)。所以 JDK8 的迭代顺序在扩容后更稳定——但注意:HashMap 本身不保证迭代顺序,这只是迁移实现带来的特性。

回答思路

答题逻辑框架(约 2 分钟)

  1. 先说两个触发场景:① size > capacity × 0.75;② 链表 ≥8 且容量 <64 先扩容
  2. 讲默认数字:容量 16、负载因子 0.75、阈值 12——"第 13 个元素 put 时扩容"
  3. 讲扩容动作:翻倍 + 重建 + 阈值同步翻倍
  4. 讲迁移细节(加分):hash & oldCap 判断高低位,元素只可能原位或原位+oldCap,不重新哈希
  5. 讲负载因子权衡:0.75 是空间/时间的统计平衡;讲 JDK7 vs JDK8(头插改尾插、死循环修复)
  6. 实践:预估容量避免扩容

重点得分点

  • 准确说出阈值 = 容量 × 0.75,默认 16 × 0.75 = 12
  • 准确说出两个触发场景(第二个场景"容量<64 先扩容不树化"是高频漏点)
  • 准确说出扩容翻倍,并解释 hash & oldCap 的位置两选一原理
  • 说出 0.75 的空间/时间权衡(而不是死记数字)
  • 说出 JDK7 头插法死循环 vs JDK8 尾插法修复(体现对历史的了解)

常见误区

  • ❌ 说"HashMap 装满了才扩容"——到 75% 就扩
  • ❌ 说"扩容要重新计算每个元素的 hash"——JDK8 用 hash & oldCap 位运算判断,不重新哈希
  • ❌ 说"链表到 8 就树化"——容量 <64 时是先扩容
  • ❌ 说"HashMap 线程安全"——并发扩容会丢数据(JDK7 还会死循环)
  • ❌ 记不住 0.75 的来源——泊松分布的统计平衡

过渡话术

  • 开场:"HashMap 扩容有两个触发点:一是元素数超过容量×负载因子,二是树化前置检查不满足……"
  • 引细节:"扩容后元素去哪?利用容量是 2 的幂,用 hash & oldCap 判断——0 留原位,1 移到原位加老容量,不用重新算哈希……"
  • 收尾:"所以实践中我都是预估容量、构造时给足,把扩容次数压到最低。"
