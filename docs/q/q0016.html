主键索引和唯一索引的区别?

联想记忆法

记忆口诀/联想

口诀："一主多唯，主空即罪；主聚唯二，回表受累"

逐句拆解：

  • 一主多唯 = 主键索引每表至多一个，唯一索引每表可以有多个
  • 主空即罪 = 主键列绝对不能为空；唯一索引列允许 NULL，且 MySQL 允许多个 NULL
  • 主聚唯二 = 主键索引是聚簇索引（叶子存整行），唯一索引是二级索引（叶子存主键值）
  • 回表受累 = 唯一索引查询先拿主键值、再回表查整行，比主键查询多一步；用覆盖索引可免

记忆原理

口诀采用"两两对照"的对仗结构：每个半句都是"主键 vs 唯一索引"的一处对比（数量、空值、存储、代价），四句恰好覆盖四个考点维度。对仗式口诀利用认知心理学的"对比记忆"效应——两个概念在差异点上互相锚定，记住"主聚唯二"，就自动带出"为什么唯一索引查询慢一点、为什么它叶子存的是主键值"。面试时背出四句口诀，四个对比维度齐活，不会漏掉任何一个。

关联知识

  • 与《MySQL都有哪些种类的索引》关联：主键索引与唯一索引在"按逻辑功能分"的维度并列，但落到存储层后分道扬镳——主键索引=聚簇索引，唯一索引=二级索引；想了解完整索引分类体系见该文
  • 与聚簇索引、回表关联：理解"叶子存整行 vs 叶子存主键值"是回答本问题的核心，也牵出覆盖索引优化手段
  • 与 B+ 树关联：两者底层都是 B+ 树，区别不在树的结构，而在"叶子上挂了什么"
  • 与外键关联：InnoDB 要求外键引用的列必须有索引（主键或唯一索引天然满足），这是主键/唯一索引在约束体系里的延伸价值

深度解答

第一层：核心概念

什么是主键索引

主键（primary key）是表的"身份标识"：每表至多定义一个，建主键时 InnoDB 自动创建主键索引。主键列满足两个硬性约束：非空（NOT NULL）+ 唯一。在 InnoDB 中，主键索引同时是聚簇索引（clustered index）——叶子节点直接存放整行数据，表的数据本身按主键顺序物理组织。

什么是唯一索引

唯一索引（unique index）是"值唯一性约束"的落地：确保索引列（或列组合）的值不重复，可为一列或多列，每表可建多个。建唯一约束（UNIQUE）时 InnoDB 自动创建唯一索引。与主键最大的不同：唯一索引列允许 NULL，且 MySQL 允许存在多个 NULL（因为 NULL = NULL 的结果是 NULL 即"未知"，不视为重复）。在 InnoDB 中，唯一索引是二级索引（secondary index）——叶子节点存"索引键 + 主键值"，不存整行。

一句话概括两者的角色分工：主键索引负责"身份 + 物理组织"，唯一索引负责"唯一性约束"。

第二层：底层原理

关键区别一览表

对比维度 主键索引（PRIMARY KEY） 唯一索引（UNIQUE）
每表数量 至多 1 个 可多个
是否允许 NULL 绝对不行（非空约束） 允许，且允许多个 NULL
底层结构（InnoDB） 聚簇索引：叶子存整行数据 二级索引：叶子存"索引键 + 主键值"
是否参与表物理组织 是——表数据按主键顺序存放 否——不影响数据物理顺序
核心作用 身份标识 + 物理组织 + 约束 唯一性约束（+ 查询加速）
查询流程 一次 B+ 树查找直接得整行 二级索引定位主键值 → 回表取整行（覆盖索引可免）
建表无主键时 — 第一个非空唯一索引可被 InnoDB 选中当聚簇索引

聚簇 vs 二级：为什么查询流程不同

InnoDB 中主键索引和唯一索引是两棵 B+ 树，区别在叶子上挂了什么：

主键索引(聚簇, 叶子存整行)          唯一索引(二级, 叶子存主键值)
┌────────────────────────┐        ┌────────────────────────┐
│ [1] → id=1 整行数据     │        │ [a@x] → 主键值 3        │
│ [2] → id=2 整行数据     │        │ [b@y] → 主键值 7        │
│ [3] → id=3 整行数据     │        │ [c@z] → 主键值 9        │
└────────────────────────┘        └────────────┬───────────┘
   一次查找，直接返回整行                         │ 拿到主键值 3
                                               ▼
                                   回到聚簇索引再查一次(回表)
  • WHERE id = 3：在聚簇索引上走一次 B+ 树查找，叶子即整行数据，一步到位
  • WHERE email = 'a@x'（email 上有唯一索引）：先在唯一索引这棵树上定位主键值 3，再拿 3 去聚簇索引查整行——多一次回表（table lookup）
  • 例外：若查询只取索引自身包含的列（如 SELECT email ... WHERE email = 'a@x'），二级索引直接返回，无需回表——这就是覆盖索引

所以"唯一索引比主键索引慢"不是绝对的：慢的是"查整行需要回表"；只查索引列时两者都是 O(log n) 级别的树查找。

唯一性约束是怎么生效的

插入/更新时，InnoDB 在二级索引树上检查新键值是否已存在：存在则报错 ERROR 1062 (23000): Duplicate entry 'xxx' for key 'uk_email' 并回滚该操作。由于二级索引叶子存主键值，这个"查重"本身也是一次索引查找，代价 O(log n)。

没有主键时 InnoDB 的兜底机制

建表不指定主键时，InnoDB 按以下顺序自动选聚簇索引：

  1. 找第一个非空（NOT NULL）的唯一索引，选它当聚簇索引
  2. 一个都没有 → 自动生成隐藏的 6 字节自增列 DB_ROW_ID，以它为主键组织数据

注意第 1 条意味着：唯一索引 + NOT NULL 就能扮演聚簇索引——这一点常被忽视。但兜底机制不可控（隐藏 rowid 不暴露给 SQL，无业务意义，且无法显式利用），所以生产规范永远是：每张表必须显式定义主键。

第三层：实践应用

建表 SQL 示例

-- 建表时同时定义主键索引 + 唯一索引
CREATE TABLE user (
    id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
    email VARCHAR(64) NOT NULL,
    phone VARCHAR(20),
    PRIMARY KEY (id),                       -- 主键索引(聚簇, 自动创建)
    UNIQUE KEY uk_email (email)             -- 唯一索引(二级, 自动创建)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 已有表上追加
ALTER TABLE user ADD PRIMARY KEY (id);
ALTER TABLE user ADD UNIQUE KEY uk_phone (phone);

-- 唯一索引支持多列(联合唯一): 同一 (a,b) 组合不重复
CREATE UNIQUE INDEX uk_a_b ON user (a, b);

-- 验证: 两次插入相同 email
INSERT INTO user (email) VALUES ('a@x.com');   -- 成功
INSERT INTO user (email) VALUES ('a@x.com');   -- ERROR 1062 Duplicate entry

主键设计最佳实践

  • 用自增（AUTO_INCREMENT）INT/BIGINT 做主键：新主键单调递增，插入总是在 B+ 树"最右叶子"追加，不触发页分裂（page split），写入高效、碎片少
  • 避免 UUID/随机字符串做主键：无序插入导致中间位置分裂、页重排、碎片化，写入放大；查询索引缓存命中率也下降
  • 必须用分布式 ID 时：用雪花算法（snowflake）等"趋势递增"ID——单调性保住写入效率，又不依赖单库自增
  • 业务唯一字段（如 email）用唯一索引而非主键：避免主键被业务耦合、后期变更困难；主键永远是"无业务含义的代理键"更稳

第四层：深入思考

1. 主键选型权衡

方案 优点 缺点 适用场景
自增 INT/BIGINT 顺序插入无页分裂、空间小、索引缓存命中率高 有暴露风险（爬虫可猜）、分布式不可用、迁移合并易冲突 单库单表、OLTP 主键
UUID 字符串 全局唯一、生成不依赖库、不暴露业务量 无序 → 页分裂 + 碎片；长度 36 字符，二级索引每棵都冗余一份，空间翻倍 极少量写、或必须离线生成
雪花算法 ID 趋势递增 + 全局唯一 + 高性能 依赖时钟（时钟回拨需处理） 分布式分库分表
联合主键 天然表达复合身份 索引冗长、被二级索引冗余、改主键成本极高 关联表（如中间表）谨慎使用

2. 能不能把唯一索引当主键用

逻辑上可以：只要列非空，UNIQUE KEY NOT NULL 在 InnoDB 里会被选为聚簇索引，功能上等价于主键。但生产不建议：

  • 主键是"身份"，唯一索引是"约束"，混用会让语义模糊；后期业务值会变（如邮箱换号），而主键不应变
  • 外键约束：InnoDB 要求外键引用的列必须是索引（主键或唯一索引均满足）——注意此处是"必须有索引"，不是"必须主键"；但用主键做引用目标语义最清晰
  • 真正该警惕的是"无主键的隐式聚簇"：唯一索引非空但含多列时，任何一列的业务更新都可能引发聚簇索引重组

3. 为什么唯一索引的 NULL 语义这么特殊

MySQL 遵循 SQL 标准：NULL 表示"未知"，两个 NULL 之间的比较结果是"未知"而非"相等"，所以不违反唯一约束。这是特性而非 bug：它意味着"允许该列部分行没值"。若业务要求"非空且唯一"，就加 NOT NULL（与主键语义对齐）；若要求"空值也只允许一个"，MySQL 原生做不到，需要借助函数索引（如 UNIQUE KEY ((IFNULL(email, id)))，MySQL 8.0）或生成列。

4. 联合主键 vs 联合唯一索引

  • 联合主键 PRIMARY KEY (a, b)：复合身份，非空，自动建聚簇索引，最左前缀同样适用
  • 联合唯一 UNIQUE KEY (a, b)：约束"组合不重复"，但单列 a 可重复
  • 注意区别：UNIQUE(a) + UNIQUE(b) 与 UNIQUE(a, b) 完全不同——前者约束两列各自唯一，后者只约束组合唯一

5. 面试官可能的追问方向

  • "唯一索引查询为什么也要回表？" → 唯一索引是二级索引，叶子只有主键值，取整行必须回表；覆盖索引可免
  • "NULL 与唯一约束的语义？" → NULL 互不相等，允许重复 NULL；这是 SQL 标准的三值逻辑
  • "为什么外键要求目标列有索引？" → 外键校验（插入/更新/删除时检查引用完整性）本质是"查目标列在不在"，没有索引就得全表扫描；InnoDB 对引用列没有索引时会自动建
  • "没有主键的表会怎样？" → 第一个非空唯一索引被选为聚簇索引，否则隐式 6 字节 DB_ROW_ID 兜底——两种都不可控，生产必须显式主键

重点得分点（面试官考察意图）

  1. 聚簇 vs 二级的存储差异（核心得分点）：能说出"主键索引叶子存整行、唯一索引叶子存主键值"，并解释回表——这证明你理解 InnoDB 的物理模型，而非只背结论

  2. NULL 语义：能说出"唯一索引允许多个 NULL，因为 NULL 之间互不相等"——这是 SQL 三值逻辑的体现，也是最容易与主键混淆的点

  3. 无主键兜底机制：能说出"第一个非空唯一索引 → 隐藏 6 字节 rowid"，并顺势给出"生产表必须显式主键"的规范——体现工程经验

  4. 主键选型权衡：能对比自增与 UUID（页分裂、碎片化、二级索引冗余）——体现对写入模型的理解

  5. 查询代价的相对性：能指出"唯一索引慢在回表，覆盖索引可免"——回答不绝对化，加分

常见误区（扣分点）

错误说法 正确理解
"唯一索引不允许 NULL" MySQL 唯一索引允许 NULL，且允许多个 NULL（NULL 互不相等）
"主键索引和唯一索引都是二级索引" 主键索引是聚簇索引（叶子存整行），唯一索引才是二级索引（叶子存主键值）
"唯一索引查询和主键一样快" 查整行时唯一索引多一次回表；但只查索引列（覆盖索引）时同样无需回表
"表不建主键也没关系" InnoDB 会用第一个非空唯一索引或隐藏 rowid 兜底，但不可控，生产必须显式主键
"外键引用的列必须是主键" 必须是"有索引的列"，主键或唯一索引都满足
"UNIQUE(a) 和 UNIQUE(a,b) 一样" 前者约束 a 单列唯一，后者约束 (a,b) 组合唯一，语义完全不同

过渡话术建议

  • 从定义到对比："主键和唯一索引都保证唯一性，但本质不同：主键是表的身份标识，唯一索引是约束。我建议从三个维度对比——数量、NULL 语义、底层结构..."
  • 从对比到底层："两者最本质的差别在存储层：主键索引是聚簇索引，叶子节点直接存整行；唯一索引是二级索引，叶子节点只存主键值，所以要取整行就得回表..."
  • 从底层到实践："这个存储模型直接决定主键怎么选——自增主键顺序插入，B+ 树只在最右追加；UUID 无序插入，中间分裂频繁、索引碎片多..."
  • 总结过渡："一句话收尾：一主多唯、主非空唯可空、主聚唯二。理解了这三组对比，就理解了 InnoDB 索引模型的另一半。"

时间分配建议

  • 如果面试官打断：说完"一主多唯、主非空唯可空、主聚唯二"三组对比即可停，这是核心
