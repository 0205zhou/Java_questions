synchronized锁的种类？

synchronized 锁升级 对象锁

synchronized锁的种类？

联想记忆法

记忆口诀/联想

口诀：“先偏向，后轻量，再重量；对象有锁，类也能锁，方法代码都可上。”

把 synchronized 想成门禁系统的升级过程：

  • 偏向锁：门默认偏向某一个熟人，他来直接进。
  • 轻量级锁：来了少量访客，先靠登记和自旋解决。
  • 重量级锁：人一多，就得排队、叫保安、挂起唤醒。

从使用形式上看，又像三种加锁位置：

  • 普通同步方法：锁当前对象（this）。
  • 同步代码块：锁括号里的对象。
  • 静态同步方法：锁类对象（Class 对象）。

记忆原理

面试里“锁的种类”常有两种问法：一种按使用维度分对象锁、类锁；另一种按状态维度分偏向锁、轻量级锁、重量级锁。最稳妥的回答方式是先说明“如果从代码写法看”和“如果从 JVM 锁状态看”这两套分类，再分别展开，这样不会答偏。

关联知识

  • 与对象头（Mark Word）结构相关。
  • 与 synchronized 和 Lock 的区别相关，前者由 JVM 完成锁升级。
  • 与线程状态 BLOCKED、自旋、上下文切换相关。
  • 与偏向锁撤销、锁膨胀、锁粗化、锁消除等优化相关。

深度解答

第一层:核心概念

是什么

synchronized 锁的种类通常有两套分类方式。

第一套：按使用位置分类

类型 锁的对象 说明
同步实例方法 当前对象 this 同一个实例上的方法互斥
同步代码块 括号中的对象 锁粒度最灵活
同步静态方法 当前类的 Class 对象 所有实例共享一把类锁

第二套：按锁状态分类（JVM 优化维度）

类型 场景 特点
偏向锁（Biased Locking） 基本无竞争 偏向第一个获得锁的线程
轻量级锁（Lightweight Lock） 轻度竞争 通过 CAS 和自旋避免挂起
重量级锁（Heavyweight Lock） 激烈竞争 线程阻塞和唤醒，开销大

第二层:底层原理

从代码层面看：对象锁和类锁

public class Demo {
    // 锁 this
    public synchronized void methodA() {}

    // 锁 Demo.class
    public static synchronized void methodB() {}

    public void methodC() {
        synchronized (this) {
            // 锁当前对象
        }
        synchronized (Demo.class) {
            // 锁类对象
        }
    }
}

关键点：

  • 两个不同实例的实例锁彼此不冲突。
  • 静态同步方法锁的是 Demo.class，与实例锁不是同一把锁。
  • 同步代码块最灵活，可以把锁范围缩小到真正需要保护的资源。

从 JVM 层面看：锁升级过程

synchronized 底层依赖对象头（Object Header）中的 Mark Word 记录锁状态。JVM 为了减少无竞争时的同步成本，引入锁升级机制：

无锁 → 偏向锁 → 轻量级锁 → 重量级锁
  1. 偏向锁：适用于“总是同一个线程进入同步块”的场景。对象会记录偏向线程 ID，后续同线程进入时几乎不需要真正加锁。
  2. 轻量级锁：当有其他线程竞争时，偏向锁会撤销，升级为轻量级锁。线程通过 CAS（Compare-And-Swap，比较并交换）尝试获取锁，失败时可短暂自旋。
  3. 重量级锁：如果竞争激烈，自旋无效，锁会膨胀为重量级锁，依赖操作系统互斥量（mutex）挂起和唤醒线程，这时线程可能进入 BLOCKED。

需要注意：锁升级通常是单向膨胀，主要目的是在不同竞争强度下折中性能和线程切换成本。

第三层:实践应用

public class Counter {
    private int num;
    private static int total;
    private final Object lock = new Object();

    public synchronized void incr() {
        num++;
    }

    public void incrSafely() {
        synchronized (lock) {
            num++;
        }
    }

    public static synchronized void incrTotal() {
        total++;
    }
}

实践上如何理解：

  • 如果只是保护某个实例变量，用实例锁即可。
  • 如果保护静态共享资源，用类锁。
  • 如果要降低锁粒度，优先使用私有 lock 对象而不是直接锁 this，避免锁暴露。
  • 如果并发竞争不高，synchronized 依靠偏向锁和轻量级锁通常已经足够高效。

第四层:深入思考

为什么 JVM 要做锁升级？ 因为绝大多数锁并不是一直高竞争。无竞争时用重量级锁太浪费；轻竞争时用 CAS + 自旋更划算；真正高竞争时才值得挂起线程。

为什么不建议随便锁 this 或字符串常量？ 因为这些对象可能被外部代码也拿来加锁，导致意外竞争甚至死锁。更稳妥的做法是使用私有不可变锁对象。

偏向锁现在还一定会讲吗？ 面试中可以讲它的思想，但也要知道不同 JDK 版本实现细节有变化。回答时重点应放在“JVM 会根据竞争程度做优化与膨胀”，而不是死记具体版本开关。

回答思路

答题逻辑框架

  1. 先说明“锁的种类”有两种常见分类口径。
  2. 先讲代码维度：实例锁、对象锁、类锁。
  3. 再讲 JVM 状态维度：偏向锁、轻量级锁、重量级锁。
  4. 补充锁升级流程和对象头原理。
  5. 结合实际代码说明何时锁 this、何时锁私有对象、何时锁类。

重点得分点

  • 明确区分对象锁和类锁。
  • 说出偏向锁、轻量级锁、重量级锁三种状态。
  • 能讲出锁升级是为了优化不同竞争场景。
  • 知道静态同步方法锁的是 Class 对象。

常见误区

  • 把实例锁和类锁混为一谈。
  • 以为 synchronized 只有一种锁，没有锁优化。
  • 误以为两个不同实例的同步方法一定互斥。
  • 锁字符串常量或公共对象，导致外部竞争不可控。

过渡话术

  • “既然锁会升级，那如果线程互相等待资源，就会进一步引出死锁问题。”
  • “了解了 synchronized 的锁形态，再看它和 Lock 的区别就更容易理解了。”
