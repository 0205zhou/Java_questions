MySQL的存储引擎都有哪些区别是什么?默认的是什么?

存储 引擎

MySQL的存储引擎都有哪些区别是什么?默认的是什么?

联想记忆法

记忆口诀/联想

口诀："默认 Inno，事务行锁；MyISAM 读快，表锁压缩；MEMORY 内存，哈希等值；ARCHIVE 归档，只插不更"

按引擎逐个拆解：

  • 默认 Inno = InnoDB 是 MySQL 5.5.5 起的默认存储引擎，支持事务（ACID）、行级锁、崩溃恢复，是"标准答案"
  • MyISAM 读快 = 读多写少场景读取快、支持压缩表，但只支持表级锁、不支持事务和外键
  • MEMORY 内存 = 数据全部驻留内存，默认哈希索引，等值查询极快，重启即丢
  • ARCHIVE 归档 = zlib 高压缩，只支持 INSERT 与 SELECT，天然适合日志归档

记忆原理

口诀采用"引擎名 + 一句话人设"的四字句结构，每句前半记住引擎名，后半记住它最抓人的标签，背住 I-M-M-A 四个字母就能逐个展开。更关键的是两两成对的对比记忆：InnoDB 与 MyISAM 是一对宿敌（事务 vs 非事务、行锁 vs 表锁、聚簇 vs 非聚簇），MEMORY 与 ARCHIVE 是两个极端（全内存 vs 高压缩）——记一个必然牵出另一个，四个引擎其实只需要记两个对比轴。

关联知识

  • 与索引体系关联：InnoDB 聚簇索引（Clustered Index）与 MyISAM 非聚簇索引的区别，是"回表（Table Lookup）""覆盖索引（Covering Index）"等高频追问的根源
  • 与事务体系关联：只有 InnoDB 完整支持 ACID，于是引出 undo log、redo log、MVCC、各种锁——MySQL 的事务知识几乎全部挂在 InnoDB 这棵树上
  • 与主从复制关联：早期 statement 格式 binlog 在部分引擎下无法保证主从一致，这是 InnoDB 上位的历史推手之一
  • 与建表规范关联：临时缓存表能不能用 MEMORY、归档表用不用 ARCHIVE，考察的都是"按场景选引擎"的工程思维

深度解答

第一层：核心概念

什么是存储引擎

存储引擎（Storage Engine）是 MySQL 表级别的存储与处理组件，决定一张表的数据如何存放、如何加锁、是否支持事务。MySQL 的架构是"Server 层（连接管理、SQL 解析、binlog）+ 引擎层（数据存储、索引、事务）"分离，同一实例可以混合使用不同引擎的表。

用 SHOW ENGINES; 可以查看当前 MySQL 支持的所有引擎及特性，输出中 Support 列为 DEFAULT 的即是默认引擎：

SHOW ENGINES;
-- 关键列：Engine | Support | Comment | Transactions | XA | Savepoints
-- InnoDB 行的 Support = DEFAULT

主要引擎全景：

引擎 一句话画像
InnoDB MySQL 5.5.5 起默认引擎，事务 + 行锁 + 崩溃恢复，OLTP 主业务表首选
MyISAM 老牌引擎，读多写少场景快，表级锁，不支持事务/外键，可压缩
MEMORY（HEAP） 数据全在内存，默认哈希索引，重启数据丢失，适合临时表/缓存
ARCHIVE zlib 高压缩，只支持 INSERT 与 SELECT，适合日志归档
CSV 表就是一个 CSV 文本文件，可用外部工具直接读写，不支持索引，适合数据交换
BLACKHOLE 写入即丢弃，但 binlog 会正常记录，可用于"只分发不存储"的复制中间层
NDB Cluster 内存型分布式引擎，面向电信级高可用（了解即可）

这些区别到底在比什么

引擎区别本质上围绕五个维度：事务支持、锁粒度、索引结构、崩溃恢复能力、适用场景。InnoDB vs MyISAM 的对比是全部考点的主轴，其他引擎是加分项。

第二层：底层原理

InnoDB：聚簇索引下的"表与索引一体"

InnoDB 的数据文件按表存放（每表一个 .ibd 文件，独立表空间），其索引结构是聚簇索引（Clustered Index）：表数据本身就以主键索引为序组织成一颗 B+ 树，索引的叶子节点直接存放整行数据。

聚簇索引（主键索引 B+ 树）          二级索引（普通索引 B+ 树）
┌─────────────┐                    ┌─────────────┐
│  非叶子节点   │  (key + 子指针)     │  非叶子节点   │
└──────┬──────┘                    └──────┬──────┘
       ▼                                  ▼
┌─────────────┐                    ┌─────────────┐
│  叶子节点     │                    │  叶子节点     │
│ [主键, 整行数据] │ ← 数据就在索引里   │ [索引列, 主键值] │ ← 只存主键
└─────────────┘                    └──────┬──────┘
                                         │ 查非索引列 → 拿主键再查聚簇索引
                                         ▼
                                 这一步就叫"回表（Table Lookup）"

由此推出两个关键结论：

  • 按主键查一行：走聚簇索引，一次 B+ 树查询即得数据，无回表
  • 按二级索引查非索引列：先在二级索引找到主键值，再回聚簇索引取整行，两次 B+ 树查询；若查询的列都在二级索引里（覆盖索引），则免回表

此外 InnoDB 还提供：行级锁（记录锁 Record Lock、间隙锁 Gap Lock、临键锁 Next-Key Lock）、MVCC（多版本并发控制，Multi-Version Concurrency Control）、redo log + doublewrite 双写缓冲的崩溃恢复、外键（Foreign Key）约束。

MyISAM：索引与数据分离的非聚簇结构

MyISAM 使用非聚簇索引：索引文件（.MYI）与数据文件（.MYD）物理分离，索引叶子节点存放的是指向数据行的指针（行偏移）。

MyISAM 表
┌─────────────┐   ┌─────────────┐
│ 索引文件 .MYI │   │ 数据文件 .MYD │
│ 主键索引 B+ 树 │   │ ┌───┐      │
│ 叶子 → 行指针 ────→ │ │行1│ ...  │
│ 二级索引 B+ 树 │   │ │行2│ ...  │
│ 叶子 → 行指针 ────→ │ │行3│ ...  │
└─────────────┘   └─────────────┘

由于没有 MVCC 和行锁，MyISAM 只能靠表级锁串行化写入；不支持事务、不支持外键；崩溃后没有 redo log 自动恢复，只能手工 REPAIR TABLE 修复，可靠性弱。它的传统优势：纯读场景快、SELECT COUNT(*) 不扫数据（内部维护行数）、支持 myisampack 压缩成只读表（压缩表）、5.6 之前全文索引仅此一家。

MEMORY 与 ARCHIVE 的底层差异

  • MEMORY：数据驻留内存，磁盘上只有表结构，服务重启数据全部丢失；默认哈希索引（Hash Index），等值查询 O(1)，但哈希索引不支持范围查询、排序优化（需要可显式建 BTREE 索引）；表级锁。
  • ARCHIVE：写入时用 zlib 流式压缩，压缩比极高，但每次查询都要解压；只支持 INSERT 与 SELECT，不支持 UPDATE/DELETE，除一个自增主键外不支持其他索引，天然用于日志、审计、历史数据归档。

第三层：实践应用

建表与配置

-- 显式指定引擎（表级别）
CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  amount DECIMAL(10,2) NOT NULL,
  INDEX idx_user (user_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- 查看表引擎 / 修改引擎（ALTER 会重建表，大表慎用）
SHOW TABLE STATUS LIKE 'orders';
ALTER TABLE orders ENGINE = MyISAM;

默认引擎在 my.cnf 中配置，自 MySQL 5.5.5 起即为 default-storage-engine = InnoDB，一般无需改动。

按场景选引擎的决策逻辑

需求信号 选型结论
需要事务、并发写入、外键、崩溃不丢数据 InnoDB（绝大多数业务场景）
只读历史数据、想极限压缩省空间 可考虑 MyISAM 压缩表，或 ARCHIVE 归档
会话级临时数据、热点缓存，丢了无所谓 MEMORY（注意容量上限和重启丢失）
日志/审计流，只增不改不删 ARCHIVE
与外部系统交换数据（纯文本） CSV

第四层：深入思考

1. 为什么 InnoDB 取代 MyISAM 成为默认

不是单纯的性能原因，而是能力与业务需求匹配：电商、金融等 OLTP 场景要求事务一致性、并发写入下的正确性（行锁 vs 表锁）、宕机不丢已提交数据（redo log 崩溃恢复）。MyISAM 表锁导致写入完全串行、崩溃后可能整表损坏，已无法满足现代业务，MySQL 5.5 起将其降级，5.5.5 正式把 InnoDB 设为默认。

2. 聚簇索引 vs 非聚簇索引的本质区别

维度 InnoDB 聚簇索引 MyISAM 非聚簇索引
数据与索引 一体，叶子即整行数据 分离（.MYI / .MYD），叶子存行指针
二级索引查询 通常两次（二级索引 → 回表） 一次定位行指针，但定位数据仍需一次 IO
主键范围扫描 快，数据物理按主键有序 一般
无索引列查询 扫聚簇索引叶子 扫数据文件
空间 主键 + 所有行冗余在二级索引中，占用更多 二级索引更小

3. 表没有主键时 InnoDB 怎么办

InnoDB 必须有聚簇索引，优先级是：显式主键 → 第一个非空唯一索引 → 自动生成一个 6 字节隐藏主键 rowid（DB_ROW_ID）。隐藏 rowid 对外不可见、无法优化查询，还给主从复制与备份埋下隐患，所以生产表必须显式定义主键（这也是阿里规范强制要求主键的原因之一）。

4. "MyISAM 读更快"在什么前提下成立

该说法只在特定场景成立：无并发写入（表锁不拖累）、COUNT(*) 全表行数统计、压缩表读取。现代 MySQL 中，InnoDB 的缓冲池（Buffer Pool）让热点数据全部驻留内存，普通查询性能与 MyISAM 已无明显差距，且 InnoDB 并发读不受写阻塞、更稳定。不能把 MyISAM 当"快读引擎"的通用结论。

5. 面试官可能的追问方向

  • "MEMORY 表为什么默认哈希索引？范围查询怎么办？" → 等值查询 O(1)；范围查询需显式建 BTREE 索引
  • "ARCHIVE 能当普通业务表用吗？" → 不能，只支持 INSERT/SELECT，无 UPDATE/DELETE
  • "为什么生产规范都强制 InnoDB + 主键？" → 事务、行锁、崩溃恢复 + 隐藏 rowid 的隐患
  • "CSV 引擎支持索引吗？" → 不支持，适合数据交换而非查询

重点得分点（面试官考察意图）

  1. 默认引擎与版本：能说出"5.5.5 起默认 InnoDB"并给出理由（事务/行锁/崩溃恢复），证明关注版本演进
  2. 聚簇 vs 非聚簇的本质：能画出"二级索引叶子存主键值 → 回表"的路径，并说出覆盖索引可免回表——这是索引知识的根基
  3. MyISAM 的劣势要精确：不支持事务、表级锁、崩溃需 REPAIR，而不是笼统说"慢"
  4. "读更快"的前提限定：能限定"表锁下纯读 / COUNT(*) / 压缩表"场景，体现严谨
  5. 无主键的兜底机制：隐藏 6 字节 rowid，说明对 InnoDB 内部结构的理解

常见误区（扣分点）

错误说法 正确理解
"MyISAM 就是比 InnoDB 快" 只在无并发写、COUNT(*)、压缩表等特定场景成立，InnoDB 缓冲池下读性能不输
"InnoDB 没有全文索引" 5.6 起 InnoDB 已支持 FULLTEXT，不再是 MyISAM 专利
"MEMORY 表适合当业务主表" 重启数据全丢，只适合临时表/缓存，且默认哈希索引不适合范围查询
"ARCHIVE 表可以 UPDATE" ARCHIVE 只支持 INSERT 与 SELECT，无 UPDATE/DELETE
"InnoDB 没有主键会建表失败" 会优先选非空唯一索引，否则自动生成隐藏 6 字节 rowid
"MyISAM 支持外键" 只有 InnoDB 支持外键约束，这是两者对比的固定考点

过渡话术建议

  • 从全景到主角："MySQL 的存储引擎是表级别的，用 SHOW ENGINES 能看全。日常开发几乎只跟两个引擎打交道——默认的 InnoDB 和曾经的默认 MyISAM..."
  • 从对比到原理："这两个引擎最本质的区别在索引：InnoDB 是聚簇索引，主键叶子直接存整行，二级索引叶子存主键，所以二级索引查询要回表；MyISAM 索引和数据是两个文件，叶子存的是行指针..."
  • 从原理到选型："所以选引擎不是拍脑袋：要事务、要并发写、要外键就 InnoDB；只读归档数据才考虑 MyISAM 压缩表或 ARCHIVE..."
  • 总结过渡："一句话总结：InnoDB 用'牺牲一点存储和回表成本'换来了事务、行锁和崩溃恢复，这正好是现代业务最需要的东西，所以它成了默认。"

时间分配建议

  • 总时长 3-4 分钟：前 30 秒全景，1 分钟五维对比，1 分钟聚簇索引原理，最后 30 秒选型结论
  • 如果面试官打断：讲完"默认 InnoDB + 五维对比"即可，聚簇索引原理是加分项，追问时再展开
  • 遇到追问如何应对：被问"MyISAM 读更快？"时先承认特定场景成立，再补前提条件，展示辩证思维而非死背结论
