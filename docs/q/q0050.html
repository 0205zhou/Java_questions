悲观锁和乐观锁的区别？

乐观锁 悲观锁 CAS

悲观锁和乐观锁的区别？

1. 🧠 联想记忆法

记忆口诀/联想：悲观先锁门，乐观先提交；前者防冲突，后者做校验。

记忆原理：悲观锁和乐观锁本质上是两种不同的并发控制思想。悲观锁假设冲突经常发生，所以先锁住再操作；乐观锁假设冲突不常发生，所以先放行，提交时再校验。记住“先锁 vs 先改后验”，就能很快展开到 Java 和数据库两个层面。

关联知识：这题常和 synchronized、ReentrantLock、CAS、版本号、数据库 for update、ABA 问题、自旋重试一起考。面试官通常想看你是否理解：乐观锁不是简单的“性能更高”，悲观锁也不等于“落后”，关键在冲突概率和业务一致性要求。

2. 📖 深度解答

2.1 核心概念：两种并发控制思路

悲观锁（Pessimistic Lock）和乐观锁（Optimistic Lock）并不是两个具体 API，而是两种控制共享资源更新的思路。

  • 悲观锁：认为并发冲突大概率会发生，所以在操作前先把资源锁住，别人不能同时改。
  • 乐观锁：认为并发冲突不常发生，所以不先锁，等更新时再检查数据是否被别人改过。

可以先看一个总表：

维度 悲观锁 乐观锁
核心思想 先加锁再操作 先操作，提交时校验
对冲突的假设 冲突经常发生 冲突不常发生
线程行为 常阻塞等待 通常不阻塞，失败后重试
典型代价 上下文切换、等待、死锁风险 自旋、重试、失败处理
典型实现 synchronized、Lock、数据库行锁 CAS、版本号、时间戳
适用场景 写多冲突高、强一致要求高 读多写少、冲突低、追求吞吐

2.2 悲观锁：先把资源占住

悲观锁的思路很直接：既然别人可能跟我抢，那我先把门锁上。

在 Java 中，最典型的就是：

synchronized (lock) {
    balance = balance - 100;
}

或者：

lock.lock();
try {
    update();
} finally {
    lock.unlock();
}

数据库里也有典型写法：

select * from account where id = 1 for update;

它的特点是：

  • 只有拿到锁的线程或事务能继续执行
  • 其他竞争方必须等待
  • 逻辑简单，强一致性强

但代价也明显：

  • 线程会阻塞
  • 有上下文切换成本
  • 持锁时间过长会导致吞吐下降
  • 多把锁顺序不一致时可能死锁

所以悲观锁不是没有成本，它是拿“更强的控制力”换“更低的并发度”。

2.3 乐观锁：先放行，提交时校验

乐观锁不急着锁住资源，而是在真正更新时检查：

这份数据是不是还是我最开始看到的那份？

如果是，就更新成功；如果不是，说明别人先改过了，我当前这次更新失败，再决定是否重试。

最典型有两种实现方式。

1）CAS

CAS（Compare-And-Swap，比较并交换）通常用于内存中的并发更新：

AtomicInteger count = new AtomicInteger(0);
count.compareAndSet(0, 1);

它的意思是：

  • 只有当当前值还是 0 时，才把它改成 1
  • 如果已经不是 0，说明有人先改了，本次更新失败
2）版本号机制

数据库里更常见的是版本号：

update product
set stock = stock - 1, version = version + 1
where id = 1 and version = 3;

这个更新语句的逻辑是：

  • 我读取数据时看到版本号是 3
  • 只有版本号仍然是 3，我才允许更新
  • 如果影响行数是 0，说明别人已经改过，当前更新失败

这就是典型的乐观锁。

2.4 两者的本质差异到底是什么

本质上可以概括成一句话：

  • 悲观锁把冲突前置
  • 乐观锁把冲突后置

悲观锁的思路是：先把冲突挡在门外，再操作。

乐观锁的思路是：大家都先试着操作，真正提交时再判断有没有冲突。

所以它们的代价也不同：

  • 悲观锁付出的是等待和阻塞
  • 乐观锁付出的是重试和失败处理

这就是为什么不能简单地说谁“更高级”或“性能一定更好”。

2.5 Java 场景下如何理解

悲观锁在 Java 里的典型体现
  • synchronized
  • ReentrantLock
  • 各种显式互斥锁

它们适合：

  • 共享状态复杂
  • 一次操作要改多个字段
  • 临界区里必须保证原子一致性
  • 冲突概率高
乐观锁在 Java 里的典型体现
  • AtomicInteger
  • AtomicReference
  • AtomicStampedReference
  • 各种基于 CAS 的并发工具

它们适合：

  • 更新逻辑相对简单
  • 冲突概率低
  • 更看重吞吐量和无阻塞特性

例如计数器、自旋状态位、无锁队列中的部分更新，常用乐观方式实现。

2.6 数据库场景下如何理解

悲观锁更适合什么

例如：

  • 库存扣减
  • 账户余额扣款
  • 高冲突热点行更新
  • 强一致要求极高的交易逻辑

这类场景里，如果大家都来抢同一条记录，乐观锁可能一直失败重试，反而更糟。此时用悲观锁先锁住，再串行处理，往往更稳。

乐观锁更适合什么

例如：

  • 配置修改
  • 用户资料更新
  • 订单备注编辑
  • 读多写少的后台管理场景

这类场景冲突低，用版本号校验可以提高并发度，避免大量锁等待。

2.7 风险和代价

悲观锁的风险
  • 长时间阻塞
  • 上下文切换成本高
  • 吞吐下降
  • 死锁风险
  • 持锁范围一大，尾延迟明显变差
乐观锁的风险
  • 高冲突下频繁重试
  • 大量 CAS 失败会空转消耗 CPU
  • 业务上必须处理失败分支
  • 存在 ABA 问题

ABA 问题的意思是：

  • 一个值从 A 变成 B
  • 又从 B 变回 A
  • CAS 看到还是 A，以为没变化，其实中间发生过修改

这时通常要引入版本戳，例如 AtomicStampedReference。

2.8 什么时候谁更合适

可以按一个简单原则判断：

更适合悲观锁
  • 写多读少
  • 冲突频繁
  • 强一致性要求高
  • 失败重试代价大
  • 操作复杂，涉及多个共享变量
更适合乐观锁
  • 读多写少
  • 冲突概率低
  • 可以接受失败后重试
  • 更关注系统吞吐和响应速度
  • 共享更新逻辑相对简单

面试里最好不要说“乐观锁一定适合高并发”。更准确的说法是：

高并发不等于高冲突。只有在高并发但低冲突场景下，乐观锁优势才明显。

这句话很加分。

2.9 深入思考：很多系统其实是混合使用

工程上并不是非黑即白。

很多系统会这样做：

  • 先尝试乐观更新
  • 如果冲突过多，再退化成更强的控制手段
  • 某些关键资源用悲观锁，其他低冲突字段用乐观锁

比如：

  • 数据库主更新用版本号
  • 极热点资源加分布式互斥
  • 内存状态位用 CAS
  • 复杂业务流程仍用互斥锁保护

所以真正成熟的答案不是死背定义，而是能说出：

这是两种并发控制思想，实际会根据冲突强度、失败成本和一致性要求混合选型。

3. 🗺️ 回答思路

3.1 面试时的答题框架

  1. 先定义：悲观锁先加锁再操作，乐观锁先操作、提交时校验
  2. 再对比核心差异：冲突假设、是否阻塞、失败处理方式
  3. 举 Java 里的例子：synchronized / Lock vs CAS / 原子类
  4. 再举数据库里的例子：for update vs 版本号字段
  5. 最后讲选型原则：冲突高用悲观，冲突低且读多写少用乐观

3.2 面试加分点

  • 能说明乐观锁常见实现是 CAS 和版本号
  • 能指出悲观锁常见实现是互斥锁和数据库行锁
  • 能说出“高并发不等于高冲突”
  • 能提到 ABA 问题和重试成本
  • 能说明这两者是思想，不只是两个 API 名词

3.3 常见误区

  • 误区 1：认为乐观锁一定性能更高
  • 冲突高时，大量重试会让它更差。
  • 误区 2：只会讲数据库，不会讲 Java CAS
  • 这样回答层次不够完整。
  • 误区 3：把乐观锁理解成“完全不加任何同步”
  • 它底层依然依赖原子操作和内存语义。
  • 误区 4：只讲优点，不讲失败后的补偿和重试逻辑
  • 这在工程上是不完整的。

3.4 可直接复述的收尾话术

你可以最后总结一句：

悲观锁和乐观锁是两种不同的并发控制思想，前者把冲突前置，先锁后操作；后者把冲突后置，更新时再校验。冲突高、强一致要求高的场景更适合悲观锁，读多写少、冲突低的场景更适合乐观锁。
