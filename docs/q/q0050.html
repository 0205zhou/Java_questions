什么情况下会产生死锁，如何解决？

联想记忆法

记忆口诀/联想

口诀：“你等我，我等你；资源不放手，大家都卡死。”

把死锁想成两辆车在窄桥上对向相遇：

  • 车 A 占着桥左半边，等车 B 后退。
  • 车 B 占着桥右半边，等车 A 后退。
  • 两边都不让，也没有外力介入，结果谁都过不去。

这就是死锁：多个线程彼此占有资源，同时等待对方释放资源，形成循环等待。

记忆原理

死锁最经典的记忆方式是“四个必要条件”。只要四个条件同时成立，就有可能死锁；只要破坏其中任何一个条件，死锁就无法成立。面试时先给定义，再背四条件，再讲解决方案，逻辑最完整。

关联知识

  • 与 synchronized、Lock、数据库行锁都可能相关。
  • 与线程状态 BLOCKED、WAITING、jstack 排查有关。
  • 与锁顺序、超时获取、资源分级策略密切相关。
  • 与数据库事务中的死锁检测和回滚也有关。

深度解答

第一层:核心概念

是什么

死锁（deadlock）是指两个或多个线程在执行过程中，因为争夺资源而互相等待，且都无法继续推进的状态。

经典例子：线程 A 持有锁 1，等待锁 2；线程 B 持有锁 2，等待锁 1。此时双方都不会主动释放已经占有的资源，于是永久僵持。

死锁通常需要四个必要条件同时成立：

条件 含义
互斥条件 资源一次只能被一个线程占有
请求并保持 线程持有一个资源时继续请求其他资源
不可剥夺 已获得的资源不能被强行抢走
循环等待 存在线程之间的环形等待链

第二层:底层原理

典型产生场景

private static final Object A = new Object();
private static final Object B = new Object();

public static void main(String[] args) {
    new Thread(() -> {
        synchronized (A) {
            sleep(100);
            synchronized (B) {
                System.out.println("t1 done");
            }
        }
    }, "t1").start();

    new Thread(() -> {
        synchronized (B) {
            sleep(100);
            synchronized (A) {
                System.out.println("t2 done");
            }
        }
    }, "t2").start();
}

这段代码中：

  • t1 先拿到 A，再等 B。
  • t2 先拿到 B，再等 A。
  • 两个线程都持有一个锁，并等待另一个锁，满足循环等待。

常见死锁场景

  1. 多把锁获取顺序不一致：最常见。例如一个地方先锁订单再锁库存，另一个地方先锁库存再锁订单。
  2. 嵌套锁过多：业务流程长，临界区里再调用其他加锁方法，锁层级失控。
  3. 数据库事务死锁：两个事务更新多行数据时顺序不同，数据库行锁相互等待。
  4. 线程池与资源组合死锁：线程池线程数太小，任务互相等待彼此提交的子任务完成。
  5. 锁和外部调用混用：持锁时做 RPC、IO、回调，导致锁持有时间过长，放大死锁概率。

如何判断是死锁

  • Java 进程中可以用 jstack 看线程堆栈，JVM 会直接提示 Found one Java-level deadlock。
  • 线程通常表现为长时间 BLOCKED 或 WAITING，业务无响应但 CPU 不高。
  • 数据库会在日志或错误信息中提示 deadlock，并通常回滚其中一个事务。

第三层:实践应用

预防方案

1. 统一加锁顺序

这是最常见、最有效的办法。所有线程都按照统一顺序获取资源，例如总是先锁小 ID，再锁大 ID。

public void transfer(Account from, Account to, int amount) {
    Account first = from.getId() < to.getId() ? from : to;
    Account second = from.getId() < to.getId() ? to : from;

    synchronized (first) {
        synchronized (second) {
            doTransfer(from, to, amount);
        }
    }
}

2. 使用可超时锁

Lock lock1 = new ReentrantLock();
Lock lock2 = new ReentrantLock();

if (lock1.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lock2.tryLock(1, TimeUnit.SECONDS)) {
            try {
                // 业务逻辑
            } finally {
                lock2.unlock();
            }
        }
    } finally {
        lock1.unlock();
    }
}

tryLock(timeout) 不能彻底消灭死锁根因，但能避免线程无限等待，给降级和重试留下空间。

3. 缩小锁范围，避免持锁做慢操作

不要在持锁状态下做网络请求、文件 IO、复杂查询、回调第三方代码。

4. 资源分级和单向依赖

对锁资源做层级设计，例如先全局锁，再局部锁；或者高层只能调用低层，避免环路。

5. 数据库层面统一访问顺序

更新多行、多表时保持一致顺序，并缩短事务时间，必要时增加合适索引减少锁范围。

第四层:深入思考

死锁和活锁有什么区别？ 死锁是大家都不动；活锁是大家都在动，但一直互相谦让，结果谁也完成不了任务。死锁通常线程挂住，活锁通常线程忙但无进展。

所有死锁都能靠检测后恢复吗？ 不一定。JVM 只能检测一部分 Java 层面的锁依赖；业务层面最稳妥的方式还是在设计时预防。数据库会主动回滚一个事务，但 Java 应用里的业务状态补偿仍然要自己处理。

为什么统一加锁顺序这么有效？ 因为它直接破坏了“四条件”中的循环等待。大家都按同一顺序拿资源，就不会形成闭环。

回答思路

答题逻辑框架

  1. 先定义死锁：互相持有资源并等待对方释放。
  2. 说出四个必要条件。
  3. 给出经典双锁代码示例。
  4. 说明常见产生场景：锁顺序不一致、数据库事务、线程池等待等。
  5. 最后给出预防和排查方案：统一顺序、超时锁、缩小临界区、jstack 排查。

重点得分点

  • 四个必要条件完整。
  • 能举出经典双锁死锁代码。
  • 说明统一加锁顺序是最核心的预防手段。
  • 能说出 tryLock(timeout) 和 jstack 排查。

常见误区

  • 认为只有 synchronized 才会死锁，实际上数据库锁、Lock、分布式锁都可能出现。
  • 只会说“线程卡住了”，说不出四个必要条件。
  • 误把长时间阻塞都当死锁，有些只是普通锁竞争或慢调用。
  • 只讲检测，不讲设计上的预防。

过渡话术

  • “死锁本质是多个线程抢资源，那资源隔离技术里还有一个高频考点是 ThreadLocal。”
  • “既然要避免共享冲突，就可以继续聊乐观锁和悲观锁的思想差异。”
