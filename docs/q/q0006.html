MySQL的字符串类型都有哪些?

基础 数据类型

MySQL的字符串类型都有哪些?

联想记忆法

记忆口诀/联想

口诀："char 定长，var 变长，text 大文档，blob 二进制；enum 单选，set 多选，charset 定规则"

或者记成四字诀："定变二进，大文多选"：

  • 定 = CHAR 定长，空间固定，访问快
  • 变 = VARCHAR 变长，按实际长度存储，省空间
  • 二进 = BINARY / VARBINARY / BLOB 家族，二进制字符串，不做字符集转换
  • 大文 = TEXT 家族（TINYTEXT / TEXT / MEDIUMTEXT / LONGTEXT），承载大文档
  • 多选 = ENUM 单选枚举、SET 多选集合

记忆原理

这个口诀按"容量从小到大 + 用途分类"组织，把十多个类型压缩成五个关键词。面试时只要背住"定、变、二进、大文、多选"，就能按类别逐个展开：先讲 CHAR 与 VARCHAR 这对最常用的取舍，再讲 TEXT 与 BLOB 这对"大对象"，最后补 ENUM / SET 这两个"语义化"类型。分类记忆符合认知心理学的组块化（chunking），比逐个背类型名效率高得多，也不容易漏点。

关联知识

  • 与行大小限制关联：65535 字节是 MySQL 一行的硬上限，直接推导出"utf8mb4 下 VARCHAR 单列最长约 16383 字符"——这是常考的计算题
  • 与字符集关联：字符串类型的"长度"单位是字符，一个字符占几个字节由字符集（charset）决定，utf8mb4 一个字符最多 4 字节——连带考到 emoji 与排序规则（collation）
  • 与索引关联：InnoDB 索引键长度上限约 3072 字节，长字符串直接建索引会失败，引出前缀索引（prefix index）
  • 与存储引擎关联：InnoDB 把大 TEXT / BLOB 内容存到行外（off-page），行内只保留前缀——关联"页（Page）与聚簇索引"知识
  • 与查询执行计划关联：TEXT 不能设默认值、排序比较可能走临时表（filesort），关联执行计划优化知识

深度解答

第一层：核心概念

是什么：MySQL 字符串类型全景

MySQL 的字符串类型可以归为四大类，加上两个特殊类型：

类别 类型 容量 特点
定长字符串 CHAR(M) 0~255 字符 定长，不足用空格填充，检索时去掉
变长字符串 VARCHAR(M) 最多 65535 字节（含 1~2 字节长度前缀） 只存实际长度，省空间
文本家族 TINYTEXT / TEXT / MEDIUMTEXT / LONGTEXT 255B / 64KB / 16MB / 4GB 大文档，按字节计数
二进制字符串 BINARY / VARBINARY / BLOB 家族 同 CHAR / VARCHAR / TEXT 上限 原样存储，不做字符集转换
枚举 ENUM 最多 65535 个成员 单选，内部存索引号
集合 SET 最多 64 个成员 多选，位图存储

关键的区分维度有两个：长度可变不可变（CHAR vs VARCHAR）、是否按字符集解释（TEXT vs BLOB）。

解决的问题

不同字符串类型解决不同场景的存储诉求：定长字段追求稳定与速度，变长字段追求空间利用率，大文本字段承载文档级内容，二进制字段承载图片、文件等原始字节流，枚举/集合在数据库层表达业务语义。

第二层：底层原理

CHAR 与 VARCHAR 的存储差异

CHAR(10) 存 "ab"：   'a''b''''''''''''    ← 固定占 10 个字符，尾部补空格，检索时去掉
VARCHAR(10) 存 "ab"：[0x02]'a''b'         ← 1 字节长度前缀 + 实际内容

65535 字节 = MySQL 行大小上限（所有列合计）
VARCHAR 长度前缀：列内容 ≤255 字节用 1 字节，>255 字节用 2 字节
  • CHAR 的代价：若字段实际长度经常不满，CHAR 会白白占空间；但定长让存储位置可精确预估，访问更快（无需解析长度前缀、无需处理碎片）
  • VARCHAR 的代价：变长更新时可能"原地放不下"，触发页分裂（page split）等额外 IO；多一次长度前缀解析；按最大长度分配内存的机制也可能浪费内存（如临时表）

TEXT 与 VARCHAR 的边界：65535 字节怎么算

65535 字节是 MySQL 行大小的硬上限（所有列合计），VARCHAR 的最大长度正是由这个限制推导出来的：

  • 单列 VARCHAR 极限：65535 - 2（长度前缀）≈ 65533 字节
  • utf8mb4 下每个字符最多 4 字节 → 单列最多约 65533 / 4 ≈ 16383 字符，这就是网上 VARCHAR(16383) 这个数字的由来
  • 而 VARCHAR(65535) 在 utf8mb4 下建表会直接报错 Column length too big，因为 65535 是字节数不是字符数

TEXT 与 VARCHAR 的实质区别：

  • TEXT 不能设置默认值（DEFAULT），VARCHAR 可以
  • TEXT 在 ORDER BY / GROUP BY 时可能走文件排序（filesort）并在临时表上操作，代价高
  • InnoDB 中较大的 TEXT / BLOB 内容存在行外（off-page），行内只保留部分前缀（旧格式约 768 字节），读取大字段是额外随机 IO

字符集与排序规则

  • 字符集（charset）：字符与字节的映射表。utf8mb4 兼容旧的 utf8（即 utf8mb3）并扩展了 4 字节字符（emoji、生僻字）
  • 排序规则（collation）：定义字符如何比较与排序。如 utf8mb4_general_ci（通用、不区分大小写，ci = case insensitive）与 utf8mb4_0900_ai_ci（MySQL 8.0 默认，基于 Unicode 9.0，ai = accent insensitive，即不区分重音）
  • 排序规则的实际影响：大小写敏感与否（影响唯一索引去重）、排序结果顺序、字符集/排序规则不一致可能导致隐式转换而使索引失效

索引键长度限制：为什么长字符串要前缀索引

InnoDB 单个索引键最大约 3072 字节（默认 innodb_large_prefix 下）。utf8mb4 下 VARCHAR(255) 最大可能占 255 × 4 = 1020 字节，单列没问题；但 VARCHAR(1000) 就是 4000 字节，直接建索引会报 Specified key was too long，此时只能建前缀索引：

CREATE INDEX idx_title ON article (title(100));   -- 只对前 100 字符建索引

前缀索引的代价：索引中只有前缀，无法覆盖"完整字符串精确匹配"的索引命中和后缀查询，且要评估区分度（选择性），区分度低的前缀建了也白建。

第三层：实践应用

建表示例：各类字符串的典型用法

CREATE TABLE t_user (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    phone CHAR(11) NOT NULL,                -- 手机号定长 11 位 → CHAR
    nickname VARCHAR(50) NOT NULL,          -- 昵称长短不一 → VARCHAR
    status ENUM('normal','disabled','banned') NOT NULL DEFAULT 'normal', -- 状态单选
    roles SET('admin','editor','viewer') NOT NULL DEFAULT 'viewer',      -- 角色多选
    avatar_url VARCHAR(255) NULL,           -- URL 一般 VARCHAR(255)
    bio TEXT NULL,                          -- 简介可长可短 → TEXT
    UNIQUE KEY uk_phone (phone)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

选择建议

场景 推荐 理由
手机号、身份证号、状态码 CHAR 定长、访问快、语义固定
用户名、地址、URL VARCHAR 长度不定，省空间
文章正文、长日志 TEXT / MEDIUMTEXT / LONGTEXT 大文档
图片、文件二进制 BLOB 原样字节流，不做字符转换
状态枚举 ENUM 语义清晰、存储小（内部索引号）
多标签、多角色 SET 一个字段表达多选
密码哈希 CHAR(60) bcrypt 固定 60 字符，定长合适

为什么到处是 VARCHAR(255)？

  • 255 字符 × 3 字节（utf8mb3） = 765 字节，正好小于旧版本 767 字节的索引键限制，保证一定建得上索引；utf8mb4 下 255×4=1020 字节也远低于当前 3072 字节限制
  • 历史习惯 + 工具默认值（旧版可视化工具逆向工程默认 VARCHAR(255)）流传至今
  • 现代实践：按业务上限精确预估（昵称 50、URL 255），不必一刀切 255

第四层：深入思考

1. 为什么推荐 utf8mb4 而不是 utf8（utf8mb3）？

  • utf8mb3 每个字符最多 3 字节，无法存储 emoji 和 4 字节生僻字，写入会乱码或报错
  • 移动端昵称、评论、国际化业务大量出现 emoji，utf8mb4 成为事实标准；MySQL 8.0 默认字符集就是 utf8mb4
  • 坑：老库用了 utf8mb3，新写入 emoji 报 Incorrect string value，需要 ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4；注意转换后字节上限收紧（3 字节变 4 字节），VARCHAR 列长度可能超限需先收缩

2. ENUM 的利弊

优点 缺点
语义清晰，数据库层约束取值 加/删成员要 ALTER TABLE，大表成本高
存储小（内部存 1~2 字节索引号） 排序按定义顺序而非字典序，容易踩坑
与 ORM 映射不友好（Java 枚举需自定义转换）
插入未定义值直接报错，业务变更要提前沟通

业界对 ENUM 有争议：不少团队改用 TINYINT + 注释或字典表，因为 ALTER 成本不可控。回答时给出"小表可用、大表慎用"的立场即可。

3. 面试官可能的追问方向

  • "CHAR 和 VARCHAR 哪个快？" → 同长度访问 CHAR 略快（定长可预计算位置），但省空间上 VARCHAR 胜，按场景取舍
  • "为什么 TEXT 不能设默认值？" → 默认值机制面向行内存储的定长/短列，TEXT 可变长且可能行外存储，不支持
  • "VARCHAR(255) 和 VARCHAR(1000) 都存 10 个字符有区别吗？" → 磁盘存储一样（都按实际长度），但内存/临时表可能按最大长度分配，定义越大越占内存，且影响索引键长度
  • "字符串比较走索引吗？" → 取决于排序规则是否一致、是否存在隐式转换（如字符串列与数字比较）

重点得分点（面试官考察意图）

  1. 分类框架清晰——能按"定长/变长/大文本/二进制 + 枚举/集合"组织，而不是逐个背名字
  2. 65535 字节计算——能推出"utf8mb4 下单列 VARCHAR 约 16383 字符"，这是硬核计算点，答出来明显加分
  3. CHAR vs VARCHAR 的取舍——从存储结构（长度前缀、空格填充）讲 WHY，而不是背结论
  4. 字符集/排序规则——能说出 utf8mb4 与 utf8mb4_general_ci / utf8mb4_0900_ai_ci 的区别
  5. 前缀索引——能解释"索引键 3072 字节限制 → 前缀索引"，联动索引知识

常见误区（扣分点）

错误说法 正确理解
"VARCHAR(65535) 可以建" 65535 是字节上限且含长度前缀，utf8mb4 下单列约 16383 字符，且所有列合计受行大小限制
"CHAR 存不满会报错" 不会，尾部补空格，检索时自动去掉
"TEXT 和 VARCHAR 没区别" TEXT 不能设默认值、内容可能行外存储、排序易走临时表
"BLOB 能存文本并正常比较" BLOB 是二进制，不按字符集解释，检索/比较按字节进行
"ENUM 可以随时加成员" 加成员要 ALTER TABLE，大表成本高

过渡话术建议

  • 从分类到原理："类型很多，但核心就两组取舍：CHAR 对 VARCHAR 是定长对变长，这是最常用的；TEXT 家族处理大文档。说到长度，有个 65535 字节的行大小限制很关键……"
  • 从原理到实践："基于这些约束，我的选型习惯是：手机号状态码用 CHAR，用户名地址用 VARCHAR，文章正文用 TEXT，文件用 BLOB……"
  • 引向深入："顺便说一个常见的疑惑——为什么到处是 VARCHAR(255)？这其实和旧版索引键 767 字节的限制有关，255×3 字节正好卡在线内，成了历史习惯……"

时间分配建议

  • 回答控制在 2-3 分钟：分类总览 30 秒，原理（65535 计算 + 存储差异）60-90 秒，选型 30 秒，深入 30 秒
  • 面试官催进度时：优先保住"分类框架 + 65535 计算"两段，选型和 ENUM 可作为加分项略讲
