如何设计数据库表？

如何设计数据库表？

联想记忆法

记忆口诀/联想

口诀：先定业务，再定实体；主键外键约束，类型长度要合适；读写查询反推索引。

设计数据库表可以联想成“建一座仓库”：先确定要存什么货（业务实体），再规划货架和编号（表、主键），明确货物之间的关联（外键或关联关系），最后根据取货路线设计索引，并用约束保证入库数据可靠。

记忆原理

用“业务 → 结构 → 约束 → 性能 → 演进”的顺序组织答案，可以避免一上来只背字段类型。表设计不是孤立地画 ER 图，而是在数据正确性、查询性能、存储成本和未来变化之间做平衡。

关联知识

  • 范式、反范式、领域建模和 ER 图。
  • 主键、唯一索引、外键、非空和检查约束。
  • 事务、并发控制、分库分表、读写分离和数据归档。

深度解答

第一层：核心概念

数据库表设计是把业务中的实体、属性、关系和约束转换成可持久化的数据模型。好的设计至少要同时满足四点：

  1. 数据正确：不能出现重复、非法或无法关联的数据。
  2. 查询可用：高频查询有合理的数据组织和索引。
  3. 写入可维护：字段类型适当，更新成本可控。
  4. 能够演进：业务变化时不需要频繁破坏历史数据。

设计时不能只问“字段有哪些”，还要问：一条记录的身份是什么？哪些字段必须存在？哪些值必须唯一？实体之间是一对一、一对多还是多对多？核心查询、写入量和数据生命周期是什么？

第二层：底层原理

1. 从业务实体和边界开始

先识别核心实体和生命周期，例如电商系统可能有用户、商品、订单、订单明细、支付记录。不要把所有信息塞进一张大表，也不要为了形式上的拆分把一个紧密事务拆得过碎。

可以先画关系：

用户 1 ─── N 订单 1 ─── N 订单明细 N ─── 1 商品
订单 1 ─── N 支付记录

多对多关系通常通过中间表拆开，例如用户和角色之间使用 user_role(user_id, role_id)。

2. 主键设计

每张核心业务表都应有稳定、短小、非空、唯一的主键。InnoDB 中主键同时决定聚簇索引的数据组织方式，因此常优先考虑自增 BIGINT 或趋势递增的分布式 ID。

主键尽量使用代理键，不要直接把手机号、邮箱等可能变化的业务字段作为主键。业务唯一性使用唯一索引表达：

id BIGINT NOT NULL PRIMARY KEY,
UNIQUE KEY uk_user_email (email)

3. 字段类型和空值

字段类型要表达真实业务边界：

  • 金额使用 DECIMAL，不要使用浮点类型。
  • 时间根据业务选择 DATETIME 或 TIMESTAMP，并统一时区策略。
  • 状态使用受控的整数或短字符串，并在代码中维护枚举含义。
  • 字符集统一使用 utf8mb4，避免中文和表情存储问题。
  • 字符串长度按真实上限设置，避免无意义地使用超大类型。
  • NOT NULL 与默认值要表达业务语义，不能为了省事全部允许 NULL。

NULL 表示未知或不存在，不等价于 0、空字符串或“未设置”。如果业务需要区分“尚未处理”和“明确为空”，应使用状态字段或明确的建模方式。

4. 范式与反范式

规范化（normalization）通过拆分重复数据减少更新异常：

  • 第一范式：字段保持原子性。
  • 第二范式：非主键字段依赖完整主键。
  • 第三范式：非主键字段不依赖另一个非主键字段。

但高并发读场景可以合理反范式，例如订单表冗余下单时的商品名称和价格，保证历史快照正确并减少查询关联。反范式不是随意复制，而是明确接受冗余，并通过事务、事件或校验机制维护一致性。

5. 约束和索引

约束负责数据正确性，索引负责访问效率，不能用索引替代约束，也不能只依赖应用层校验：

CREATE TABLE orders (
    id BIGINT NOT NULL AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    order_no VARCHAR(32) NOT NULL,
    total_amount DECIMAL(18, 2) NOT NULL,
    status TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no),
    KEY idx_user_status_created (user_id, status, created_at)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

索引应围绕实际查询设计，联合索引注意最左前缀，避免重复和低选择性索引。每个索引都增加写入维护成本，必须通过慢查询和执行计划验证收益。

第三层：实践应用

1. 通用设计流程

需求和查询场景
    ↓
识别实体、属性、关系、生命周期
    ↓
确定主键、唯一性、非空和状态约束
    ↓
选择类型、字符集、时间和金额表示
    ↓
按高频查询设计索引
    ↓
用真实数据压测、EXPLAIN 验证
    ↓
制定扩展、归档、备份和迁移方案

2. 订单表的几个取舍

订单金额应保存下单时的价格快照，而不是每次展示时再去商品表取当前价格；否则商品改价后历史订单会被错误地“重算”。订单状态使用有限状态机约束流转，例如待支付不能直接跳到已完成。订单号可以作为业务唯一标识，但主键仍使用内部 ID，减少业务耦合。

3. 外键是否一定要用

外键能由数据库保证引用完整性，适合数据边界清晰、强一致要求高且规模可控的系统；在高并发微服务、跨库分片或需要独立部署的场景，物理外键可能增加变更和扩展成本，团队也可能选择应用层约束、异步校验和定期对账。无论是否使用物理外键，都不能放弃索引、幂等和数据校验。

4. 分页、冷热数据和审计

大表避免深分页 LIMIT 100000, 20，可使用基于主键或时间的游标分页。日志、订单、事件等持续增长的表要提前考虑按时间归档、分区或分表。重要数据保留 created_at、updated_at、操作者和来源等审计字段，必要时保存状态变更记录，而不是只保留当前状态。

第四层：深入思考

数据库设计的优先级

推荐按以下顺序决策：

  1. 先保证业务语义和数据正确。
  2. 再保证事务边界和并发下的一致性。
  3. 再根据高频查询添加索引。
  4. 数据量和吞吐达到瓶颈后，才考虑分库分表、读写分离或缓存。

过早分库分表会增加跨库查询、事务和运维复杂度；索引过多则会拖慢写入。设计不是追求“最复杂”，而是让当前规模下的系统可验证、可维护。

分布式场景下的表设计

如果未来可能分库分表，需要提前评估：

  • 主键是否能全局唯一且趋势递增。
  • 分片键是否能均匀分布，并覆盖主要查询条件。
  • 是否需要冗余租户 ID、用户 ID 等路由字段。
  • 跨分片统计、排序和事务如何处理。
  • 唯一约束在分片后如何实现。

常见反模式

  • 所有字段都用 VARCHAR，导致类型语义丢失和索引膨胀。
  • 用逗号拼接 ID，破坏原子性和索引能力。
  • 用 SELECT * 作为长期接口契约。
  • 把状态、金额、时间含义写进没有文档的魔法数字。
  • 只在 Java 代码里校验唯一性，不在数据库建唯一索引。
  • 把可变业务字段作为主键。
  • 忽略删除语义，导致“物理删除”破坏审计和关联数据。

面试官常见追问

  • 为什么金额不用 double：浮点表示存在精度误差，金额需要定点精确计算。
  • 为什么主键不建议 UUID 字符串：长度大、无序写入容易页分裂，且会放大二级索引。
  • 范式越高越好吗：不绝对，读性能和历史快照需求可能支持合理反范式。
  • 外键要不要建：取决于一致性边界、分库分表和运维策略，关键是确保引用完整性有可执行方案。

回答思路

答题逻辑框架

  1. 先说明目标：正确性、性能、可维护性和可演进性。
  2. 按实体关系、主键、字段类型、约束、范式、索引展开。
  3. 用订单表举例说明金额、状态、业务唯一键和审计字段。
  4. 再补充查询驱动、冷热数据、分页和分库分表。
  5. 最后强调设计要以真实业务和执行计划验证，不要迷信单一规则。

重点得分点

  • 能从业务实体和关系开始，而不是直接列字段。
  • 能说明主键、唯一索引和外键各自职责。
  • 能说出金额、时间、字符集和 NULL 的工程细节。
  • 能同时考虑范式、反范式、查询模式和数据生命周期。
  • 能讨论未来扩展但不过度设计。

常见误区

  • 认为表字段越少越好或范式越高越好。
  • 把所有业务唯一字段都当主键。
  • 只做应用层校验，不做数据库约束。
  • 只按“区分度最高”机械排列联合索引。
  • 在数据量还没达到瓶颈时直接分库分表。

过渡话术

“数据库表设计不能脱离业务和查询场景。我会先建模实体和关系，再确定主键、约束和类型，最后根据高频读写设计索引，并用真实执行计划验证。”

时间分配建议

  • 30 秒讲四个设计目标。
  • 90 秒讲实体、主键、字段、约束和索引。
  • 60 秒用订单表说明范式、反范式和扩展性。
  • 30 秒补充分库分表、审计和常见反模式。
