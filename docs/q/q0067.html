Redis的持久化机制？

Redis 持久化 RDB AOF

Redis的持久化机制？

联想记忆法

记忆口诀/联想

口诀：RDB 像拍照，AOF 像记账，混合持久化是“先放照片，再补流水账”。

可以这样记：

  • RDB：某一时刻给 Redis 全量拍一张快照
  • AOF：把每次写命令顺序记进操作日志
  • 混合持久化：先快速放出一张快照，再把快照之后的增量命令补上

记忆原理

“拍照”和“记账”是两个生活里非常直观的动作：拍照强调恢复快、体积小、但有时间差；记账强调记录细、数据更完整、但恢复慢。面试时顺着这个类比说，几乎所有后续追问都能自然展开。

关联知识

  • 会关联到 主从复制：从节点做全量同步时常结合 RDB
  • 会关联到 高可用：哨兵切主不等于持久化，持久化解决的是数据恢复
  • 会关联到 性能与安全权衡：越频繁刷盘，越安全，但性能越受影响
  • 会关联到 操作系统刷盘机制：AOF 的 everysec 本质就是性能和数据安全的折中

深度解答

1. 核心概念：Redis 是内存数据库，但不能只活在内存里

Redis 之所以快，很大程度上因为它把数据放在内存里。但如果只放内存，一旦进程退出、机器重启、实例崩溃，数据就会全部丢失。
所以 Redis 提供持久化能力，把内存中的数据以某种形式落到磁盘，达到两个目的：

  1. 故障恢复：服务重启后还能把数据恢复回来
  2. 数据备份：可以把持久化文件复制到别的机器

Redis 主要有两类持久化方式：RDB 和 AOF。

2. RDB：快照持久化

RDB（Redis Database Backup）可以理解成“定期全量快照”。
在某个时间点，Redis 会把当前内存中的所有数据序列化，写成一个 .rdb 文件。

触发方式

  • 手动执行：SAVE 或 BGSAVE
  • 自动触发：配置满足条件时触发，例如“多少秒内发生多少次写操作”

常见配置：

save 900 1
save 300 10
save 60 10000

意思是：

  • 900 秒内有 1 次修改就触发
  • 300 秒内有 10 次修改就触发
  • 60 秒内有 10000 次修改就触发

工作过程

生产环境中更常见的是 BGSAVE。它会通过 fork 子进程来生成快照，父进程继续处理客户端请求，避免长时间阻塞。

主进程处理请求
   -> fork 子进程
   -> 子进程把当前内存视图写入 RDB 文件
   -> 完成后替换旧快照

优点

  • 文件相对紧凑，适合备份和远程传输
  • 恢复速度快，重启时直接加载快照即可
  • 对线上读请求影响相对较小

缺点

  • 两次快照之间如果宕机，会丢失中间那段数据
  • fork 和大快照写盘仍然会带来 CPU、内存和 IO 压力

所以 RDB 的关键词是：恢复快，但不是最实时。

3. AOF：追加日志持久化

AOF（Append Only File）是另一种思路：不是存“某一刻的数据结果”，而是存“我执行过哪些写命令”。Redis 重启时只要把这些命令重新执行一遍，就能把数据恢复出来。

例如：

SET user:1 zhangsan
HSET user:1:profile age 20 city beijing
INCR article:100:view

这些写操作会按顺序追加到 AOF 文件中。

三种刷盘策略

appendonly yes
appendfsync always

或者：

appendonly yes
appendfsync everysec

或者：

appendonly yes
appendfsync no

三者区别如下：

  • always：每次写命令都刷盘，最安全，但性能开销最大
  • everysec：每秒刷盘一次，通常最多丢 1 秒数据，是最常见方案
  • no：由操作系统决定何时刷盘，性能高，但数据风险更大

优点

  • 数据安全性通常高于 RDB
  • 记录粒度更细，故障丢失窗口更小
  • 日志可读性比二进制快照更强，便于排查

缺点

  • 文件通常会比 RDB 更大
  • 恢复时要重放命令，速度通常慢于 RDB
  • 长期追加会膨胀，需要定期重写

4. AOF 重写：不是“复制旧日志”，而是“压缩成结果”

如果一直把历史写命令往后堆，AOF 文件会越来越大。
所以 Redis 提供 AOF Rewrite 机制，用当前内存里的最终结果生成一份更精简的新 AOF 文件。

比如原来有这样的命令：

INCR counter
INCR counter
INCR counter

重写后可能直接变成：

SET counter 3

这意味着 AOF 重写不是简单日志裁剪，而是基于当前状态重新构造最少必要命令。

5. 混合持久化：结合 RDB 和 AOF 的优点

从 Redis 4.0 开始，支持 AOF 混合持久化。
它的思路是：AOF 重写时，前半段使用 RDB 快照格式保存全量数据，后半段再追加最近的增量写命令。

启动恢复时：
先快速加载 RDB 快照
再重放快照之后的增量 AOF

这样做的好处是：

  • 恢复速度比纯 AOF 快
  • 数据完整性又比纯 RDB 更好

所以很多生产环境会把它当成比较均衡的选择。

6. 实践应用：生产上怎么选

方案一：只开 RDB

适合：

  • 对极少量数据丢失不敏感
  • 更关注备份与恢复速度
  • Redis 更偏缓存用途

方案二：只开 AOF

适合：

  • 更关注数据完整性
  • Redis 承载了较重要的业务状态

方案三：RDB + AOF 一起开

这是最常见的生产方案。
RDB 提供快速恢复和备份能力，AOF 降低数据丢失窗口，两者互补。

7. 深入思考：持久化从来不是“白送”的

1. 持久化一定会带来开销

无论是 RDB 快照、AOF 追加还是 AOF 重写，都会消耗：

  • CPU
  • 磁盘 IO
  • 内存

所以不能只开功能不做压测。特别是写入量高时，持久化参数会直接影响吞吐。

2. “缓存型 Redis”和“状态型 Redis”配置应该不同

如果 Redis 主要做热点缓存，即使丢一点数据也能从 DB 回填，那么可以把持久化策略设得轻一些。
但如果 Redis 里存了秒杀库存、订单状态、业务计数，那就要更谨慎，通常至少要开 AOF。

3. 持久化不等于高可用

很多人会把“持久化”和“哨兵/集群”混在一起。
其实：

  • 持久化：解决数据落盘与恢复问题
  • 哨兵/集群：解决节点故障切换与可用性问题

两者经常一起出现，但不是一回事。

回答思路

答题逻辑框架

建议按这个顺序说：

  1. Redis 是内存数据库，所以需要持久化防止重启丢数据
  2. RDB 是快照，AOF 是命令日志
  3. 对比两者的优缺点
  4. 最后补充混合持久化和生产选型

重点得分点

  • 能准确区分 RDB 是“数据快照”，AOF 是“写命令日志”
  • 能说出 AOF 的三种刷盘策略：always、everysec、no
  • 能说明 AOF Rewrite 的本质
  • 能补充 混合持久化，这是比较容易拉开层次的一点

常见误区

  • 误区 1：RDB 完全不会阻塞
    正解：BGSAVE 能降低阻塞，但 fork 和写盘仍有成本

  • 误区 2：AOF 一定绝对不丢数据
    正解：everysec 方案仍可能丢最近 1 秒左右数据

  • 误区 3：开了哨兵就不用持久化
    正解：哨兵解决高可用，持久化解决数据恢复

面试话术

“Redis 的持久化主要有两种：RDB 和 AOF。RDB 像定时拍快照，恢复快但可能丢失两次快照之间的数据；AOF 像记操作流水，数据更完整，但文件更大、恢复更慢。生产里通常会结合使用，或者使用混合持久化，在恢复速度和数据安全之间做平衡。”
