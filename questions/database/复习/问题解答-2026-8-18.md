## 1. Java 里在实际开发中怎么快速实现对象的深拷贝？浅拷贝与深拷贝区别是什么？

**面试话术：**
深拷贝和浅拷贝的核心区别在于，**浅拷贝只复制对象本身，引用类型字段仍然共用原来的对象；深拷贝不仅复制对象本身，也会把内部引用对象一并复制出来**。

在实际开发里，快速实现深拷贝常见有三种方式：

1. **手写拷贝构造函数或 copy 方法**
   - 这是最推荐的方式
   - 可控性强，性能也比较好
   - 适合核心业务对象

2. **通过序列化实现深拷贝**
   - 比如 JSON 序列化再反序列化
   - 开发快，但性能一般
   - 复杂对象、循环引用场景要谨慎

3. **重写 clone 方法并递归复制引用字段**
   - 理论上可行
   - 但 Java 原生 `clone()` 机制比较容易踩坑，实际项目里不算首选

**总结：**
如果是面试回答，我一般会说：**深拷贝推荐手写 copy 方法，浅拷贝通常只会复制第一层对象，内部引用对象还是共享的。**

## 2. TreeMap 和 LinkedHashMap 各自适合什么场景？它们的底层数据结构有什么区别？LinkedHashMap 有什么特性？

**面试话术：**
TreeMap 和 LinkedHashMap 的核心区别在于，**TreeMap 强调有序，LinkedHashMap 强调顺序保持**。

### 1）TreeMap
- 底层是 **红黑树**
- Key 会按自然顺序或者 Comparator 排序
- 查找、插入、删除时间复杂度一般是 `O(log n)`

**适用场景：**
- 需要按 Key 排序
- 需要范围查询，比如 `subMap()`、`headMap()`、`tailMap()`
- 比如排行榜、区间检索、时间有序数据

### 2）LinkedHashMap
- 底层是 **HashMap + 双向链表**
- HashMap 负责快速查找
- 双向链表负责维护顺序
- 平均查找效率是 `O(1)`

**适用场景：**
- 需要保持插入顺序
- 或者需要按访问顺序排序
- 比如缓存、稳定遍历输出

### 3）LinkedHashMap 的特性
1. **可以保持插入顺序**
2. **也可以保持访问顺序**，适合做 LRU
3. **遍历结果稳定**
4. 性能略低于 HashMap，因为要额外维护链表

**总结：**
如果要排序选 TreeMap，如果要保持顺序或者做缓存选 LinkedHashMap。

## 3. HashMap 存值有什么特点？如果向同一个 Key 先后 put “张三” 和 “李四”，输出结果是什么？

**面试话术：**
HashMap 的特点是：**Key 不能重复，Value 可以重复**。如果向同一个 Key 先后 `put("张三")` 和 `put("李四")`，那么后面的值会覆盖前面的值，最终取出来的是 **李四**。

另外补充一点，`put` 方法本身返回的是旧值，如果之前没有值就返回 `null`。

## 4. Java 中常见的数据结构有哪些？分别适用于什么场景？

**面试话术：**
Java 里常见的数据结构主要有以下几类：

1. **数组**：随机访问快，适合读多写少、长度相对固定场景
2. **链表**：插入删除方便，适合频繁增删
3. **栈**：后进先出，适合括号匹配、递归回溯
4. **队列**：先进先出，适合任务排队、消息处理
5. **双端队列**：两端都能操作，适合滑动窗口、单调队列
6. **哈希表**：查找快，适合 KV 映射、去重、计数
7. **树结构**：比如红黑树，适合有序存储、范围查询
8. **堆**：适合优先级队列、TopK 问题
9. **图**：适合表示复杂关系，比如路径搜索、依赖分析
10. **集合 Set**：适合去重和唯一性判断

**总结：**
面试回答时可以强调：**没有最好的数据结构，只有最适合场景的数据结构。**

## 5. synchronized 锁 Class 对象和锁具体实例对象有什么区别？分别适用于什么场景？

**面试话术：**
`synchronized` 锁 Class 对象和锁实例对象，本质区别是**锁的粒度不同**。

### 1）锁实例对象
- 比如 `synchronized(this)` 或普通同步方法
- 锁的是当前对象实例
- 不同实例之间互不影响

**适用场景：**
- 保护对象内部成员变量
- 每个对象维护自己的状态

### 2）锁 Class 对象
- 比如 `synchronized(MyClass.class)` 或静态同步方法
- 锁的是类对象
- 所有实例共享同一把锁

**适用场景：**
- 保护静态变量
- 控制整个类级别的共享资源

**总结：**
实例锁是对象级别，Class 锁是类级别。**实例锁并发度更高，Class 锁控制范围更大。**

## 6. 什么是可重入锁？synchronized 是否属于可重入锁？为什么？

**面试话术：**
可重入锁指的是：**同一个线程在已经拿到某把锁之后，再次请求这把锁时不会被阻塞，而是可以继续进入。**

`synchronized` 是可重入锁。因为 JVM 在实现 `synchronized` 时，会记录：
- 当前锁的持有线程是谁
- 当前线程重入了几次

同一个线程再次进入同步代码时，重入次数加 1；退出时减 1；只有计数归零时，锁才真正释放。

**总结：**
`synchronized` 属于可重入锁，这样做的好处是**避免同一个线程调用链上的同步方法互相把自己锁死。**

## 7. 如果 CAS 失败率很高怎么解决？

**面试话术：**
CAS 失败率很高，说明竞争非常激烈，这时候要做的不是一味重试，而是**减少冲突、降低自旋、必要时改用锁**。

常见优化方式：

1. **分散热点**
   - 比如用 `LongAdder` 代替单点原子变量
   - 把一个热点拆成多个槽位，降低竞争

2. **限制自旋次数**
   - CAS 失败后不要无限重试
   - 可以失败一定次数后退化为锁

3. **改成分段锁或互斥锁**
   - 冲突特别大时，CAS 不一定比锁性能好

4. **批量更新**
   - 先本地累计，再合并提交
   - 减少对同一共享变量的频繁修改

**总结：**
CAS 适合低冲突场景；如果失败率高，核心思路就是**分散热点、减少重试、必要时换锁。**

## 8. 讲一下数据库的锁。

**面试话术：**
数据库锁本质上是为了保证**并发情况下数据的一致性和隔离性**。

### 1）按粒度分
- **表锁**：锁整张表，粒度大，并发低
- **行锁**：锁某一行，粒度小，并发高
- **页锁**：介于表锁和行锁之间

### 2）按功能分
- **共享锁（S 锁）**：允许读，不允许写
- **排他锁（X 锁）**：独占，其他事务不能读写

### 3）InnoDB 常见锁
- **记录锁**：锁索引记录本身
- **间隙锁**：锁记录之间的空隙
- **临键锁**：记录锁 + 间隙锁，主要用于防止幻读

**总结：**
数据库锁的核心是：**牺牲一部分并发，换取事务隔离和数据一致性。**

## 9. 间隙锁有什么弊端？

**面试话术：**
间隙锁最大的弊端是：**会扩大锁的范围，降低并发，特别容易阻塞插入操作。**

具体来说：
1. 锁住的是区间，不是单条记录
2. 其他事务无法在这个间隙里插入新数据
3. 容易让本来不冲突的事务也互相等待
4. 并发高时还可能增加死锁概率

**总结：**
间隙锁的价值是防止幻读，但代价就是**并发性能下降，插入容易被卡住。**

## 10. MVCC 的 ReadView 是在 select 时生成的还是 update 时？

**面试话术：**
ReadView 一般是在**普通 `select` 做快照读时生成的**，不是在 `update` 时生成的。

原因是：
- 普通 `select` 属于**一致性读 / 快照读**，需要通过 ReadView 判断哪个版本可见
- `update`、`delete`、`select ... for update` 属于**当前读**，它们读的是最新版本，并且会加锁

**总结：**
ReadView 主要服务于快照读，所以面试里可以直接说：**ReadView 是在 select 时生成和使用的，update 走的是当前读。**

## 11. MySQL 索引的底层实现原理是什么？为什么索引可以提升查询效率？

**面试话术：**
MySQL，尤其是 InnoDB，最常见的索引底层结构是 **B+ 树**。

### 1）底层原理
- 非叶子节点存索引键和指针
- 叶子节点存数据或者主键值
- 叶子节点之间通过链表连接，便于范围查询

### 2）为什么能提升效率
1. **减少磁盘 I/O**
   - 不用全表扫描，只需要访问少量索引页
2. **降低查找复杂度**
   - 从 `O(n)` 全表扫描变成近似 `O(log n)` 的树查找
3. **范围查询友好**
   - B+ 树天然有序，叶子节点又是链表

**总结：**
索引之所以快，本质上是因为它通过 B+ 树这种适合磁盘的数据结构，**把无序查找变成了有序快速定位。**

## 12. 有一个联合索引（类别 + 年份 + 姓名），查询“今年出版的科幻类张三书籍”时是否可以使用该索引？为什么？

**面试话术：**
可以使用，而且利用率比较高。因为联合索引 `(类别, 年份, 姓名)` 满足**最左前缀原则**，而这个查询正好是从左到右都命中了。

比如条件是：
- 类别 = 科幻类
- 年份 = 今年
- 姓名 = 张三

这三个字段都是等值匹配，MySQL 可以直接利用联合索引从前到后定位。

**补充：**
如果跳过中间列，比如只查“类别 + 姓名”，那后面的姓名列通常就不能被完整利用。

**总结：**
这条 SQL 可以命中联合索引，原因就是**满足最左前缀原则，并且字段顺序和索引顺序一致。**

## 13. 设计一个系统，统计全国 14 亿人的收入总和。系统在 1 月 1 日上午 8 点同时开放，大量用户提交自己的收入信息，应该如何设计系统架构保证高并发和数据准确性？

**面试话术：**
这个题本质上考的是：**如何在海量并发写入下保证系统可用性，同时保证统计结果准确。**

我会从四个方面设计：

### 1）接入层削峰限流
- 网关层做限流、排队、验证码、熔断
- 防止瞬时流量直接打爆应用层

### 2）业务层异步化
- 用户提交后先快速响应
- 请求写入消息队列
- 后台异步消费，完成落库和统计

### 3）存储层分库分表
- 按用户 ID 分库分表
- 提升写入能力，避免单库单表瓶颈

### 4）准确性保障
- 用 `userId + 批次号` 做唯一键，防止重复提交
- 消费端做幂等处理，防止 MQ 重复消费
- 明细表保存原始数据，汇总表做增量汇总
- 通过最终一致性保证总收入统计正确

**总结：**
整体思路就是：**限流削峰 + MQ 异步 + 分库分表 + 幂等去重 + 增量汇总**。

## 14. 手撕一个 Java 乐观锁版本号实现库存扣减。

**面试话术：**
乐观锁版本号的核心思想是：**先读库存和版本号，更新时校验版本号没变，没变才允许更新。**

### Java 示例

```java
class Stock {
    private int count;
    private int version;

    public synchronized boolean deduct(int num, int expectVersion) {
        if (this.version != expectVersion) {
            return false;
        }
        if (this.count < num) {
            return false;
        }
        this.count -= num;
        this.version++;
        return true;
    }

    public int getCount() {
        return count;
    }

    public int getVersion() {
        return version;
    }
}
```

### SQL 版本思路
实际项目中更常见的是：

```sql
update stock
set count = count - 1,
    version = version + 1
where id = ?
  and count > 0
  and version = ?;
```

如果影响行数是 1，说明扣减成功；如果是 0，说明版本冲突或库存不足。

**总结：**
乐观锁适合**读多写少、冲突没那么高**的场景，核心就在于 **version 校验**。

## 15. Java 如何实现 streaming response？

**面试话术：**
Java 里实现 streaming response，本质上就是：**服务端边生成数据边写给客户端，而不是等全部生成完一次性返回。**

### Spring MVC 写法
可以通过 `HttpServletResponse`：

```java
@GetMapping("/stream")
public void stream(HttpServletResponse response) throws Exception {
    response.setContentType("text/plain;charset=UTF-8");
    ServletOutputStream out = response.getOutputStream();
    for (int i = 0; i < 5; i++) {
        out.write(("chunk-" + i + "\n").getBytes(StandardCharsets.UTF_8));
        out.flush();
        Thread.sleep(1000);
    }
}
```

### 核心点
- 分块写出
- 每次写完后 `flush()`
- 客户端可以边接收边处理

**总结：**
streaming response 的核心就是**分块返回、及时刷新、降低首包等待时间。**

## 16. 如何实现 SSE 推送？

**面试话术：**
SSE，也就是 Server-Sent Events，本质上是**服务端通过一个长连接持续向客户端单向推送消息**。

### Spring MVC 示例

```java
@GetMapping("/sse")
public SseEmitter sse() {
    SseEmitter emitter = new SseEmitter(0L);
    new Thread(() -> {
        try {
            for (int i = 0; i < 5; i++) {
                emitter.send(SseEmitter.event().name("message").data("hello-" + i));
                Thread.sleep(1000);
            }
            emitter.complete();
        } catch (Exception e) {
            emitter.completeWithError(e);
        }
    }).start();
    return emitter;
}
```

### 前端接收
```javascript
const source = new EventSource('/sse');
source.onmessage = (event) => console.log(event.data);
```

**总结：**
SSE 的核心是：**服务端不断写事件流，客户端通过 EventSource 持续监听。**

## 17. SSE、WebSocket、流式响应的区别是什么？

**面试话术：**
这三者都能实现“边传边收”或实时效果，但侧重点不同。

### 1）SSE
- 基于 HTTP
- 单向：服务端推客户端
- 浏览器原生支持好
- 适合消息通知、进度推送

### 2）WebSocket
- 全双工通信
- 客户端和服务端都可以主动发消息
- 更适合聊天、游戏、协同编辑

### 3）流式响应
- 更强调“分块返回结果”
- 不一定是长连接常驻推送
- 常用于大模型输出、日志流、文件流

**总结：**
如果是单向推送，优先考虑 SSE；如果是双向实时通信，选 WebSocket；如果只是把一次响应改成边生成边返回，就是流式响应。

## 20. 补充复习点：深拷贝、synchronized / ReentrantLock / volatile、CAS / ABA

### 1）深拷贝与浅拷贝
- 浅拷贝只复制对象本身，引用对象共享
- 深拷贝会连引用对象一起复制

### 2）synchronized、ReentrantLock、volatile 区别
- `synchronized`：JVM 层面的互斥锁，使用简单，可重入
- `ReentrantLock`：JDK 显式锁，更灵活，支持可中断、公平锁、条件队列
- `volatile`：只保证可见性和有序性，不保证原子性

### 3）CAS、ABA、适用场景
- CAS 是无锁并发的核心机制，适合低冲突场景
- ABA 问题是值从 A 改成 B 又改回 A，CAS 可能察觉不到
- 解决方案通常是加版本号，比如 `AtomicStampedReference`

**总结：**
这一组知识点在面试里经常会连着问，建议从**可见性、原子性、加锁粒度、适用场景**几个维度统一回答。
