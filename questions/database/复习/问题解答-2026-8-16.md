## 1. SaaS 多租户数据怎么隔离？

### 联想记忆法

#### 记忆口诀/联想

**口诀：共享表最省，独立库最稳，按客户分层隔离。**

- 共享表：所有租户共用一张表，靠 `tenant_id` 区分
- 独立 Schema / 独立表：隔离更强，但运维更复杂
- 独立库 / 独立实例：隔离最强，成本最高

#### 记忆原理

这题本质是在考多租户架构的隔离层级。按“共享程度从高到低、隔离能力从弱到强”去记，顺序就很清楚：**共享表 -> 独立表/Schema -> 独立库**。

#### 关联知识

- 与 `tenant_id` 兜底策略关联
- 与权限模型、数据安全、合规要求关联
- 与分库分表、大客户单独部署关联

---

### 深度解答

#### 核心概念

SaaS 多租户数据隔离，核心目标是：**不同租户共享一套系统，但数据绝不能互相串读串写**。常见方案有三类。

#### 方案一：共享数据库、共享表

所有租户的数据都落在同一张表中，通过 `tenant_id` 区分。

优点：
- 成本最低
- 运维简单
- 适合中小 SaaS

缺点：
- 最怕业务 SQL 漏带 `tenant_id`
- 大租户可能拖累小租户
- 安全隔离最弱

适用场景：
- 租户量大，但单租户数据量不大
- 更关注成本和快速扩张

#### 方案二：共享数据库、独立 Schema 或独立表

不同租户在同一个数据库实例内，但逻辑上拆成不同 Schema 或不同表。

优点：
- 隔离性比共享表好
- 数据迁移、备份更方便
- 可以针对部分租户做定制化运维

缺点：
- 租户多了以后表数量会爆炸
- DDL 和变更管理复杂
- 运维成本明显提高

#### 方案三：独立数据库 / 独立实例

每个租户一套独立数据库，核心大客户甚至独享数据库实例。

优点：
- 隔离性最强
- 安全和合规最好做
- 性能边界清晰

缺点：
- 成本最高
- 运维复杂度最高
- 资源利用率可能不均衡

#### 实践应用

真实项目里常常不是一刀切，而是**分层隔离策略**：

- 小客户共享表
- 中客户独立 Schema
- 大客户独立库

这样能兼顾成本、性能和安全。

#### 深入思考

面试里加分点是说明：

> 多租户隔离不是只有技术方案，还要结合客户等级、数据规模、合规要求和运维成本做分层设计。

---

### 回答思路

答题时先给结论：多租户隔离一般分共享表、独立 Schema、独立库三层。然后分别讲隔离性、成本和适用场景，最后补一句生产上常用“按客户等级分层隔离”。

## 2. SQL 漏带 tenant_id 怎么兜底？

### 联想记忆法

#### 记忆口诀/联想

**口诀：代码自动带，数据库再兜底，审计测试防漏网。**

#### 记忆原理

这题不是问“规范”，而是问“防线”。所以记成三层防线最好：**应用层注入、数据库层约束、测试审计补漏**。

#### 关联知识

- 与多租户数据隔离关联
- 与 ORM 拦截器、RLS、SQL 审计关联
- 与集成测试、越权测试关联

---

### 深度解答

#### 核心概念

`tenant_id` 是共享表多租户的核心隔离条件。如果 SQL 漏带租户条件，就可能造成越权读写，这是严重的数据安全问题。

#### 第一层：应用层自动注入

常见做法：
- MyBatis 拦截器自动拼接 `tenant_id`
- Hibernate Filter / JPA Specification 自动带租户条件
- DAO 层封装统一查询入口

优点：
- 对业务代码侵入小
- 大部分场景可统一治理

风险：
- 原生 SQL、复杂子查询、手写 join 可能绕过

#### 第二层：数据库层兜底

如果数据库支持 **RLS（Row Level Security）**，可以在数据库层直接限制只能访问当前租户数据。

优点：
- 就算开发漏写 SQL，也查不到其他租户数据
- 这是最硬的一层防线

如果是 MySQL，原生 RLS 能力不如 PostgreSQL 强，常常需要借助中间层或权限设计来补。

#### 第三层：权限和账号隔离

可以让不同租户或不同业务角色使用不同数据库账号，限制访问范围。虽然灵活性不如 RLS，但也能提供一定约束。

#### 第四层：测试与审计

- SQL 审计日志扫描是否存在未带租户条件的查询
- 编写跨租户穿透测试
- 对重点 Mapper、原生 SQL 做静态扫描

#### 实践应用

最稳的方案是：

> 应用层自动注入 + 数据库层强约束 + 测试审计兜底

只靠“开发别忘了写 tenant_id”是不够的。

#### 深入思考

面试里要体现安全意识：

> 多租户问题本质上不是一个 SQL 写法问题，而是数据越权风险问题，所以必须做多层防线。

---

### 回答思路

先说不能只靠开发规范，然后按“应用层、数据库层、测试层”三段讲。结尾落一句：`tenant_id` 必须做成系统能力，不该依赖人工记忆。

## 3. 权限修改后缓存怎么失效？

### 联想记忆法

#### 记忆口诀/联想

**口诀：改权限，删缓存；多节点，要广播；要稳妥，加版本。**

#### 记忆原理

权限缓存失效的核心问题就两个：**什么时候失效、怎么通知所有节点失效**。围绕这两个点去答最稳。

#### 关联知识

- 与 Redis 缓存一致性关联
- 与 JWT、RBAC、角色权限关联
- 与本地缓存 + Redis 二级缓存关联

---

### 深度解答

#### 核心概念

权限修改后，如果缓存不及时失效，用户可能看到旧菜单、旧按钮，甚至继续保留旧权限，这是典型的一致性问题。

#### 方案一：主动删除缓存

权限变更后，直接删相关缓存 key，例如：
- `user_permission:{userId}`
- `role_permission:{roleId}`

优点：
- 生效快
- 实现简单

缺点：
- 如果角色绑定用户很多，删除关联用户缓存成本高

#### 方案二：版本号机制

给用户或租户维护一个 `permission_version`。

请求时：
- 版本一致，缓存继续用
- 版本不一致，重新加载权限并刷新缓存

优点：
- 不用精确删除所有 key
- 分布式场景稳定性更好

缺点：
- 每次鉴权多一次版本校验

#### 方案三：消息广播失效

如果是多节点部署，权限修改后发 MQ 或 Redis Pub/Sub 通知各节点清本地缓存。

适合：
- 本地 Caffeine + Redis 二级缓存
- 多服务实例环境

#### 方案四：TTL 兜底

权限缓存设置较短过期时间，比如 5 分钟。

优点：
- 实现简单

缺点：
- 不适合作为唯一方案
- 无法做到权限实时生效

#### 特别注意：JWT 权限快照

如果权限已经写进 JWT，就要考虑：
- 缩短 token 生命周期
- 校验权限版本号
- 或引入黑名单/二次校验

#### 实践应用

最常见组合是：

> 主动删除 + 版本号 + 广播通知

这样单机和分布式都能覆盖。

---

### 回答思路

先说权限缓存失效的本质是一致性问题，再讲删除缓存、版本号、广播通知三种常见方案，最后补充 JWT 场景下还要让旧 token 失效。

## 4. 百万客户数据怎么导出？

### 联想记忆法

#### 记忆口诀/联想

**口诀：导出不直等，查询要分批，写文件用流式，结果走对象存储。**

#### 记忆原理

大数据量导出的关键就是四件事：**异步、分批、流式、限流**。把这四步记住，这题基本不会乱。

#### 关联知识

- 与分页查询、游标查询关联
- 与对象存储、任务中心关联
- 与内存溢出、数据库压测、限流关联

---

### 深度解答

#### 核心概念

百万级导出不能走普通同步接口，否则会出现：
- HTTP 超时
- 应用内存爆掉
- 数据库压力飙升
- 用户体验差

#### 第一步：异步任务化

用户点导出后：
- 创建导出任务
- 返回任务 ID
- 后台慢慢生成文件
- 用户在任务中心查看进度并下载

这样能避免长时间阻塞请求线程。

#### 第二步：分批查询

不要一次性 `select *` 查百万数据。

更合适的方式：
- 主键递增分页：`where id > lastId limit 1000`
- 或数据库游标

尽量避免深分页：

```sql
limit 1000000, 1000
```

这种扫描成本很高。

#### 第三步：流式写文件

边查边写，不把所有数据放到内存。

- 大数据量优先 CSV
- 如果一定要 Excel，用流式写模式，比如 EasyExcel / SAX

#### 第四步：结果文件落盘或上传对象存储

生成完成后上传到：
- OSS / S3 / MinIO
- 或内部文件服务器

前端拿下载链接即可，不要再经过应用内存中转。

#### 第五步：限流和拆分

为了保护系统：
- 限制单次导出行数
- 限制并发导出任务数
- 超大文件按时间、地区、状态拆分
- 做敏感字段脱敏

#### 深入思考

这题面试官看的是你有没有工程意识。真正问题不是“怎么写文件”，而是：
- 怎么避免拖垮线上系统
- 怎么让用户感知进度
- 怎么保证数据安全

---

### 回答思路

先定调：百万级导出不能同步做。然后按“异步任务、分批查、流式写、对象存储、限流脱敏”五步回答，基本就是标准答案。

## 5. Spring AOP 自调用为何失效？

### 联想记忆法

#### 记忆口诀/联想

**口诀：AOP 靠代理，自己调自己，不走代理就失效。**

#### 记忆原理

这题核心只记一句话：**Spring AOP 基于代理，自调用走的是 `this.xxx()`，不会经过代理对象。**

#### 关联知识

- 与 `@Transactional` 失效关联
- 与 `@Cacheable`、`@Async`、自定义切面关联
- 与 JDK 动态代理、CGLIB 代理关联

---

### 深度解答

#### 核心概念

Spring AOP 的增强逻辑，依赖于代理对象拦截方法调用。外部调用时，会先到代理对象，再由代理决定是否织入事务、日志、缓存等逻辑。

#### 为什么自调用失效

例如：

```java
@Service
public class OrderService {
    public void create() {
        this.pay();
    }

    @Transactional
    public void pay() {
    }
}
```

`create()` 方法内部调用 `this.pay()`，本质是目标对象直接调用自身方法，没有经过 Spring 生成的代理对象，因此切面逻辑不会执行。

#### 受影响的注解

典型包括：
- `@Transactional`
- `@Cacheable`
- `@Async`
- 自定义 AOP 切面

#### 解决方案一：拆到另一个 Bean

最推荐的方案是把需要增强的方法拆到另一个 Service 中，通过 Spring 注入调用。

优点：
- 结构清晰
- 侵入性低
- 最符合 Spring 设计习惯

#### 解决方案二：通过代理对象调用自己

例如：

```java
((OrderService) AopContext.currentProxy()).pay();
```

或注入自身代理对象。

缺点：
- 侵入业务代码
- 可读性一般
- 需要开启 `exposeProxy=true`

#### 解决方案三：使用 AspectJ

AspectJ 通过字节码织入而不是运行时代理，自调用也能增强。

缺点：
- 配置和维护成本高
- 一般项目里用得少

---

### 回答思路

这题直接先说结论：Spring AOP 基于代理，自调用不经过代理，所以增强失效。然后举 `@Transactional` 例子，最后给出最推荐的解决方案：拆成另一个 Bean。

## 6. MySQL 覆盖索引是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：查的列都在索引里，省掉回表就是覆盖索引。**

#### 记忆原理

覆盖索引不是一种新索引类型，而是一种查询效果。只要查询所需字段都能从索引中拿到，就叫覆盖索引。

#### 关联知识

- 与回表关联
- 与联合索引、最左前缀原则关联
- 与 `EXPLAIN` 中的 `Using index` 关联

---

### 深度解答

#### 核心概念

覆盖索引指的是：

> 查询所需的列都可以直接从索引中取到，不需要再回到数据行里查询。

例如表：

```sql
user(id, name, age, city)
```

有联合索引：

```sql
idx_name_age(name, age)
```

如果执行：

```sql
select name, age from user where name = 'Tom';
```

因为 `name` 和 `age` 都在索引里，所以只查索引就够了。

#### 为什么更快

普通二级索引查询往往是两步：
- 先查二级索引拿主键
- 再根据主键回聚簇索引查整行

覆盖索引省掉了第二步回表，所以 IO 更少，性能更好。

#### 常见场景

- 高频列表查询
- 分页接口只查少量字段
- 条件查询 + 排序字段都可落在联合索引上

#### 注意点

1. 覆盖索引不是独立索引类型，是查询命中的一种效果。
2. 不是把所有字段都加进索引就一定好，索引太宽会影响写性能和内存。
3. 联合索引是否生效，还要满足最左前缀原则。

#### 深入思考

列表接口优化时，覆盖索引是很高频的手段，因为大量页面只展示有限字段，没有必要每次回表拿整行数据。

---

### 回答思路

一句话定义覆盖索引，再解释它为什么快，本质就是省掉回表。最后补充一句：覆盖索引不是索引类型，而是查询命中效果。

## 7. Redis 大 Key 怎么拆？

### 联想记忆法

#### 记忆口诀/联想

**口诀：大对象分段，大集合分桶，删用 UNLINK，冷热要分层。**

#### 记忆原理

这题最好按“是什么 -> 有什么问题 -> 怎么拆 -> 怎么治理”四段来记。

#### 关联知识

- 与热 Key、Redis 单线程、网络 IO 关联
- 与 `redis-cli --bigkeys`、`UNLINK` 关联
- 与缓存建模、冷热分层关联

---

### 深度解答

#### 核心概念

大 Key 指的是：
- 单个 String 很大，比如几 MB
- 或集合元素很多，比如几十万、上百万条

#### 大 Key 的问题

- 单次网络传输慢
- 删除容易阻塞
- 主从复制、迁移压力大
- 集群 rehash 和故障恢复成本高
- 更容易变成热 Key

#### 拆分方法一：按业务维度拆

例如一个用户订单集合：

```text
user:orders:1001
```

可以拆成：

```text
user:orders:1001:202608
user:orders:1001:202609
```

按时间、地区、状态等业务维度切分。

#### 拆分方法二：固定分片拆桶

比如超大的 Hash 或 Set，可以按用户 ID 尾号或 hash 路由到多个桶：

```text
post:like:1001:0
post:like:1001:1
...
post:like:1001:15
```

#### 拆分方法三：大 String 分段

超长 JSON、文本可以拆成多段：

```text
article:1:part1
article:1:part2
article:1:part3
```

不过如果走到这一步，通常也要反思数据建模是否合理。

#### 治理手段

- 定期扫描：`redis-cli --bigkeys`
- 删除时优先用 `UNLINK`
- 避免把大对象整体序列化后直接塞 Redis
- 冷数据落库，Redis 只放热点和索引
- 设置合理 TTL

#### 深入思考

这题面试里不要只说“拆”。更好的表达是：

> 大 Key 问题本质是单次操作成本过高，所以要从数据建模层面把一次大操作拆成多次小操作。

---

### 回答思路

先定义大 Key，再说它带来的网络、阻塞、迁移问题，最后讲按时间、业务维度、固定桶拆分，并补充 `bigkeys` 扫描和 `UNLINK` 治理。

---

## 8. 线程池满了怎么处理？

### 联想记忆法

#### 记忆口诀/联想

**口诀：线程满、队列满、最大线程也满，就走拒绝策略。先找原因，再做治理。**

#### 记忆原理

这题不是背四个拒绝策略就够了，真正得分点是：**为什么会满、默认怎么处理、线上怎么优化**。

#### 关联知识

- 与 `ThreadPoolExecutor` 参数关联
- 与限流、降级、反压关联
- 与任务堆积、锁竞争、下游阻塞关联

---

### 深度解答

#### 核心概念

线程池满了说明：
- 核心线程都忙
- 队列也满
- 已经扩到最大线程数
- 此时新任务只能走拒绝策略

#### 常见拒绝策略

1. `AbortPolicy`
   - 默认策略
   - 直接抛 `RejectedExecutionException`

2. `CallerRunsPolicy`
   - 提交任务的线程自己执行
   - 能形成反压，让上游慢下来

3. `DiscardPolicy`
   - 直接丢弃任务
   - 风险是业务无感知地丢数据

4. `DiscardOldestPolicy`
   - 丢弃队列里最老的任务，再尝试提交新任务

#### 为什么会满

常见原因：
- 任务执行太慢
- 下游数据库 / RPC 阻塞
- 锁竞争
- 参数设置不合理
- 瞬时流量洪峰
- 把 CPU 密集和 IO 密集任务混在一个池里

#### 线上处理思路

- 调整核心线程数、最大线程数、队列大小
- 业务隔离：不同任务不同线程池
- 大任务拆小任务
- 入口做限流削峰
- 加监控：活跃线程、队列长度、拒绝次数
- 根据业务选合适的拒绝策略

#### 深入思考

面试里加分表达：

> 线程池满不是一个“换个拒绝策略”就结束的问题，它往往是在暴露系统吞吐、下游依赖或线程池设计上的瓶颈。

---

### 回答思路

先解释线程池满意味着什么，再讲四种拒绝策略，最后重点落到线上分析原因和治理思路上，这样比只背 API 更像实战回答。

---

## 9. MySQL 有一张表，它有一个学科、学号还有分数，怎么查总分大于 600 的学生和总分？

### 联想记忆法

#### 记忆口诀/联想

**口诀：先按学号分组，再把分数求和，最后用 HAVING 过滤。**

#### 记忆原理

这题是标准聚合查询。关键点不是 SQL 能不能写，而是要记住：**聚合结果过滤用 `HAVING`，不是 `WHERE`。**

#### 关联知识

- 与 `GROUP BY` 聚合关联
- 与 `WHERE` 和 `HAVING` 区别关联
- 与总分最高、平均分、选课门数等扩展题关联

---

### 深度解答

#### 标准 SQL

如果字段分别是学科、学号、分数，可以写成：

```sql
SELECT
    学号,
    SUM(分数) AS 总分
FROM 成绩表
GROUP BY 学号
HAVING SUM(分数) > 600;
```

如果是英文表结构，例如：
- `subject`
- `student_id`
- `score`

那就是：

```sql
SELECT
    student_id,
    SUM(score) AS total_score
FROM score_table
GROUP BY student_id
HAVING SUM(score) > 600;
```

#### 为什么用 HAVING

- `WHERE` 是对原始行过滤
- `HAVING` 是对分组后的聚合结果过滤

这里的总分是 `SUM(score)` 计算出来的聚合值，所以必须用 `HAVING`。

#### 扩展追问

如果面试官继续问：
- 查总分最高的学生
- 查平均分大于多少的学生
- 查总分大于 600 且至少 3 门课的学生

本质还是聚合 + 过滤的组合。

---

### 回答思路

直接给 SQL，然后补一句：这里不能用 `WHERE`，因为总分是聚合结果，要用 `HAVING` 过滤。这一句通常就是面试官想听的点。

## 10. MySQL 的 undo log、redo log 和 binlog 是做什么的？

### 联想记忆法

#### 记忆口诀/联想

**口诀：undo 能回头，redo 能重做，binlog 管复制和恢复。**

#### 记忆原理

这三个日志最好拆成两组记：
- `undo log`、`redo log` 属于 **InnoDB 引擎层**
- `binlog` 属于 **MySQL Server 层**

#### 关联知识

- 与 ACID、事务持久性关联
- 与 MVCC、回滚关联
- 与主从复制、数据恢复、两阶段提交关联

---

### 深度解答

#### undo log

主要有两个作用：
1. **事务回滚**
2. **MVCC 多版本并发控制**

更新数据前，InnoDB 会先记录旧值。如果事务回滚，就根据 `undo log` 把数据恢复回去。

同时，InnoDB 做一致性读时，历史版本也依赖 `undo log` 构造。

所以可以概括为：

> `undo log` 记录旧数据，用于回滚和 MVCC。

#### redo log

`redo log` 的核心作用是：
- 宕机恢复
- 保证事务持久性

InnoDB 修改数据时，不是每次都立即刷磁盘，而是先改内存中的 Buffer Pool，同时把修改写入 `redo log`。如果数据库宕机，重启后就根据 `redo log` 重做已提交事务。

这背后是 **WAL（Write-Ahead Logging）** 思想：

> 先写日志，再择机刷数据页。

#### binlog

`binlog` 是 MySQL Server 层的归档日志，主要用于：
- 主从复制
- 基于时间点的数据恢复

主库执行的数据变更会写入 `binlog`，从库再拉取并重放这些日志。

#### redo log 和 binlog 的区别

1. 层次不同
   - `redo log`：InnoDB 引擎层
   - `binlog`：MySQL Server 层

2. 内容不同
   - `redo log`：偏物理日志，记录页修改
   - `binlog`：偏逻辑日志，记录数据变更操作

3. 用途不同
   - `redo log`：崩溃恢复
   - `binlog`：主从复制、归档恢复

4. 写入方式不同
   - `redo log`：循环写
   - `binlog`：追加写

#### 深入思考

事务提交时，`redo log` 和 `binlog` 需要配合，两阶段提交就是为了解决两者一致性问题。

---

### 回答思路

先用一句话总括三者作用，再分别展开 undo、redo、binlog 的职责，最后补上 `redo log` 和 `binlog` 的区别，结构会很完整。

## 11. 说到主从复制，有了解过异步复制和同步复制吗？

### 联想记忆法

#### 记忆口诀/联想

**口诀：不等从库是异步，要等从库是同步，中间折中叫半同步。**

#### 记忆原理

这题核心在于比较“**主库提交时要不要等从库确认**”。围绕提交时机来答，逻辑最稳。

#### 关联知识

- 与 binlog、主从复制流程关联
- 与复制延迟、数据丢失风险关联
- 与半同步复制、组复制关联

---

### 深度解答

#### 异步复制

流程：
1. 主库事务提交
2. 主库返回客户端成功
3. 从库再异步拉取并重放 binlog

特点：
- 主库提交时不等从库
- 性能最好
- 会有主从延迟
- 主库宕机时可能丢一部分尚未同步到从库的数据

#### 同步复制

流程：
1. 主库执行事务
2. 必须等待从库确认收到，甚至确认执行完成
3. 主库才返回客户端成功

特点：
- 一致性最强
- 延迟和性能代价最大
- 很依赖网络和从库稳定性

#### 半同步复制

生产里更常见的是半同步。它介于两者之间：
- 主库提交后至少等一个从库 ACK
- 一致性比异步好
- 性能比严格同步更好

注意：通常只是保证从库收到 binlog，不一定已经执行完成。

#### 三者对比

- 异步复制：性能最好，可能丢数据
- 半同步复制：可靠性和性能折中
- 同步复制：一致性最强，性能最差

#### 深入思考

面试里可以补一句：

> 传统 MySQL 生产环境最常见的是异步和半同步，严格同步复制因为性能代价太大，并不是默认主流方案。

---

### 回答思路

先按“主库是否等待从库确认”给出三种模式，再分别讲一致性和性能取舍。最后落一句：生产中常见的是异步和半同步。

---

## 12. 说一下 Redis 中的基本数据结构有哪些，并且简单说一下它们的底层原理

### 联想记忆法

#### 记忆口诀/联想

**口诀：五大类型对外看，底层编码按规模切换。**

再细一点：
- `String -> SDS`
- `List -> quicklist`
- `Hash -> listpack / hashtable`
- `Set -> intset / hashtable`
- `ZSet -> listpack / skiplist + hashtable`

#### 记忆原理

Redis 对外暴露的是 5 种基础类型，但底层实现并不是固定一种结构，而是根据元素数量和值大小在不同编码之间切换。

#### 关联知识

- 与大 Key、热 Key 关联
- 与跳表、哈希表、压缩结构关联
- 与内存优化、性能权衡关联

---

### 深度解答

#### 1. String

最常见的数据类型，可存字符串、数字、二进制内容。

底层主要是 **SDS（Simple Dynamic String）**。

优点：
- O(1) 获取长度
- 动态扩容
- 二进制安全
- 避免 C 字符串缓冲区溢出问题

#### 2. List

特点：
- 有序
- 可重复
- 适合头尾插入

现代 Redis 底层主要是 **quicklist**。

可以理解成：
- 外层是双向链表
- 每个节点内部是一段紧凑存储块

这样兼顾了插入删除效率和内存利用率。

#### 3. Hash

适合存对象，如用户资料。

底层常见两种：
- 小对象：`listpack`
- 大对象：`hashtable`

这样设计是为了在小数据量时节省内存，在大数据量时保证查找效率。

#### 4. Set

特点：
- 无序
- 去重
- 支持交并差

底层：
- 全是整数且元素少时：`intset`
- 其他情况：`hashtable`

#### 5. ZSet

特点：
- 元素唯一
- 每个元素带 score
- 按 score 排序

底层：
- 小数据量：`listpack`
- 大数据量：`skiplist + hashtable`

这里用两套结构是因为要同时满足：
- 按 member 快速找分数
- 按 score 做排序和范围查询

#### 深入思考

面试里最好补一句：

> Redis 一个类型会对应多种底层结构，本质是在不同数据规模下平衡内存占用和操作性能。

---

### 回答思路

先列出 5 大基础类型，再按类型说底层编码，最后解释为什么一种类型会有多种底层结构，这一句是加分点。

## 13. 比如我现在要实现一个场景，如何保存页面的点击量和用户量，你会怎么设计？

### 联想记忆法

#### 记忆口诀/联想

**口诀：PV 用计数，UV 要去重；小量用 Set，大量用 HLL。**

#### 记忆原理

这题本质就是把“点击量”和“用户量”拆开：
- PV 是累加
- UV 是去重

两者的数据结构天然不同。

#### 关联知识

- 与 Redis String、Set、HyperLogLog 关联
- 与实时统计、离线落库关联
- 与热 Key、分桶、精确与近似统计关联

---

### 深度解答

#### 核心概念

页面点击量和用户量不要混着设计：
- **PV（Page View）**：每次点击都算一次
- **UV（Unique Visitor）**：同一用户重复访问只算一次

#### PV 设计

适合用 Redis 的 `String` 计数器。

按天统计时：

```text
pv:page:1001:20260816
```

每次点击：

```redis
INCR pv:page:1001:20260816
```

如果还要统计累计总量，可以再维护一个：

```text
pv:page:1001:total
```

#### UV 精确方案：Set

如果要求精确统计，用 `Set` 存 `userId`。

```redis
SADD uv:page:1001:20260816 20001
SCARD uv:page:1001:20260816
```

优点：
- 精确

缺点：
- 大数据量时占内存高

#### UV 海量方案：HyperLogLog

如果访问量很大、允许少量误差，用 `HyperLogLog`：

```redis
PFADD uv:page:1001:20260816 20001
PFCOUNT uv:page:1001:20260816
```

优点：
- 内存占用很小
- 适合大规模 UV 统计

缺点：
- 不是绝对精确

#### 整体架构建议

- Redis 负责高并发实时统计
- MySQL 负责异步汇总落库
- 前台看板实时读 Redis
- 报表系统查数据库或离线数仓

#### 无登录用户怎么办

如果没有 `userId`，可以用：
- 设备 ID
- Cookie ID
- 用户指纹
- IP + UA

但准确性会比登录用户差。

#### 深入思考

这题加分点是说明：

> 设计时要先区分“业务是否要求绝对准确”，因为这会直接决定 UV 用 Set 还是 HyperLogLog。

---

### 回答思路

先把 PV 和 UV 拆开讲，再分别给出 Redis 结构设计。最后补一句：Redis 扛实时统计，MySQL 做异步持久化，这是标准工程落地方式。

## 14. 后台系统查询列表接口响应很慢，可能是什么原因，如何定位？

### 联想记忆法

#### 记忆口诀/联想

**口诀：先分层，再定点；前端、网关、服务、缓存、数据库、下游逐层查。**

#### 记忆原理

这题不是只考 SQL 优化，而是考你有没有**整条调用链排查思维**。按链路从外到内查，逻辑最完整。

#### 关联知识

- 与慢 SQL、`EXPLAIN`、索引失效关联
- 与线程池、GC、锁竞争关联
- 与 Redis 命中率、下游服务超时、链路追踪关联

---

### 深度解答

#### 核心概念

用户感知的是“列表接口慢”，但问题可能不只在数据库，也可能在：
- 前端渲染
- 网关排队
- 应用层逻辑
- 缓存未命中
- 下游服务调用
- 数据库慢查询

所以不能一开始就把锅甩给 SQL。

#### 可能原因

##### 1. 前端层

- 页面初始化阻塞
- 请求串行太多
- 表格渲染慢
- 一次拉取数据太大
- 浏览器网络慢

##### 2. 网关 / Nginx 层

- 网关限流或队列堆积
- 某台机器负载过高
- 连接复用异常
- TLS 开销

##### 3. 应用服务层

- 业务逻辑太重
- N+1 查询
- 串行调用多个下游服务
- 线程池满、任务排队
- 锁竞争
- JVM 频繁 GC
- 返回数据太大，序列化慢

##### 4. 缓存层

- 缓存没命中
- 缓存穿透 / 击穿
- Redis 热 Key / 大 Key
- Redis 本身负载高

##### 5. 数据库层

- 没走索引，全表扫描
- 索引失效
- 深分页 `limit offset` 太大
- 排序 / 分组没走索引
- join 太复杂
- 锁等待
- 数据量膨胀后执行计划变差

##### 6. 外部依赖层

- 用户中心慢
- 权限系统慢
- 搜索服务慢
- 文件服务慢

#### 如何定位

##### 第一步：确认是真慢接口还是慢页面

- 浏览器开发者工具看 Network
- 用 Postman / curl 单独调接口
- 对比接口返回耗时和前端渲染耗时

##### 第二步：看监控和链路追踪

重点看：
- 接口 RT、QPS、错误率
- 机器 CPU、内存、Load
- JVM GC
- 线程池活跃数、队列积压
- Redis 命中率和耗时
- MySQL 慢查询、CPU、IO
- 下游 RPC 耗时

有 SkyWalking / Zipkin / Jaeger 时，能很快看出时间耗在哪一层。

##### 第三步：关键节点拆耗时

把接口耗时拆开：
- 参数处理
- 主查询 SQL
- Redis 查询
- 补充信息查询
- RPC 调用
- JSON 序列化

这样就能知道是 SQL 慢，还是“组装结果”慢。

##### 第四步：如果是数据库问题，专项排查 SQL

- 看慢查询日志
- 跑 `EXPLAIN`
- 重点看：
  - 是否走索引
  - 扫描行数
  - 是否 `filesort`
  - 是否 `temporary`
  - join 类型

常见问题包括：
- `%xx` 前缀模糊匹配
- 对索引列做函数
- 隐式类型转换
- 深分页
- 排序和过滤字段未命中联合索引

##### 第五步：如果不是 SQL，再查应用层

- `jstack` 看线程阻塞
- `jstat` / Arthas 看 GC 和热点方法
- 检查线程池是否满
- 看是否存在锁竞争或重复调用下游

#### 深入思考

这题真正的加分点是：

> 慢接口排查一定是先分层定位，再做专项优化，而不是直接猜数据库慢。

---

### 回答思路

先说慢接口可能卡在前端、网关、服务、缓存、数据库、下游多个层面。然后强调排查思路：先确认哪里慢，再用监控和 trace 缩小范围，最后对具体层做专项分析。这样回答最像有线上经验的人。
