# Redisson看门狗机制的原理？

## 联想记忆法

### 记忆口诀/联想

**口诀：不设过期就看门，十秒一续保三十。**

- **不设过期**：`lock()` 没指定 leaseTime 时才会触发看门狗。
- **看门**：后台线程盯着锁，防止业务没做完锁先失效。
- **十秒一续**：默认每隔一段时间自动续期一次。
- **保三十**：默认把锁有效期续到 30 秒左右的安全窗口。

### 记忆原理

看门狗本质上是“**自动续命线程**”。你不需要记住太多参数，只要记住一句：**锁还活着，后台就一直帮你把 TTL 往后推；进程死了，续期也停了，锁就自然过期。**

### 关联知识

- 会关联到 **leaseTime**：显式指定过期时间时，看门狗通常不启用。
- 会关联到 **定时续期**：后台任务不断刷新 TTL。
- 会关联到 **JVM 崩溃**：进程挂了续期停止，避免死锁。
- 会关联到 **幂等性**：锁自动释放不等于业务一定成功。

## 深度解答

### 1. 核心概念：看门狗就是锁的自动续期机制

Redisson 的看门狗（watchdog）机制，解决的是一个现实问题：  
业务执行时间不确定，如果锁 TTL 写太短，业务还没跑完锁就过期了；如果写太长，又会让别的线程白等。

所以 Redisson 在你不显式指定过期时间时，会默认给锁一个初始有效期，并启动后台续期任务，确保业务没结束前锁不会意外释放。

### 2. 底层原理：它怎么续

典型流程是：

1. 线程获取锁
2. Redisson 记录锁持有者信息
3. 启动定时任务
4. 在锁到期前，把 TTL 再延长一段时间
5. 只要持锁线程还活着，就持续续期

可以理解成：

```text
业务线程拿到锁
   ↓
watchdog 每隔一段时间检查
   ↓
发现还是自己持有
   ↓
执行 PEXPIRE 延长过期时间
```

底层通常是借助 Redis 的原子脚本刷新过期时间，避免并发场景下续期错乱。

### 3. 关键参数：什么时候触发，看多久

最常见的是：

- `lock.lock()`：默认走看门狗
- `lock.tryLock(waitTime, leaseTime, unit)`：如果显式指定 `leaseTime`，通常就不再依赖看门狗

默认看门狗超时时间通常是 30 秒，续期任务会在更短周期内执行一次，给锁延长有效期。

### 4. 实践应用：为什么它很有用

假设你在做一个慢接口：

```java
RLock lock = redissonClient.getLock("job:rebuild");
lock.lock();
try {
    rebuildIndex(); // 可能跑几十秒
} finally {
    lock.unlock();
}
```

如果没有看门狗，30 秒后锁过期，别的机器可能会抢到同一把锁，导致同一个任务被重复执行。  
有了看门狗，只要当前 JVM 还活着、线程还在持锁，锁就会持续续期。

### 5. 深入思考：看门狗解决的是“锁过期”，不是“业务正确性”

看门狗很有用，但它不是万能的：

- 如果 JVM 卡死、网络断开、进程崩溃，续期会停止
- 如果业务逻辑本身不幂等，锁短暂失效也可能造成重复执行
- 如果任务执行时间极长，仍要考虑手动设置更合适的 `leaseTime`

所以正确姿势是：

- 短任务：可以显式设置过期时间
- 长任务：依赖看门狗续期
- 核心业务：再加幂等和补偿

## 回答思路

### 答题逻辑框架

1. 先说看门狗是自动续期机制。
2. 再说默认在未显式指定 `leaseTime` 时生效。
3. 然后讲它会周期性延长 TTL。
4. 最后补充 JVM 宕机后续期停止，锁自然过期。

### 重点得分点

- 能说清“自动续期”。
- 能说出它的触发条件。
- 能解释为什么不会永久死锁。
- 能区分看门狗和显式过期时间。

### 常见误区

- 误区 1：看门狗会让锁永不过期。  
  正解：进程挂了就不会续期。

- 误区 2：有看门狗就不用管业务时长。  
  正解：仍要根据场景设计超时和幂等。

- 误区 3：显式设置 `leaseTime` 也会自动续期。  
  正解：通常不会。

### 面试话术

“Redisson 看门狗机制本质上是自动续期。默认锁没有显式指定 leaseTime 时，Redisson 会给锁一个初始过期时间，并启动后台定时任务，在锁快到期前不断延长 TTL。这样即使业务执行很久，锁也不会提前释放；但如果 JVM 挂了，续期停止，锁最终还是会自动过期。”
