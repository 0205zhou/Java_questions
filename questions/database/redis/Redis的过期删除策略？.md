# Redis的过期删除策略？

## 联想记忆法

### 记忆口诀/联想

**口诀：访问时顺手删，后台抽样删；过期管时间，淘汰管内存。**

- 惰性删除：像进门查票，访问到期键时才清理
- 定期删除：像巡逻抽查，后台周期性抽样清理
- 内存淘汰：内存紧张时做容量管理，不以键是否过期为唯一条件

### 记忆原理

过期键数量可能很大，逐个设置定时器会带来大量定时任务和调度开销；如果完全等到访问才清理，长期无人访问的过期键又会占用内存。因此 Redis 把“访问时检查”和“后台抽样清理”结合起来，在及时性与系统开销之间折中。

### 关联知识

- 过期删除回答“键到期后何时从数据库字典中移除”
- 内存淘汰回答“达到 maxmemory 后如何腾出空间”
- 主从复制和持久化还需要处理过期事件，避免副本之间出现不一致

---

## 深度解答

### 1. 核心概念：设置过期时间不等于到点立即删除

Redis 为带过期时间的键维护过期信息。键的 TTL 到期，首先意味着它在逻辑上已经过期；实际内存回收可能发生在后续访问或后台清理时。因此，不能把过期时间理解成一个精确到点执行的删除定时器。

通常所说的过期键删除策略是**惰性删除 + 定期删除**。内存淘汰是另一个机制，虽然也可能删除键，但触发条件和目标不同。

### 2. 惰性删除：访问键时检查并删除

客户端访问一个键时，Redis 检查它是否已过期。如果已过期，则删除该键并将其视为不存在；否则正常返回。

```text
读取 key
  ├─ 未过期：返回值
  └─ 已过期：删除 key，返回不存在
```

优点是没有访问的键不需要额外扫描，CPU 开销低；缺点是过期后一直没有被访问的键不会因此被清理，可能继续占用内存。

惰性删除是访问路径上的检查，不意味着 Redis 为每个键创建独立定时器。

### 3. 定期删除：后台抽样清理过期键

Redis 后台定期运行过期键清理逻辑，从设置了过期时间的键中抽样检查，删除已过期的键。若样本中过期键比例较高，会继续清理；如果比例下降或清理预算用尽，则暂缓并在后续周期再检查。

抽样而非每次扫描全部过期键，是为了避免键数量很大时清理任务长时间占用主线程、影响正常命令处理。不同 Redis 版本在具体时间预算、采样数量和实现细节上有所演进，面试回答重点应放在“后台抽样、限制工作量、分批清理”，不必把某个固定数值当作所有版本通用的常量。

优点是可以回收长期无人访问的过期键；缺点是清理有延迟，而且后台清理会消耗 CPU。

### 4. 为什么组合使用

| 策略 | 触发时机 | 优点 | 局限 |
|---|---|---|---|
| 惰性删除 | 访问键时 | 不访问就不付扫描成本 | 冷键可能长期占内存 |
| 定期删除 | 后台周期性抽样 | 能清理冷的过期键 | 有清理延迟，消耗后台 CPU |

只用惰性删除，冷过期键可能堆积；只用定期删除，要么清理不及时，要么全量扫描造成较大开销。两者配合，访问路径保证过期键不会作为有效值返回，后台任务逐步回收无人访问的过期键。

### 5. 内存淘汰：与过期删除不要混为一谈

当使用量达到 `maxmemory` 限制时，Redis 按配置的 `maxmemory-policy` 处理写入压力。这是内存容量管理，并非 TTL 到期后的常规清理。

常见策略可概括为：

- `noeviction`：不淘汰键，可能拒绝需要额外内存的写命令
- `allkeys-lru`、`allkeys-lfu`、`allkeys-random`：从所有键中按策略选择淘汰对象
- `volatile-lru`、`volatile-lfu`、`volatile-random`：只在设置了过期时间的键中选择
- `volatile-ttl`：优先淘汰剩余 TTL 较短的键

具体可用策略取决于 Redis 版本。即使配置了淘汰策略，也不应依赖它来代替业务 TTL；反过来，键设置了 TTL 也不代表它到期瞬间就释放内存。

### 6. 过期事件与复制中的处理

过期时间到达与实际删除之间存在延迟，因此过期通知也不是精确的定时器，不能用它承担必须准时执行的业务调度。需要可靠定时任务时，应使用专门的任务调度、消息队列或持久化任务表。

在复制架构中，过期键的权威判断和删除需要避免主从各自独立计时造成不一致；通常由主节点处理过期并将删除结果传播给副本。具体传播和过期实现随版本演进，但核心理解是：过期处理不仅关乎单机内存回收，也关乎复制一致性。

### 7. 实践建议

- 给缓存设置合理 TTL，并对批量数据使用随机抖动，减少同一时刻集中失效
- 结合 `INFO memory`、`INFO stats`、键空间统计及业务监控观察内存和过期清理情况
- 不依赖过期通知实现强准时性，也不要用 `KEYS` 全量扫描生产大库
- 根据 Redis 承载的是缓存还是重要业务状态，单独评估淘汰策略和持久化；淘汰可能造成业务键被提前删除

### 8. 一句话总结

Redis 通过惰性删除和定期抽样删除共同清理过期键：前者在访问时发现并删除，后者在后台逐步回收冷键；内存淘汰则是在内存达到上限时按策略腾空间，三者解决的问题不同。

## 回答思路

### 答题逻辑框架

1. 先说明 TTL 到期不代表键在那个瞬间立即从内存删除
2. 解释惰性删除：访问时判断，过期则删除
3. 解释定期删除：后台抽样扫描，控制清理开销
4. 说明两者互补，并区分内存达到上限时的淘汰策略
5. 补充过期通知不保证精确准时，不能当可靠定时任务

### 重点得分点

- 主动说出常规过期键清理是**惰性删除 + 定期删除**
- 解释组合原因：避免全量扫描开销，也避免冷过期键一直占内存
- 清楚区分 TTL 删除与 `maxmemory-policy` 内存淘汰
- 知道过期时间是逻辑失效时点，不是精确的物理回收承诺

### 常见误区

| 错误说法 | 正确理解 |
|---|---|
| “键一到过期时间就立刻释放内存” | 过期后可能等访问检查或后台清理才实际删除 |
| “Redis 给每个过期键都开一个定时器” | 常见实现不是逐键定时器，而是访问检查与后台抽样清理 |
| “内存淘汰就是过期删除” | 过期删除依据 TTL；淘汰由内存压力和淘汰策略触发 |
| “过期通知会准时触发” | 通知可能延迟，不适合作为可靠定时任务 |

### 面试话术

“Redis 的过期键通常采用惰性删除和定期删除结合。惰性删除是在访问键时检查 TTL，过期就删除；定期删除则由后台任务抽样检查并清理，避免冷键一直占内存。这样既避免全量扫描带来的性能开销，也能逐步回收没人访问的过期键。达到 `maxmemory` 后的 LRU、LFU 等属于内存淘汰，和 TTL 过期删除不是一回事。”
