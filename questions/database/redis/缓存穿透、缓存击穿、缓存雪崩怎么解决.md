# 缓存穿透、缓存击穿、缓存雪崩怎么解决



---

## 联想记忆法

### 记忆口诀/联想

**口诀："一穿空，二击热，三崩片；布隆空值防穿透，锁和逻辑防击穿，随机多级防雪崩"**

或者用 **"穿透查空，击穿热点，雪崩成片；空值布隆挡穿透，互斥逻辑顶击穿，随机多级抗雪崩"** 来记忆整个知识体系：

- **穿空** = 缓存穿透：查询「缓存和 DB 都不存在」的**空数据**，每次都打到数据库
- **击热** = 缓存击穿：某个**热点 key** 过期瞬间，大量并发同时打数据库
- **崩片** = 缓存雪崩：**大片 key** 同时过期或 Redis 宕机，请求全部直达数据库
- **空值布隆** = 穿透解法：缓存空值 + 布隆过滤器 + 参数校验
- **锁和逻辑** = 击穿解法：互斥锁 / 逻辑过期 / 热点 key 永不过期
- **随机多级** = 雪崩解法：过期时间加随机值 + 多级缓存 + 高可用 + 限流降级

### 记忆原理

这个口诀采用**"三字特征词 + 方案对仗"**的结构，第一句"穿空、击热、崩片"用三个字分别抓住三个问题的**特征**（空数据 / 热点 / 成片），先记住"问题长什么样"；第二句"空值布隆、锁和逻辑、随机多级"按顺序与问题一一对应，形成 **"问题 → 方案"** 的映射链。面试时先报特征词区分问题（这一下就能让面试官知道你真的理解区别），再按顺序展开方案，逻辑清晰不会漏。

### 关联知识

- **与分布式锁关联**：互斥锁方案本质就是 Redis 分布式锁（SET NX EX + Lua 解锁）——两个考点打通记忆，见 [[Redis 分布式锁如何实现]]
- **与布隆过滤器关联**：位数组 + 多次 hash 映射，判断"一定不存在"和"可能存在"，是穿透方案的核心数据结构
- **与本地缓存关联**：多级缓存（Caffeine / Guava 本地缓存 + Redis）是雪崩方案的核心，也常用于缓存预热
- **与限流降级关联**：Sentinel / Hystrix 熔断限流，保护数据库是三大问题的共同兜底防线
- **与缓存一致性关联**：逻辑过期方案会引入短暂脏读，牵扯出缓存更新策略（Cache Aside / 双写 / 延迟双删）——高频追问方向
- **与数据库保护关联**：三大问题的本质都是"保护数据库不被压垮"，可以引出连接池、读写分离、分库分表等纵深防护

## 深度解答

### 第一层：核心概念

#### 缓存的工作流程

```
请求 → 查 Redis 缓存
        ├─ 命中 → 直接返回
        └─ 未命中 → 查数据库 → 回写缓存 → 返回
```

缓存的意义：把数据库的压力转移到 Redis（内存），换取更低的响应时间和更高的吞吐。**一旦缓存失效，请求就会穿透到数据库**，这就是三大问题的根源。

#### 三大问题的定义与区别

| 问题 | 特征 | 一句话描述 |
|---|---|---|
| **缓存穿透** | 数据**不存在** | 查「缓存和 DB 都不存在」的数据，每次请求都打 DB |
| **缓存击穿** | **热点 key** 过期瞬间 | 一个热点 key 过期，大量并发同时打 DB |
| **缓存雪崩** | **大片 key** 同时失效 | 大量 key 集体过期，或 Redis 宕机，请求全部打 DB |

**一句话区分**：穿透是"查空"、击穿是"热 key 过期瞬间"、雪崩是"成片失效"——问题大小从单个 key 到整个缓存逐步升级。

---

### 第二层：底层原理

#### 一、缓存穿透：为什么"不存在"最危险

**根因**：缓存和数据库中都不存在该 key，缓存永远无法命中，**每次请求都直达数据库**。

- 正常流量：查到的都是存在的 key，缓存很快回填，DB 压力小
- 穿透流量：恶意攻击者故意构造大量不存在的 id（如负数 id、超长 id、随机 uuid），绕过缓存直接打 DB
- 后果：DB 被无效查询打垮，甚至引发 **DB 级 DoS**

#### 二、缓存击穿：为什么"瞬间"最危险

**根因**：热点 key 过期的**一瞬间**，所有并发请求同时发现缓存未命中，**同时去查数据库**。

- 热点 key 平时命中率极高，DB 从不承受它的压力
- 过期瞬间，N 个并发请求同时未命中 → N 个请求同时打 DB → DB 瞬间被打垮
- 与穿透的区别：击穿查的**数据是存在的**，只是缓存刚好失效；穿透查的**数据不存在**

#### 三、缓存雪崩：为什么"成片"最危险

**根因**：两个场景 ——

1. **大量 key 同时过期**：批量设置的 key 用了相同过期时间（如缓存预热时统一设置 30 分钟），同一时刻集体失效
2. **Redis 宕机**：整个缓存层不可用，所有请求（不管 key 存不存在）全部直达数据库

- 与击穿的区别：击穿是**一个 key**，雪崩是**一群 key 或整个缓存层**
- 后果：DB 承受全量流量，直接打垮

### 第三层：实践应用

#### 一、缓存穿透的解决方案

**方案 1：缓存空值（最常用）**

```java
public Object queryProduct(String id) {
    // 1. 查缓存
    Object val = redis.get("product:" + id);
    if (val != null) {
        return val;
    }
    // 2. 缓存未命中，查 DB
    Product product = productDao.getById(id);
    if (product == null) {
        // 3. 关键：查不到也写缓存，防止穿透
        redis.set("product:" + id, "NULL", 300);  // 空值也缓存，TTL 设短（5 分钟）
        return null;
    }
    // 4. 查到了，回写缓存
    redis.set("product:" + id, JSON.toJSONString(product), 1800);
    return product;
}
```

**方案 2：布隆过滤器（前置拦截）**

```java
// Redisson 布隆过滤器
RBloomFilter<String> filter = redisson.getBloomFilter("product-bloom");
filter.tryInit(1000000L, 0.01);   // 预期 100 万条数据，误判率 1%

// 请求进来先过布隆过滤器
if (!filter.contains(productId)) {
    return null;   // 一定不存在，直接拒绝，不查缓存不查 DB
}
// 可能存在 → 放行，继续查缓存/DB
```

原理：位数组 + k 个 hash 函数，把 key 映射到位数组上。判断结果只有两种：**"一定不存在"** 和 **"可能存在"**（有误判）。

**方案 3：参数校验**：id 必须为正数、长度合法，非法直接拒绝。

#### 二、缓存击穿的解决方案

**方案 1：互斥锁（Mutex）——用分布式锁挡住并发**

```java
public Object queryHotKey(String key) {
    Object val = redis.get(key);
    if (val != null) {
        return val;
    }
    // 缓存未命中，加锁只让一个线程查 DB
    String lockKey = "lock:" + key;
    boolean locked = redis.setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
    if (locked) {
        try {
            // 双重检查：锁等到的线程可能已经重建缓存
            val = redis.get(key);
            if (val != null) return val;
            // 真正查 DB 并回写缓存
            val = queryDb(key);
            redis.set(key, val, 1800);
            return val;
        } finally {
            redis.delete(lockKey);   // 释放锁
        }
    } else {
        // 没抢到锁：自旋等待 / 短暂休眠后重查缓存
        Thread.sleep(50);
        return queryHotKey(key);     // 递归重查（注意加尝试次数上限）
    }
}
```

**方案 2：逻辑过期——读写不阻塞，后台异步更新**

```java
// 缓存中存「数据 + 逻辑过期时间」
public class RedisData<T> {
    private T data;          // 业务数据
    private Long expireTime; // 逻辑过期时间戳
}

public Object queryHotKey(String key) {
    // 1. 查到缓存（缓存本身永不过期）
    RedisData redisData = JSON.parseObject(redis.get(key), RedisData.class);
    // 2. 判断逻辑是否过期
    if (redisData.getExpireTime() > System.currentTimeMillis()) {
        return redisData.getData();          // 未过期 → 直接返回
    }
    // 3. 逻辑过期 → 先返回旧数据（保证响应快）
    //    再抢锁让一个线程异步重建缓存（交给线程池执行）
    boolean locked = tryLock("lock:" + key);
    if (locked) {
        asyncExecutor.submit(() -> {
            try {
                Object newData = queryDb(key);   // 重建缓存
                redis.set(key, buildRedisData(newData, 30 * 60 * 1000));
            } finally {
                unlock("lock:" + key);
            }
        });
    }
    return redisData.getData();   // 返回旧数据（短暂脏读可接受）
}
```

**方案 3：热点 key 永不过期**：物理上不设 TTL，由后台定时任务主动刷新。

#### 三、缓存雪崩的解决方案

**方案 1：过期时间加随机值**

```java
// 不写死统一过期时间，加随机数分散过期时刻
int baseExpire = 1800;   // 30 分钟
int randomDelta = ThreadLocalRandom.current().nextInt(300);  // 0~5 分钟随机
redis.set(key, value, baseExpire + randomDelta, TimeUnit.SECONDS);
```

**方案 2：多级缓存（本地缓存兜底）**

```
请求 → 本地缓存 Caffeine（毫秒级，JVM 内存）
       ↓ 未命中
     Redis 缓存
       ↓ 未命中
     数据库
```

- Redis 宕机时，本地缓存还能挡住一部分热点流量
- 注意本地缓存的一致性：多实例有缓存副本，需要设置较短 TTL 或主动失效广播

**方案 3：Redis 高可用**：主从 + 哨兵 / Cluster 集群，保证 Redis 本身不宕机；做好持久化（RDB + AOF）防重启丢数据。

**方案 4：限流降级**：Sentinel / Hystrix 对 DB 访问限流，熔断降级返回兜底数据。

**方案 5：数据预热**：上线前/大促前把热点数据提前加载进缓存，避免冷启动时集中打 DB。

### 第四层：深入思考

#### 1. 三大问题横向对比

| 维度 | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 失效范围 | 单个 key（不存在） | 单个 key（热点） | 大量 key / 整个缓存 |
| 数据存在性 | 不存在 | 存在 | 存在 |
| 触发时刻 | 任意时刻（被攻击） | 热点 key 过期瞬间 | 集体过期 / 宕机 |
| 核心解法 | 空值 / 布隆 / 校验 | 互斥锁 / 逻辑过期 | 随机化 / 多级 / 高可用 |
| 后果严重度 | ★★★ | ★★★★ | ★★★★★ |

#### 2. 方案权衡：互斥锁 vs 逻辑过期

| 维度 | 互斥锁 | 逻辑过期 |
|---|---|---|
| 数据一致性 | 强（重建期间没人读旧数据，但有等待） | 弱（短暂脏读） |
| 吞吐 | 有锁等待，略有下降 | 最高，读不阻塞 |
| 实现复杂度 | 低 | 较高（要维护逻辑过期时间和异步任务） |
| 适用场景 | 一致性要求高的写后读 | 允许短暂脏读的高并发读多场景 |

#### 3. 布隆过滤器的局限

- **有误判率**：会把"不存在"判为"存在"（放行后缓存/DB 兜底），但绝不会把"存在"判为"不存在"（不会误杀）
- **不能删除元素**：位数组的 1 可能是多个 key 的 hash 叠加，删除会误伤 → 用**计数布隆过滤器（Counting Bloom Filter）**可解决
- **误判率与空间成正比**：trade-off 通过 `tryInit(size, errorRate)` 配置

#### 4. 生产环境的组合拳

```
第一道防线：参数校验 + 布隆过滤器      → 挡掉恶意/非法 key（防穿透）
第二道防线：互斥锁 / 逻辑过期          → 控制热点重建并发（防击穿）
第三道防线：过期随机化 + 多级缓存      → 避免集体失效（防雪崩）
第四道防线：Redis 高可用 + 限流降级    → 缓存挂了也不让 DB 挂（兜底）
```

#### 5. 高频追问方向

- **"逻辑过期怎么保证一致性？"** → 牺牲短暂一致性换吞吐，配合 Cache Aside + 延迟双删做最终一致
- **"布隆过滤器误判了怎么办？"** → 误判只是多放行一个请求，缓存/DB 正常兜底，不会出错
- **"热点 key 怎么发现？"** → 热 key 探测（如京东 hotkey 中间件、访问计数采样）、监控 Redis 大 key 与命中率
- **"Redis 挂了本地缓存也挂了怎么办？"** → 限流降级 + 服务降级返回兜底数据（如库存直接返回 0）

### 常见误区（扣分点）

| 错误说法 | 正确理解 |
|----------|----------|
| "穿透和击穿是一个问题" | 穿透查不存在的数据；击穿查存在的热点 key 过期瞬间 |
| "布隆过滤器零误判" | 有误判率，但只可能把不存在的判成存在，不会误杀 |
| "缓存空值能根治穿透" | 空值 TTL 到期后还会被打，要配合布隆过滤器和校验 |
| "互斥锁完全没有缺点" | 有锁等待延迟，极端情况有死锁风险（需锁超时） |
| "热点 key 不过期就安全" | 业务更新后缓存不更新会脏读，需配合主动刷新机制 |
| "雪崩只能靠随机过期解决" | 随机化只是防集体过期，Redis 宕机要靠高可用和降级 |

### 过渡话术建议

- **从场景到问题**："高并发系统里 Redis 缓存是数据库的第一道防线，但有三类场景会让这道防线失效，分别是缓存穿透、缓存击穿和缓存雪崩..."
- **从问题到方案**："先说穿透，它的特点是查空——数据根本不存在，缓存永远空着。对策有三板斧：缓存空值、布隆过滤器、参数校验..."
- **从击穿到锁**："击穿的解法里互斥锁最经典，它本质上就是 Redis 分布式锁：SET NX EX 加锁，Lua 脚本解锁，只让一个线程去重建缓存..."
- **总结过渡**："总的来说，这三个问题可以概括为：穿透靠挡（空值/布隆）、击穿靠锁（互斥/逻辑过期）、雪崩靠散（随机/多级/高可用），最终目的都是保护数据库不被压垮。"
