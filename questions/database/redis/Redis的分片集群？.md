# Redis的分片集群？

## 联想记忆法

### 记忆口诀/联想

**口诀：16384 个槽切数据，主节点分槽扩容量，从节点复制保可用，客户端按槽找节点。**

- **固定槽空间**：Redis Cluster 把 key 空间映射到 16384 个 hash slot。
- **槽分给主节点**：每个主节点负责一部分槽，数据和写请求因此分散到多台机器。
- **副本提供故障转移**：主节点可以配置副本节点，主节点故障时副本经选举提升。
- **客户端按槽路由**：客户端根据 key 算出槽位并访问负责该槽的节点，收到 `MOVED` / `ASK` 时按重定向处理。

### 记忆原理

把“分片集群”记成“**先切槽，再把槽分给主节点，副本负责接管**”最容易串起来。槽是 key 与节点之间稳定的中间层：扩缩容时迁移槽的归属即可，不必改变 key 的计算规则。

### 关联知识

- 会关联到 **哨兵**：哨兵只做高可用，不做分片。
- 会关联到 **hash slot**：Redis Cluster 按槽分配 key。
- 会关联到 **MOVED / ASK**：客户端重定向机制。
- 会关联到 **hash tag**：让多个 key 落到同一槽位。

## 深度解答

### 1. 核心概念：Redis Cluster 既分片，又高可用

Redis Cluster 通常就是面试里说的“Redis 分片集群”。它把 key 空间映射到固定的 **16384 个哈希槽（hash slot）**，槽编号为 `0` 到 `16383`。不同主节点负责不同槽位，于是数据和写流量可以横向分散。

它和哨兵最大的区别是：

- **哨兵**：主从复制 + 自动故障转移
- **Cluster**：主从复制 + 自动故障转移 + 数据分片

所以 Cluster 同时提供数据分片和主从故障转移能力，主要用于扩展容量、分散写入压力并提高可用性。副本复制是异步的，故障切换期间仍可能丢失尚未复制的写入；它不能承诺零数据丢失。

### 2. 底层原理：hash slot 怎么分

Redis Cluster 先对 key（或 hash tag 指定的子串）计算 CRC16，再取低 14 位；这等价于对 `16384` 取模：

```text
slot = CRC16(key) % 16384
```

每个 slot 在集群中归属于一个 master。客户端访问某个 key 时，会先算 slot，再根据槽位映射访问对应 master。`16384` 个槽是固定的逻辑分片空间，不等于集群只能有 16384 个节点；槽可以分配给不同数量的主节点，一个主节点也可负责很多槽。

### 哈希槽有什么用

槽把 key 的计算规则与物理节点解耦，主要有三点作用：

1. **决定数据归属**：先由 key 算槽，再查槽归属节点，避免把 key 固定绑定到某个节点编号。
2. **支持弹性扩缩容**：新增或移除主节点时，可以将一部分槽及其数据迁移到目标节点，迁移后更新槽位映射；key 的槽计算公式不变。
3. **支持多 key 同槽约束**：事务、Lua 脚本等多 key 操作通常要求相关 key 位于同一槽。用 hash tag 可以让多个 key 共享同一个参与哈希的片段。

例如 `order:{1001}:base` 和 `order:{1001}:items` 都只对 `{1001}` 计算槽位，因此会落到同一个槽。槽相同才满足同槽路由条件，具体操作仍需遵守命令和客户端限制。

为什么是 16384 个？它是 `2^14`，可以用 CRC16 结果的低 14 位快速得到槽号；集群节点用位图记录槽位归属，16384 个槽对应每节点约 2 KB 的位图，兼顾了分片粒度与集群元数据开销。它不是按机器数预先划分的槽数。

如果连错节点，Redis 会返回重定向：

- `MOVED`：这个槽现在在别的节点，去新地址
- `ASK`：迁槽过程中临时跳转一次

### 3. 集群内部是怎么运转的

Cluster 里每个节点都保存全量的槽位映射信息，并通过集群总线交换状态。节点之间会互相感知对方是否在线、是否失联、是否需要切主。

典型结构可以理解成：

```text
Master1 <- Slave1
Master2 <- Slave2
Master3 <- Slave3
```

每个 master 管一部分槽位，master 挂了以后，自己的从节点可以提升为新的 master，整个槽位归属关系再同步给集群。

### 4. 实践应用：怎么搭和怎么用

常见创建方式：

```bash
redis-cli --cluster create \
  127.0.0.1:7001 127.0.0.1:7002 127.0.0.1:7003 \
  127.0.0.1:7004 127.0.0.1:7005 127.0.0.1:7006 \
  --cluster-replicas 1
```

常见排查命令：

```bash
CLUSTER INFO
CLUSTER NODES
CLUSTER KEYSLOT user:1
```

如果要让多个 key 落到同一个槽位，可以用 **hash tag**：

```redis
user:{1001}:name
user:{1001}:age
```

Redis 对 key 中第一个非空 `{...}` 子串计算槽位。花括号里的内容相同，这两个 key 就会被路由到同一槽，方便需要同槽的事务、Lua 脚本或多 key 操作。要谨慎选择 tag，过于集中会造成热点槽，削弱分片带来的负载分散效果。

### 5. 深入思考：Cluster 的代价

Cluster 不是“免费午餐”：

- 多 key 操作会受跨槽限制
- 迁槽、扩容、缩容都比单机复杂
- 客户端必须支持 Cluster 协议
- 业务上最好尽量按业务维度设计 key，减少跨槽访问

所以它更适合：

- 数据量明显超过单机容量
- 写流量比较大
- 可接受一定的运维复杂度

不适合：

- 只是想要高可用但数据量不大
- 业务经常依赖大量跨 key 原子操作

### 6. 分片集群特点小结

- **数据分片**：固定 16384 个槽映射到多个主节点，扩展存储容量和写入能力。
- **无中心代理**：节点之间通过 Cluster 总线交换集群状态，客户端需支持集群路由或处理重定向。
- **副本与自动故障转移**：主节点可配置副本，但复制通常是异步的，故障切换存在短暂不可用和少量数据丢失风险。
- **槽迁移支持扩缩容**：通过迁移槽及其数据调整节点负责范围。
- **多 key 有同槽要求**：跨槽命令通常会报 `CROSSSLOT`；hash tag 可将相关 key 放到同槽，也可能形成热点。
- **运维复杂度较高**：客户端、监控、扩缩容、备份恢复都要考虑集群形态。

## 回答思路

### 答题逻辑框架

1. 先概括 Cluster 的特点：数据分片、多主节点、副本故障转移、客户端路由。
2. 明确哈希槽总数是 **16384 个**，编号 `0` 到 `16383`。
3. 解释 key 经 CRC16 映射到槽，槽归属决定负责节点。
4. 说明槽提供稳定的逻辑分片层，便于数据分配和扩缩容迁移。
5. 补充 hash tag、多 key 同槽限制、`MOVED` / `ASK` 以及副本异步复制的边界。

### 重点得分点

- 能说出 `16384` 个 slot。
- 能解释槽是 key 到节点之间的逻辑映射层，扩容通过迁移槽调整归属。
- 能区分分片扩容与副本故障转移，并指出异步复制不保证零数据丢失。
- 能解释 `MOVED` 和 `ASK`。
- 能区分 Cluster 和 Sentinel。
- 能说明 hash tag 的用途。

### 常见误区

- 误区 1：Cluster 就是多台 Redis 简单复制。  
  正解：它是分片架构，不是纯复制。

- 误区 2：Cluster 可以随便做多 key 操作。  
  正解：跨槽多 key 会受限制。

- 误区 3：Cluster 只解决容量，不解决高可用。  
  正解：Cluster 也支持主从切换。

### 面试话术

“Redis Cluster 的特点是把数据分片到多个主节点，并通过副本和故障转移提高可用性。它总共有 16384 个哈希槽，编号从 0 到 16383；key 经过 CRC16 计算得到槽，再由槽的归属确定节点。哈希槽把 key 的路由和物理节点解耦，扩缩容时迁移槽就能调整数据分布。多个 key 若要执行需要同槽的操作，可以用 hash tag 让它们落在一起，但要注意跨槽限制和热点风险。”
