# Redis的缓存预热是什么？

## 联想记忆法

### 记忆口诀/联想

**口诀：上线前装热点，分批限流防洪峰，失效后再补热。**

缓存预热就是在流量正式进入前，把预计会访问的数据提前放入缓存。把缓存想成店铺货架：开门前先把畅销品摆好，避免第一批顾客同时去仓库取货。

### 记忆原理

“预热”解决冷启动，不等于永久缓存。真正完整的记忆链是：识别热点、准备数据、批量写入、控制并发、校验结果、持续更新。面试中把这六步说出来，能体现你考虑了容量、数据库压力和数据时效。

### 关联知识

预热与缓存击穿、缓存雪崩、缓存穿透、双写一致性、热点 Key、大 Key、TTL、消息队列和分布式任务密切相关。预热失败时还要有降级和懒加载兜底。

## 深度解答

### 1. 核心概念：什么是缓存预热

缓存预热（Cache Warming）是在系统启动、发布、扩容或大型活动开始前，根据历史访问数据、业务配置或活动清单，把热点数据提前加载到 Redis 等缓存中。请求到达后直接命中缓存，减少首批请求的数据库查询延迟和并发压力。

它与懒加载相反：懒加载是第一次请求时才查询并写缓存；预热是把第一次查询提前到业务低峰或发布阶段。预热不是把数据库所有数据都复制到 Redis，而是选择高命中价值的数据。

### 2. 底层原理：一套可落地的预热流程

典型流程如下：

```text
统计热点候选 -> 查询数据库/搜索服务 -> 分批序列化
      -> Redis 批量写入 + TTL -> 校验数量和抽样命中率
      -> 发布流量 -> 未命中时走懒加载和限流兜底
```

第一步是确定候选集。可以读取 Top N 访问 Key、商品活动清单、推荐系统结果或运营配置，并设置上限，防止把低价值数据全部预热。热点是动态的，昨天热门的数据不一定适合长期预热。

第二步是控制加载节奏。预热任务应分页读取数据库，使用固定大小批次和限速；写 Redis 时可以用 pipeline 减少网络往返，但批次不宜无限增大。多实例部署时使用分布式锁、任务调度分片或幂等标记，避免每台实例重复全量查询。预热与线上请求争抢数据库连接时，应给任务设置独立线程池和并发上限。

第三步是设计 Key、TTL 和版本。Key 应与线上读取逻辑完全一致，TTL 可加随机抖动，避免所有 Key 在同一秒失效形成雪崩。序列化格式和版本必须与读请求兼容；发布新版本时，可以使用版本前缀或双版本 Key，等预热验证通过后再切换流量。

第四步是校验和观测。不能仅看“任务返回成功”，还应记录成功数、失败数、耗时、Redis 内存、写入 QPS、抽样读取结果和上线后的命中率。部分 Key 失败时重试要幂等；超过阈值应告警，但不能阻塞整个发布流程。

### 3. 实践应用：Java/Spring 示例

下面示例展示一个简单的分批预热，生产环境还应加入分页查询、限速、重试和指标：

```java
public void warmProducts(List<Product> products) {
    int batchSize = 500;
    for (int from = 0; from < products.size(); from += batchSize) {
        int to = Math.min(from + batchSize, products.size());
        redis.executePipelined((RedisCallback<Object>) connection -> {
            for (Product product : products.subList(from, to)) {
                String key = "product:v2:" + product.id();
                byte[] rawKey = keySerializer.serialize(key);
                byte[] rawValue = valueSerializer.serialize(product);
                connection.stringCommands().set(rawKey, rawValue);
                connection.keyCommands().expire(rawKey,
                        600 + ThreadLocalRandom.current().nextInt(60));
            }
            return null;
        });
    }
}
```

实际项目中，通常由定时任务或发布钩子调用 `warmProducts`，数据库采用 `WHERE id > ? ORDER BY id LIMIT ?` 这类游标分页，避免深分页。读请求仍然要保留“缓存未命中 -> 查询数据库 -> 回填”的路径，并用互斥锁、逻辑过期或请求合并防止大量请求同时回源。

活动预热可以把商品详情、库存展示、优惠规则等只读数据提前加载；库存扣减等强一致数据不能只依靠预热，必须由原子扣减、数据库约束或可靠消息保证正确性。预热写入缓存成功，也不代表数据库和缓存已经形成事务一致性。

### 4. 深入思考：预热的边界和方案选择

全量预热简单但浪费内存、耗时长；按 Top N 预热命中率高但依赖准确的热点统计；发布前同步预热可阻塞发布，异步预热更灵活但要承受冷启动窗口。常见折中是“核心热点同步预热 + 次热点异步预热 + 未命中懒加载”。

需要特别防范四类问题：

- **击穿**：单个热点过期时用互斥更新、逻辑过期或永不过期加后台刷新。
- **雪崩**：TTL 加随机值，分批预热，避免同一时刻大量失效。
- **穿透**：对不存在数据缓存空值并设置较短 TTL，必要时使用布隆过滤器。
- **容量超限**：估算序列化大小，监控 `used_memory` 和淘汰策略，优先保障核心 Key。

预热任务本身应可重复执行、可暂停、可重试和可审计。不能把“启动时一次性执行”当作完整方案，因为扩容、故障切换、热点变化都会产生新的冷数据。

## 回答思路

### 答题逻辑框架

1. 定义预热：业务流量前提前写入热点数据。
2. 说明目的：减少冷启动延迟，保护数据库。
3. 按候选识别、分批加载、TTL、校验监控讲执行流程。
4. 说明懒加载兜底，以及击穿、雪崩和容量风险。

### 重点得分点与常见误区

得分点是说出热点来源、分页限速、分布式任务、TTL 抖动、失败重试和监控。误区包括把预热等同于全量同步、认为预热后永远不会回源、用一个大 pipeline 写完所有数据、认为缓存写成功就等于数据一致。

### 过渡话术与时间分配

前 30 秒讲定义和价值，60 秒讲流程，30 秒讲异常和一致性。可这样过渡：“预热只是把冷启动提前处理，线上仍必须保留未命中回源和防击穿方案。”

### 面试参考回答

“缓存预热是在系统启动、发布或活动开始前，把预计会访问的热点数据提前写入 Redis，避免第一批请求同时回源数据库。一般先从访问统计或业务清单识别热点，再按分页分批查询、限速写入，设置带随机抖动的 TTL，并校验成功数、命中率和 Redis 内存。多实例要做任务分片或分布式锁，失败可以幂等重试。预热不能替代懒加载，线上还要处理击穿、雪崩、穿透和数据更新一致性。”
