## 1. HashMap 的底层原理是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：数组定桶位，链表解冲突，链长过长转红树。**

#### 记忆原理

HashMap 的核心就三步：先算 hash，再定位数组下标，冲突时挂到同一个桶里。面试时按“**数组 + 链表 + 红黑树**”这条线讲，结构就很清楚。

#### 关联知识

- 与 `hashCode()`、`equals()` 关联
- 与负载因子、扩容机制关联
- 与 `ConcurrentHashMap`、哈希冲突关联

### 深度解答

HashMap 在 JDK 1.8 里的底层结构是 **数组 + 链表 + 红黑树**。

1. **数组**
   - 主体是 `Node<K,V>[] table`
   - 每个数组下标叫一个桶（bucket）
   - 通过 `(n - 1) & hash` 计算元素落在哪个桶

2. **链表**
   - 如果多个 key 算出来的桶位相同，就会发生哈希冲突
   - 冲突元素会先挂成链表

3. **红黑树**
   - 当链表长度超过阈值 `8`，并且数组容量达到 `64` 时，链表会转成红黑树
   - 这样查找复杂度从 `O(n)` 优化到 `O(log n)`

4. **扩容**
   - 默认初始容量是 `16`
   - 默认负载因子是 `0.75`
   - 当元素个数超过 `容量 * 负载因子` 时触发扩容
   - 扩容时容量翻倍，并重新分布元素

JDK 1.8 相比 1.7 的一个关键优化，是在高冲突场景下引入红黑树，避免链表过长导致性能明显下降。

### 回答思路

面试时建议按这三步答：

1. 先说底层结构是数组 + 链表 + 红黑树
2. 再说 put 时怎么计算 hash 和定位桶位
3. 最后补充冲突处理、树化条件和扩容机制

一句话收尾：

> HashMap 的本质是用数组做快速定位，用链表或红黑树处理哈希冲突。

## 2. ConcurrentHashMap 与 HashMap 的区别是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：HashMap 快但不安全，ConcurrentHashMap 并发安全分段管。**

#### 记忆原理

这题不要只背“线程安全和不安全”，更要从**并发安全、空值支持、性能实现**三个维度比较。

#### 关联知识

- 与 `Hashtable` 区别关联
- 与 CAS、synchronized、并发容器关联
- 与多线程读写场景关联

### 深度解答

两者最核心的区别是：**HashMap 线程不安全，ConcurrentHashMap 线程安全。**

1. **线程安全性**
   - `HashMap` 在并发 put 时可能出现数据覆盖、链表成环、扩容异常等问题
   - `ConcurrentHashMap` 专门为并发场景设计，支持多线程安全读写

2. **实现机制**
   - JDK 1.7 的 `ConcurrentHashMap` 采用 **Segment 分段锁**
   - JDK 1.8 改成 **数组 + 链表/红黑树 + CAS + synchronized**
   - 读操作大多无锁，写操作锁桶或用 CAS 更新

3. **性能**
   - 单线程场景下，`HashMap` 一般更轻
   - 并发场景下，`ConcurrentHashMap` 吞吐和正确性更好

4. **null 支持**
   - `HashMap` 允许 `key` 为 `null`，也允许 `value` 为 `null`
   - `ConcurrentHashMap` 不允许 `key` 或 `value` 为 `null`
   - 原因是并发场景下无法区分“值本来就是 null”还是“没查到”

### 回答思路

建议按这四点答：

1. 线程安全性不同
2. 底层实现不同
3. 并发性能不同
4. null 支持不同

一句话总结：

> HashMap 适合单线程普通场景，ConcurrentHashMap 适合高并发共享 Map 场景。

## 3. CAS 机制是什么？它有什么问题和局限？

### 联想记忆法

#### 记忆口诀/联想

**口诀：先比旧值，再尝试改；改不成就重试，重试多了也有害。**

#### 记忆原理

CAS 的核心动作就是“**比较并交换**”。面试时先解释它怎么工作，再讲常见问题：ABA、自旋开销、只能保证单变量原子性。

#### 关联知识

- 与 `AtomicInteger`、`Unsafe`、`VarHandle` 关联
- 与乐观锁、自旋、版本号关联
- 与 `AtomicStampedReference` 关联

### 深度解答

CAS 全称是 **Compare And Swap**，中文一般叫“比较并交换”。

它的执行逻辑是：

```text
如果内存中的值 == 期望值
就把它改成新值
否则什么都不做
```

这是一种典型的**乐观锁**思想，认为冲突不一定发生，先尝试更新，失败再重试。

常见问题有：

1. **ABA 问题**
   - 变量从 A 改成 B，又改回 A
   - CAS 只看当前值还是不是 A，看不出中间变过
   - 常见解决方案是加版本号，比如 `AtomicStampedReference`

2. **自旋开销大**
   - 在高并发冲突下，CAS 可能一直失败并不断重试
   - 会浪费 CPU
   - 所以 CAS 更适合低冲突场景

3. **只能保证单个共享变量的原子性**
   - 一个变量好办
   - 多个变量一起更新时，单纯 CAS 不够
   - 这时通常要用锁，或者把多个状态合并封装

4. **可能有活锁问题**
   - 多个线程都很积极重试，谁都不让谁，系统一直转

### 回答思路

回答顺序建议是：

1. 解释 CAS 是什么
2. 说它属于乐观锁
3. 再讲三类问题：ABA、自旋开销、单变量限制

一句话总结：

> CAS 是无锁并发的基础，但不是万能方案，冲突高或涉及复合状态时往往还得配合锁或版本机制。

## 4. 线程池的核心参数有哪些？

### 联想记忆法

#### 记忆口诀/联想

**口诀：核心线程先顶上，队列排满再扩张，超了最大走拒绝，空闲线程按时亡。**

#### 记忆原理

线程池参数最适合按 `ThreadPoolExecutor` 的构造方法来记，因为面试官通常问的就是那 7 个核心参数。

#### 关联知识

- 与拒绝策略、队列类型关联
- 与 CPU 密集 / IO 密集线程池配置关联
- 与 `Executors` 风险关联

### 深度解答

`ThreadPoolExecutor` 的核心参数主要有 7 个：

1. **corePoolSize**
   - 核心线程数
   - 即使空闲，一般也会保留

2. **maximumPoolSize**
   - 最大线程数
   - 当队列满了以后，线程池最多还能扩多少线程

3. **keepAliveTime**
   - 非核心线程空闲多久会被回收

4. **unit**
   - `keepAliveTime` 的时间单位

5. **workQueue**
   - 任务阻塞队列
   - 常见有 `ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue`

6. **threadFactory**
   - 线程工厂
   - 用来定制线程名称、是否守护线程等

7. **RejectedExecutionHandler**
   - 拒绝策略
   - 当线程数到最大且队列也满时，决定怎么处理新任务

常见拒绝策略：
- `AbortPolicy`
- `CallerRunsPolicy`
- `DiscardPolicy`
- `DiscardOldestPolicy`

### 回答思路

建议直接按构造参数答，这样最标准：

> 核心线程数、最大线程数、存活时间、时间单位、阻塞队列、线程工厂、拒绝策略。

然后补一句：

> 真正常考的是 corePoolSize、maximumPoolSize、workQueue 和拒绝策略。

## 5. 线程池的执行流程是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：先开核心，后进队列，队列满了再扩容，扩容也满就拒绝。**

#### 记忆原理

线程池流程题最重要的是顺序。只要记住“**核心线程 -> 队列 -> 最大线程 -> 拒绝策略**”，就不会答乱。

#### 关联知识

- 与线程池参数关联
- 与拒绝策略关联
- 与任务堆积、吞吐分析关联

### 深度解答

线程池执行一个任务的大致流程如下：

1. **当前运行线程数 < corePoolSize**
   - 直接创建核心线程执行任务

2. **核心线程已满**
   - 尝试把任务放入阻塞队列

3. **队列也满了**
   - 如果当前线程数 < maximumPoolSize
   - 就继续创建非核心线程处理任务

4. **线程数已到最大，队列也满**
   - 触发拒绝策略

5. **非核心线程空闲时间超过 keepAliveTime**
   - 会被回收

所以它的本质不是“有任务就疯狂创建线程”，而是优先用核心线程，再用队列缓冲，最后才扩大线程数。

### 回答思路

建议面试时用流程化表达：

> 线程池先判断核心线程够不够，不够就建核心线程；够了先入队；队列满了再扩容到最大线程数；再满就走拒绝策略。

这就是标准答法。

## 6. 为什么不推荐使用 Executors 创建线程池？

### 联想记忆法

#### 记忆口诀/联想

**口诀：看着省事，实则失控；不是队列太大，就是线程太多。**

#### 记忆原理

这题关键不是背“不推荐”，而是说明**为什么危险**。核心风险是：线程数或队列长度默认可能没有边界。

#### 关联知识

- 与 OOM 关联
- 与 `ThreadPoolExecutor` 手动配置关联
- 与阿里开发手册关联

### 深度解答

阿里巴巴开发手册明确建议：**线程池不要使用 Executors 去创建，而是通过 ThreadPoolExecutor 手动创建。**

原因主要有：

1. **FixedThreadPool / SingleThreadExecutor**
   - 使用的是 `LinkedBlockingQueue`
   - 队列长度理论上接近无界
   - 大量任务堆积时可能导致 OOM

2. **CachedThreadPool**
   - 使用 `SynchronousQueue`
   - 最大线程数是 `Integer.MAX_VALUE`
   - 高并发时可能疯狂创建线程，导致系统被打爆

3. **ScheduledThreadPool**
   - 也可能因为排队任务过多导致资源问题

本质上，`Executors` 帮你隐藏了底层参数，但生产环境恰恰最需要对这些参数进行明确控制。

### 回答思路

最稳的答法是：

1. 先说不推荐
2. 再举两个典型风险：
   - 队列无界
   - 线程数无界
3. 最后补一句应该自己 new `ThreadPoolExecutor`

## 7. Spring Bean 的生命周期是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：先实例，后注入；Aware 回调知环境；前置后置夹初始化；销毁回调收尾巴。**

#### 记忆原理

Bean 生命周期题很容易答散，最好按时间顺序记：**实例化 -> 依赖注入 -> 初始化 -> 使用 -> 销毁**。

#### 关联知识

- 与 `BeanPostProcessor` 关联
- 与 `@PostConstruct`、`InitializingBean` 关联
- 与 AOP 代理生成时机关联

### 深度解答

Spring Bean 的典型生命周期大致如下：

1. **实例化**
   - Spring 创建 Bean 对象

2. **属性填充 / 依赖注入**
   - 给 Bean 注入依赖

3. **Aware 回调**
   - 比如 `BeanNameAware`、`BeanFactoryAware`、`ApplicationContextAware`

4. **BeanPostProcessor 前置处理**
   - `postProcessBeforeInitialization`

5. **初始化**
   - `@PostConstruct`
   - `InitializingBean.afterPropertiesSet()`
   - 自定义 `init-method`

6. **BeanPostProcessor 后置处理**
   - `postProcessAfterInitialization`
   - AOP 代理很多就是在这里增强出来的

7. **Bean 使用阶段**
   - 正常被业务代码调用

8. **销毁**
   - `@PreDestroy`
   - `DisposableBean.destroy()`
   - 自定义 `destroy-method`

### 回答思路

答题时建议抓主线：

> 实例化、依赖注入、Aware 回调、初始化前后置处理器、初始化方法、销毁方法。

然后补一句：

> AOP 代理一般是在后置处理器阶段织入的。

## 8. Spring AOP 的应用场景与底层原理是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：横切逻辑别硬写，代理一拦全接管。**

#### 记忆原理

AOP 题要分成两块答：

1. **能做什么**
2. **为什么能做到**

这样更完整。

#### 关联知识

- 与事务、日志、权限校验关联
- 与 JDK 动态代理、CGLIB 关联
- 与 Bean 生命周期、后置处理器关联

### 深度解答

#### 应用场景

Spring AOP 适合处理**横切关注点**，也就是很多业务都要做、但又不想每个方法都手写一遍的逻辑，比如：

- 事务管理
- 日志记录
- 权限校验
- 参数校验
- 性能监控
- 缓存增强

#### 底层原理

Spring AOP 的核心是**动态代理**。

1. **如果目标类实现了接口**
   - 默认优先用 **JDK 动态代理**

2. **如果没有实现接口**
   - 一般用 **CGLIB**
   - 通过生成子类的方式做代理

调用时不是直接调目标对象，而是先走代理对象。代理对象在调用前后插入增强逻辑，于是就实现了“无侵入式扩展”。

### 回答思路

建议按“场景 + 原理”答：

1. 先举几个横切场景
2. 再说 AOP 基于动态代理
3. 最后补 JDK 代理和 CGLIB 的区别

一句话总结：

> AOP 通过代理把公共逻辑从业务代码里抽出来，做到低耦合复用。

## 9. Spring 事务失效的常见场景有哪些？

### 联想记忆法

#### 记忆口诀/联想

**口诀：不是代理不生效，异常不对不回滚，权限不够也白搭。**

#### 记忆原理

事务失效题本质上考三个点：

1. 有没有走代理
2. 异常类型对不对
3. 事务配置是否真的生效

#### 关联知识

- 与 AOP 代理关联
- 与 `@Transactional` 回滚规则关联
- 与数据库引擎、传播行为关联

### 深度解答

常见事务失效场景有：

1. **方法不是 public**
   - Spring 声明式事务通常代理的是 public 方法

2. **自调用**
   - 类内部 `this.xxx()` 调用不会经过代理对象
   - 所以事务增强失效

3. **捕获异常但没继续抛**
   - 事务感知不到异常，就不会回滚

4. **抛出的不是默认回滚异常**
   - 默认只对 `RuntimeException` 和 `Error` 回滚
   - 如果抛 `checked exception`，要手动指定 `rollbackFor`

5. **数据库不支持事务**
   - 比如 MyISAM 引擎

6. **事务方法不在 Spring 容器管理范围内**
   - 自己 new 出来的对象不会有事务代理

7. **传播行为设置不当**
   - 比如外层事务和内层事务边界理解错误

### 回答思路

最好按分类答：

1. 代理没生效
2. 异常没触发回滚
3. 底层数据库或配置问题

这三类基本覆盖大多数面试追问。

## 10. Redis 的三大缓存问题是什么？分别如何解决？

### 联想记忆法

#### 记忆口诀/联想

**口诀：穿透查空，击穿热点，雪崩成片；空值布隆防穿透，锁和逻辑防击穿，随机高可用抗雪崩。**

#### 记忆原理

三大问题最容易混。面试时一定先区分：

- 穿透：查不存在的数据
- 击穿：热点 key 失效
- 雪崩：大量 key 同时失效

#### 关联知识

- 与布隆过滤器关联
- 与互斥锁、逻辑过期关联
- 与 Redis 高可用、限流降级关联

### 深度解答

1. **缓存穿透**
   - 查询的数据在缓存和数据库里都不存在
   - 请求每次都打到数据库
   - 解决：
     - 缓存空值
     - 布隆过滤器
     - 参数校验

2. **缓存击穿**
   - 某个热点 key 过期瞬间，大量请求同时打 DB
   - 解决：
     - 互斥锁
     - 逻辑过期
     - 热点 key 永不过期 + 异步刷新

3. **缓存雪崩**
   - 大量 key 同时过期，或 Redis 宕机
   - 解决：
     - 过期时间加随机值
     - Redis 高可用
     - 多级缓存
     - 限流、降级、熔断

### 回答思路

先用一句话区分三者，再分别讲解决方案。  
这是典型的“先分类，再对策”题。

## 11. 限流、熔断与降级分别是什么？适用场景是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：流量太大先限流，故障扩散就熔断，顶不住时做降级。**

#### 记忆原理

这三者本质都是高可用手段，但关注点不同：

- 限流：控入口
- 熔断：断故障
- 降级：保核心

#### 关联知识

- 与 Sentinel、Hystrix、Resilience4j 关联
- 与秒杀、高并发、防雪崩关联
- 与服务治理、稳定性设计关联

### 深度解答

1. **限流**
   - 限制单位时间内的请求数量
   - 目的是防止系统被突发流量打垮
   - 常见算法：
     - 固定窗口
     - 滑动窗口
     - 漏桶
     - 令牌桶

2. **熔断**
   - 当下游服务持续失败或超时时，暂时切断调用
   - 避免故障不断放大
   - 常见状态：
     - 关闭
     - 打开
     - 半开

3. **降级**
   - 当系统资源紧张时，优先保核心功能
   - 非核心功能返回兜底数据、默认值，或临时关闭
   - 比如：
     - 评论列表先不展示
     - 推荐功能先降级
     - 非关键统计改为异步

### 回答思路

最简单的答法是：

> 限流是限制流量入口，熔断是切断故障依赖，降级是牺牲非核心能力保核心链路。
