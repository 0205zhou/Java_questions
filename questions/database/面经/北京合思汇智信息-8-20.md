## 1. HashMap 的底层原理是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：数组定桶位，链表解冲突，链长过长转红树。**

#### 记忆原理

HashMap 的核心就三步：先算 hash，再定位数组下标，冲突时挂到同一个桶里。面试时按“**数组 + 链表 + 红黑树**”这条线讲，结构就很清楚。

#### 关联知识

- 与 `hashCode()`、`equals()` 关联
- 与负载因子、扩容机制关联
- 与 `ConcurrentHashMap`、哈希冲突关联

### 深度解答

HashMap 在 JDK 1.8 里的底层结构是 **数组 + 链表 + 红黑树**。

1. **数组**
   - 主体是 `Node<K,V>[] table`
   - 每个数组下标叫一个桶（bucket）
   - 通过 `(n - 1) & hash` 计算元素落在哪个桶

2. **链表**
   - 如果多个 key 算出来的桶位相同，就会发生哈希冲突
   - 冲突元素会先挂成链表

3. **红黑树**
   - 当链表长度超过阈值 `8`，并且数组容量达到 `64` 时，链表会转成红黑树
   - 这样查找复杂度从 `O(n)` 优化到 `O(log n)`

4. **扩容**
   - 默认初始容量是 `16`
   - 默认负载因子是 `0.75`
   - 当元素个数超过 `容量 * 负载因子` 时触发扩容
   - 扩容时容量翻倍，并重新分布元素

JDK 1.8 相比 1.7 的一个关键优化，是在高冲突场景下引入红黑树，避免链表过长导致性能明显下降。

### 回答思路

面试时建议按这三步答：

1. 先说底层结构是数组 + 链表 + 红黑树
2. 再说 put 时怎么计算 hash 和定位桶位
3. 最后补充冲突处理、树化条件和扩容机制

一句话收尾：

> HashMap 的本质是用数组做快速定位，用链表或红黑树处理哈希冲突。

## 2. ConcurrentHashMap 与 HashMap 的区别是什么？

### 联想记忆法

#### 记忆口诀/联想

**口诀：HashMap 快但不安全，ConcurrentHashMap 并发安全分段管。**

#### 记忆原理

这题不要只背“线程安全和不安全”，更要从**并发安全、空值支持、性能实现**三个维度比较。

#### 关联知识

- 与 `Hashtable` 区别关联
- 与 CAS、synchronized、并发容器关联
- 与多线程读写场景关联

### 深度解答

两者最核心的区别是：**HashMap 线程不安全，ConcurrentHashMap 线程安全。**

1. **线程安全性**
   - `HashMap` 在并发 put 时可能出现数据覆盖、链表成环、扩容异常等问题
   - `ConcurrentHashMap` 专门为并发场景设计，支持多线程安全读写

2. **实现机制**
   - JDK 1.7 的 `ConcurrentHashMap` 采用 **Segment 分段锁**
   - JDK 1.8 改成 **数组 + 链表/红黑树 + CAS + synchronized**
   - 读操作大多无锁，写操作锁桶或用 CAS 更新

3. **性能**
   - 单线程场景下，`HashMap` 一般更轻
   - 并发场景下，`ConcurrentHashMap` 吞吐和正确性更好

4. **null 支持**
   - `HashMap` 允许 `key` 为 `null`，也允许 `value` 为 `null`
   - `ConcurrentHashMap` 不允许 `key` 或 `value` 为 `null`
   - 原因是并发场景下无法区分“值本来就是 null”还是“没查到”

### 回答思路

建议按这四点答：

1. 线程安全性不同
2. 底层实现不同
3. 并发性能不同
4. null 支持不同

一句话总结：

> HashMap 适合单线程普通场景，ConcurrentHashMap 适合高并发共享 Map 场景。

## 3. CAS 机制是什么？它有什么问题和局限？

### 联想记忆法

#### 记忆口诀/联想

**口诀：先比旧值，再尝试改；改不成就重试，重试多了也有害。**

#### 记忆原理

CAS 的核心动作就是“**比较并交换**”。面试时先解释它怎么工作，再讲常见问题：ABA、自旋开销、只能保证单变量原子性。

#### 关联知识

- 与 `AtomicInteger`、`Unsafe`、`VarHandle` 关联
- 与乐观锁、自旋、版本号关联
- 与 `AtomicStampedReference` 关联

### 深度解答

CAS 全称是 **Compare And Swap**，中文一般叫“比较并交换”。

它的执行逻辑是：

```text
如果内存中的值 == 期望值
就把它改成新值
否则什么都不做
```

这是一种典型的**乐观锁**思想，认为冲突不一定发生，先尝试更新，失败再重试。

常见问题有：

1. **ABA 问题**
   - 变量从 A 改成 B，又改回 A
   - CAS 只看当前值还是不是 A，看不出中间变过
   - 常见解决方案是加版本号，比如 `AtomicStampedReference`

2. **自旋开销大**
   - 在高并发冲突下，CAS 可能一直失败并不断重试
   - 会浪费 CPU
   - 所以 CAS 更适合低冲突场景

3. **只能保证单个共享变量的原子性**
   - 一个变量好办
   - 多个变量一起更新时，单纯 CAS 不够
   - 这时通常要用锁，或者把多个状态合并封装

4. **可能有活锁问题**
   - 多个线程都很积极重试，谁都不让谁，系统一直转

### 回答思路

回答顺序建议是：

1. 解释 CAS 是什么
2. 说它属于乐观锁
3. 再讲三类问题：ABA、自旋开销、单变量限制

一句话总结：

> CAS 是无锁并发的基础，但不是万能方案，冲突高或涉及复合状态时往往还得配合锁或版本机制。

## 4. 线程池的核心参数有哪些？

### 联想记忆法

#### 记忆口诀/联想

**口诀：核心线程先顶上，队列排满再扩张，超了最大走拒绝，空闲线程按时亡。**

#### 记忆原理

线程池参数最适合按 `ThreadPoolExecutor` 的构造方法来记，因为面试官通常问的就是那 7 个核心参数。

#### 关联知识

- 与拒绝策略、队列类型关联
- 与 CPU 密集 / IO 密集线程池配置关联
- 与 `Executors` 风险关联

### 深度解答

`ThreadPoolExecutor` 的核心参数主要有 7 个：

1. **corePoolSize**
   - 核心线程数
   - 即使空闲，一般也会保留

2. **maximumPoolSize**
   - 最大线程数
   - 当队列满了以后，线程池最多还能扩多少线程

3. **keepAliveTime**
   - 非核心线程空闲多久会被回收

4. **unit**
   - `keepAliveTime` 的时间单位

5. **workQueue**
   - 任务阻塞队列
   - 常见有 `ArrayBlockingQueue`、`LinkedBlockingQueue`、`SynchronousQueue`

6. **threadFactory**
   - 线程工厂
   - 用来定制线程名称、是否守护线程等

7. **RejectedExecutionHandler**
   - 拒绝策略
   - 当线程数到最大且队列也满时，决定怎么处理新任务

常见拒绝策略：
- `AbortPolicy`
- `CallerRunsPolicy`
- `DiscardPolicy`
- `DiscardOldestPolicy`

### 回答思路

建议直接按构造参数答，这样最标准：

> 核心线程数、最大线程数、存活时间、时间单位、阻塞队列、线程工厂、拒绝策略。

然后补一句：

> 真正常考的是 corePoolSize、maximumPoolSize、workQueue 和拒绝策略。
