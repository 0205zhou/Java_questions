# JDK8 中 HashMap 为什么要转成红黑树

---

## 联想记忆法

### 记忆口诀/联想

**口诀："八树六链，六四把关，泊松分布，扩容优先"**

或者用 **"链长八，树当家；退到六，回归链；六十四，才动树；泊松算，防退化"** 来记忆整个知识体系：

- **八树六链** = 链表长度 ≥ 8 时树化为红黑树，长度 ≤ 6 时退化为链表 —— 两个核心阈值
- **六四把关** = 树化的第二个条件：数组长度 ≥ 64，不满足就先扩容
- **泊松分布** = 为什么阈值是 8：泊松分布计算得出出现 8 个冲突的概率约千万分之六
- **扩容优先** = 数组太小的时候，扩容比重建树更划算

### 记忆原理

这个口诀采用**"四字诀"的节奏**，押"i"韵（链、先），把 HashMap 的四个关键数字（8、6、64、以及隐含的负载因子 0.75）浓缩成八个字，形成 **"数字→条件"** 的线索链。面试时只要背住 "八、六、六四" 三个数字，就能顺着展开：8 为什么（泊松分布）→ 6 为什么（防抖动）→ 64 为什么（扩容优先）→ 红黑树为什么（性能兜底）。四个问号就是四段答题内容，不会漏点。

### 关联知识

- **与 ConcurrentHashMap 关联**：JDK8 的 ConcurrentHashMap 同样采用「数组+链表+红黑树」，链表长度 ≥ 8 且数组长度 ≥ 64 时树化 —— 同一个设计思想的两处落地
- **与 Redis 的跳表关联**：Redis 的 ZSet 用跳表实现有序集合（需要范围查询、排序），而 HashMap 只需要按键查找，所以用红黑树；对比能体现"数据结构选型要匹配操作模式"
- **与 AVL 树、B+ 树关联**：AVL 平衡严格但旋转多；MySQL 的 B+ 树是"矮胖"结构（多路搜索树），面向磁盘 IO；HashMap 的红黑树是"瘦高"结构，面向内存 —— 三种树的适用场景对比是经典追问
- **与 JDK7 的死循环问题关联**：JDK7 头插法 + 并发扩容会产生环形链表，JDK8 改尾插法解决，并引入红黑树兜底 —— 树化是 JDK8 对 HashMap 整体优化的一部分
- **与负载因子 0.75 关联**：泊松分布的计算前提就是负载因子 0.75，两者绑定记忆（扩容阈值与树化阈值同源）

## 深度解答

### 第一层：核心概念

#### 什么是 HashMap 的哈希冲突

HashMap 底层是「数组 + 链表」结构：计算 key 的 hash 值，通过 `(n - 1) & hash` 定位到数组的桶（bucket）。当两个不同 key 定位到同一个桶时，就发生了**哈希冲突（Hash Collision）**，冲突的 key 用链表串起来。

- 平均情况下：插入、查找都是 **O(1)**
- 冲突严重时：链表不断变长，查找需要从头遍历，**最坏退化为 O(n)**

#### 为什么要处理"链表过长"

链表的查询是线性的，当 hash 分布极其不均匀（例如攻击者故意构造 hash 值相同的 key），HashMap 会退化成一条超长链表：

- 查询性能灾难性下降：**O(n)**
- 历史上真实发生过利用 HashMap 哈希碰撞发起的 **DoS 攻击**（如通过请求参数构造碰撞 key 打满 CPU）

JDK8 的解法就是：链表过长时，把链表**树化成红黑树**。

### 第二层：底层原理

#### 树化的两个条件

JDK8 中，HashMap 结构变为「数组 + 链表 + 红黑树」，但**不是链表一长就树化**，必须同时满足：

```
条件①：链表长度 ≥ 8
条件②：数组长度 ≥ 64
```

源码逻辑（`treeifyBin` 方法）：

```java
final void treeifyBin(Node<K,V>[] tab, int hash) {
    int n, index; Node<K,V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)  // 64
        resize();                       // 条件②不满足 → 先扩容
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // 条件①②都满足 → 链表转为红黑树
    }
}
```

#### 为什么阈值是 8（泊松分布）

HashMap 源码注释给出了答案——**泊松分布（Poisson Distribution）**：

- 负载因子为 0.75 时，某个桶中恰好出现 k 个 key 的概率符合泊松分布（λ ≈ 0.5）
- 计算结果：链表长度达到 8 的概率约为 **0.00000006（千万分之六）**，几乎不可能发生
- 也就是说：**正常情况下永远触发不了树化**；一旦触发，说明 hash 分布严重异常，此时才值得用红黑树兜底

概率对照表（源码注释节选）：

| 链表长度 k | 概率 |
|---|---|
| 6 | 0.00000016 |
| 7 | 0.00000094 |
| 8 | 0.00000006 |

#### 为什么退化阈值是 6（防抖动）

- 如果退化阈值也是 8，元素数量在 7、8 之间反复横跳时，链表会**频繁树化 / 退化**，白白浪费 CPU（称为"抖动"）
- 阈值设为 **6，与 8 之间留出缓冲区间**，避免频繁转换
- 权衡逻辑：树化成本高（要建 TreeNode、做旋转），必须用"单向的冗余区间"保证稳定性

#### 为什么红黑树，而不是 AVL / 跳表 / B+ 树

| 方案 | 分析 |
|---|---|
| **AVL 树** | 平衡最严格，查询最快，但插入删除要频繁旋转维护平衡；HashMap 以插入为主，**写入成本不可接受** |
| **跳表** | 需要多级索引指针，**空间开销大**；Redis 用它是因为 ZSet 需要范围查询和排序，HashMap 只按键查找，用不上 |
| **B+ 树** | 多路搜索，矮胖结构，面向磁盘批量 IO；HashMap 在内存中，**没有磁盘 IO 问题**，用不上 |
| **红黑树** | 自平衡二叉查找树，插入/删除/查找都稳定在 **O(logn)**；允许局部不平衡，**旋转次数少**，写入效率高，综合最优 |

#### TreeNode 的内存代价

红黑树节点 `TreeNode` 继承自普通 `Node`，额外持有 parent / left / right / prev 指针和 red 颜色标志：

- TreeNode 的内存约为普通 Node 的 **2 倍**
- 因此树化是"花内存买性能兜底"，不能随便触发 —— 这也解释了为什么阈值设得那么高（8）

### 第三层：实践应用

#### 源码关键流程

```
put(k,v)
  → hash 定位桶
  → 桶是链表 && 链表长度 ≥ 8
    → treeifyBin()
      → 数组长度 ≥ 64 ? 树化 : 扩容
      → treeify() 把链表节点替换为 TreeNode，构建红黑树
```

扩容时（resize）：

```
resize()
  → 遍历每个桶
  → 桶是红黑树
    → split()：按高位 0/1 拆分成两棵子树（或两条链表）
    → 拆分后任一段长度 ≤ 6 → untreeify() 退化为链表
```

#### 工程影响

- **防御性编程**：对传入的 key 做约束（如限制长度、白名单），避免被构造 hash 碰撞攻击
- **自定义 key 的 hashCode 要分散**：业务对象作为 key 时，hashCode 实现不好会导致大面积冲突（虽然树化兜底，但 O(logn) 仍远不如 O(1)）
- **遍历有序性**：树化后桶内元素按 key 有序，但 HashMap 本来就不保证顺序，不要依赖

### 第四层：深入思考

#### 1. 树化真的能根治长链表吗

不能。红黑树只是把最坏复杂度从 **O(n) 降到 O(logn)**，但：

- 如果 hash 分布持续恶劣（如 hashCode 返回常量），即使树化，每次操作也稳定在 O(logn)，性能远低于正常 O(1)
- **树化是兜底而非修复**：根本手段是保证 hash 分散（key 的 hashCode 质量、扰动函数）

#### 2. 为什么用"扰动函数"（hash 高 16 位异或低 16 位）

```
JDK8:  hash = h ^ (h >>> 16)   // 高16位与低16位异或
       index = (n - 1) & hash
```

- 数组长度 n 通常是 2 的幂，`(n-1) & hash` 只用到 hash 的低位
- 扰动函数把高位的随机性"混入"低位，**小数组下也能分散**
- 与树化配合：先尽量从源头减少冲突，树化只做最后防线

#### 3. JDK7 → JDK8 的完整改进清单

| 改进 | JDK7 | JDK8 |
|---|---|---|
| 存储结构 | 数组 + 链表 | 数组 + 链表 + 红黑树 |
| 树化 | 无 | 链表 ≥8 且数组 ≥64 |
| 插入方式 | 头插法 | 尾插法 |
| 并发问题 | 扩容成环死循环 | 成环问题解决（仍非线程安全） |
| 哈希扰动 | 4 次扰动 | 1 次异或扰动 |

#### 4. 面试官可能的追问方向

- **"那 ConcurrentHashMap 的树化条件一样吗？"** → 一样（≥8 且 ≥64），设计同源
- **"红黑树和哈希表能共存的场景还有吗？"** → Linux 的 epoll 用红黑树管理 fd、TreeMap 本身就是红黑树
- **"为什么不用二叉查找树（BST）？"** → 普通 BST 可能退化成链表（有序插入时），红黑树自平衡保证不退化
- **"0.75 负载因子怎么来的？"** → 泊松分布推导 + 空间与冲突的工程权衡，链长 8 的概率千万分之六正是基于 0.75

### 常见误区（扣分点）

| 错误说法 | 正确理解 |
|----------|----------|
| "链表超过 8 就转红黑树" | 必须同时满足数组长度 ≥ 64，否则先扩容 |
| "红黑树查询是 O(1)" | 红黑树是二叉查找树，查询 O(logn) |
| "转红黑树能根治哈希冲突" | 只是把最坏 O(n) 兜底到 O(logn)，根本靠哈希分散 |
| "阈值 8 是拍脑袋定的" | 基于负载因子 0.75 下的泊松分布计算 |
| "JDK8 的 HashMap 线程安全了" | 仍非线程安全，只是修复了死循环问题，并发要用 ConcurrentHashMap |
