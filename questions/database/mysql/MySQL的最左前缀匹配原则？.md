# MySQL的最左前缀匹配原则？

## 联想记忆法

### 记忆口诀/联想

**口诀：联合索引排成队，最左开始不能跳；等值锁定往后走，范围之后少利用。**

以联合索引 `(a, b, c)` 想象成电话簿：先按 `a` 排序，`a` 相同再按 `b`，最后按 `c`。只有先确定左侧目录，右侧排序才有意义。

### 记忆原理

最左前缀不是“SQL 条件必须按书写顺序出现”，而是索引键的排序结构决定了可利用的有序区间。记住“队伍按 a、再 b、再 c 排”，就能推导出为什么跳过 `a` 时 `b` 无法独立定位，以及为什么范围条件可能影响后续列的精确定位。

### 关联知识

- 联合索引、覆盖索引、索引下推和回表查询。
- `EXPLAIN` 的 `key_len` 可以辅助观察实际使用了哪些索引列。
- 等值查询、范围查询、排序和分组都可能利用联合索引，但最终以优化器执行计划为准。

## 深度解答

### 第一层：核心概念

最左前缀匹配原则（Leftmost Prefix Principle）是指：对于联合索引 `(a, b, c)`，MySQL 通常只能从索引最左侧开始，按连续前缀利用索引的有序性。可以使用 `a`，也可以使用 `a,b` 或 `a,b,c`；如果缺少最左列或跳过中间列，后续列通常不能继续用于精确定位。

示例：

```sql
CREATE INDEX idx_abc ON t (a, b, c);
```

常见条件的效果：

| 条件 | 典型利用情况 |
|---|---|
| `a = 1` | 使用 `a` |
| `a = 1 AND b = 2` | 使用 `a,b` |
| `a = 1 AND b = 2 AND c = 3` | 使用 `a,b,c` |
| `b = 2` | 缺少最左列，通常无法有效使用该联合索引 |
| `a = 1 AND c = 3` | 使用 `a`，`c` 通常在索引或回表后过滤 |
| `a = 1 AND b > 2 AND c = 3` | 通常定位到 `a,b` 的范围，`c` 难以继续形成精确范围 |

“使用索引”还要区分索引访问和索引列的完整利用。即使 `a = 1 AND c = 3` 能走 `a`，也不代表三列都命中了。

### 第二层：底层原理

联合索引的每个索引项按字典序排序：

```text
(a, b, c)
(1, 1, 9)
(1, 2, 3)
(1, 2, 8)
(1, 5, 1)
(2, 1, 4)
(2, 3, 7)
```

先按 `a` 分组，在相同 `a` 中按 `b` 排序，在相同 `(a,b)` 中按 `c` 排序。查询 `a = 1 AND b = 2` 可以直接定位到连续区间 `(1,2,*)`；但只查询 `b = 2` 时，`b=2` 的记录分散在不同 `a` 的区间中，没有一个连续的起点和终点，索引无法像单列 `b` 索引那样快速定位。

#### 1. 为什么跳过中间列会截断

`(a,b,c)` 中查询 `a=1 AND c=3` 时，MySQL 能先定位 `a=1` 的区间，但在这个区间内，`c=3` 的记录可能分散在各种 `b` 值中。`c` 仍可能用于索引条件下推或过滤，却通常不能继续缩小 B+ 树的搜索范围。

#### 2. 范围条件的影响

范围条件如 `b > 10` 会把索引定位扩展成一段范围。范围内的 `c` 仍按顺序排列，但对于优化器来说，继续用 `c` 缩小范围的收益和实现方式受限，常见面试表述是“遇到范围列，后续列通常不能用于继续精确定位”。具体行为还与 MySQL 版本、条件形式、ICP 和成本估算有关，不能绝对化。

#### 3. 与 SQL 书写顺序无关

优化器会对 `WHERE` 条件进行分析和重排，因此：

```sql
WHERE c = 3 AND a = 1 AND b = 2
```

仍可能完整使用 `(a,b,c)`。最左前缀约束的是索引列的逻辑顺序，不是 `WHERE` 子句中文字的先后顺序。

### 第三层：实践应用

#### 1. 用执行计划验证

```sql
EXPLAIN
SELECT * FROM t
WHERE a = 1 AND b = 2 AND c = 3;
```

重点查看：

- `key`：实际选择的索引。
- `key_len`：在固定数据类型和字符集后，可辅助判断使用了哪些前缀列，但不能单独当作绝对结论。
- `type`：`const`、`ref`、`range` 等访问类型。
- `rows`：预计扫描行数。
- `Extra`：是否出现索引条件下推、排序或临时表等信息。

应使用接近生产规模的数据测试，因为小表即使全表扫描也可能比走索引便宜。

#### 2. 按查询模式设计索引

假设高频查询是：

```sql
WHERE tenant_id = ? AND status = ? AND created_at >= ?
ORDER BY created_at DESC
```

通常可以评估联合索引：

```sql
CREATE INDEX idx_tenant_status_created
ON orders (tenant_id, status, created_at);
```

租户和状态是等值条件，放在范围时间列之前，有助于缩小扫描范围；但最终还需结合选择性、排序、分页方式和实际执行计划调整。

#### 3. 避免人为破坏索引条件

```sql
-- 可能导致索引列被函数包裹
WHERE DATE(created_at) = '2026-08-21'

-- 更适合改写为范围
WHERE created_at >= '2026-08-21 00:00:00'
  AND created_at <  '2026-08-22 00:00:00'
```

另外还要注意隐式类型转换、前导 `%`、对列进行计算，以及在联合索引中跳过左侧列。

### 第四层：深入思考

#### 最左前缀不是“后面的列完全没用”

跳过列后，后续列通常不能用于 B+ 树的主要搜索范围，但不等于它永远无效。它可能用于：

- 索引条件下推，在存储引擎层过滤。
- 覆盖索引，避免回表。
- 读取索引叶子做扫描后再过滤。
- 满足部分排序或分组需求。

所以应区分“能否访问这棵索引”“使用了几列定位”“是否覆盖查询”三个问题。

#### 为什么不为每种组合都建索引

索引数量过多会增加磁盘空间、Buffer Pool 压力以及写入维护成本。应先收集慢查询和高频查询，按“等值列、范围列、排序列、返回列”的模式设计少量高价值索引，并清理冗余前缀。例如已有 `(a,b)` 时，单独的 `(a)` 可能是冗余索引，但仍要检查特殊排序、覆盖需求和优化器行为后再删除。

#### 列顺序如何权衡

“区分度最高的列永远放第一”不是绝对规则。列顺序要同时考虑：

- 是否经常作为等值条件。
- 是否是范围条件。
- 能否支持排序、分组和覆盖查询。
- 业务查询是否需要左侧列单独使用。
- 数据分布和更新成本。

例如一个低基数的租户字段，如果所有查询都必须带租户条件，仍可能适合放在第一列；设计要以真实查询集合为依据。

#### 面试官常见追问

- `WHERE b = 1 AND a = 2` 是否能用 `(a,b)`：可以，优化器不看条件书写顺序。
- `(a,b,c)` 查询 `a=1 AND c=3` 使用几列：通常用 `a` 定位，`c` 过滤，具体由执行计划验证。
- `LIKE 'abc%'` 能否使用：通常能形成范围；`LIKE '%abc'` 因无法确定起点，通常不能有效利用 B+ 树顺序。
- 联合索引一定比多个单列索引好：不一定，要看查询组合、写入成本和优化器选择。

## 回答思路

### 答题逻辑框架

1. 先给定义和 `(a,b,c)` 例子。
2. 用字典序解释“为什么必须从左开始”。
3. 依次说明缺列、跳列、范围列的影响。
4. 补充 `WHERE` 书写顺序不影响索引逻辑顺序。
5. 结合 `EXPLAIN`、索引设计和覆盖/ICP 收尾。

### 重点得分点

- 说清“最左前缀”约束的是联合索引列顺序，不是 SQL 文本顺序。
- 区分“能走索引”和“完整利用了几列”。
- 说明范围条件对后续列的典型影响，并保留版本与成本模型的边界。
- 能用真实查询模式而非单纯“区分度最高优先”设计索引。

### 常见误区

- 认为 `WHERE` 条件必须按索引顺序书写。
- 认为跳过 `b` 后 `c` 一定完全不能被读取或过滤。
- 认为只要执行计划出现索引名，就代表所有索引列都被利用。
- 把最左前缀误解成字符串 `LIKE` 专属规则。

### 过渡话术

“最左前缀的根源是联合索引按字典序排列，所以先确定左侧列，后面的排序才有意义。接下来我用缺列、跳列和范围列三个场景说明索引到底能用到哪一步。”

- 30 秒定义和口诀。
- 90 秒讲 `(a,b,c)` 的典型组合及字典序原理。
- 40 秒讲范围、执行计划和索引设计权衡。
