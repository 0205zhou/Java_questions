# 索引的类型?

---

## 联想记忆法

### 记忆口诀/联想

**口诀："按用途分主唯普，按结构分 B 哈全，按组织分聚非聚，按字段分单联合。"**

把索引的类型按四个维度拆开记：

1. **按用途/约束分**：主键索引、唯一索引、普通索引
2. **按底层结构分**：B+Tree 索引、Hash 索引、FullText 全文索引
3. **按数据组织分**：聚簇索引、非聚簇索引
4. **按字段个数分**：单列索引、联合索引

如果要一句话总纲，就记：**“面试答索引类型，别只背三个名字，要先说明你按什么维度分类。”**

### 记忆原理

很多人答“索引的类型”时容易乱，因为脑子里混着“主键索引、B+Tree、联合索引、聚簇索引”这些并不处于同一维度的概念。正确记忆方式是先立分类坐标轴，再往里面填类型。这样面试时结构更清晰，也能防止答漏。

### 关联知识

- 与索引底层原理直接相关，InnoDB 主流索引结构是 B+Tree。
- 与最左前缀原则、回表、覆盖索引强相关。
- 与索引失效题关联非常紧密，因为很多失效场景都发生在联合索引使用不当时。
- 与存储引擎相关，Hash 索引常见于 Memory，引擎不同支持的索引类型也不同。

## 深度解答

### 第一层：核心概念

索引（Index）本质上是帮助数据库快速定位数据的数据结构。你可以把它理解成书的目录：不建索引时，数据库可能要一行行扫描整张表；建了索引以后，可以先从索引找到目标位置，再定位到具体数据。

面试里“索引的类型”通常有两种答法：

1. **按业务用途分**：主键、唯一、普通
2. **按技术实现分**：B+Tree、Hash、FullText、聚簇、联合等

更好的方式是把这两种答法合并，用分类视角回答。

#### 1. 按用途分类

##### 主键索引（Primary Key Index）

主键索引建立在主键字段上，要求值唯一且不能为 `NULL`。在 InnoDB 里，主键索引还是**聚簇索引**，叶子节点直接存整行数据。

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50)
);
```

特点：

- 唯一且非空
- 一张 InnoDB 表只能有一个主键索引
- 通常也是查询性能最核心的索引

##### 唯一索引（Unique Index）

唯一索引要求索引列的值不能重复，但通常允许 `NULL`（具体表现和数据库实现有关，MySQL 中多个 `NULL` 一般是允许的）。

```sql
CREATE UNIQUE INDEX uk_email ON user(email);
```

用途：

- 保证业务唯一性，如邮箱、手机号、订单号
- 在并发场景下配合数据库唯一约束，避免重复写入

##### 普通索引（Normal Index）

普通索引没有唯一性约束，只是为了提升查询性能。

```sql
CREATE INDEX idx_name ON user(name);
```

它是最常见的索引类型，适用于经常作为查询条件、排序条件、分组条件的字段。

### 第二层：底层原理

#### 2. 按底层结构分类

##### B+Tree 索引

这是 MySQL InnoDB 最主流、最重要的索引结构。

特点：

- 非叶子节点只存键值和指针
- 叶子节点存完整索引记录
- 叶子节点之间通过链表连接
- 天然适合范围查询、排序、分页

```text
           [10 | 20 | 30]
          /      |      \
   [1..9]   [10..19] [20..29] [30..]
```

B+Tree 适合数据库的核心原因是：

- 树高低，磁盘 IO 次数少
- 支持范围查询
- 支持顺序遍历
- 适合联合索引的最左匹配

##### Hash 索引

Hash 索引底层是哈希表，通过 key 计算 hash 值后快速定位。

优点：

- 等值查询很快

缺点：

- 不支持范围查询
- 不支持排序
- 不支持最左前缀匹配
- 哈希冲突时性能会下降

所以在 MySQL 里 Hash 索引不是主流，更多见于 Memory 存储引擎，InnoDB 主要是自适应哈希索引（Adaptive Hash Index），而不是用户手动定义的通用 Hash 索引。

##### FullText 全文索引

全文索引用于文本搜索，而不是普通精确匹配。

```sql
CREATE FULLTEXT INDEX ft_content ON article(content);
```

适合：

- 文章搜索
- 关键字匹配
- 自然语言检索

不过在真实项目里，如果搜索需求复杂，往往会使用 Elasticsearch 之类的专门搜索引擎，而不是完全依赖数据库全文索引。

#### 3. 按数据组织方式分类

##### 聚簇索引（Clustered Index）

聚簇索引的叶子节点存储的是**整行数据**。在 InnoDB 中，主键索引就是聚簇索引。

这意味着：

- 根据主键查询时，查到叶子节点就拿到了整行数据
- 数据在磁盘上的逻辑组织顺序与主键索引顺序接近
- 一张表只能有一个聚簇索引

##### 非聚簇索引 / 二级索引（Secondary Index）

非聚簇索引的叶子节点存的不是整行数据，而是**索引列值 + 主键值**。如果通过二级索引查到了主键，再根据主键去聚簇索引取整行数据，这个过程就叫**回表**。

```text
二级索引(name) -> 主键 id -> 聚簇索引 -> 整行记录
```

这是面试很高频的点：很多查询看似命中了索引，但如果需要额外字段，仍然可能因为回表而增加成本。

### 第三层：实践应用

#### 4. 按字段个数分类

##### 单列索引

只包含一个字段的索引：

```sql
CREATE INDEX idx_age ON user(age);
```

##### 联合索引（Composite Index）

由多个字段组合而成：

```sql
CREATE INDEX idx_name_age_city ON user(name, age, city);
```

联合索引非常重要，因为它不仅影响能否命中索引，还决定是否符合**最左前缀原则**。比如 `(name, age, city)`：

- `where name = ?` 可以用
- `where name = ? and age = ?` 可以用
- `where age = ?` 一般不能充分利用

#### 5. 覆盖索引也是高频补充点

严格说覆盖索引（Covering Index）不是“索引类型”，而是**查询是否只从索引就能拿到所需列**的一种优化状态。

```sql
CREATE INDEX idx_name_age ON user(name, age);
SELECT name, age FROM user WHERE name = 'Tom';
```

这时查询只访问索引，不需要回表，性能通常更好。面试时如果能主动补一句“覆盖索引不是独立类型，而是一种使用效果”，会显得更严谨。

#### 6. 不同维度的索引概念不要混淆

比如“主键索引”和“B+Tree 索引”并不是并列关系：

- 主键索引是按**用途**分类
- B+Tree 索引是按**底层结构**分类
- 聚簇索引是按**存储组织方式**分类
- 联合索引是按**字段组合方式**分类

同一个索引完全可能同时具有多个标签，例如：

> 一个 InnoDB 表上的主键索引，通常同时是：**主键索引 + B+Tree 索引 + 聚簇索引 + 单列/联合索引中的一种**。

这个总结非常加分。

### 第四层：深入思考

#### 1. 为什么 InnoDB 主流选择 B+Tree

因为数据库查询不仅有等值查询，还有大量范围查询、排序、分页，而 B+Tree 在这些场景下表现都比较均衡。Hash 虽然等值快，但能力太单一，不适合通用 OLTP 查询。

#### 2. 为什么不建议乱建索引

索引不是越多越好。虽然它能加速查询，但也带来代价：

- 占用更多磁盘和内存
- 插入、更新、删除时要维护索引
- 可能导致优化器选错执行计划

所以建索引要围绕查询场景设计，而不是“看到字段就加”。

#### 3. 主键为什么建议短且稳定

因为 InnoDB 的二级索引叶子节点存的是主键值。主键越长：

- 二级索引占用越大
- 树层级可能更高
- 回表成本更高

同时主键频繁更新会导致聚簇索引数据移动，代价比较大，所以通常建议使用短、稳定、递增的主键。

#### 4. 高频追问方向

- 主键索引和唯一索引有什么区别？
- 聚簇索引和非聚簇索引有什么区别？
- 联合索引为什么要遵守最左前缀？
- 覆盖索引和回表是什么？
- 索引为什么会失效？

## 回答思路

### 答题逻辑框架

1. 先说索引类型不能只按一个维度看。
2. 按四个维度展开：用途、结构、组织方式、字段个数。
3. 核心重点放在主键/唯一/普通，B+Tree/Hash/FullText，聚簇/非聚簇，单列/联合。
4. 最后补一句：覆盖索引不是独立类型，而是一种优化效果。
5. 再总结：同一个索引可能同时具有多个分类标签。

### 重点得分点

- 能明确“分类维度”这个答题视角。
- 能说出 InnoDB 主流索引结构是 B+Tree。
- 能说出主键索引在 InnoDB 中是聚簇索引。
- 能说出二级索引叶子节点存主键，查询可能回表。
- 能说出联合索引和最左前缀原则的关系。

### 常见误区

- ❌ 把主键索引、B+Tree、联合索引当成完全并列概念。
- ❌ 说唯一索引绝对不允许任何 `NULL`，回答过于绝对。
- ❌ 说 Hash 索引比 B+Tree 一定更快，忽略适用场景。
- ❌ 把覆盖索引说成一种物理索引结构；它更像查询优化效果。
- ❌ 认为索引越多越好，忽略维护成本。
