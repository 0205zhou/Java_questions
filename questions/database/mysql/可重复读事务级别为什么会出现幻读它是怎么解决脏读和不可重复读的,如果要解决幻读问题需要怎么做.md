# 可重复读事务级别为什么会出现幻读?它是怎么解决脏读和不可重复读的,如果要解决幻读问题需要怎么做?


---

## 联想记忆法

### 记忆口诀/联想

**口诀："脏读脏，重复跳，幻读增；视图锁，串行消，四招解"**

- **脏读脏** = 脏读（Dirty Read）读到的是另一个事务**未提交**的脏数据，可能是"从未存在过"的假数据
- **重复跳** = 不可重复读（Non-Repeatable Read）是同一条记录的**值在跳**（被 UPDATE 改了），前后两次读不一致
- **幻读增** = 幻读（Phantom Read）是同一条件查两次，结果集**行数在增**（多了新 INSERT 的行）——重点在"行"，不在"值"
- **视图锁** = MySQL 解决前两种异常靠两条路：快照读走 MVCC 的 **ReadView 视图**，当前读走**锁**（Next-Key Lock）
- **串行消** = 要 100% 杜绝幻读，最终手段是 **SERIALIZABLE 串行化**
- **四招解** = 解决幻读的实操四招：升级隔离级别、手动加锁（FOR UPDATE）、唯一索引兜底、应用层兜底

### 记忆原理

口诀前半句是"异常三分法"，用三个动词（脏、跳、增）把三种异常的**作用对象**钉死：读到的数据是脏的、记录的值在跳、结果集的行数在增。记住"脏、值、行"三个维度，就永远不会把三种异常搞混——这是全题的第一道分水岭。后半句是"解法三分法"：视图（MVCC）、锁（间隙锁）、串行（SERIALIZABLE）对应三条解决路径，"四招"是落地清单。前后各三个关键词，背诵负担小；面试时只要想起"脏、跳、增"，异常定义就全出来了，再顺着"怎么防"自然引出 MVCC 与锁的机制，不会漏点。

### 关联知识

- **与"隔离级别总览"题关联**：本题与《数据库的事务隔离级别都有哪些》互为姊妹题——那道题覆盖四级隔离级别全景、MVCC 与 Next-Key Lock 的全貌以及 MySQL 默认 RR 的历史原因；本题只深入**三种异常的产生机制与解决手段**，ReadView 和间隙锁只讲机制细节，历史原因等不再展开，建议两题配套记忆
- **与锁体系关联**：记录锁（Record Lock）锁已存在的行、间隙锁（Gap Lock）锁行与行之间的空档、临键锁（Next-Key Lock）两者相加——幻读的本质是"锁不住还没存在的行"，所以才需要间隙锁这个特殊设计
- **与唯一索引关联**：RR 快照读看不见新提交的行，"先查后插"会重复插入，唯一索引（Unique Index）是数据库层最后的兜底
- **与 binlog / 主从复制关联**：RC + ROW 格式 binlog 的组合是生产上替代 RR 的主流方案
- **与应用层关联**：分布式锁、幂等设计是跳出数据库的最终兜底手段

## 深度解答

### 第一层：核心概念

#### 1. 三种异常的精确定义

并发事务同时读写同一批数据时，会产生三种异常，按严重程度排列：

- **脏读（Dirty Read）**：读到**另一个事务尚未提交**的数据。如果对方之后回滚，读到的就是"从未真正存在过"的数据，业务基于它做出的判断全部作废——这是最严重的错误
- **不可重复读（Non-Repeatable Read）**：同一事务内**同一条记录读两次，值不同**。原因是另一个事务在这期间对这条记录执行了 UPDATE 并提交——变化对象是**行内的值**
- **幻读（Phantom Read）**：同一事务内**同一个条件查询两次，结果集行数不同**。原因是另一个事务在这期间插入了满足条件的新行——变化对象是**结果集的行数**

一句话区分："**脏读读的是脏数据，不可重复读是值变，幻读是行数变**"。三者都造成"前后不一致"，但作用对象完全不同：脏读的"脏"来自未提交，不可重复读的"跳"发生在同一行内，幻读的"增"来自新插入的行。答题时先把这个框架立住，后面所有机制都是围绕它展开的。

#### 2. 幻读的本质

幻读这个词本身就暗示了它的可怕之处：多出来的那一行像"幻影"一样——它不在你的任何锁保护范围内，却凭空出现在你的结果集里。

本质原因只有一句话：**记录锁锁不住"还不存在的行"**。事务第一次查询时，按条件把命中的记录加了锁，但另一事务插入的新行在加锁时**根本还不存在**，没有任何锁能锁住一个不存在的对象。SQL 标准正是从这个角度定义隔离级别的：可重复读只要求"锁住读过的行"，不要求锁住"未来插入的行"，所以标准定义下 RR 允许幻读。

### 第二层：底层原理

#### 1. 快照读与当前读：两条完全不同的读路径

InnoDB 的读分两种，这是理解本问的关键前提：

| 读类型 | 对应 SQL | 读什么 | 加锁吗 |
|---|---|---|---|
| 快照读（Snapshot Read，一致性非锁定读） | 普通 SELECT | 按 ReadView 可见性从版本链里挑版本 | 不加锁 |
| 当前读（Current Read，锁定读） | SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE | **最新已提交版本** | 加锁 |

同一个事务里，两条路径读到的结果**可能不一样**——这正是幻读产生的温床。

#### 2. MVCC 如何解决脏读和不可重复读

快照读走 **MVCC（多版本并发控制，Multi-Version Concurrency Control）**：每行数据用 undo log 串成版本链，每次读时先生成（或复用）一个 **ReadView（读视图）**，再按可见性规则沿版本链挑出"当前读应该看到的版本"。

```
undo log 版本链（每行数据）：
  最新版本 ← roll_pointer ← 旧版本 ← roll_pointer ← 更旧版本
  (trx_id=30)                (trx_id=25)             (trx_id=20)

ReadView 可见性判断流程（对链上每个版本比较其 trx_id）：
  trx_id < min_trx_id                → 事务开始前已提交 → 可见，直接返回
  trx_id ∈ m_ids（活跃事务列表）     → 事务还没提交 → 不可见，沿 roll_pointer 找更旧版本
  trx_id ≥ max_trx_id                → ReadView 创建后才开启的事务 → 不可见，继续往前找
  其余情况（min_trx_id ≤ trx_id
  且不在 m_ids 中）                  → 已提交的事务 → 可见
```

- **解决脏读**：未提交事务产生的版本，其 trx_id 一定还在活跃事务列表（m_ids）中，可见性判断直接判"不可见"——快照读永远读不到未提交的数据
- **解决不可重复读**：**RR 事务内第一次快照读时生成 ReadView，之后一直复用**。无论其他事务中途提交了什么，后续所有快照读都只看这一个视图，前后两次读到的版本链位置完全相同，结果自然一致。这纯粹是 MVCC 的功劳，**没花一把锁**

#### 3. 为什么 RR 下还有幻读（SQL 标准视角）

SQL 标准定义隔离级别时只谈"锁"：RR 级别要求事务读过的记录加锁（防止其他事务修改这些行），但**锁不住"未来才插入的新行"**——因为加锁时那行还不存在。所以标准明确指出：RR 允许幻读，只有 SERIALIZABLE 能通过范围锁彻底杜绝。这是"RR 有幻读"的第一个层面，是标准定义层面的答案。

#### 4. MySQL 的 RR 为什么还有幻读（MySQL 视角，关键）

MySQL 的 RR 做得比标准更强：快照读路径下**其实没有幻读**——ReadView 复用，另一个事务插入并提交的新行，对当前事务的所有快照读都不可见。那"MySQL 的 RR 还有幻读"这句话到底对不对？答案是：**幻读没有发生在快照读路径，而是发生在当前读路径**。两个典型场景：

**场景一：先快照读，后当前读（最经典）**。事务先普通 SELECT（快照读，看不见新行），然后执行 UPDATE / DELETE / SELECT ... FOR UPDATE（当前读）。当前读要"处理最新已提交的所有行"，于是另一个事务**已经插入并提交**的新行被扫到、被处理——此时事务第一次"看到"了那行幻影。间隙锁在这里无能为力：**间隙锁只能拦"还没插入的"，拦不住"已经插入并提交的"**。

**场景二：两次当前读之间的窗口**。当前读加的是 Next-Key Lock，正常锁住了区间、挡住并发插入；但如果两条当前读的查询条件不同（第二个条件扫到了第一个没锁住的间隙），另一事务插入提交后，第二次当前读就会多出这行。

所以标准答案是：MySQL 的 RR 下，幻读不是"经常发生"，而是**只在快照读与当前读混用的特定读写序列里被感知**；纯粹的快照读（只查不写）在 RR 下绝对没有幻读。

### 第三层：实践应用

#### 1. 双会话 SQL 演示：幻读发生在哪条路径上

```sql
-- 会话 A（RR）                          -- 会话 B
START TRANSACTION;
SELECT COUNT(*) FROM orders
  WHERE status = 'PENDING';              -- 快照读，返回 3，生成 ReadView

                                         START TRANSACTION;
                                         INSERT INTO orders(status)
                                           VALUES ('PENDING');
                                         COMMIT;

SELECT COUNT(*) FROM orders
  WHERE status = 'PENDING';              -- 仍是 3！复用 ReadView，新行不可见
                                         -- （快照读路径：无幻读）

SELECT COUNT(*) FROM orders
  WHERE status = 'PENDING'
  FOR UPDATE;                            -- 返回 4！当前读扫到并处理了新行
                                         -- （幻读发生在当前读路径）
COMMIT;
```

这个演示同时回答了"为什么 RR 还有幻读"和"为什么平时又感觉不到"：快照读的两次查询完全一致，只有切到当前读的瞬间才看到那行幻影。

#### 2. 解决幻读的方案一：升级隔离级别（SERIALIZABLE）

```sql
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

SERIALIZABLE 下普通 SELECT 也被强制变成当前读（自动加共享锁，相当于 `SELECT ... LOCK IN SHARE MODE`），读写互斥，事务彻底串行，幻读在物理上不可能发生。代价是全库并发趋近于 1，只适合强一致、低并发的场景，生产几乎不用。

#### 3. 解决幻读的方案二：保持 RR + 手动加锁（核心答案）

既然幻读发生在当前读路径，那就让"判断 + 操作"统一走当前读：**业务里先 `SELECT ... FOR UPDATE` 加锁，再做后续判断与写入**。RR 下 InnoDB 对当前读自动加 **Next-Key Lock（临键锁 = 记录锁 + 间隙锁）**，把命中区间连同行与行之间的空档一起锁住，其他事务往这个区间 INSERT 会被阻塞，幻读被物理挡死。

```sql
-- 会话 A（RR）                          -- 会话 B
START TRANSACTION;
SELECT * FROM user
  WHERE age BETWEEN 20 AND 30
  FOR UPDATE;    -- 对区间加 Next-Key Lock

                                         START TRANSACTION;
                                         INSERT INTO user(age) VALUES (26);
                                         -- 阻塞！直到 A 提交
                                         -- （默认锁等待超时 50 秒）
COMMIT;                                  -- A 提交后，B 的 INSERT 才执行
```

锁区间示意（age 索引上已有值 10、25、40）：

```
执行 SELECT ... WHERE age BETWEEN 20 AND 30 FOR UPDATE
加锁结果：
  记录 25 → Next-Key Lock (10, 25]
  记录 40 → Next-Key Lock (25, 40]
被阻塞的插入：age = 15 / 21 / 26 / 35（落在锁定的区间或间隙内）
不受影响：    age = 5 / 45（在未锁定的间隙之外）
```

注意：间隙锁的覆盖范围会**超出查询条件本身**（age = 35 不在 20~30 内也一样被锁），这是间隙锁"锁区间而非锁行"的直观体现。另外，如果条件列**没有索引**，InnoDB 只能全表扫描，会对全表的记录和间隙全部加锁——这就是"无索引 UPDATE/DELETE 锁全表"生产事故的根源。

#### 4. 解决幻读的方案三：唯一索引/唯一约束兜底

针对 RR 最常见的生产事故"**先查后插重复插入**"（快照读看不到新行，业务判断"不存在"后插入，结果插入重复），数据库层最后的兜底是唯一索引：

```sql
CREATE UNIQUE INDEX uk_order_no ON orders(order_no);

-- 方式一：冲突时报错（错误码 1062）
INSERT INTO orders(order_no, status) VALUES ('20260810-001', 'PENDING');
-- 方式二：冲突时吞掉
INSERT IGNORE INTO orders(order_no, status) VALUES ('20260810-001', 'PENDING');
-- 方式三：冲突时转为更新，避免重复行
INSERT INTO orders(order_no, status) VALUES ('20260810-001', 'PENDING')
  ON DUPLICATE KEY UPDATE update_time = NOW();
```

即使业务读到的是旧快照，并发插入也会在唯一索引上撞出冲突——**用数据库的约束兜住并发，而不是指望快照读的可见性**。

#### 5. 解决幻读的方案四：应用层兜底

- **业务串行化**：把"检查 + 插入"整段逻辑放进分布式锁（如 Redisson）临界区，或用消息队列单线程消费，让同一类业务在同一时刻只有一个执行者
- **幂等设计**：接口幂等键 + 幂等表，重复请求直接返回旧结果，从源头杜绝"重复处理产生新行"

生产上的真实组合拳往往是：**RR + FOR UPDATE 或唯一索引管数据库正确性，分布式锁/幂等管业务并发**，分级防御。

### 第四层：深入思考

#### 1. MySQL 的 RR 与 SQL 标准的差异

| 维度 | SQL 标准定义 | MySQL（InnoDB）实现 |
|---|---|---|
| 快照读 | 无此概念，按锁实现 | ReadView 复用，新行不可见，**无幻读** |
| 当前读 | RR 只锁读过的行 | Next-Key Lock 锁整个区间，**挡住并发插入** |
| 结论 | RR 允许幻读 | 绝大多数场景无幻读，是**超标准实现**；仅"先快照后当前读"等特定序列可感知新行 |

#### 2. "MySQL 的 RR 到底有没有幻读"——辩证答案

这道送分题的满分答法是分情况作答：

- **有**：标准定义层面有（锁不住未来的行）；MySQL 当前读路径上，先快照后当前读能感知新插入的行——间隙锁拦不住已插入的行
- **没有**：纯快照读路径下 ReadView 复用，物理上看不见新行；当前读路径有 Next-Key Lock 把区间锁死，并发的插入根本进不来

#### 3. 间隙锁的代价

| 代价 | 机制根源 | 后果 |
|---|---|---|
| 死锁概率上升 | 间隙锁锁的是区间，两个事务交叉锁不同区间后互相等待 | 死锁日志中 Gap Locks 占比极高 |
| 并发度下降 | 锁从"几行"扩大到"整个区间" | 区间内插入全部串行，高并发插入吞吐受限 |
| 锁全表事故 | 条件列无索引，扫描退化为全表 | 全表间隙被锁，整个表的插入瘫痪 |

#### 4. RC + ROW binlog：替代 RR 的主流方案

阿里《Java 开发手册》推荐 RC：RC 当前读不加间隙锁，死锁少；快照读每次都读最新已提交版本，语义贴近业务直觉；配合 `binlog_format=ROW`（记录行变更，从库逐行重放），主从复制同样安全，解决了历史上 statement 格式 binlog 在 RC 下主从不一致的问题。代价是 RC 下**幻读彻底回归**（两次当前读之间可插入新行），需要业务用唯一索引或应用层锁兜底——方案三、四在 RC 下反而成了必需品。

#### 5. 面试官可能的追问方向

- "ReadView 是什么时候生成的？" → RC 每条语句生成新的，RR 事务内首次读生成后一直复用
- "当前读为什么能看到新提交的行？" → 当前读不做 ReadView 版本过滤，直接读最新已提交版本，并给扫描到的区间加锁
- "SERIALIZABLE 是怎么实现的？" → 关闭 autocommit 时，普通 SELECT 自动升级为共享锁当前读（LOCK IN SHARE MODE），读写互斥
- "RC 下还有幻读吗？" → 有，RC 无间隙锁，两次当前读之间可插入新行
- "间隙锁和临键锁什么关系？" → 临键锁 = 记录锁 + 间隙锁，是 RR 下当前读的默认加锁方式

### 重点得分点（面试官考察意图）

1. **异常三分法**（核心得分点）：能一句话说出"脏读读脏、不可重复读值变、幻读行数变"，并点明幻读的本质是"锁不住还没存在的行"——这是全题的地基
2. **快照读与当前读的区分**（全场最亮的机制答案）：能指出普通 SELECT 走 MVCC、FOR UPDATE/UPDATE/DELETE 走当前读，且两者在同一事务内可能结果不同
3. **幻读发生的路径**：能说出"快照读下 RR 其实没有幻读，幻读发生在当前读路径（先快照后当前读），间隙锁拦不住已插入的行"——这是本题最核心的辩证点
4. **解决幻读四招**：能按"数据库层 → 应用层"给全四招，并画出 FOR UPDATE 的加锁区间（记录锁 + 间隙锁覆盖超出查询范围）
5. **MySQL 与 SQL 标准的差异**：能说出 MySQL RR 是"超标准实现"，并给出"有没有幻读"的分情况答案

### 常见误区（扣分点）

| 错误说法 | 正确理解 |
|----------|----------|
| "幻读就是读到的值变了" | 值变是不可重复读；幻读是同一条件结果集**行数**变了（新插入的行） |
| "MySQL 的 RR 就是有幻读，和标准一样" | 快照读路径无幻读（ReadView 复用）；幻读发生在当前读路径，且只在特定读写序列下可感知 |
| "间隙锁能拦住所有幻读" | 间隙锁只能拦**还没插入的**，拦不住已经插入并提交的行 |
| "锁住查到的行就能防幻读" | 记录锁锁不住不存在的行，必须用间隙锁锁"区间" |
| "解决幻读只能升级 SERIALIZABLE" | 升级只是方案一；RR + FOR UPDATE（Next-Key Lock）、唯一索引、应用层锁都是方案 |
| "FOR UPDATE 锁住的只是查到的记录" | RR 下默认加的是 Next-Key Lock（记录锁 + 间隙锁），锁的是整个区间，且覆盖范围超出查询条件 |

### 过渡话术建议

- **从异常到机制**："三种异常里，脏读和不可重复读都是'行内'问题，幻读是'行间'问题——行内问题 MVCC 就能解决，行间问题才需要锁。先把普通 SELECT 和 FOR UPDATE 分清楚..."
- **从标准到实现**："SQL 标准说 RR 允许幻读，因为标准只要求锁住读过的行。MySQL 做得更强：快照读复用 ReadView，新行根本不可见；但当前读要处理最新提交的所有行，所以幻读最后落在了'先快照后当前读'这个缝隙里..."
- **从机制到方案**："那怎么解决？四招：升级 SERIALIZABLE 代价太大；保持 RR 用 SELECT ... FOR UPDATE 让 InnoDB 加 Next-Key Lock 锁住区间；再用唯一索引兜住'先查后插'；最后应用层用分布式锁和幂等做最终防线..."
- **总结过渡**："总结一下：脏读是读到未提交，不可重复读是值在变，幻读是行在长；MVCC 的 ReadView 解决了前两个，幻读的根治靠锁区间 + 唯一索引 + 应用层兜底。MySQL 的 RR 是超标准实现，但并非免费——间隙锁的死锁代价，正是生产上讨论 RC 的原因。"

- **如果面试官打断**：保住"快照读无幻读、幻读在当前读路径、间隙锁拦不住已插入的行"三句话即可，这是本题的灵魂
