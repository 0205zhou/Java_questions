# 项目中MySQL的表设计有什么规范

## 联想记忆法

### 记忆口诀/联想

**口诀："命名见名知义，类型够用就好；主键必设，非空默认；三大字段规范，两准一避；冷热分离，注释齐全。"**

也可以联想成"**盖房子**"：表是房间，字段是家具——家具尺寸要合适（类型规范）、每件家具要有标签（注释）、门牌号要清楚（命名规范）、承重墙不能随便拆（主键/非空约束），住进去之后才发现要添置的东西越少越好（避免频繁 ALTER）。

### 记忆原理

这个口诀按"**建表前 → 建表时 → 建表后**"的时间线组织，把散落的几十条规范压缩成四个抓手：命名、类型、主键与约束、注释与演进。表设计规范本质上是团队协作的契约，记框架比记条目更抗遗忘——面试时按时间线展开，每一步带 2~3 个具体例子，就能覆盖大部分得分点。

### 关联知识

- **与三大范式关联**：1NF 原子性、2NF 消除部分依赖、3NF 消除传递依赖，是表结构拆分的理论依据
- **与索引设计关联**：规范里"频繁查询字段建索引、避免过多索引"直接联动最左前缀、覆盖索引、索引失效
- **与字符集关联**：utf8mb4 选型、排序规则选择，联动 VARCHAR 长度上限计算（65535 字节行限制）
- **与存储引擎关联**：InnoDB 事务与行锁 → 为什么规范强制 InnoDB 而不用 MyISAM
- **与分库分表关联**：预留字段之争、冷热数据分离，是表规范在架构层面的延伸

## 深度解答

### 面试版回答

我们项目里的 MySQL 表设计主要按“**命名统一、类型合适、约束明确、索引克制、可维护可扩展**”这几个维度来做。

首先，命名上要求库名、表名、字段名统一小写下划线，做到见名知义；普通索引用 `idx_`，唯一索引用 `uk_`，布尔字段一般用 `is_xxx`。其次，字段类型会按业务范围选择，不会无脑用 `VARCHAR(255)`，主键通常用 `BIGINT UNSIGNED`，金额用 `DECIMAL`，状态和枚举值用 `TINYINT` 加注释，时间字段统一用 `DATETIME`，字符集统一 `utf8mb4`。

约束方面，每张业务表基本都会有 `id`、`create_time`、`update_time`，需要逻辑删除的表会加 `is_deleted`；字段尽量 `NOT NULL` 并设置默认值，避免 NULL 带来的三值逻辑和统计问题。索引方面，唯一性必须交给数据库唯一索引兜底，普通索引会围绕高频查询条件、排序字段和联合索引最左前缀设计，但不会为了所有字段都建索引，因为索引会影响写入性能。

最后，表和字段都要写清楚注释，状态值必须说明含义；高频大表会考虑冷热数据拆分，避免大字段和频繁查询字段混在一起。整体目标不是追求“规则多”，而是让表结构长期可读、查询稳定、后续扩展成本低。

### 第一层：核心概念

#### 是什么：MySQL 表设计规范是什么、解决什么问题

MySQL 表设计规范（Table Design Convention）是团队对建表行为的统一约定，覆盖**命名、字段类型、主键、约束、索引、注释、字符集/存储引擎**等维度。它解决四个问题：

1. **协作一致性**——多人开发时表结构风格统一，降低阅读与维护成本
2. **性能保障**——合适的类型与索引策略从源头避免慢查询
3. **可演进性**——预留合理的扩展空间，减少破坏性变更
4. **规避踩坑**——把"NULL 三值逻辑"、"隐式转换索引失效"这类已知坑用规范提前挡掉

#### 主流参考规范

最常被引用的是 **阿里巴巴《Java 开发手册》（嵩山版/黄山版）的 MySQL 数据库规约部分**，它分四节：建表规约、索引规约、SQL 语句规约、ORM 映射规约。面试中回答"你们项目的表设计规范"，按阿里的框架展开再补充团队自定义条款即可。

### 第二层：底层原理

#### 1. 命名规范——为什么"见名知义"是硬要求

- 库名、表名、字段名一律**小写 + 下划线分隔**：`user_order`、`order_item`，不用驼峰、不用拼音缩写
- 为什么小写：Windows 下 MySQL 表名默认不区分大小写（`lower_case_table_names=1`），Linux 下默认区分（=0），小写命名可避免跨平台迁移时 `Table doesn't exist` 报错
- 表名不使用复数（阿里规约：`user` 而非 `users`），避免单复数混用引发的心智负担
- 布尔字段用 `is_xxx` 前缀，类型 `TINYINT UNSIGNED`（1 是 0 否）：`is_deleted`、`is_vip`——统一语义，避免 `deleted`/`delete_flag`/`if_delete` 各写各的
- 唯一索引 `uk_` 前缀、普通索引 `idx_` 前缀：从名字就能区分索引类型，排查执行计划时一眼可辨

#### 2. 类型规范——"够用就好"背后的存储原理

- **主键**：统一 `BIGINT UNSIGNED AUTO_INCREMENT`（阿里规约：`id`，单表行数超 500 万或容量超 2GB 才推荐分库分表）。为什么不用 UUID 做主键——InnoDB 是聚簇索引组织表，主键即数据行的物理顺序，UUID 无序导致随机插入、频繁页分裂；自增主键顺序追加写，页利用率高
- **小数**：用 `DECIMAL`，禁止 `FLOAT`/`DOUBLE`——浮点是近似值存储（IEEE 754），金额计算会有精度丢失；DECIMAL 是精确小数
- **字符串**：定长用 `CHAR`，变长用 `VARCHAR`，超长文本用 `TEXT`；VARCHAR 是可变长，不预估长度反而浪费（内存/临时表按最大长度分配）
- **枚举/布尔**：禁止 `ENUM`（阿里规约），用 `TINYINT`——ENUM 加值要 ALTER TABLE，DDL 在大表上代价高，且与 ORM 映射不友好
- **时间**：统一 `DATETIME`（阿里规约强制），不用 `TIMESTAMP`——TIMESTAMP 只有 4 字节，上限 2038-01-19（"2038 问题"），且受时区影响
- **金额**：`DECIMAL`，禁止 FLOAT/DOUBLE（同上，资金安全）
- **字符集**：统一 `utf8mb4`，不用 `utf8`（utf8mb3）——utf8mb3 无法存 emoji 等 4 字节字符
- **NULL**：所有字段定义为 `NOT NULL` + 默认值（阿里规约），理由：
  - NULL 参与 `count(*)`/`count(列)` 结果不同，聚合易出错
  - NULL 参与比较是三值逻辑（NULL != NULL），`where col != 'x'` 会漏掉 NULL 行
  - NULL 列使索引/统计/值比较更复杂，需要额外的标记字节
  - 例外说明：`TEXT`/`BLOB` 等大字段、以及确实存在"无值语义"的字段可用 NULL，但要明确注释

#### 3. 必备三字段与注释规范

- 每张表必备：`id`（主键）、`create_time`（创建时间）、`update_time`（更新时间）。有的团队还加 `create_by`/`update_by`/`is_deleted`（逻辑删除标记）——这是逻辑删除方案的标准配置
- 字段允许适当**冗余**以提高查询性能（阿里规约允许"非频繁修改字段、非 varchar 超长字段"冗余，如订单表冗余商品名）——这是反范式的实践：用空间换 JOIN 成本
- 表和字段一定要加**中文注释**（COMMENT），说明业务含义；枚举值在注释里列出每个值的含义

#### 4. 索引规范

- 业务上具有唯一性的字段，即使是逻辑删除场景，也必须建**唯一索引**（用 `uk_` 前缀），不能只靠应用层防重——唯一索引是数据库层最后一道防线（对应并发防重，如验证码去重就靠唯一索引兜底）
- 超过三个表禁止 JOIN（阿里规约）：多表 JOIN 优化器成本爆炸，字段类型与字符集必须一致避免隐式转换
- 单表索引建议不超过 5 个，单个索引字段不超过 5 个；索引过多会拖慢写入（每次写都要维护所有索引）并占空间
- 页面搜索严禁左模糊或全模糊（`LIKE '%xx'`）——B+ 树按最左前缀组织，左模糊直接失效
- 利用**覆盖索引**减少回表；利用**延迟关联**或子查询优化分页

#### 5. 存储引擎与参数

- 统一 `InnoDB`：支持事务、行级锁、崩溃恢复（redo log）；MyISAM 表锁、不支持事务，已被淘汰
- 统一 `utf8mb4` + 明确的排序规则（如 `utf8mb4_general_ci` 或 8.0 默认 `utf8mb4_0900_ai_ci`）

### 第三层：实践应用

#### 一张符合规范的建表模板

```sql
CREATE TABLE t_order (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    order_no VARCHAR(32) NOT NULL DEFAULT '' COMMENT '业务订单号',
    user_id BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '用户ID',
    product_name VARCHAR(128) NOT NULL DEFAULT '' COMMENT '商品名称(冗余)',
    amount DECIMAL(10, 2) NOT NULL DEFAULT 0.00 COMMENT '订单金额',
    status TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '订单状态:0-待支付 1-已支付 2-已取消',
    is_deleted TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '逻辑删除:0-未删 1-已删',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no),
    KEY idx_user_id_create_time (user_id, create_time)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci
  COMMENT = '订单表';
```

对照检查表：

| 规范点 | 模板中的体现 |
|---|---|
| 主键 BIGINT 自增 | `id BIGINT UNSIGNED AUTO_INCREMENT` |
| 布尔 is_xxx + TINYINT | `is_deleted` |
| 禁 ENUM → TINYINT + 注释枚举值 | `status` 注释列出 0/1/2 含义 |
| 金额 DECIMAL | `amount DECIMAL(10,2)` |
| 必备三字段 | `id` / `create_time` / `update_time` |
| 唯一索引 uk_ 前缀 | `uk_order_no` |
| 联合索引最左前缀 | `idx_user_id_create_time`（按 user_id 查 + 按时间排序可命中） |
| utf8mb4 + InnoDB + 注释 | 表尾声明 + 每字段 COMMENT |

#### 团队如何落地规范

- **Code Review**：DDL 变更走工单/评审，检查命名、类型、索引
- **工具扫描**：如阿里的 SOLAR/Yearning/Archery 等 SQL 审核平台，自动拦截违规 DDL
- **规范文档化**：写入团队 Wiki，新人上手必读

### 第四层：深入思考

#### 1. 为什么要"预留字段之争"说不

阿里规约明确**禁止使用保留字、禁止预留字段**。反对预留字段的理由：

- 预留字段无法提前确定类型与含义，真用的时候往往还是要 ALTER（改类型、改注释）
- 无注释的预留字段会变成"垃圾抽屉"，后来者不敢动也不敢删
- 加列在 MySQL 8.0 的 InnoDB 里是 `INSTANT` 操作（秒级完成，不重建表），"加列慢"的旧理由已不成立

正确做法：真的需要新字段时，通过规范的 DDL 工单加一个语义明确的新列。

#### 2. 逻辑删除 vs 物理删除

规范普遍推荐逻辑删除（`is_deleted` 标记），理由是数据可追溯、误删可恢复、满足审计要求。但要注意两个坑：

- **唯一索引与逻辑删除冲突**：`uk_phone` 在"删除后重新注册同号"场景会撞唯一键——解决方案是"删除时把唯一键值改写"（如 phone 后拼删除时间戳），或引入 `delete_token` 参与唯一索引
- **逻辑删除的数据膨胀**：删除行仍占空间，需要定期归档冷数据（归档表/历史库），这也是"冷热分离"规范的由来

#### 3. 面试官可能的追问方向

- "为什么不建议用外键？" → 阿里规约禁止物理外键（`FOREIGN KEY`）：高并发下外键检查带来额外锁开销，且级联操作不可控；关联关系应在**应用层保证**。但注意分寸：说"互联网场景禁外键"，传统强一致场景仍可用
- "NULL 到底能不能用？" → 说清规范是"尽量 NOT NULL + 默认值"，权衡点是语义（0 和 NULL 是否同义）与三值逻辑风险，体现独立思考
- "为什么 500 万行要分库分表？" → 经验值，本质是 B+ 树层数与缓冲池命中率的权衡；要能接上"不是硬性阈值，3 层 B+ 树约 2000 万行才是理论边界，关键看查询模式"
- "你们项目怎么做的？" → 结合实际：统一 BaseModel（id/create_time/update_time/is_deleted）、SQL 审核平台拦截、DDL 走工单

### 重点得分点（面试官考察意图）

1. **体系化而非报条目**——能按"命名 → 类型 → 主键约束 → 索引 → 引擎字符集"分维度组织，说明真正用过规范而不是背清单
2. **WHY 层面**——每个规范能说出原理：自增主键关联聚簇索引顺序插入、DECIMAL 关联浮点精度、NOT NULL 关联三值逻辑与 count 差异、DATETIME 关联 2038 问题
3. **必备字段张口就来**——id/create_time/update_time/is_deleted，说明有真实开发经验
4. **索引规范联动**——唯一索引兜底防重、最左前缀、索引数量控制，能联动索引专题知识
5. **知道出处**——提一句"参考阿里《Java 开发手册》MySQL 规约"，体现工程素养

### 常见误区（扣分点）

| 错误说法 | 正确理解 |
|---|---|
| "字段用 VARCHAR(255) 随便定" | 按业务上限精确预估，过大会浪费内存/临时表空间并影响索引键长度 |
| "外键保证数据一致性，应该都用" | 互联网高并发场景禁物理外键，关联靠应用层；外键检查有锁开销 |
| "预留几个字段以后用" | 预留字段类型语义不可控，且 MySQL 8.0 加列是 INSTANT 操作，无需预留 |
| "NULL 和空字符串一样" | NULL 是未知值，参与比较走三值逻辑，count(列) 不统计 NULL 行 |
| "TIMESTAMP 和 DATETIME 差不多" | TIMESTAMP 4 字节、上限 2038 年且受时区影响，规范统一用 DATETIME |
| "表设计完就不用管索引" | 索引规范是表设计的一部分，唯一索引必须兜底，避免滥用索引 |
