# 索引失效的情况有哪些?

---

## 联想记忆法

### 记忆口诀/联想

**口诀："左模函数会计算，类型隐转范围断；不等否定 OR 乱串，低选排序也可能换。"**

把索引失效的高频场景压缩成几个触发词：

- **左**：联合索引不满足最左前缀
- **模**：`like '%xx'` 前缀模糊匹配
- **函数**：对索引列做函数、运算、表达式
- **计算**：`age + 1 = 20` 这类对列做计算
- **类型隐转**：字符串列和数字比较导致隐式转换
- **范围断**：联合索引遇到范围查询后，后续列利用受限
- **不等否定**：`!=`、`<>`、`not in`、`not like` 等可能放弃索引
- **OR 乱串**：`or` 两边条件不都能走索引时，优化器可能直接全表扫
- **低选**：区分度太低，优化器认为走索引不划算

### 记忆原理

这些场景表面上很多，其实本质只有三类：

1. **索引树没法有序查找了**：比如函数、计算、前缀模糊。
2. **虽然能查，但代价太高**：比如低选择性、大范围扫描、回表太多。
3. **联合索引顺序被破坏了**：比如不满足最左前缀、范围截断。

把失效原因归纳为“**不能用**”和“**不值得用**”两大类，面试时就不容易答乱。

### 关联知识

- 与 B+Tree 底层结构紧密相关，很多失效场景本质上是在破坏有序性。
- 与联合索引、最左前缀原则直接关联。
- 与执行计划 `EXPLAIN` 相关，判断是否真正命中索引不能只靠猜。
- 与覆盖索引、回表成本、区分度（选择性）强相关。

## 深度解答

### 第一层：核心概念

先强调一个面试里非常重要的认知：**索引失效，不一定是“完全没走索引”，很多时候是“没有按我们预期高效利用索引”，或者优化器判断走索引成本更高，所以放弃了。**

也就是说，索引失效分两种：

1. **语义上难以利用索引结构**：比如对列做函数、最左模糊匹配。
2. **优化器主动放弃索引**：比如扫描行太多，走索引还要大量回表，不如直接全表扫。

### 第二层：底层原理

#### 1. 联合索引不满足最左前缀原则

假设有联合索引：

```sql
CREATE INDEX idx_name_age_city ON user(name, age, city);
```

那么以下查询：

```sql
SELECT * FROM user WHERE age = 20;
```

通常无法高效使用这个联合索引，因为 B+Tree 是先按 `name` 排序，再按 `age`，再按 `city`。跳过第一列去查第二列，相当于目录第一层都没进，自然无法直接定位。

可利用的典型写法是：

```sql
WHERE name = ?
WHERE name = ? AND age = ?
WHERE name = ? AND age = ? AND city = ?
```

所以最左前缀不是死记规则，而是 B+Tree 排序方式决定的。

#### 2. like 以 `%` 开头的模糊查询

```sql
SELECT * FROM user WHERE name LIKE '%tom';
```

这种写法通常很难使用普通 B+Tree 索引，因为索引只能根据有序前缀查找，而 `%tom` 的左边是未知的，无法确定从索引树哪个位置开始扫描。

但如果是：

```sql
SELECT * FROM user WHERE name LIKE 'tom%';
```

这是可以利用索引的，因为它依然保留了左侧前缀的有序性。

#### 3. 对索引列做函数、表达式、计算

```sql
SELECT * FROM user WHERE YEAR(create_time) = 2026;
SELECT * FROM user WHERE age + 1 = 20;
SELECT * FROM user WHERE UPPER(name) = 'TOM';
```

这类 SQL 常导致索引失效。原因是索引里存的是原始列值，而不是函数结果或计算结果。数据库如果要判断 `YEAR(create_time)` 是否等于 2026，往往只能对每一行先算函数，再比较，自然破坏了索引的有序查找能力。

更好的改写方式：

```sql
SELECT * FROM user WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';
SELECT * FROM user WHERE age = 19;
```

面试里这一点非常爱考，因为它直接反映你是否理解“不要在列上做操作，要把操作放到常量这一侧”。

#### 4. 隐式类型转换

```sql
-- phone 是 varchar 类型
SELECT * FROM user WHERE phone = 13800138000;
```

如果字段是字符串类型，而条件传的是数字，MySQL 可能会做隐式转换。很多情况下，数据库需要把列值逐行转换后比较，导致索引无法按预期工作。

规范写法应保持类型一致：

```sql
SELECT * FROM user WHERE phone = '13800138000';
```

这个问题在 Java 项目中很常见，比如前端传字符串，后端又误用数字类型，最终导致线上 SQL 性能异常。

#### 5. 联合索引中范围查询导致后续列利用受限

```sql
CREATE INDEX idx_a_b_c ON t(a, b, c);
SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 3;
```

这里 `a` 可以用，`b` 是范围查询，也可以部分利用索引，但到了 `c`，通常就很难继续按完整有序条件使用索引了。原因是当 B+Tree 走到范围条件时，后续叶子节点对应的是一个区间，`c` 的顺序性已经不再像等值匹配那样稳定。

注意：这不代表 `c` 一定完全没用，在不同版本和不同执行计划下可能有索引下推（ICP）等优化，但面试标准答法通常是：**联合索引遇到范围条件，后面的列利用会明显受限。**

#### 6. 使用 `!=`、`<>`、`not in`、`not like`

```sql
SELECT * FROM user WHERE status != 1;
SELECT * FROM user WHERE name NOT LIKE 'Tom%';
```

这类条件选择范围往往很大，优化器会认为扫描大部分数据还不如直接全表扫。它不是语法上绝对不能用索引，而是**成本上通常不划算**。

#### 7. `or` 条件一边有索引、一边没索引

```sql
SELECT * FROM user WHERE name = 'Tom' OR remark = 'vip';
```

如果 `name` 上有索引，但 `remark` 没有，优化器可能直接放弃索引，因为要同时满足 OR 条件，最终仍需要大量扫描。要么给两边都建合适索引，要么拆成 `UNION ALL` / `UNION` 让优化器更容易处理。

#### 8. 选择性太差，优化器主动放弃索引

例如性别字段：

```sql
SELECT * FROM user WHERE gender = 1;
```

如果表里 50% 甚至 90% 都是 `gender = 1`，走索引可能需要先扫大量索引记录，再回表取完整数据，反而不如直接全表扫描更高效。

所以这里不是“索引坏了”，而是**优化器觉得不用更划算**。

### 第三层：实践应用

#### 9. 排序、分组与索引顺序不一致

```sql
CREATE INDEX idx_name_age ON user(name, age);
SELECT * FROM user ORDER BY age;
```

如果排序字段顺序和索引顺序不匹配，数据库可能无法利用索引完成有序输出，转而使用 `filesort`。这虽然不一定属于最狭义的“where 条件索引失效”，但在面试里通常也算高频场景。

同理，`group by` 如果和索引顺序一致，也更容易利用索引；不一致则可能退化为临时表和额外排序。

#### 10. 覆盖索引与回表成本影响优化器选择

```sql
CREATE INDEX idx_name ON user(name);
SELECT * FROM user WHERE name = 'Tom';
```

虽然 `name` 命中了索引，但 `select *` 需要回表拿所有字段。如果匹配行很多，回表成本会很高，优化器可能最终选择全表扫描。

相反如果写成：

```sql
SELECT name FROM user WHERE name = 'Tom';
```

这可能形成覆盖索引，只访问索引本身，不需要回表，执行计划就更容易稳定命中索引。

#### 11. 用 EXPLAIN 验证，不要靠猜

```sql
EXPLAIN SELECT * FROM user WHERE name LIKE '%tom';
```

面试和工作里都应该强调：是否真正用了索引，要看 `EXPLAIN`，重点关注：

- `type`
- `key`
- `rows`
- `Extra`

如果 `key` 为空、`type=ALL`，通常说明走了全表扫描。

### 第四层：深入思考

#### 1. 索引失效的本质

索引能高效工作的前提，是数据库可以通过有序性快速缩小范围。凡是破坏有序性、放大扫描范围、增加回表代价的写法，都可能导致索引失效或被优化器放弃。

所以索引优化不只是“会不会建”，更关键是“会不会写 SQL”。

#### 2. 为什么有时“用了索引”依然慢

因为命中索引 ≠ 高性能。可能的问题包括：

- 命中的是低选择性索引
- 回表次数太多
- 范围过大
- 排序、分组无法利用索引
- 联合索引顺序设计不合理

这也是为什么线上调优不能只看“有没有索引”，还要看扫描行数和回表成本。

#### 3. 怎么避免索引失效

经验上可以总结为几条：

- 联合索引按最常用查询条件顺序设计
- 避免对索引列做函数、计算、隐式转换
- 模糊匹配尽量避免前置 `%`
- 减少 `select *`，争取覆盖索引
- 用 `EXPLAIN` 验证执行计划
- 对低选择性字段慎建索引

#### 4. 高频追问方向

- 联合索引为什么要遵守最左前缀？
- 范围查询后为什么后续列利用受限？
- 覆盖索引和回表是什么？
- `like '%xx'` 为什么不用索引？
- 如何通过 `EXPLAIN` 判断索引是否生效？

## 回答思路

### 答题逻辑框架

1. 先总述：索引失效分为“不能用”和“优化器不想用”两类。
2. 核心场景按顺序讲：最左前缀、前置 `%`、函数/计算、隐式转换、范围截断。
3. 再补成本型场景：`!=`、`or`、低选择性、回表过多。
4. 最后强调用 `EXPLAIN` 验证，别只靠经验猜。

### 重点得分点

- 能把最左前缀和 B+Tree 排序方式联系起来。
- 能解释为什么函数和计算会破坏索引查找。
- 能说出 `like 'xx%'` 和 `like '%xx'` 的本质区别。
- 能说出索引失效有时是优化器主动选择。
- 能提到覆盖索引、回表和 `EXPLAIN`。

### 常见误区

- ❌ 把索引失效理解成“索引完全没建好”；很多时候是 SQL 写法问题。
- ❌ 说范围查询后后面列“绝对没用”；更准确是“利用受限”。
- ❌ 认为 `!=`、`or` 永远不走索引；应回答“通常不划算，视执行计划而定”。
- ❌ 只背口诀，不解释 B+Tree 为什么会这样。
- ❌ 不看 `EXPLAIN` 就武断判断执行计划。

### 过渡话术

“如果面试官继续追问，通常会问两个方向：一个是‘为什么会失效’，要回到 B+Tree 和最左前缀；另一个是‘怎么解决’，就要讲 SQL 改写、联合索引设计和 `EXPLAIN` 分析。”
