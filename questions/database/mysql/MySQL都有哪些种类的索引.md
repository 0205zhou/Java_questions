# MySQL都有哪些种类的索引?


---

## 联想记忆法

### 记忆口诀/联想

**口诀："四个维度看索引，树哈全空、单联、主唯普前、聚二覆"**

拆开背就是四句话：

- **树哈全空** = 按**数据结构**分：B+ 树索引、Hash 索引、全文索引、空间索引
- **单联** = 按**键数量**分：单列索引、联合索引（复合索引）
- **主唯普前** = 按**逻辑功能**分：主键索引、唯一索引、普通索引、前缀索引
- **聚二覆** = 按**物理存储**分：聚簇索引、二级索引（非聚簇索引）、覆盖索引

### 记忆原理

这个口诀用的是**"分类维度先行"**的框架记忆法：先背四个"字头"，每个字头代表一种分类维度，再顺着字头展开具体类型。认知心理学的"组块化（chunking）"原理——11 种索引名直接背很难，但压缩成"树哈全空 / 单联 / 主唯普前 / 聚二覆"四个组块后，每个组块 3~5 个字，极易入脑。面试时背出四个维度，就等于拿到了答题的骨架，顺着骨架逐类展开，不会遗漏也不会混淆（比如不会把"聚簇索引"归错到逻辑功能维度）。

### 关联知识

- **与《主键索引和唯一索引的区别》关联**：主键索引与唯一索引在"按逻辑功能分"里并排出现，但它们本质上一个是聚簇索引、一个是二级索引——这是两篇的交叉点，详见本仓库《主键索引和唯一索引的区别》
- **与聚簇索引、回表关联**：二级索引查询"先走二级索引拿主键值，再回表查整行"，理解了存储结构才能解释"为什么二级索引查询比主键查询多一次 IO"
- **与 B+ 树关联**：B+ 树是所有索引形式的物理基础，InnoDB 中每种索引（含全文、空间索引之外的普通/唯一/联合/前缀索引）底层都是一棵 B+ 树
- **与最左前缀关联**：联合索引的命中规则（最左前缀原则）是面试高频追问，理解了"索引键排序存储"才能解释"为什么必须从第一列开始用"
- **与覆盖索引关联**：覆盖索引（索引列已包含查询所需全部字段，无需回表）是查询优化的头号利器，常与二级索引的回表代价成对考察

## 深度解答

### 第一层：核心概念

#### 什么是索引

索引（index）是数据库为加速数据检索而建立的一种**有序的辅助数据结构**，本质是"数据目录"：把表数据按某个或多个字段组织成有序结构，查询时先在索引上快速定位，再按定位结果取数，避免全表扫描（full table scan）。

索引解决的问题只有一个：**减少磁盘 IO 次数**。磁盘随机 IO 是数据库性能的最大瓶颈（一次随机 IO 约 10ms 量级），而索引通过有序结构 + 多路分支，把定位数据所需的 IO 从"扫全表"降到"走树高几次"。代价是：占额外存储空间、写入（INSERT/UPDATE/DELETE）时需要同步维护索引，所以索引不是越多越好。

#### 索引分类总览（先总后分）

MySQL 官方与业界通常从四个维度给索引分类：

| 分类维度 | 具体类型 |
|---|---|
| 按数据结构 | B+ 树索引、Hash 索引、全文索引（FULLTEXT）、空间索引（SPATIAL） |
| 按索引键数量 | 单列索引、联合索引（composite index，又称复合索引） |
| 按逻辑功能 | 主键索引（PRIMARY KEY）、唯一索引（UNIQUE）、普通索引（INDEX）、前缀索引 |
| 按物理存储 | 聚簇索引（clustered index）、二级索引（secondary index，非聚簇索引）、覆盖索引（covering index） |

注意：同一个索引可以同时属于多个维度，比如"主键索引"既是逻辑功能维度的类型，也是物理存储维度的**聚簇索引**，还可以是联合索引（联合主键）。回答时先给这个总览，再逐类展开，是标准"先总后分"结构。

### 第二层：底层原理

#### 按数据结构分（重点）

**① B+ 树索引（B+Tree Index）——MySQL 默认、InnoDB 主力**

B+ 树是多路平衡查找树，MySQL 所有普通/唯一/联合/前缀索引的默认实现。结构如下（文字架构图）：

```
                    ┌──────────────┐
                    │   根节点(非叶子) │  只存索引键(不含数据)
                    │   [10] [20]  │
                    └──────┬───────┘
            ┌──────────────┼──────────────┐
       ┌────┴─────┐   ┌────┴─────┐   ┌────┴─────┐
       │ 内节点     │   │ 内节点     │   │ 内节点     │   只存键 + 子节点指针
       │[1][5][8] │   │[11][15]  │   │[21][25]  │
       └────┬─────┘   └────┬─────┘   └────┬─────┘
            │      叶子节点全部在同一层，由双向链表相连
       ┌────┴───────────────────────────────┴────┐
       │ 叶子节点: [1|row] [2|row] ... [25|row]     │  存全部数据(键+完整记录/主键值)
       │ ←────── 双向链表，支持范围扫描 ──────→     │
       └──────────────────────────────────────────┘
```

关键特征，记住这五点：

- **多路平衡**：每个节点可存多个键（页大小默认 16KB，可容纳上千个键），树"矮胖"，树高通常 3~4 层，百万级数据 3 次磁盘 IO 即可定位
- **非叶子节点只存索引键**，不存数据 → 单页能容纳更多键 → 扇出（fan-out）大 → 树更矮
- **叶子节点存全部数据**（InnoDB 中：聚簇索引存整行，二级索引存主键值）
- **叶子节点间用双向链表相连** → 范围查询（BETWEEN、>、<）只需在叶子层顺序遍历，不用回溯
- **节点大小 = 页大小（16KB）** → 一次 IO 读入一页，节点间 IO 次数即树高，把"磁盘 IO"优化到极致

**② Hash 索引**

基于哈希表，等值查询（`WHERE col = x`）理论 O(1)；但**不支持范围查询、不支持排序、不支持最左前缀匹配**，且哈希冲突需要链表/开放寻址处理。注意两点易错细节：

- MEMORY 引擎默认索引类型是 Hash
- **InnoDB 不支持用户手动创建 Hash 索引**——你写 `USING HASH` 会被静默转成 B+ 树；InnoDB 内部只有一个由引擎自动维护的**自适应哈希索引（adaptive hash index，AHI）**：当某个等值查询热点命中频繁时，InnoDB 自动在 B+ 树上建一层哈希缓存加速，用户无法干预

**③ 全文索引（FULLTEXT Index）**

基于**倒排索引（inverted index）**思想：索引记录"词 → 文档（行）"的映射，而非"值 → 位置"。用 `MATCH (col) AGAINST ('关键词')` 查询。历史背景：MyISAM 时代的招牌特性，MySQL 5.6 起 InnoDB 也支持；中文需要分词插件（如 ngram、ik）支持，因为倒排索引的前提是分词。

**④ 空间索引（SPATIAL Index）**

基于 **R-Tree**（空间数据专用树），用于地理/几何数据（POINT、LINESTRING、POLYGON 等空间数据类型），支持 `MBRContains` 这类空间函数查询。MyISAM 与 InnoDB（5.7+）均支持。

#### 按索引键数量分

- **单列索引**：索引只有一列
- **联合索引/复合索引（composite index）**：索引包含多列，如 `(a, b, c)`。注意它是"一列一组键"整体有序：先按 a 排序，a 相同按 b，b 相同按 c
- **最左前缀原则（leftmost prefix）**：命中规则以 `(a, b, c)` 为例——

| WHERE 条件 | 索引使用情况 |
|---|---|
| `a = 1` | 完整使用 |
| `a = 1 AND b = 2` | 完整使用 |
| `a = 1 AND b = 2 AND c = 3` | 完整使用 |
| `a = 1 AND c = 3`（跳过 b） | 只用 a 列定位，c 无法走索引（会被二次过滤） |
| `b = 2`（不带 a） | 完全不使用（除非走索引下推，见第四层） |

原因：索引键按"第一列优先"整体排序，跳过了第一列，后续列的有序性无从利用。这就是"最左前缀"的"最左"二字含义。

#### 按逻辑功能分

| 类型 | 定义要点 |
|---|---|
| 主键索引（PRIMARY KEY） | 每表至多一个；建主键时自动创建；列必须非空（NOT NULL） |
| 唯一索引（UNIQUE） | 可多个；建唯一约束时自动创建；**允许 NULL**（MySQL 中 NULL 与 NULL 互不相等，可存多个 NULL） |
| 普通索引（INDEX） | 无唯一性要求，纯粹加速查询 |
| 前缀索引（prefix index） | 只对字符串字段**前 N 个字符**建索引，如 `INDEX (email(10))`；适用于长字符串字段（省空间、省比较成本），但要保证前缀**区分度（cardinality）**足够，否则索引选择性差、优化器可能不用 |

#### 按物理存储分（重点）

InnoDB 表数据整体就是一棵以主键排序的 B+ 树，这一层必须讲透：

**① 聚簇索引（clustered index）**

- InnoDB 的主键索引就是聚簇索引：**叶子节点直接存整行数据**，数据即索引，表本身按主键物理有序
- 每表**只能有一个**聚簇索引（数据只能按一种顺序物理存放）

**② 二级索引/非聚簇索引（secondary index）**

- 所有非主键索引（唯一、普通、联合、前缀）都是二级索引：**叶子节点只存索引键 + 主键值**（而非整行）
- 查询流程：先在二级索引 B+ 树上定位主键值，再拿主键值去聚簇索引查整行——多出来的这一步叫**回表（table lookup / book lookup）**

```
聚簇索引(主键索引)            二级索引(如 uk_email)
┌───────────────┐            ┌───────────────┐
│ [1][5][9]     │            │ [a@x][3]      │
└───────┬───────┘            └───────┬───────┘
        │                            │
┌───────┴───────────────┐    ┌───────┴───────────────┐
│ 叶子: [1|整行数据]      │    │ 叶子: [a@x|主键值3]    │
│       [5|整行数据]      │    │       [b@y|主键值7]    │
│ 数据即索引，无需回表    │    │ 查主键值 → 回表到左边   │
└───────────────────────┘    └───────────────────────┘
```

**③ 覆盖索引（covering index）**

如果查询所需的列**全部包含在二级索引键里**（含主键值），那么二级索引"自给自足"，直接返回索引里的数据，**无需回表**——这就是覆盖索引。例如 `SELECT email FROM user WHERE email = 'a@x'`（索引为 `uk_email`），二级索引里有 email 和主键值，直接返回 email，不回表。它是查询优化的头号利器。

### 第三层：实践应用

#### 建索引 SQL 示例

```sql
-- 建表时创建
CREATE TABLE user (
    id BIGINT NOT NULL AUTO_INCREMENT,
    email VARCHAR(64),
    name VARCHAR(32),
    city VARCHAR(32),
    age INT,
    PRIMARY KEY (id),                                  -- 主键索引(聚簇)
    UNIQUE KEY uk_email (email),                       -- 唯一索引(二级)
    KEY idx_city (city),                               -- 普通索引(二级)
    KEY idx_name_prefix (name(5)),                     -- 前缀索引
    KEY idx_city_age (city, age)                       -- 联合索引(最左前缀)
) ENGINE = InnoDB;

-- 已有表上追加
ALTER TABLE user ADD INDEX idx_age (age);
ALTER TABLE user ADD UNIQUE INDEX uk_email2 (email);
ALTER TABLE user ADD FULLTEXT INDEX ft_content (content);   -- 全文索引
ALTER TABLE user ADD SPATIAL INDEX sp_loc (location);        -- 空间索引

-- 独立语句形式
CREATE INDEX idx_name ON user (name);
CREATE FULLTEXT INDEX ft_content ON user (content);
```

#### 最佳实践

- **区分度优先**：索引列的选择性（distinct 值 / 总行数）越高越好，越低优化器越可能弃用
- **联合索引列序**：把查询最频繁、区分度最高的列放最左；`(a, b)` 联合索引可同时覆盖 `a` 与 `a+b` 两种查询，即"一索引多用"
- **避免冗余索引**：已有 `(a, b)` 时，再建单独的 `a` 索引就是冗余（前者已含 a 的最左前缀能力）
- **前缀索引用于长字段**：如邮箱、URL，取前 N 字符建索引，注意区分度验证
- **查询写法配合**：让索引列保持"裸列"，避免函数包裹、隐式类型转换、`LIKE '%xx'` 等导致索引失效（详见第四层）

### 第四层：深入思考

#### 1. 为什么 InnoDB 选 B+ 树而不是其他结构

| 候选结构 | 为什么不行 / 对比结论 |
|---|---|
| **Hash** | 等值 O(1) 快，但不支持范围查询与排序；而 SQL 中范围条件极其常见 |
| **B 树** | 非叶子也存数据，单页能容纳的键少，树更高、IO 更多；且叶子间无链表，范围查询需中序遍历，慢 |
| **红黑树 / AVL** | 二叉树，树高随数据量对数增长——1 亿数据树高约 27 层；且节点在磁盘上随机分布，27 次随机 IO 不可接受；它们是内存数据结构，MySQL 是磁盘数据库 |
| **跳表** | 多级索引指针，空间开销大，主要服务于内存场景（Redis） |

结论一句话：**B+ 树把"树高"压到 3~4 层（百万数据 3 次 IO），把"范围查询"变成叶子链表的顺序扫描，是磁盘 IO 模型下的最优解。**

#### 2. 回表与索引下推（index condition pushdown，ICP）

- 回表代价：每命中一行多一次主键查询 IO。优化手段：覆盖索引（首选）、索引下推
- **索引下推（ICP，MySQL 5.6+）**：联合索引查询时，把 WHERE 里"非最左的其余条件"下推到存储引擎层，在**索引遍历过程中**先过滤掉不满足条件的记录，减少回表次数。例：`(a, b)` 索引 + `WHERE a = 1 AND b > 5`——不下推时每行 a=1 都回表再过滤 b；下推后引擎层直接判断 b，仅少数行回表

#### 3. 索引失效的常见场景（简列）

| 场景 | 原因 |
|---|---|
| `WHERE YEAR(create_time) = 2026` | 函数包裹索引列，索引键顺序被破坏 |
| `WHERE phone = 13812345678`（phone 为 VARCHAR，参数为数字） | 隐式类型转换，比较时对列做转换 |
| `LIKE '%abc'` | 前导模糊匹配，无法利用有序性（`'abc%'` 可以） |
| 联合索引跳列 / 不带最左列 | 违背最左前缀原则 |
| 优化器判定走索引不如全表扫描 | 选择性过低时优化器主动弃用 |

#### 4. 面试官可能的追问方向

- **"联合索引 (a,b,c) 什么情况只能部分命中？"** → 最左前缀原则 + 跳过中间列（见第二层表格）
- **"覆盖索引一定比回表快吗？"** → 是，少一次主键树查找；但覆盖索引的键要"恰好覆盖查询列"，设计时需要按查询反推
- **"冗余索引的危害？"** → 占空间 + 写入维护成本翻倍，MySQL 8.0 可借助 `information_schema` 或性能分析工具发现冗余索引
- **"主键索引和唯一索引到底差在哪？"** → 详见本仓库《主键索引和唯一索引的区别》

## 回答思路

### 答题逻辑框架

面试时按"总-分-总"递进，总时长控制在 **3-4 分钟**：

```
┌──────────────────────────────────────────────────────┐
│ 第一层（20秒）：一句话定义 + 分类总览                  │
│ "索引是有序辅助结构，分四个维度：                     │
│  数据结构/键数量/逻辑功能/物理存储"                   │
├──────────────────────────────────────────────────────┤
│ 第二层（90秒）：按数据结构展开（重点）                 │
│ B+树(默认,讲透五特征+架构图) → Hash → 全文 → 空间     │
├──────────────────────────────────────────────────────┤
│ 第三层（60秒）：按物理存储展开（加分）                 │
│ 聚簇(叶子存整行,每表一个) vs 二级(叶子存主键,要回表)  │
│ → 覆盖索引免回表                                     │
├──────────────────────────────────────────────────────┤
│ 第四层（40秒）：联合索引最左前缀 + 最佳实践            │
│ (a,b,c) 命中规则 → 区分度/冗余索引                    │
└──────────────────────────────────────────────────────┘
```

### 重点得分点（面试官考察意图）

1. **B+ 树五特征**（核心得分点）：多路平衡、非叶子只存键、叶子存全部数据、叶子双向链表、节点=16KB 页——能画出结构图并说出"矮胖、扇出大、IO 少"即达标

2. **聚簇 vs 二级的本质**：能说出"叶子存整行 vs 叶子存主键值"并引出回表与覆盖索引——这是 InnoDB 索引模型的核心，也是后续所有索引问题的地基

3. **最左前缀命中规则**：能完整给出 (a,b,c) 四种条件下的命中情况——面试官最爱现场出组合题

4. **维度区分不混淆**：能把"主键索引是逻辑功能类型、同时也是聚簇索引"这种跨维度属性说清楚——体现体系化理解

5. **对比选型**：能说出"为什么不用哈希/红黑树"——证明你理解 B+ 树是为磁盘 IO 而生的

### 常见误区（扣分点）

| 错误说法 | 正确理解 |
|----------|----------|
| "InnoDB 可以手动建 Hash 索引" | InnoDB 不支持用户建 Hash 索引（会自动转 B+ 树），只有 MEMORY 引擎默认用 Hash；InnoDB 只有内部自维护的自适应哈希索引 AHI |
| "二级索引叶子存整行数据" | 二级索引叶子存"索引键 + 主键值"，取整行需回表 |
| "聚簇索引可以建多个" | 每表只能一个聚簇索引（数据只能按一种顺序物理存放） |
| "前缀索引随便取前几位" | 必须验证区分度，区分度低会白建甚至帮倒忙 |
| "索引越多查询越快" | 索引占空间且拖慢写入，需权衡；冗余索引是负资产 |
| "LIKE '%xx' 能用索引" | 前导 % 无法利用有序性，索引失效（'xx%' 可以） |

### 过渡话术建议

- **从定义到分类**："索引本质是有序的辅助数据结构，减少磁盘 IO。MySQL 的索引可以从四个维度分类——数据结构、键数量、逻辑功能、物理存储，我按维度展开讲..."
- **从结构到设计**："B+ 树的精髓是叶子节点用双向链表串起来，所以范围查询天然高效——这也解释了为什么 InnoDB 不用哈希：哈希等值 O(1)，但 SQL 里范围条件太常见了..."
- **从存储到查询**："聚簇索引叶子存整行，二级索引叶子只存主键值，所以二级索引查询多一步回表。要省这一步，就让索引'覆盖'查询所需的所有列——这就是覆盖索引..."
- **总结过渡**："所以回答'有哪些索引'，核心是 B+ 树 + 聚簇/二级这对存储模型，其他类型都是在这两个地基上的变体。"
