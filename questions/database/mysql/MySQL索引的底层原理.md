# MySQL索引的底层原理?

---

## 联想记忆法

### 记忆口诀/联想

**口诀："页里存键和指针，叶子存值链成串；根到叶子少 IO，二级回表找主键，联合索引守最左。"**

这句话覆盖 InnoDB B+Tree 索引最核心的五件事：

- **页里存键和指针**：非叶子节点主要保存索引键和子页指针。
- **叶子存值链成串**：叶子节点保存索引记录，并按顺序通过双向链表连接。
- **根到叶子少 IO**：B+Tree 通过高扇出降低树高，减少磁盘 IO。
- **二级回表找主键**：二级索引叶子节点存主键值，需要回到聚簇索引取整行。
- **联合索引守最左**：联合索引按多列排序，遵守最左前缀原则。

### 记忆原理

索引原理不要从“树长什么样”开始死背，而要沿着一次查询来记：先从根节点查到中间节点，再到叶子；如果是主键索引，叶子直接拿整行；如果是二级索引，拿到主键后再回表。最后把范围查询、联合索引和覆盖索引放进这条路径里，所有追问都能顺着查询链路解释。

### 关联知识

- 与 InnoDB 页、Buffer Pool、磁盘 IO 相关。
- 与聚簇索引、二级索引、回表和覆盖索引相关。
- 与最左前缀、索引下推、范围查询相关。
- 与 `EXPLAIN`、选择性和优化器成本模型相关。
- 与 MyISAM 的非聚簇索引组织方式相关。

## 深度解答

### 第一层：核心概念

索引（Index）是一种按照特定字段组织的数据结构，用额外的存储空间换取更快的定位速度。没有索引时，数据库通常需要从表的第一行开始逐行判断条件，时间复杂度接近 O(n)；有合适的 B+Tree 索引后，可以从根节点开始逐层缩小范围，定位到目标记录，复杂度通常接近 O(log n)。

不过这个说法只是抽象模型。真实数据库的数据存放在磁盘页中，索引性能的关键不只是“比较次数少”，还包括：**一次查询需要访问多少个页、这些页是否在 Buffer Pool 中、是否需要大量回表。**

### 第二层：底层原理

#### 1. 为什么不用二叉树或普通红黑树

如果使用普通二叉搜索树，数据量很大时树可能退化，树高变得很高；即使使用平衡二叉树，每个节点的分支也很少。数据库索引主要面向磁盘和页式存储，访问一个节点通常意味着一次页访问或缓存查找，因此树高非常重要。

B+Tree 每个节点可以存放很多 key 和指针，具有很高的扇出。节点通常对应一个或多个数据库页，根到叶子的层数较少，查询就能用更少的随机 IO 找到目标范围。

#### 2. B+Tree 的结构

```text
                         根节点
                    [20 | 50 | 80]
                 /       |       |       \
             子节点    子节点    子节点    子节点
           [1..19]  [20..49] [50..79] [80..]
                ↓        ↓        ↓        ↓
        叶子节点按 key 排序，并通过链表连接
        [1,2,3] ↔ [20,21,22] ↔ [50,51,52] ↔ [80,81,82]
```

B+Tree 和 B-Tree 的重要区别是：B+Tree 的真实数据记录主要集中在叶子节点，非叶子节点负责导航。这样每个非叶子节点可以放更多索引键，树的扇出更高；同时叶子链表让范围查询可以从起点向后顺序扫描。

#### 3. 一次等值查询经历了什么

假设有：

```sql
SELECT * FROM user WHERE id = 100;
```

InnoDB 大致会执行：

```text
1. 从 Buffer Pool 查找索引页，未命中则从磁盘读入
2. 在根节点定位 key=100 应进入的子页
3. 继续在中间节点向下查找
4. 到达叶子节点，定位 id=100
5. 如果是主键聚簇索引，直接取出整行
6. 返回结果
```

整个过程的关键是避免扫描全表，且树高通常不大。热数据和索引页如果已经在 Buffer Pool 中，查询甚至不需要磁盘 IO。

#### 4. B+Tree 为什么适合范围查询

```sql
SELECT * FROM user WHERE id >= 100 AND id < 200;
```

数据库先通过树找到 `id=100` 的第一个叶子记录，然后沿着叶子节点之间的有序链表向后扫描，直到 `id >= 200`。它不需要从根节点反复查找每个 id。

这也是 Hash 索引不适合范围查询的原因：Hash 只保证根据等值 key 定位，不保留 key 的全局有序关系。

#### 5. InnoDB 的聚簇索引

InnoDB 的主键索引是聚簇索引，叶子节点中保存完整行数据：

```text
主键 B+Tree
  叶子：[id, name, age, create_time, ...]
```

因此主键查询定位到叶子页后，不需要再访问另一棵树。也正因为整行数据跟着主键索引组织，InnoDB 一张表只能有一个聚簇索引。

如果没有显式主键，InnoDB 会选择非空唯一索引作为聚簇索引；如果连合适的唯一索引也没有，InnoDB 会生成隐藏的 row ID。生产表通常应显式设计主键，避免不可控的隐藏结构。

#### 6. 二级索引与回表

假设建立：

```sql
CREATE INDEX idx_name ON user(name);
SELECT id, name, age FROM user WHERE name = 'Tom';
```

二级索引叶子节点通常保存：

```text
[name, 主键 id]
```

查询流程是：

```text
二级索引 idx_name 找到 name='Tom'
  ↓
拿到主键 id
  ↓
回到主键聚簇索引查找 id
  ↓
读取完整行
```

第二次访问聚簇索引的动作就叫回表（回到主键索引查数据）。如果一次命中很多行，回表次数就很多，性能可能明显下降。

#### 7. 覆盖索引如何避免回表

如果索引包含查询需要的全部列：

```sql
CREATE INDEX idx_name_age ON user(name, age);
SELECT name, age FROM user WHERE name = 'Tom';
```

那么二级索引叶子节点已经包含 `name` 和 `age`，数据库可以直接返回结果，不必再访问聚簇索引，这叫覆盖索引（Covering Index）。覆盖索引不是一种独立的 B+Tree 结构，而是查询所需列被索引完全覆盖时形成的优化效果。

#### 8. 联合索引的底层排序

```sql
CREATE INDEX idx_a_b_c ON t(a, b, c);
```

联合索引不是三棵独立索引，而是按 `(a, b, c)` 的字典序排序：

1. 先按 `a` 排序
2. `a` 相同的记录再按 `b` 排序
3. `a`、`b` 都相同的记录再按 `c` 排序

所以：

- `where a = 1` 可以定位
- `where a = 1 and b = 2` 可以进一步缩小范围
- `where b = 2` 缺少第一层 `a`，通常不能直接利用完整有序结构

这就是最左前缀原则。它不是数据库硬编码的口诀，而是联合索引排序结构自然推导出来的结果。

### 第三层：实践应用

#### 9. 范围查询为什么影响后续列

```sql
CREATE INDEX idx_a_b_c ON t(a, b, c);
SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 3;
```

`a=1` 可以精确定位；`b>10` 把查询扩大为一个连续范围；进入范围以后，`c` 不再能像等值条件那样继续把 B+Tree 的有序范围切得很细。因此通常说：联合索引遇到范围查询后，后续列的索引利用受限。

实际执行还可能有索引下推（Index Condition Pushdown，ICP），让存储引擎在索引扫描阶段提前判断部分条件，减少回表，但这不等于完全恢复了后续列的有序定位能力。

#### 10. 索引下推（ICP）

没有 ICP 时，Server 层可能先根据前导列找到很多候选主键，再逐条回表判断后续条件；有 ICP 时，存储引擎可以在扫描二级索引时利用能判断的条件，过滤掉一部分候选，再回表。

它优化的是“减少回表”，不是改变 B+Tree 的排序结构。面试中要把这两个概念分开。

#### 11. 查询优化器为什么可能不用索引

索引不是命中率越高越好。优化器会估算全表扫描和索引扫描的成本：

- 预计匹配行太多
- 回表次数太多
- 索引选择性太差
- 统计信息过期
- 排序或分组还需要额外操作

在这些情况下，即使表上存在索引，优化器也可能选择 `type=ALL` 的全表扫描。因此排查索引问题时要看 `EXPLAIN`，而不是只看建表语句。

#### 12. 为什么主键通常建议递增

InnoDB 聚簇索引的叶子节点按主键顺序组织。递增主键插入时，大部分新记录追加到索引末端，页分裂较少；随机主键插入可能不断在中间页写入，引发页分裂、数据移动和更多随机 IO。

这不是说所有系统都必须用自增主键，而是要认识到随机 UUID 等主键会带来索引局部性和写入放大的代价。可以根据分布式场景选择有序 ID 或其他折中方案。

### 第四层：深入思考

#### 1. 索引为什么会让写入变慢

每次插入、更新、删除不仅要修改表数据，还要维护所有相关索引。更新索引列可能改变 B+Tree 中记录的位置，甚至触发页分裂。因此索引本质上是用写入和存储成本换取查询速度。

#### 2. InnoDB 与 MyISAM 的索引差异

- InnoDB：主键索引叶子存整行，二级索引叶子存主键；支持事务和 MVCC。
- MyISAM：索引叶子通常存数据文件地址，主键索引和普通索引在组织形式上没有 InnoDB 那种“聚簇索引”区别。

因此同一条查询在两个存储引擎中的回表含义和成本不能完全照搬。

#### 3. B+Tree 索引的边界

B+Tree 适合结构化字段的等值、范围、排序和前缀查询，但不适合复杂文本相关性搜索、跨字段模糊检索和部分地理空间检索。遇到这些需求，应评估全文搜索引擎或专用索引结构，而不是不断堆叠关系型数据库索引。

## 回答思路

### 答题逻辑框架

1. 先定义索引：用空间和维护成本换取查询定位速度。
2. 说明 InnoDB 主要使用 B+Tree，并画出根节点、叶子节点和叶子链表。
3. 顺着一次查询讲主键聚簇索引和二级索引回表。
4. 再讲覆盖索引、联合索引最左前缀、范围查询和索引下推。
5. 最后补充 Buffer Pool、优化器成本和递增主键。

### 重点得分点

- 能说出 B+Tree 高扇出、树高低、磁盘 IO 少。
- 能说出叶子节点有序链表支持范围查询。
- 能分清聚簇索引叶子存整行、二级索引叶子存主键。
- 能解释回表和覆盖索引。
- 能从字典序解释联合索引最左前缀，而不是死背结论。

### 常见误区

- ❌ 说 B+Tree 的每个节点都存完整行数据；InnoDB 主要在聚簇索引叶子存整行。
- ❌ 认为二级索引叶子直接存物理地址；InnoDB 通常存主键值。
- ❌ 说用了二级索引就一定只查一棵树；需要完整行时还要回表。
- ❌ 把覆盖索引说成另一种树结构；它是查询被索引覆盖的状态。
- ❌ 说范围条件后的列绝对完全不能用；应考虑索引下推等优化。

### 过渡话术

“结构讲清楚以后，很多索引失效现象就能自然推导出来：前缀模糊是因为无法确定树的起点，跳过联合索引第一列是因为破坏了字典序，而回表过多则是优化器选择全表扫描的成本原因。”
