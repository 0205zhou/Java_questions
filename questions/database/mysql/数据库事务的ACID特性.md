# 数据库事务的ACID特性?

---

## 联想记忆法

### 记忆口诀/联想

**口诀："A 要么全做，C 前后一致，I 并发隔开，D 提交不赖。"**

再进一层记实现：**"原子靠 undo，持久靠 redo，隔离靠锁与 MVCC，一致靠约束和规则兜。"**

- **A = Atomicity（原子性）**：事务中的操作要么全部成功，要么全部失败回滚。
- **C = Consistency（一致性）**：事务执行前后，数据库都处于合法状态。
- **I = Isolation（隔离性）**：并发事务互不干扰。
- **D = Durability（持久性）**：事务提交后结果永久生效，即使数据库崩溃也不能丢。

### 记忆原理

记忆时不要把 ACID 当作四个孤立名词，而是记成一条事务的完整命运线：**开始执行时不能只做一半（A），执行过程中不能和别人串台（I），执行完以后状态必须正确（C），提交以后还不能反悔（D）。** 其中 A、I、D 更像手段，C 是最终目标。

### 关联知识

- 与 MySQL undo log、redo log、binlog 两阶段提交强相关。
- 与事务隔离级别、脏读、不可重复读、幻读强相关。
- 与 Spring `@Transactional` 直接相关，注解本质是在应用层使用数据库事务能力。
- 与分布式事务相关，单机 ACID 很强，但跨服务后要考虑 BASE、最终一致性等方案。

## 深度解答

### 第一层：核心概念

事务（Transaction）是把多条操作打包成一个逻辑整体，要么全部成功，要么全部失败。数据库之所以需要事务，是因为现实业务里大量操作不能只做一半。最经典的例子就是转账：

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

如果第一条扣款成功、第二条加款失败，那么资金就不守恒了。所以事务必须提供 ACID 四大特性。

#### 1. Atomicity：原子性

原子性强调一个事务是不可分割的工作单元。事务中的多条 SQL 不允许只执行一部分，出现异常必须整体回滚。

例如下单场景里通常会有：

1. 扣减库存
2. 创建订单
3. 扣减余额
4. 记录流水

只要其中一步失败，前面的步骤都应该撤销。否则就会出现“扣了库存没订单”或者“扣了钱但没发货”的脏状态。

#### 2. Consistency：一致性

一致性表示事务执行前后，数据库都必须满足完整性约束和业务规则。比如：

- 主键不能重复
- 金额不能凭空增减
- 订单必须关联合法用户
- 库存不能减成负数

一致性不是某一个日志独立保证的，而是原子性、隔离性、持久性，加上主键、唯一约束、外键、业务校验共同保证的结果。

#### 3. Isolation：隔离性

数据库通常是并发执行事务的。如果多个事务同时修改同一份数据，而彼此完全不隔离，就会出现脏读、不可重复读、幻读等并发问题。隔离性的目标，就是让每个事务看起来像“独占数据库”一样执行。

#### 4. Durability：持久性

持久性要求事务一旦提交成功，结果就必须永久保存。即使数据库进程崩溃、服务器断电、实例重启，已经提交的数据也不能丢失。

### 第二层：底层原理

#### 原子性为什么靠 undo log

MySQL InnoDB 在修改数据前，会先记录旧值或回滚所需信息到 **undo log（回滚日志）**。如果事务失败或显式执行 `ROLLBACK`，数据库就按照 undo log 反向恢复现场。

```text
事务开始
  ↓
记录旧值到 undo log
  ↓
修改 Buffer Pool 中的数据页
  ↓
如果失败 → 按 undo log 回滚
```

这就是原子性的根本：**先留后路，再做修改。**

undo log 还有一个高频面试点：它不只是回滚用，还被 MVCC 复用来构建版本链，所以它同时服务原子性和隔离性。

#### 持久性为什么靠 redo log + WAL

如果每次事务提交都立刻把完整数据页刷盘，随机 IO 成本会很高。InnoDB 的做法是 WAL（Write-Ahead Logging，预写日志）：

1. 先把修改写到内存中的数据页
2. 同时顺序追加 redo log
3. 提交时先保证 redo log 落盘
4. 数据页之后再异步刷盘

```text
用户提交事务
  ↓
redo log buffer 写入 redo log file
  ↓
fsync 落盘成功
  ↓
事务提交成功
  ↓
后台线程再慢慢刷脏页
```

这样做的本质是：**先把“怎么恢复”记下来，再允许真正的数据页延迟落盘。**

数据库崩溃重启后，会根据 redo log 重做已提交但还未来得及刷盘的数据，这就是持久性的基础。

#### redo 与 binlog 为什么需要两阶段提交

InnoDB 有 redo log，MySQL Server 层还有 binlog。一个用于崩溃恢复，一个用于主从复制。如果两者提交顺序不协调，就可能出现：

- redo 成功、binlog 失败：主库有数据，从库没有
- binlog 成功、redo 失败：从库有数据，主库恢复后没有

所以 MySQL 使用内部两阶段提交（2PC）：

```text
1. redo log prepare
2. 写 binlog 并落盘
3. redo log commit
```

这样崩溃恢复时可以根据 redo 的状态和 binlog 是否完整，决定补提交还是回滚，最终保证主库数据和 binlog 一致。

#### 隔离性为什么靠锁和 MVCC

隔离性主要依赖两套机制：

1. **锁（Lock）**：如行锁、间隙锁、Next-Key Lock，用于控制写写冲突和部分读写冲突。
2. **MVCC（Multi-Version Concurrency Control，多版本并发控制）**：让读操作读取历史快照，尽量避免读写互相阻塞。

比如在 MySQL 默认的可重复读（RR）级别下，普通 `select` 走快照读，可以重复读取到同一版本；而 `update/delete/select ... for update` 则会加锁，保证修改期间的并发安全。

#### 一致性为什么是“目标”而不是“工具”

很多人会背 ACID，但讲不清为什么一致性和另外三个不在一个维度。更准确的理解是：

- 原子性防止做一半
- 隔离性防止并发串台
- 持久性防止提交后丢失
- 这三个能力共同服务于一致性

所以常见说法是：**AID 是手段，C 是目的。**

### 第三层：实践应用

#### Spring 里如何使用事务

```java
@Service
public class TransferService {

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        accountMapper.decreaseBalance(fromId, amount);
        accountMapper.increaseBalance(toId, amount);
    }
}
```

Spring `@Transactional` 并不是自己实现了一套事务协议，而是借助代理模式，在方法调用前开启数据库事务，在方法成功时提交、异常时回滚。它是应用层对数据库 ACID 能力的封装。

#### 常见并发异常与隔离性关系

| 并发问题 | 含义 |
|---|---|
| 脏读（Dirty Read） | 读到了别的事务尚未提交的数据 |
| 不可重复读（Non-Repeatable Read） | 同一事务两次读取同一行，结果不一样 |
| 幻读（Phantom Read） | 同一事务两次范围查询，行数变化 |

面试时如果问到隔离性，不要只停在“互不干扰”四个字，最好顺手提一下这些典型异常和四种事务隔离级别。

#### 一个更真实的例子：库存扣减

```sql
START TRANSACTION;
UPDATE goods SET stock = stock - 1 WHERE id = 10 AND stock > 0;
INSERT INTO orders(user_id, goods_id) VALUES (1001, 10);
COMMIT;
```

这里：

- 原子性保证扣库存和下单一起成功或失败
- 一致性保证不会出现负库存和孤儿订单
- 隔离性保证高并发下多个请求不会乱扣库存
- 持久性保证订单提交后不会因机器重启而消失

### 第四层：深入思考

#### 1. ACID 是不是越强越好

不一定。隔离级别越高，并发能力通常越差。比如串行化（Serializable）隔离性最强，但锁冲突最多、吞吐量最低。真实项目会在一致性和性能之间做平衡，所以 MySQL 默认选择可重复读，而不是最强的串行化。

#### 2. 单机 ACID 到分布式事务为什么变难

单机数据库里，事务协调集中在一个存储引擎内，相对容易保证。但到了分布式场景，多个服务、多个数据库、多个网络节点参与同一个事务，就会出现协调者单点、网络分区、参与者阻塞等问题。所以业界会引入 2PC、TCC、SAGA、消息最终一致性等方案，而不是简单复制单机事务模型。

#### 3. 长事务为什么危险

长事务会导致：

- undo log 持续膨胀
- 锁持有时间变长
- MVCC 版本链变长
- 崩溃恢复成本增加

所以虽然事务能保证 ACID，但事务边界也不能无限放大。项目里通常强调“小事务、短事务、尽快提交”。

### 答题逻辑框架

1. 先定义事务和 ACID。
2. 分别解释 A/C/I/D，每个都给一个直观场景。
3. 重点下钻实现机制：原子靠 undo，持久靠 redo，隔离靠锁和 MVCC。
4. 再升华一句：AID 是手段，C 是目的。
5. 最后补充 Spring `@Transactional` 和隔离级别追问。

### 重点得分点

- 能准确说出四个英文全称。
- 能把每个特性和实现机制绑定起来。
- 能说出 redo + binlog 两阶段提交存在的原因。
- 能把隔离性和脏读、不可重复读、幻读联系起来。
- 能说出一致性是最终目标，而不是某一种单独机制。

### 常见误区

- ❌ 把一致性理解成“多个副本数据一致”；这里说的是事务前后状态合法。
- ❌ 说原子性靠 redo log；原子性主要靠 undo log。
- ❌ 说事务提交必须把数据页全部刷盘；通常只要求日志先持久化。
- ❌ 认为有了事务就一定不会有并发问题；还取决于隔离级别设计。
- ❌ 把 Spring 事务和数据库事务混为一谈；前者是框架封装，后者是底层能力。
