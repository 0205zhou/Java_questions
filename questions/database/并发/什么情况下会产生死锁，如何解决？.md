# 什么情况下会产生死锁，如何解决？

﻿### 1. 🧠 联想记忆法

**记忆口诀/联想**："你等我，我等你；资源不放手，大家都卡死。"

**记忆原理**：死锁最好记的方式就是“四个必要条件”。只要互斥、请求并保持、不可剥夺、循环等待同时成立，就有死锁风险。面试时从定义讲到四条件，再落到预防方案，结构最稳。

**关联知识**：这题常和 `synchronized`、`Lock`、数据库事务锁、`jstack` 线程排查、线程池任务互等一起考。面试官通常想看你是不是只会说概念，还是能落到代码、事务和排障实践上。

### 2. 📖 深度解答

#### 2.1 核心概念：什么是死锁

死锁（deadlock）是指多个线程或事务彼此占有对方所需的资源，同时相互等待，导致所有参与方都无法继续执行的状态。

最经典的例子就是：

- 线程 A 拿着锁 1，等锁 2
- 线程 B 拿着锁 2，等锁 1

两边都不释放已有资源，也都拿不到下一把锁，结果整个流程永久卡住。

---

#### 2.2 死锁为什么会发生：四个必要条件

死锁通常需要下面四个条件同时成立：

| 条件 | 含义 |
|---|---|
| 互斥条件 | 资源同一时刻只能被一个线程占用 |
| 请求并保持 | 线程拿着已有资源时，继续请求新资源 |
| 不可剥夺 | 已拿到的资源不能被外部强制抢走 |
| 循环等待 | 多个线程形成首尾相接的等待环 |

这里最关键的是：

- 只要四个条件同时满足，就有可能死锁
- 只要破坏其中任意一个条件，死锁就不成立

所以很多解决方案的本质，其实就是在想办法破坏这四个条件之一，尤其是最常破坏的“循环等待”。

---

#### 2.3 典型代码示例：双锁顺序不一致

```java
private static final Object A = new Object();
private static final Object B = new Object();

public static void main(String[] args) {
    new Thread(() -> {
        synchronized (A) {
            sleep(100);
            synchronized (B) {
                System.out.println("t1 done");
            }
        }
    }, "t1").start();

    new Thread(() -> {
        synchronized (B) {
            sleep(100);
            synchronized (A) {
                System.out.println("t2 done");
            }
        }
    }, "t2").start();
}
```

这段代码里：

- `t1` 先拿 A，再等 B
- `t2` 先拿 B，再等 A

如果时机刚好撞上，就形成环路：

```text
t1 持有 A → 等待 B
t2 持有 B → 等待 A
```

这就是最常见的 Java 级死锁。

---

#### 2.4 常见死锁场景

##### 1）多把锁获取顺序不一致

这是最典型、也最常见的死锁来源。

例如：

- 一段代码先锁订单对象，再锁库存对象
- 另一段代码先锁库存对象，再锁订单对象

如果两个线程同时执行，就很容易形成环形等待。

##### 2）嵌套锁过深

业务方法 A 加锁后又调用方法 B，方法 B 再加另一把锁；调用链一长，锁层次变得不透明，很容易出现谁先拿哪把锁都说不清的情况。

##### 3）数据库事务死锁

这不只是 Java 代码问题，数据库里也很常见。

比如两个事务：

- 事务 1 先更新记录 X，再更新记录 Y
- 事务 2 先更新记录 Y，再更新记录 X

数据库行锁顺序不一致，同样会形成死锁。MySQL 这类数据库通常会检测到死锁，然后主动回滚其中一个事务。

##### 4）线程池任务互相等待

例如线程池大小只有 2，但两个任务都在等待各自提交的子任务执行完成，而子任务又没有空闲线程去跑，这也会形成一种资源等待闭环。

##### 5）持锁做慢操作

如果线程持有锁去做：

- RPC 调用
- 数据库慢查询
- 文件 IO
- 第三方回调

锁持有时间会被拉长，虽然不一定直接造成死锁，但会极大放大死锁和长阻塞的概率。

---

#### 2.5 如何排查死锁

##### Java 应用层排查

最常用的是 `jstack`。

如果是典型 Java 锁死锁，`jstack` 往往会直接给出提示：

```text
Found one Java-level deadlock:
```

你还能看到：

- 哪个线程在等哪把锁
- 哪个线程持有那把锁
- 锁等待链条是什么

##### 运行现象

死锁通常表现为：

- 服务卡住不响应
- 某些请求一直不返回
- CPU 不一定高
- 线程长期处于 `BLOCKED` 或等待状态

这点和死循环不一样。死循环往往 CPU 飙高，死锁更多是线程互相卡住不动。

##### 数据库层排查

数据库死锁通常会在错误日志、慢日志或事务异常中体现出来。MySQL 里可以通过 `show engine innodb status` 查看最近一次死锁信息。

#### 2.6 如何解决和预防死锁

##### 1）统一加锁顺序

这是最核心、最有效的方法。

所有线程都按照固定顺序获取资源，例如：

- 永远先锁 ID 小的对象
- 再锁 ID 大的对象

```java
public void transfer(Account from, Account to, int amount) {
    Account first = from.getId() < to.getId() ? from : to;
    Account second = from.getId() < to.getId() ? to : from;

    synchronized (first) {
        synchronized (second) {
            doTransfer(from, to, amount);
        }
    }
}
```

这个办法本质上就是破坏“循环等待”。只要所有人都按同一顺序拿锁，就很难形成闭环。

##### 2）使用可超时锁

显式锁可以用 `tryLock(timeout)`：

```java
Lock lock1 = new ReentrantLock();
Lock lock2 = new ReentrantLock();

if (lock1.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lock2.tryLock(1, TimeUnit.SECONDS)) {
            try {
                // 业务逻辑
            } finally {
                lock2.unlock();
            }
        }
    } finally {
        lock1.unlock();
    }
}
```

这种方式不能从根上消灭所有问题，但它避免了“无限等待”，给失败返回、降级处理、重试策略留了空间。

##### 3）缩小临界区

不要把锁包得太大，也不要持锁执行慢操作。

正确思路是：

- 只把真正修改共享资源的那一小段逻辑放进临界区
- 其他 IO、RPC、日志、通知尽量挪到锁外面

##### 4）减少嵌套锁

如果业务代码一层套一层加锁，复杂度很快会失控。能合并资源控制就合并，能拆成单锁就不要双锁、多锁。

##### 5）数据库统一更新顺序

数据库层也一样：

- 多行更新时保持固定顺序
- 多表操作时保持固定访问顺序
- 缩短事务时间
- 用好索引，减少锁范围

#### 2.7 深入思考：死锁和其他问题的区别

##### 死锁 vs 活锁

- **死锁**：大家都不动，彼此等待
- **活锁**：大家都在动，但一直互相避让，谁也完不成

##### 死锁 vs 普通锁竞争

- **普通锁竞争**：只是等一会，最终能拿到锁
- **死锁**：永远等不到，因为等待链条是闭环

##### 死锁 vs 线程饥饿

- **死锁**：线程之间互相卡住
- **饥饿**：某个线程长期拿不到资源，但系统整体仍然在推进

面试里如果能顺手提一句这些区别，层次会更高。

### 3. 🗺️ 回答思路

#### 3.1 面试时的答题框架

可以按这个顺序答：

1. **先定义死锁**：多个线程互相持有资源并等待对方释放
2. **再说四个必要条件**：互斥、请求并保持、不可剥夺、循环等待
3. **举一个经典双锁代码例子**
4. **补充常见场景**：锁顺序不一致、数据库事务、线程池任务互等
5. **最后说解决方案**：统一加锁顺序、超时锁、缩小临界区、`jstack` 排查

#### 3.2 面试加分点

- 能完整说出四个必要条件
- 能把 Java 代码死锁和数据库死锁都讲到
- 能解释为什么统一加锁顺序最有效
- 能说出 `tryLock(timeout)` 和 `jstack`
- 能区分死锁、活锁、普通锁竞争

#### 3.3 常见误区

- 误区 1：以为只有 `synchronized` 会死锁
  - 其实 `Lock`、数据库行锁、分布式锁都可能死锁。
- 误区 2：把所有线程阻塞都叫死锁
  - 很多只是普通等待，不一定形成闭环。
- 误区 3：只会说检测，不会说设计预防
  - 面试官更看重你是否知道如何从架构上避免死锁。
- 误区 4：只讲代码，不讲事务
  - 数据库死锁在实际工作里非常常见。

#### 3.4 可直接复述的收尾话术

你可以最后总结一句：

> 死锁本质上是多个执行单元彼此持有资源并等待对方释放，四个必要条件同时成立时就会出现。解决上最核心的是统一加锁顺序，排查上 Java 可以用 `jstack`，数据库则要看事务锁等待和死锁日志。
