# 线程池的拒绝策略有哪些？

### 1. 🧠 联想记忆法

**记忆口诀/联想**："四种拒绝像四个前台：报错、调用者自己干、直接丢、挤掉最老再进新单。"

**记忆原理**：线程池满载时，本质是在做"过载保护（overload protection）"。把 4 种拒绝策略记成 4 种处置动作，就能快速回忆它们分别对系统稳定性、吞吐量、任务可靠性的影响。

**关联知识**：这个考点通常会和 `ThreadPoolExecutor` 的 7 个核心参数、阻塞队列、线程池大小设定、背压（backpressure）一起问。面试官真正想考的，不只是你会背策略名字，更想看你是否理解：**线程池为什么必须拒绝，以及拒绝后业务要如何兜底。**

### 2. 📖 深度解答

#### 2.1 核心概念：什么是线程池拒绝策略

线程池的拒绝策略（Rejected Execution Handler）指的是：当线程池已经**无法继续接收新任务**时，应该如何处理这个新提交进来的任务。

在线程池里，一个任务从提交到真正执行，通常会经历这样的路径：

1. 当前运行线程数 < `corePoolSize`：优先创建核心线程执行。
2. 核心线程都忙：尝试把任务放入阻塞队列（`workQueue`）。
3. 队列满了，但当前线程数 < `maximumPoolSize`：继续创建非核心线程执行。
4. 队列也满了，线程数也到上限：**触发拒绝策略。**

所以，拒绝策略不是可有可无的边角配置，而是线程池在高并发场景下的最后一道闸门。没有合理的拒绝策略，系统就可能出现：

- 请求无限堆积
- 内存持续膨胀
- 响应时间失控
- 上游继续施压，最终把服务拖垮

也就是说，**拒绝策略本质上是在系统容量触顶时决定"是保稳定、保吞吐、保老任务，还是保新任务"。**

#### 2.2 JDK 内置的 4 种拒绝策略

`ThreadPoolExecutor` 在 JDK 中内置了 4 种 `RejectedExecutionHandler` 实现。

| 策略 | 类名 | 行为 | 特点 | 常见适用场景 |
|---|---|---|---|---|
| 直接抛异常 | `AbortPolicy` | 拒绝任务并抛出 `RejectedExecutionException` | 最"硬"，失败最明显 | 核心业务、不能悄悄丢任务 |
| 调用者运行 | `CallerRunsPolicy` | 由提交任务的线程自己执行任务 | 形成天然背压 | 希望削峰限流、允许调用方变慢 |
| 直接丢弃 | `DiscardPolicy` | 静默丢弃当前任务 | 风险最大，调用方无感知 | 非关键、允许丢失的数据任务 |
| 丢弃最老任务 | `DiscardOldestPolicy` | 丢弃队列中最旧任务，再尝试提交当前任务 | 保新不保旧 | 更关注最新数据的场景 |

下面分别展开。

##### 1）`AbortPolicy`

这是 JDK 默认策略。

```java
ExecutorService pool = new ThreadPoolExecutor(
        2,
        4,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(2),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.AbortPolicy()
);
```

当线程池满时，`execute()` 会直接抛出 `RejectedExecutionException`。

**优点：**

- 失败显式，问题不会被掩盖
- 便于监控、报警、快速定位容量瓶颈
- 适合对任务可靠性要求高的业务

**缺点：**

- 上层如果没有捕获异常，可能直接导致接口报错
- 峰值流量下用户体验会变差

**适用场景：**

- 支付、下单、库存扣减等关键链路
- 任务绝对不能无声失败的系统
- 希望尽快暴露容量问题、触发扩容或降级的场景

很多团队在线上会把这个策略和日志、监控、熔断结合起来使用：一旦出现拒绝，就说明线程池容量、任务执行时间或请求峰值已经超出设计预期。

##### 2）`CallerRunsPolicy`

当线程池不能接收新任务时，不再交给线程池里的工作线程，而是让**提交任务的那个线程自己执行**。

```java
ExecutorService pool = new ThreadPoolExecutor(
        2,
        4,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(2),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.CallerRunsPolicy()
);
```

这个策略最重要的价值是：**它会把压力反向传递给调用方。**

假设 Web 线程不断往线程池里扔任务，线程池满了以后，Web 线程自己就得干活。这样它处理后续请求的速度自然会下降，相当于形成了一种"背压"机制。

**优点：**

- 不会直接丢任务
- 不会立刻抛异常
- 能自动降低提交速度，抑制流量洪峰

**缺点：**

- 调用线程可能被阻塞更久
- 如果调用线程本身很关键，比如 Tomcat 业务线程、Netty I/O 线程，就可能连带影响主流程响应时间
- 如果任务执行很慢，可能导致上游雪崩式超时

**适用场景：**

- 可接受调用方变慢，但不希望丢任务
- 批处理、异步削峰、日志聚合等场景
- 明确知道调用线程可以承受这部分执行开销

面试里常见追问是：为什么说它能限流？

回答关键点就是：**因为提交线程被迫自己执行任务，提交动作不再是 O(1) 的快速投递，而变成了真实执行，生产速度自然下降。**

##### 3）`DiscardPolicy`

该策略会**直接丢弃当前任务，而且不抛异常。**

```java
ExecutorService pool = new ThreadPoolExecutor(
        2,
        4,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(2),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.DiscardPolicy()
);
```

**优点：**

- 实现最简单
- 不阻塞调用线程
- 不抛异常，表面上调用链很平稳

**缺点：**

- 最危险，因为任务丢了但业务可能完全不知道
- 如果没有额外埋点，排查问题会很困难
- 关键业务中几乎不可接受

**适用场景：**

- 非核心监控埋点
- 可丢弃的统计数据
- 重复上报、冗余刷新、低价值异步通知

这个策略最大的问题是"静默失败"。所以如果业务真要用，一般会包装一个自定义拒绝策略，在丢弃前至少打印日志、打指标、计数报警，而不是完全无痕丢弃。

##### 4）`DiscardOldestPolicy`

当线程池满时，它会**先丢弃阻塞队列中等待最久的任务**，然后重新尝试提交当前新任务。

```java
ExecutorService pool = new ThreadPoolExecutor(
        2,
        4,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(2),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.DiscardOldestPolicy()
);
```

这意味着它的取舍是：**牺牲旧任务，优先给新任务让路。**

**优点：**

- 保证新任务有机会进入线程池
- 适合数据具有时效性的业务

**缺点：**

- 被丢弃的旧任务也可能很重要
- 如果队列中的任务都必须执行，那这个策略就很危险
- 在高压场景下可能反复丢老任务，造成任务饥饿

**适用场景：**

- 实时性比完整性更重要
- 例如最新状态刷新、行情更新、监控面板刷新
- 旧数据即使执行了也没价值的场景

#### 2.3 自定义拒绝策略为什么更常见

实际生产里，很多团队并不会直接裸用 JDK 默认策略，而是会实现自己的 `RejectedExecutionHandler`。

原因很简单：JDK 提供的是通用行为，但业务往往需要更细的控制，例如：

- 记录被拒绝任务的关键信息
- 打 Prometheus / Micrometer 指标
- 触发告警
- 把任务写入降级队列、消息队列或本地磁盘
- 对不同任务做差异化处理

例如：

```java
public class LoggingRejectHandler implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        System.err.println("任务被拒绝: queueSize=" + executor.getQueue().size()
                + ", active=" + executor.getActiveCount()
                + ", task=" + r);
        throw new RejectedExecutionException("线程池已满，任务被拒绝");
    }
}
```

这种方式比直接用 `AbortPolicy` 更适合线上，因为它把容量问题透明化了。

进一步还可以做成"拒绝后转异步补偿"：

- 主线程池满了 →
- 任务投递到 MQ / Redis Stream / 本地失败队列 →
- 后续补偿消费

这就是把简单的拒绝策略升级为完整的系统过载治理方案。

#### 2.4 拒绝策略的本质：不是选名字，而是选系统取舍

面试官真正想听到的，不只是"有 4 种"，而是你能说出每种背后的取舍。

可以从 3 个维度去理解：

##### 维度一：任务能不能丢

- **不能丢**：优先 `AbortPolicy` 或自定义策略做落库 / 重试 / 补偿
- **尽量不丢**：可考虑 `CallerRunsPolicy`
- **可以丢**：才考虑 `DiscardPolicy` 或 `DiscardOldestPolicy`

##### 维度二：是保调用方，还是保任务

- **保调用方响应**：可能会倾向丢任务
- **保任务完成**：可能会接受调用方变慢甚至报错

##### 维度三：更重视新数据还是旧数据

- **旧任务更重要**：不要用 `DiscardOldestPolicy`
- **新任务更重要**：`DiscardOldestPolicy` 可以考虑

所以线程池拒绝策略的选型，本质上是在回答一句话：

> 当系统满载时，业务到底允许牺牲什么？

这是架构思维，不只是 API 背诵。

#### 2.5 实践建议：如何在面试中答得更像有实战经验

如果面试官问："生产里一般怎么选？"

比较稳妥的回答是：

1. **默认不会直接使用无声丢弃策略。** 因为丢任务但没监控，问题很难排查。
2. **核心链路常用显式失败或自定义拒绝策略。** 例如抛异常 + 监控报警 + 降级处理。
3. **允许调用方降速的异步任务可用 `CallerRunsPolicy`。** 它能形成天然背压。
4. **如果任务有时效性，可考虑丢旧保新。** 但前提是确认旧任务确实可以废弃。
5. **真正重要的不是拒绝策略本身，而是线程池容量评估、任务执行时长控制、监控和降级。**

因为拒绝策略只是最后一道防线。一个设计良好的系统，不应该长期依赖拒绝策略来正常运转；如果经常触发拒绝，说明线程池参数、任务模型、上游流量控制可能已经有问题。

#### 2.6 一个完整示例

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        4,
        8,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(100),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.CallerRunsPolicy()
);

for (int i = 0; i < 1000; i++) {
    int taskId = i;
    executor.execute(() -> {
        System.out.println(Thread.currentThread().getName() + " 执行任务 " + taskId);
        try {
            Thread.sleep(200);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });
}
```

这个例子里，当线程池和队列都吃满后，一部分任务会回退到提交线程执行。现象上通常会看到：

- 线程池线程在执行任务
- main 线程也开始执行任务
- 整体提交速度下降

这正是 `CallerRunsPolicy` 的背压效果。

### 3. 🗺️ 回答思路

#### 3.1 面试时的答题框架

可以按"定义 → 触发时机 → 四种策略 → 选型原则 → 实战建议"来答：

1. **先定义**：拒绝策略是线程池满载后如何处理新任务的机制。
2. **再说触发时机**：核心线程满、队列满、最大线程数也满时触发。
3. **然后枚举 4 种策略**：
   - `AbortPolicy`：抛异常
   - `CallerRunsPolicy`：调用者执行
   - `DiscardPolicy`：直接丢弃
   - `DiscardOldestPolicy`：丢最老任务后重试
4. **补充选型原则**：是否允许丢任务、是否允许调用方变慢、是否更看重新任务。
5. **最后落到生产实践**：一般会配合日志、指标、报警、自定义降级策略。

#### 3.2 面试加分点

- 能说出拒绝策略的**触发前提**，而不是只会背名字
- 能讲清 `CallerRunsPolicy` 的**背压机制**
- 能指出 `DiscardPolicy` 的**静默丢失风险**
- 能从业务角度说出：**关键任务不能简单丢**
- 能补一句：**频繁触发拒绝说明线程池设计有问题，不能把拒绝策略当常态**

#### 3.3 常见误区

- 误区 1：以为线程池只要设大一点就不会拒绝
  - 实际上线程数过大可能带来上下文切换、内存占用和系统抖动问题。
- 误区 2：以为 `DiscardPolicy` 比较"平滑"
  - 它只是把问题藏起来，并没有解决问题。
- 误区 3：以为 `CallerRunsPolicy` 一定最好
  - 如果调用线程是核心业务线程，它可能反而拖慢主链路。
- 误区 4：忽略监控
  - 拒绝策略必须和日志、指标、报警一起设计。

#### 3.4 可直接复述的收尾话术

你可以最后总结一句：

> 线程池的拒绝策略一共有 4 种，但真正重要的不是背名字，而是理解线程池在容量打满时到底牺牲什么。核心业务通常要显式失败或做补偿，削峰场景可以用 CallerRunsPolicy 做背压，能不能丢任务、保新还是保旧，要结合业务语义来选。
