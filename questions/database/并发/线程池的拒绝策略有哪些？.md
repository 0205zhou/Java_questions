# 线程池的拒绝策略有哪些？

## 联想记忆法

### 记忆口诀/联想

**口诀：“满了就拒绝，四策记心间：抛异常、调用跑、静默丢、丢旧再投。”**

把线程池想成一家餐厅：核心员工和临时员工都在忙，取餐台（工作队列）也排满了，新订单再来时就必须做决定：

- **AbortPolicy**：前台直接报错，明确告诉调用方“接不了”。
- **CallerRunsPolicy**：谁下的订单谁自己做，提交任务的线程亲自执行。
- **DiscardPolicy**：把新订单直接扔掉，不通知任何人。
- **DiscardOldestPolicy**：先丢掉排队最久的订单，再尝试接收新订单。

### 记忆原理

四种策略可以按两个维度记忆：是否抛异常、是否丢任务。Abort 不丢任务但抛异常；CallerRuns 不丢任务并通过让提交方变慢形成反压；Discard 和 DiscardOldest 都可能丢任务，只是丢新任务还是丢旧任务。面试时先说触发条件，再按这两个维度展开，答案会很有条理。

### 关联知识

- 线程池执行顺序是“核心线程 → 工作队列 → 非核心线程 → 拒绝策略”。
- 有界队列是拒绝策略真正生效的前提；无界队列可能导致任务无限积压。
- 拒绝策略和业务可靠性、消息重试、监控告警直接相关。
- `CallerRunsPolicy` 的效果类似一种自然反压（back pressure），但不能代替完整的限流和降级方案。

## 深度解答

### 第一层:核心概念

#### 是什么

线程池在以下条件同时满足时触发拒绝策略：线程池仍允许接收任务，但工作队列已满，且当前线程数已经达到 `maximumPoolSize`。在 `ThreadPoolExecutor` 中，拒绝策略通过 `RejectedExecutionHandler` 表示：

```java
public interface RejectedExecutionHandler {
    void rejectedExecution(Runnable r, ThreadPoolExecutor executor);
}
```

JDK 内置四种实现：

| 策略 | 行为 | 是否抛异常 | 是否可能丢任务 |
|---|---|---:|---:|
| `AbortPolicy` | 抛出 `RejectedExecutionException` | 是 | 否，但任务未执行 |
| `CallerRunsPolicy` | 由提交任务的线程执行 | 否 | 通常否 |
| `DiscardPolicy` | 静默丢弃新任务 | 否 | 是 |
| `DiscardOldestPolicy` | 丢弃队列头部任务，再重试新任务 | 否 | 是 |

### 第二层:底层原理

#### 触发流程

```text
execute(task)
  ├─ 工作线程数 < corePoolSize：创建核心线程
  ├─ 核心线程已满：尝试加入 workQueue
  ├─ 入队失败且线程数 < maximumPoolSize：创建非核心线程
  └─ 入队失败且线程数达到 maximumPoolSize：reject(task)
```

`execute` 和 `submit` 都可能触发拒绝。需要注意，`submit` 会先把任务包装成 `FutureTask`，拒绝时抛出的仍然是 `RejectedExecutionException`。线程池关闭后提交任务，也会进入拒绝处理逻辑。

1. **AbortPolicy（默认）**：调用 `reject` 后直接抛异常。它不会吞掉任务，调用方可以记录日志、重试、降级或返回明确错误，是对核心业务最容易观察和治理的选择。
2. **CallerRunsPolicy**：如果线程池没有关闭，就在调用 `execute` 的线程中同步执行任务。提交方因此被占用，提交速度下降，形成反馈式限流；如果线程池已关闭，则任务不会执行。
3. **DiscardPolicy**：什么也不做。它适合明确允许丢弃的非关键任务，例如过期的监控采样，但必须配合指标，否则任务丢失很难发现。
4. **DiscardOldestPolicy**：调用队列的 `poll` 丢掉队首任务，再重新调用 `execute`。它假设队列头是最不重要或最过时的任务；如果队列是优先级队列，队首不一定是“最早提交”的任务，不能望文生义。

### 第三层:实践应用

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        4,
        8,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(100),
        runnable -> new Thread(runnable, "order-worker"),
        new ThreadPoolExecutor.AbortPolicy()
);

try {
    pool.execute(() -> createOrder());
} catch (RejectedExecutionException ex) {
    // 记录指标、告警，并根据业务决定重试或降级
    rejectCounter.increment();
    return fallbackResponse();
}
```

选择建议：

- 订单、支付、库存等不能静默丢失的任务，优先使用 `AbortPolicy`，在调用方做可控处理。
- 日志、统计等允许提交方暂时变慢的任务，可以考虑 `CallerRunsPolicy`，但要确认提交线程不会持有事务锁或处理 HTTP 超时敏感逻辑。
- 允许丢弃且能接受数据不完整的采样任务，才考虑 `DiscardPolicy`。
- 只保留最新数据的刷新任务，可以使用自定义“丢旧”策略；比直接套 `DiscardOldestPolicy` 更容易表达业务意图。

生产环境还应监控活跃线程数、队列长度、拒绝次数、任务耗时和完成数，并设置有界队列，避免拒绝策略永远触发不到而最终 OOM。

### 第四层:深入思考

**为什么不能所有场景都使用 `CallerRunsPolicy`？** 它会把线程池压力转移到提交方。如果提交方是 Web 容器线程，可能拖慢请求；如果提交方持有数据库事务或锁，任务执行时间过长还会扩大锁持有范围。因此它是一种反压手段，不是万能的可靠性方案。

**为什么默认策略是 AbortPolicy？** 默认策略优先保证故障可见性。静默丢任务会把问题隐藏到业务数据中，而抛异常能让调用方根据业务语义决定重试、降级或失败。

**拒绝策略能保证任务不丢吗？** 不能。CallerRuns 只能在特定情况下同步执行，Abort 只是把失败交给调用方；进程崩溃、重试失败、队列内存任务丢失仍然存在。强可靠任务应使用持久化消息队列或数据库状态机。

## 回答思路

### 答题逻辑框架

1. 先说触发条件：队列满且线程数达到最大值，或线程池已关闭。
2. 直接列出四种策略和默认值 `AbortPolicy`。
3. 按“抛不抛异常、丢不丢任务”比较行为。
4. 说明 `CallerRunsPolicy` 的反压效果和使用限制。
5. 结合有界队列、监控、重试和业务可靠性给出生产建议。

### 重点得分点

- 四种内置策略名称和行为完整。
- 说清楚拒绝发生在“队列满 + 最大线程数已达”时。
- 指出 `AbortPolicy` 是默认策略。
- 能解释 `CallerRunsPolicy` 为什么可以降低提交速度。
- 能指出无界队列会让最大线程数和拒绝策略难以发挥作用。

### 常见误区

- 误以为线程数达到核心线程数就会拒绝，实际上还会先入队、再创建非核心线程。
- 误以为 `DiscardOldestPolicy` 丢的是最先提交的任务，实际上是队列头任务。
- 误以为 `CallerRunsPolicy` 一定执行，线程池关闭时任务仍会被丢弃。
- 用 `DiscardPolicy` 处理支付、订单等关键任务，造成静默数据丢失。

### 过渡话术

- “拒绝策略决定满载时怎么处理，那线程池本身的锁和同步机制又是怎样的？”
- “如果业务不能接受任务丢失，就需要继续讨论消息持久化和重试，而不能只依赖线程池策略。”
