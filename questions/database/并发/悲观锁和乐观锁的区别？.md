# 悲观锁和乐观锁的区别？

## 联想记忆法

### 记忆口诀/联想

**口诀：“悲观先锁住，乐观先尝试；前者防冲突，后者靠校验。”**

把两者想成两种办业务方式：

- **悲观锁**：我先把窗口占住，别人都别来，等我办完再说。
- **乐观锁**：大家先各自填表，提交时再看有没有人改过，冲突了就重试。

### 记忆原理

它们本质上是两种并发控制思想：悲观锁认为冲突大概率发生，所以先加锁；乐观锁认为冲突不常发生，所以先放行，更新时再检测。记住“先锁 vs 先改后校验”，面试时就能很快展开到数据库和 Java 并发两个层面。

### 关联知识

- 悲观锁与 `synchronized`、`ReentrantLock`、数据库 `select ... for update` 相关。
- 乐观锁与 CAS（Compare-And-Swap）、版本号（version）、时间戳校验相关。
- 乐观锁常配合自旋、重试；悲观锁常带来阻塞和上下文切换。
- 与高并发读多写少场景、ABA 问题、自旋开销相关。

## 深度解答

### 第一层:核心概念

#### 是什么

悲观锁（pessimistic lock）和乐观锁（optimistic lock）是两种不同的并发控制思路。

| 维度 | 悲观锁 | 乐观锁 |
|---|---|---|
| 基本假设 | 冲突经常发生 | 冲突不常发生 |
| 控制方式 | 先加锁再操作 | 先操作，提交时校验 |
| 是否阻塞 | 常阻塞其他线程 | 通常不阻塞 |
| 失败处理 | 等待拿锁 | 重试或失败返回 |
| 典型实现 | `synchronized`、`Lock`、数据库行锁 | CAS、版本号、时间戳 |
| 适用场景 | 写多、冲突高、强一致要求高 | 读多写少、冲突低、追求吞吐 |

### 第二层:底层原理

#### 悲观锁原理

悲观锁的思想是：既然别人可能改，我就先把资源锁住。只有拿到锁的线程才能进入临界区，其他线程必须等待。

```java
synchronized (lock) {
    balance = balance - 100;
}
```

或者：

```java
lock.lock();
try {
    update();
} finally {
    lock.unlock();
}
```

数据库里典型写法是：

```sql
select * from account where id = 1 for update;
```

它的优点是语义简单、强一致性强；缺点是会阻塞、可能死锁，并且上下文切换成本高。

#### 乐观锁原理

乐观锁不先锁资源，而是在更新时校验“数据是否还是我看到的那个版本”。如果不是，说明有人改过，当前操作失败并重试。

最常见两种方式：

1. **CAS**：比较内存中的旧值和预期值，一致才更新。
2. **版本号机制**：读取数据时带出版本号，更新时 `where version = oldVersion`。

```java
AtomicInteger count = new AtomicInteger(0);
count.compareAndSet(0, 1);
```

数据库版本号示例：

```sql
update product
set stock = stock - 1, version = version + 1
where id = 1 and version = 3;
```

如果影响行数是 0，说明版本已变，更新失败，需要重试或提示用户。

#### 核心差异本质

- 悲观锁把冲突前置，代价是等待和阻塞。
- 乐观锁把冲突后置，代价是重试和失败处理。
- 悲观锁更像“串行化访问”，乐观锁更像“并发尝试 + 最终校验”。

### 第三层:实践应用

#### Java 并发场景

- 多线程更新共享计数器、状态位时，常用 `AtomicInteger`、`AtomicReference` 这类 CAS 工具实现乐观锁。
- 复杂临界区、涉及多个变量一致性时，更适合悲观锁或显式锁。

#### 数据库场景

- 库存扣减、账户余额等强一致场景，如果冲突高，悲观锁更稳。
- 订单备注、配置编辑、低冲突更新场景，乐观锁更适合，提高并发度。

#### 风险点

- 乐观锁在高冲突场景下可能频繁重试，反而浪费 CPU。
- CAS 有 ABA 问题，需要 `AtomicStampedReference` 等版本化方案辅助。
- 悲观锁持锁时间过长会带来吞吐下降、死锁风险和尾延迟放大。

### 第四层:深入思考

**为什么乐观锁不是真正“无锁”？** 因为它只是没有传统互斥锁，但底层 CAS 依然依赖 CPU 原子指令和内存语义，不是完全没有同步成本。

**什么时候乐观锁反而不如悲观锁？** 当写冲突非常频繁时，大量线程不断 CAS 失败、自旋重试，CPU 会空转，系统吞吐反而下降。这时悲观锁虽然会阻塞，但可能更稳定。

**两者能结合吗？** 可以。很多系统会先用乐观方式尝试，失败次数过多再退化为悲观控制；数据库和缓存双写场景中也经常混合使用。

### 重点得分点

- 说清楚核心思想差异，不只是罗列例子。
- 乐观锁常见实现：CAS、版本号。
- 悲观锁常见实现：互斥锁、数据库行锁。
- 知道各自适用场景和代价。

### 常见误区

- 认为乐观锁一定比悲观锁性能高。
- 只会说数据库层面的例子，不会讲 Java 并发中的 CAS。
- 只说“悲观锁安全，乐观锁不安全”，表述过于粗糙。
- 忽略乐观锁失败后的重试与补偿逻辑。

### 过渡话术

- “如果是共享资源竞争，就用悲观或乐观；如果是每线程独享数据，就更像 `ThreadLocal` 的思路。”
- “乐观锁底层很多时候依赖 CAS，再往下追问就会到原子类和 AQS。”
