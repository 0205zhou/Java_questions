# 如何创建线程池

## 联想记忆法

### 记忆口诀/联想

**口诀:"五种捷径一个坑:固定、缓存、单例、定时、工作窃取——Executors 图省事,手写 ThreadPoolExecutor 最稳"**

把创建线程池想成**开餐厅的两种方式**:

- **Executors 五件套(快捷加盟)**:固定店(固定 N 人)、缓存店(招之即来挥之即去)、单间店(只留 1 人)、定时店(定时送货)、窃取店(忙人帮闲人)——**方便但有暗坑**(无界队列/无界线程 → OOM)
- **ThreadPoolExecutor(自营)**:7 个参数自己定,有界队列 + 命名线程 + 明确拒绝策略,**生产首选**

**口诀:"快捷五连,暗藏 OOM;手写七参,稳如泰山"**

### 记忆原理

用"快捷加盟 vs 自营"区分两条路线,五个快捷方式按"人数特点"记:固定(不增不减)、缓存(零常态、按需伸缩)、单例(就一个)、定时(延迟/周期)、窃取(分而治之并行)。核心记忆锚点是**每个快捷方式背后的参数组合**,反推出"为什么危险":Fixed/Single 用无界队列, Cached/Scheduled 用无界线程——背下这两条,Executors 陷阱题就稳了。

### 关联知识

- **与核心参数关联**:Executors 就是 7 参数的具体组合,理解了参数就理解了工厂方法
- **与拒绝策略关联**:默认 AbortPolicy 抛异常,业务上要按场景换成 CallerRuns
- **与阻塞队列关联**:SynchronousQueue 无缓冲,是 CachedThreadPool 弹性伸缩的关键
- **与 Java 19+/21 关联**:虚拟线程(Executors.newVirtualThreadPerTaskExecutor())是 IO 密集场景新选项

## 深度解答

### 第一层:核心概念

#### 是什么

创建线程池有两条路:**Executors 工具类的 5 个工厂方法**(图省事)和 **new ThreadPoolExecutor(…)**(手动全参数)。生产规范(阿里 Java 开发手册)**明确禁止使用 Executors**,推荐手动创建:

```java
// ===== 路线一:Executors 快捷创建(5 种)=====

// 1. 固定线程数:core = max = N
ExecutorService pool1 = Executors.newFixedThreadPool(4);
//    内部:ThreadPoolExecutor(4, 4, 0L, MILLISECONDS, new LinkedBlockingQueue<>())
//    ⚠️ 无界队列 → 任务无限积压,可能 OOM

// 2. 缓存线程池:core = 0, max = Integer.MAX_VALUE
ExecutorService pool2 = Executors.newCachedThreadPool();
//    内部:ThreadPoolExecutor(0, MAX_VALUE, 60L, SECONDS, new SynchronousQueue<>())
//    ⚠️ 线程数无上限,任务激增可创建海量线程 → OOM(线程栈占内存)

// 3. 单线程池:core = max = 1
ExecutorService pool3 = Executors.newSingleThreadExecutor();
//    ⚠️ 无界队列,且比 newFixedThreadPool(1) 多一层包装(防止被改 core)

// 4. 定时/周期池:支持 delay 与周期执行
ScheduledExecutorService pool4 = Executors.newScheduledThreadPool(2);
pool4.schedule(task, 10, TimeUnit.SECONDS);            // 延迟 10s
pool4.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS); // 固定频率(任务执行时间 > 周期时,不并发)

// 5. 工作窃取池(JDK 1.8):ForkJoinPool,线程数 = CPU 核数
ExecutorService pool5 = Executors.newWorkStealingPool();
//    ⚠️ 没有公平性保证,适合可分解的大任务,不适合通用业务

// ===== 路线二:手动创建(生产推荐)=====
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4, 8, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),                 // 有界队列
    r -> new Thread(r, "biz-" + ThreadLocalRandom.current().nextInt(1000)),
    new ThreadPoolExecutor.CallerRunsPolicy()      // 或按业务选
);
```

### 第二层:底层原理

#### Executors 五个方法的参数真相

| 工厂方法 | core/max | 队列 | 隐患 |
|---|---|---|---|
| newFixedThreadPool(n) | n / n | **LinkedBlockingQueue 无界** | 任务积压 → OOM |
| newCachedThreadPool | 0 / **Integer.MAX_VALUE** | SynchronousQueue | 线程数失控 → OOM |
| newSingleThreadExecutor | 1 / 1 | LinkedBlockingQueue 无界 | 同 Fixed,且多一层包装 |
| newScheduledThreadPool(n) | n / MAX | DelayedWorkQueue | 同 Cached,线程数失控 |
| newWorkStealingPool | CPU 核数 | 任务窃取双端队列 | 无公平性,不适合小任务 |

**核心陷阱两条:**
1. **无界队列**:Fixed/Single 的任务全排队,`maximumPoolSize` 和拒绝策略**永不触发**,内存被排队任务吃光 → **OutOfMemoryError**
2. **无界线程**:Cached/Scheduled 的 max = Integer.MAX_VALUE,高并发瞬间创建海量线程,每个线程默认栈 1MB(可配),**线程数失控直接 OOM**

#### 为什么"禁止 Executors"成了行业规范

- **不可控**:关键参数(队列上限、线程上限)被隐藏,出问题无法靠参数自愈
- **难排查**:无界资源膨胀是缓慢型故障,监控滞后,线上才发现
- **反例教育**:阿里手册把这条列为**强制**级规范,面试直接背"因为 FixedThreadPool 无界队列会 OOM,所以要手动 ThreadPoolExecutor 配 ArrayBlockingQueue"

### 第三层:实践应用

```java
// 完整的生产配置模板(按需调整数值)
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    Runtime.getRuntime().availableProcessors(),   // core:CPU 核数(IO 密集再乘系数)
    Runtime.getRuntime().availableProcessors() * 2, // max
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),                // 有界队列:积压上限 500
    new NamedThreadFactory("order-service"),      // 自定义命名工厂(排查利器)
    new ThreadPoolExecutor.CallerRunsPolicy()     // 拒绝时提交线程执行,不丢任务
);
```

- **命名线程工厂**:`ThreadFactory` 里给线程起名(如 "order-service-1"),jstack 定位问题一目了然
- **优雅关闭**:
```java
pool.shutdown();                          // 拒绝新任务,存量跑完
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();                   // 超时强制中断
}
```
- **Java 21 虚拟线程池**:IO 密集场景可 `Executors.newVirtualThreadPerTaskExecutor()`(每次任务一个虚拟线程,几百万不 OOM),但 CPU 密集场景仍用平台线程池

### 第四层:深入思考

**追问 1:SynchronousQueue 为什么让 CachedThreadPool "弹性伸缩"?**
SynchronousQueue **不存任务**:put 必须等 take,即"任务一来就必须有线程接"。所以 core=0 时,任务到达就创建新线程;线程空闲 60s 被回收——线程数跟着流量走。

**追问 2:newFixedThreadPool(1) 和 newSingleThreadExecutor 有区别吗?**
Fixed(1) 的 core 可被反射/子类修改,且默认**可被替换为多个线程的配置**(参数在构造后可调?Fixed 的 core 是 final 的,但 Single 包了一层 FinalizableDelegatedExecutorService 防止改 core)——**Single 保证"永远单线程"语义**,即使异常也会新建线程保证队列处理不中断。

**追问 3:什么时候用 newWorkStealingPool?**
任务可递归分解、计算密集、需要充分利用多核(如大数组排序、矩阵运算)。普通业务(短任务、IO 任务)用它反而有调度开销。
