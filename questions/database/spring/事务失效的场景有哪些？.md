# 事务失效的场景有哪些？

## 联想记忆法

### 记忆口诀/联想

**口诀：不是 Spring 管、没走代理、异常没回滚、配置不对口、线程边界断。**

事务失效场景可以归成 5 类：

1. **对象不是 Spring 容器管理**
2. **调用没有经过事务代理**
3. **异常类型或处理方式导致没回滚**
4. **事务配置本身不匹配**
5. **跨线程、跨方法边界后上下文丢失**

### 记忆原理

Spring 声明式事务的底层是 **AOP 代理**。所以凡是事务失效，本质上都可以倒推回两个问题：

- 这个方法有没有被 Spring 代理到？
- 代理到以后，回滚条件和事务配置是否真的生效？

### 关联知识

- `@Transactional` 默认基于 AOP 代理实现。
- Spring 默认只对 **运行时异常（RuntimeException）和 Error** 回滚。
- 事务绑定在当前线程的上下文里，跨线程后不会自动传递。

## 深度解答

### 第一层：核心概念

所谓“事务失效”，通常指开发者明明加了 `@Transactional`，但执行结果没有按预期提交或回滚。Spring 声明式事务不是魔法，它依赖代理拦截、事务管理器和回滚规则协同工作，所以任何一个环节出问题，事务都可能看起来“失效”。

### 第二层：常见失效场景

#### 1. 方法不是 `public`

在常见的 Spring 代理模式下，`@Transactional` 一般加在 `public` 方法上更稳妥。若方法是 `private`、`protected` 或包可见，很多情况下代理无法按预期拦截。

```java
@Transactional
private void saveOrder() {
}
```

这种写法往往不会生效。

#### 2. 同类内部自调用

这是最经典的事务失效场景。

```java
@Service
public class OrderService {

    public void create() {
        saveOrder();
    }

    @Transactional
    public void saveOrder() {
        // ...
    }
}
```

`create()` 里直接 `this.saveOrder()`，没有经过 Spring 生成的代理对象，而是对象内部直接调用，因此事务拦截器不会触发。

#### 3. 当前对象不是 Spring 管理的 Bean

如果对象是自己 `new` 出来的，而不是容器管理的 Bean，那么 `@Transactional` 根本不会被代理：

```java
OrderService service = new OrderService();
service.saveOrder();
```

这种场景下事务注解形同虚设。

#### 4. 异常被吃掉，没有继续抛出

Spring 事务回滚依赖异常传播。如果你在事务方法里把异常 catch 住了，又没有继续抛出，事务管理器会认为方法正常结束，于是提交事务。

```java
@Transactional
public void createOrder() {
    try {
        // 数据库操作
        int x = 1 / 0;
    } catch (Exception e) {
        log.error("异常", e);
    }
}
```

最终很可能提交，而不是回滚。

#### 5. 抛出的是受检异常，但没配置回滚

Spring 默认回滚规则是：

- `RuntimeException`
- `Error`

如果抛出的是 `Exception` 这类受检异常（checked exception），默认不一定回滚：

```java
@Transactional
public void createOrder() throws Exception {
    throw new Exception("checked exception");
}
```

此时通常需要：

```java
@Transactional(rollbackFor = Exception.class)
```

#### 6. 配置了错误的事务管理器

如果系统里有多个数据源或多个事务管理器，`@Transactional` 可能没有绑定到正确的那个事务管理器上，导致看似加了事务，实际没管到目标数据源。

#### 7. 数据库引擎本身不支持事务

比如 MySQL 中如果用了不支持事务的存储引擎，就算 Spring 事务配置正确，数据库层面也无法真正回滚。

#### 8. 异步、跨线程导致事务上下文丢失

事务通常绑定在当前线程。若在事务方法里又开新线程、用线程池、`@Async`、异步回调，新的线程默认拿不到原线程事务上下文。

```java
@Transactional
public void createOrder() {
    executor.submit(() -> {
        // 这里默认不在原事务里
    });
}
```

#### 9. `final`、代理方式限制或类设计不适合代理

事务依赖代理。若类或方法设计让代理无法生效，例如某些 `final` 限制、代理方式不匹配，也可能导致事务失效。面试里不一定要展开源码细节，但要知道：**事务本质是代理增强，不是 JVM 原生能力**。

#### 10. 传播行为理解错误

比如方法 A 开启事务，方法 B 设置了不同传播行为，开发者误以为两个操作一定在同一个事务里，但实际上可能：

- B 开了新事务
- B 根本没加入 A
- A 回滚但 B 已经独立提交

这类问题不叫“注解没生效”，但业务表现上常被误判成事务失效。

### 第三层：本质总结

事务失效可以归结成一句话：

```text
没有被代理到
或者
虽然被代理到了，但没有满足回滚和事务生效条件
```

### 第四层：排查思路

线上排查时建议按这个顺序看：

1. 方法是不是 `public`
2. 调用有没有走代理
3. Bean 是不是 Spring 管理
4. 异常有没有被吞
5. 抛出的异常类型是否触发默认回滚
6. 事务管理器和数据源是否匹配
7. 是否跨线程、异步
8. 数据库本身是否支持事务

### 第五层：实践建议

- 新代码优先把事务边界放在 Service 层 `public` 方法
- 事务方法不要被同类内部直接调用
- 异常不要随意吞掉
- 常见业务异常可显式写 `rollbackFor = Exception.class`
- 异步逻辑不要想当然地继承调用方事务

## 回答思路

### 答题逻辑框架

1. 先说 Spring 事务底层依赖 AOP 代理。
2. 再按“没走代理、异常没回滚、配置不匹配、线程边界断”四大类讲。
3. 重点举内部自调用、异常吞掉、checked exception 这三个高频例子。
4. 最后给出排查顺序。

### 重点得分点

- 能说出事务本质依赖代理。
- 能说出同类内部自调用是高频失效点。
- 能说出默认只回滚运行时异常。
- 能说出异步跨线程事务不会自动传递。

### 常见误区

- 认为只要加了 `@Transactional` 就一定回滚。
- 把业务传播行为差异误判成事务失效。
- 不知道异常被吞掉会直接导致事务提交。

### 面试话术

“Spring 事务失效，本质上要么是没走到事务代理，要么是虽然走到了代理，但回滚条件或事务配置没满足。高频场景包括同类内部自调用、方法不是 `public`、对象不是 Spring Bean、异常被 catch 吞掉、抛的是 checked exception 却没配 `rollbackFor`、事务管理器不匹配，以及 `@Async` 或线程池导致事务上下文丢失。”
