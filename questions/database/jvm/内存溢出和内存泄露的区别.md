# 内存溢出和内存泄露的区别

## 联想记忆法

### 记忆口诀/联想

**口诀:"泄漏是'该放的不放',溢出是'地方不够装';泄漏是因,溢出是果"**

把内存想成**仓库**:

- **内存泄漏(Memory Leak)**:货已经卖出去了(对象不再被使用),但仓库管理员**忘了登记出库**(对象仍被强引用),货一直占着货架——**占着茅坑不拉屎**
- **内存溢出(Out Of Memory)**:仓库真的**装不下了**,新货进不来(内存分配失败)——**爆仓了**
- 二者关系:泄漏是**慢性病**(持续占用,慢慢把仓库填满),溢出是**爆发的症状**(装不下抛 OOM);**泄漏最终必然导致溢出**

### 记忆原理

"占着茅坑不拉屎"和"爆仓了"两个生活场景,把抽象概念变成画面:泄漏=**该回收的没回收**,溢出=**真的不够用了**。再记"因→果"关系:**泄漏是溢出的最常见原因**——所以排查溢出,第一步就是查泄漏。这是面试最核心的一句话。

### 关联知识

- **与 GC 关联**:泄漏的本质是"GC 判断该对象还活着"(存在可达引用),GC 机制是理解泄漏的理论基础
- **与 OOM 排查关联**:排查溢出 = 顺着泄漏的思路找"谁把内存慢慢吃掉了"
- **与代码实践关联**:静态集合缓存、未关闭的连接/流、ThreadLocal 不清理是三大高频泄漏源
- **与 JVM 调优关联**:调大堆只治"装不下",治不了"该放的不放"——先修泄漏再谈调参

## 深度解答

### 第一层:核心概念

#### 是什么

| 维度 | 内存泄漏(Memory Leak) | 内存溢出(Out Of Memory) |
|---|---|---|
| 定义 | 对象不再被使用,但仍被引用,**GC 无法回收**,内存被无效占用 | 内存分配时**无足够空间**,抛出 `OutOfMemoryError` |
| 性质 | **原因/慢性病**,是程序设计缺陷 | **结果/急性症状**,是 JVM 抛出的错误 |
| 表现 | 占用率缓慢上升,程序"越来越慢",无明显报错 | 直接抛异常,进程可能崩溃 |
| 能否察觉 | 需监控 GC/堆占用趋势才能发现 | 报错明显,一触即发 |
| 危害 | 长期运行后性能劣化,最终走向溢出 | 进程死亡,业务中断 |

一句话:**泄漏是"垃圾回收不掉",溢出是"内存真的没了";泄漏积累到一定程度就会触发溢出**——泄漏是因,溢出是果。

#### 代码层面的直观对比

```java
// 内存泄漏:不再使用的对象仍被静态集合持有,GC 收不掉
class LeakDemo {
    static List<Object> cache = new ArrayList<>();
    void handle(Request req) {
        cache.add(new BigData(req));   // 用完忘了 remove —— 每个请求都留下一个"死货"
    }
}

// 内存溢出:一次性创建太多对象,堆装不下
void boom() {
    List<byte[]> list = new ArrayList<>();
    while (true) {
        list.add(new byte[10 * 1024 * 1024]);  // 堆迟早被撑爆 → OutOfMemoryError
    }
}
```

### 第二层:底层原理

#### 泄漏为什么收不掉:可达性分析的盲区

GC 用**可达性分析**判定存活:从 GC Roots 出发**能到达的对象就认为是存活的**。"被引用" ≠ "被使用"——一个对象不再有业务价值,但只要**引用链依然存在**(如静态 Map 里的 key),GC 就认为它活着,永远不回收。**JVM 无法理解业务语义**,它只知道"可达即存活",这就是泄漏的技术根源。

#### 三类高频泄漏源(必背)

**① 静态集合/长生命周期容器持有短期对象**

```java
static Map<String, Object> sessionCache = new HashMap<>();
// 只 put 不 remove,key 持续新增 → 静态 Map 永久持有 → 典型泄漏
```

**② 资源未关闭**(连接、流、监听器)

数据库连接、IO 流、Netty channel 不 close,对象通过资源内部引用链(如连接池的活跃列表)一直被持有。**根因往往是异常路径上忘记 finally 关闭**。

**③ ThreadLocal 不清理**

```java
ThreadLocal<BigObject> tl = new ThreadLocal<>();
tl.set(big);            // 用完不 remove
```

线程池的线程**长期存活**,ThreadLocalMap 的 key(ThreadLocal 弱引用)可能被回收,但 **value 强引用还在**,且线程不复用时会跟着线程池一直存活——**"value 泄漏"**。规范:业务代码 finally 里 `tl.remove()`。

#### 溢出为什么发生:四个角度

| 原因 | 说明 |
|---|---|
| 泄漏积累 | 该回收的收不掉,堆被无效对象占满(最常见) |
| 堆本身太小 | 业务真实需求超过 -Xmx,属于容量规划问题 |
| 瞬时大对象 | 一次性加载全表/大文件到内存,峰值超出堆 |
| 特殊区域 | 元空间(动态生成类)、直接内存(NIO)、线程栈(线程数爆炸)各自溢出 |

### 第三层:实践应用

#### 如何判断是泄漏还是容量不足(排查第一步)

```bash
# 观察 Full GC 前后老年代占用
jstat -gc <pid> 5000
```

| GC 后占用趋势 | 结论 | 对策 |
|---|---|---|
| Full GC 后占用**明显回落** | 纯容量不足 | 调大 -Xmx,或优化对象大小 |
| Full GC 后占用**几乎不降** | 内存泄漏 | MAT 分析引用链,修代码 |
| 占用缓慢爬升,每次 GC 回收一点点 | 轻度泄漏 | 监控趋势,尽早处理 |

**关键判据:Full GC 都收不回来的对象,一定是被"不该存在的引用"持有——即泄漏。**

#### 泄漏排查工具链

1. `jmap -dump:format=b,file=heap.hprof <pid>` 抓堆(或开 `-XX:+HeapDumpOnOutOfMemoryError` 自动转储)
2. MAT 打开 dump:
   - `Histogram` 看哪个类型对象占用最大
   - `Dominator Tree` 看持有链
   - `Leak Suspects` 自动标注嫌疑对象与引用路径
3. 顺引用链回代码:如 `ThreadLocalMap -> Entry.value -> byte[]` → 定位 ThreadLocal 未 remove

#### 防御性写法(面试展示工程意识)

```java
// ① 静态缓存必须带容量/过期策略
private static final Map<String, Object> CACHE = Caffeine.newBuilder()
        .maximumSize(10_000).expireAfterWrite(1, TimeUnit.HOURS).build().asMap();

// ② 资源必须 finally 关闭(try-with-resources 更优)
try (InputStream in = new FileInputStream(f);
     OutputStream out = new FileOutputStream(outF)) { ... }

// ③ ThreadLocal 用完必 remove
try {
    tl.set(bigObj);
    doWork();
} finally {
    tl.remove();
}
```

### 第四层:深入思考

#### 追问 1:泄漏一定导致溢出吗?

**长期运行必然**。泄漏使可用内存持续减少,哪怕开始内存富余,也会在某个时刻耗尽(除非泄漏对象量级可忽略且系统定期重启)。但短周期进程(如批处理跑完即退)可能"带病运行"不溢出。

#### 追问 2:Java 有"自动内存管理"为什么还会泄漏?

自动内存管理解决的是"**忘记释放**"的显式问题,解决不了"**该释放时引用还在**"的隐式问题——GC 按引用可达性工作,无法识别"对象已无业务价值"。所以泄漏不是 Java 的缺陷,而是**引用生命周期管理不当**。

#### 追问 3:泄漏导致溢出 vs 大对象导致溢出,现象上怎么区分?

- 泄漏:运行**越久**越容易爆,Full GC 后占用不降,复现需要时间
- 大对象:爆在**峰值时刻**(如某次大查询),Full GC 后占用回落,可压测复现

#### 追问 4:弱引用能根治泄漏吗?

弱引用(WeakReference)是**缓解手段**:ThreadLocal 的 key 用弱引用就是例子——但弱引用对象**下一次 GC 即回收**,语义脆弱,业务缓存用弱引用会导致频繁失效。**根治之道仍是正确管理生命周期**(remove、过期策略、作用域控制),而不是依赖引用类型。

## 回答思路

### 答题逻辑框架(约 2 分钟)

1. **一句话定调**:泄漏是"该回收的回收不掉"(原因/慢性),溢出是"内存真不够了"(结果/症状);**泄漏必然导致溢出**
2. **对比展开**:定义、性质、表现、危害四维度
3. **讲泄漏技术根源**:可达性分析"可达即存活",引用存在 ≠ 对象被使用
4. **背三个高频泄漏源**:静态集合、资源未关闭、ThreadLocal 不清理(各举一行代码)
5. **讲排查方法**:Full GC 后占用是否回落判断泄漏 vs 容量;MAT 找引用链
6. **收尾防御**:过期缓存、try-with-resources、finally remove(工程意识)

### 重点得分点

- 准确说出"**泄漏是因、溢出是果**"的因果关系
- 准确说出**判断泄漏 vs 容量不足的方法**(Full GC 后老年代占用是否回落)——这是区分二者的硬核标准
- 背出三大泄漏源并各举一个代码场景
- 说出泄漏的技术根源:GC 可达性分析"可达即存活",无法识别业务语义
- 说出 ThreadLocal 泄漏的细节:key 弱引用、**value 强引用泄漏**(细节控加分)

### 常见误区

- ❌ 把两者当同义词——一个原因是过程,一个是结果的错误
- ❌ 说"泄漏就是内存不够"——泄漏是"该回收没回收",溢出才是"不够"
- ❌ 说"JVM 自动回收就不会泄漏"——泄漏恰恰发生在"GC 认为还活着"的对象上
- ❌ 说"调大堆能根治泄漏"——只能推迟溢出时间,泄漏还在
- ❌ 忽略 ThreadLocal 泄漏——线程池场景下这是高频坑

### 过渡话术

- 开场:"一句话区分:泄漏是垃圾收不掉,溢出是内存不够用;而且泄漏是溢出的最主要原因。展开说……"
- 从理论到实践:"怎么在实际项目里判断是哪种?看 Full GC 之后老年代降不降——回落是容量问题,不降就是泄漏……"
- 收尾:"所以我的习惯是:排查溢出先查泄漏,写代码时把缓存、资源、ThreadLocal 这三类高危点提前防御。"
