# JVM的GC垃圾回收机制

## 联想记忆法

### 记忆口诀/联想

**口诀:"先问死活,再选算法,最后挑收集器"**

把 GC 想成**公司清理工位**:

1. **先判断"工位还有没有人用"**(对象是否存活)——用**可达性分析**:从 GC Roots 出发,能链到的对象都是"有人在用",链不到的就是"该清的空位"
2. **再选"清理方式"**(回收算法):标记-清除(贴上"废弃"标签再扫掉)、标记-复制(把活人搬去新工位,旧区整体清空)、标记-整理(把活人往一起挤,腾出连续空间)
3. **最后挑"保洁队"**(垃圾收集器):Serial(单线程保洁)、Parallel(多线程保洁)、CMS(边干边扫)、G1(把办公区分成小格子逐个清扫)

### 记忆原理

用"清理工位"的完整故事,把 GC 三件套(**判活 → 算法 → 收集器**)按"先干什么后干什么"的因果关系串起来——这是 GC 知识的骨架,面试时顺着这个顺序讲不会乱。三个算法的名字就对应三个动作(贴标扫掉/搬走清空/挤拢腾地),好记又形象。**STW(Stop The World)** 是贯穿始终的线索:"保洁队干活时,所有人必须停下工作"。

### 关联知识

- **与 JVM 内存结构关联**:GC 主战场是堆(新生代/老年代),分代假说决定"新生代用复制、老年代用标记类算法"
- **与类加载关联**:方法区的类卸载也是 GC 一部分(元空间回收,条件苛刻)
- **与 JVM 调优关联**:GC 频率、停顿时间直接决定调优方向——调优本质上就是调 GC 行为
- **与 OOM 关联**:GC 无法回收的内存(泄漏对象)会一步步把堆撑爆,最终 OOM

## 深度解答

### 第一层:核心概念

#### 是什么

GC(Garbage Collection)是 JVM 的**自动内存回收机制**:自动识别并回收"不再被引用的对象",腾出堆空间,避免开发者手动管理内存(相比 C/C++ 的 malloc/free)。三个问题构成 GC 全貌:

1. **哪些对象要回收** —— 判断存活(可达性分析)
2. **怎么回收** —— 回收算法(标记-清除 / 标记-复制 / 标记-整理)
3. **谁来回收、何时回收** —— 垃圾收集器(Serial / Parallel / CMS / G1 / ZGC)

#### 分代假说(一切收集器设计的基础)

**弱分代假说**:绝大多数对象"朝生夕灭"(如方法内的临时对象),只有少数活很久。**强分代假说**:熬过多次回收的对象,越难被回收。据此把堆分成:

```
堆 (Heap)
├── 新生代 (Young)          — 对象诞生地,回收频繁,用"标记-复制"
│   ├── Eden(伊甸园,新对象)     8 : 1 : 1
│   ├── Survivor S0             (Eden : S0 : S1 默认比例)
│   └── Survivor S1
└── 老年代 (Old)            — 熬过 N 次 Minor GC 的对象,回收少,用标记类算法
```

新生代对象每熬过一次 GC,**年龄 +1**,默认到 15(可通过 `-XX:MaxTenuringThreshold` 调)升入老年代;大对象直接进老年代。

### 第二层:底层原理

#### ① 判断对象存活:可达性分析(Reachability Analysis)

主流 JVM 用**可达性分析**而非引用计数(引用计数有循环引用无解问题:两个对象互相引用但都不再可达,计数永远不为 0,GC 无法回收):

从 **GC Roots** 集合出发,沿引用链遍历,能被到达的对象是**存活的**,其余**判定为垃圾**。

GC Roots 有哪些:

| GC Root | 说明 |
|---|---|
| 虚拟机栈(栈帧局部变量表)中引用的对象 | 正在被方法使用的对象 |
| 方法区中静态属性引用的对象 | `static` 引用的对象 |
| 方法区中常量引用的对象 | 如字符串常量池中的引用 |
| 本地方法栈中 JNI 引用的对象 | native 方法引用的对象 |
| 活跃线程对象、被同步锁(synchronized)持有的对象等 | 附加根 |

#### ② 四种引用类型(决定回收优先级)

| 引用 | 回收时机 | 典型用途 |
|---|---|---|
| 强引用(Strong) | 永不回收(可达即存活) | 普通 `new` 赋值 |
| 软引用(Soft) | **内存不足时**回收 | 缓存(内存敏感的图片缓存) |
| 弱引用(Weak) | **下次 GC 即回收** | ThreadLocal 的 ThreadLocalMap key |
| 虚引用(Phantom) | 无法通过它访问对象,回收后通知 | 堆外内存(直接内存)回收通知、对象生命周期跟踪 |

#### ③ 三大回收算法

**标记-清除(Mark-Sweep)**
- 第一步标记存活对象,第二步**清除未被标记的**
- 缺点:产生**内存碎片**;标记和清除都要停顿(STW)

**标记-复制(Copying)**
- 把存活对象**复制到另一块空区**,整块旧区一次性清空
- 优点:无碎片、高效(存活对象少时);缺点:**浪费一半空间**(用 S0/S1 把浪费降到 10%),不适合存活对象多的老年代

**标记-整理(Mark-Compact)**
- 标记存活对象后,**把它们向一端移动**(压缩),清理边界以外的空间
- 优点:无碎片、空间利用率高;缺点:**移动对象需要更新引用**,停顿更长,通常配合"分段式/并行的整理"

> 演化主线:新生代用**复制**(存活少、快);老年代用**标记-清除或标记-整理**(存活多、不能复制);CMS 用清除(碎片由压缩兜底),G1 混合两者。

#### ④ Stop The World(STW)

GC 执行时,所有用户线程必须暂停,等待 GC 完成——因为**对象引用关系在运动中无法安全统计**。STW 时间(停顿)是收集器设计的**核心优化目标**:从 Serial 的"全停顿",到 CMS/G1 的"低停顿",到 ZGC 的"几乎不停顿(纳秒/毫秒级)"。

#### ⑤ 常见垃圾收集器(JDK 演进视角)

| 收集器 | 区域 | 特点 | 状态 |
|---|---|---|---|
| Serial | 新生代 | 单线程,简单,Client 模式默认 | 古老 |
| Parallel Scavenge | 新生代 | 多线程,吞吐量优先 | JDK8 默认(Parallel + Parallel Old) |
| ParNew | 新生代 | 多线程,配合 CMS | 被 G1 取代 |
| CMS | 老年代 | **并发标记清除**,低停顿 | 已被 G1 取代(JDK9 标记废弃) |
| G1 | 整堆 | **分 Region + 可预测停顿**,默认 | JDK9+ 默认 |
| ZGC / Shenandoah | 整堆 | 着色指针、染色指针,亚毫秒停顿 | JDK15+ 生产可用 |

**G1 核心思想**:把堆分成**大量小 Region**(默认 2048 个),新生代/老年代不再连续,而是 Region 的逻辑集合;跟踪每个 Region 的垃圾占比,**优先回收垃圾最多的 Region**(Garbage First),且可设置停顿目标 `-XX:MaxGCPauseMillis`。内部用**三色标记(Tri-color Marking)+ 写屏障(SATB)**处理并发标记,配合 **RSet(Remembered Set)** 处理跨 Region 引用,实现在回收的同时基本不停顿地工作。

### 第三层:实践应用

#### GC 日志怎么看(面试/排查必备)

```bash
java -Xlog:gc*:gc.log           # JDK9+ 统一日志
java -XX:+PrintGCDetails        # JDK8 传统参数
```

典型日志片段含义:

```text
[GC (Allocation Failure) [PSYoungGen: 6144K->512K(6144K)] 6144K->461K(19968K)
 0.0024389 secs]
```

- `PSYoungGen: 6144K->512K`:新生代回收前 6144K → 回收后 512K(存活率低,说明新生代工作正常)
- `6144K->461K(19968K)`:整个堆从 6144K → 461K
- `Allocation Failure`:Eden 放不下新对象,触发 Minor GC

#### 调参实战(配合 -Xms/-Xmx)

```bash
java -Xms2g -Xmx2g -Xmn1g \
     -XX:SurvivorRatio=8 \
     -XX:MaxTenuringThreshold=15 \
     -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
     -Xlog:gc*:gc.log MyApp
```

#### 常见 GC 异常排查

- **频繁 Full GC**:老年代不足(大对象多、内存泄漏、晋升过快)→ 看日志确认,再决定加内存还是修泄漏
- **GC 停顿过长**:换 G1 设置停顿目标、加大堆、检查是否 GC 线程抢占
- **Concurrent Mode Failure**(G1/CMS 特有):并发回收来不及,退化为串行 Full GC——需要调大堆或调触发阈值

### 第四层:深入思考

#### 追问 1:为什么新生代不用标记-清除而用复制?

新生代对象**存活率极低**(一般 <10%),复制成本与存活量成正比,复制很快且无碎片;老年代存活率高,复制成本高,所以用标记-清除/整理。这正是**分代假说在算法选择上的落地**。

#### 追问 2:GC Roots 里的"方法区静态引用"举个例子?

`private static List<Object> cache;`——只要这个静态字段存在且不置 null,cache 引用链上的所有对象**永远不会被回收**,这就是**静态集合内存泄漏**的根因,也是排查 OOM 时最先检查的点。

#### 追问 3:什么是"三色标记"?(G1/CMS 并发标记细节)

把对象标成:白(未访问)、灰(自身已访问、引用未访问完)、黑(自身与引用都访问完)。并发标记时,如果**黑色对象新增引用白色对象**,可能把"仍被使用"的白色对象误判成垃圾(漏标)。解决办法:G1 用 **SATB(Snapshot At The Beginning)写屏障**记录引用变更;CMS 用**增量更新(Incremental Update)**,配合最终重标记(Remark)修正。

#### 追问 4:ZGC 为什么停顿这么短?

核心是**染色指针(Colored Pointer)**:把引用指针的额外位用于标记对象状态,读写屏障极轻;回收过程**并发整理**(移动对象不暂停用户线程),配合多阶段并发标记,把 STW 压到毫秒级以下。代价是只能跑在 64 位机器上,且占用部分地址空间。

#### 追问 5:GC 什么时候会回收方法区(元空间)的类?

条件苛刻:类**无任何实例、ClassLoader 已被回收、类对应的 Class 对象无引用**。所以反射/动态代理滥用时元空间"只进不出",最终元空间 OOM——这也是"类卸载难"的经典解释。

## 回答思路

### 答题逻辑框架(约 3 分钟)

1. **先给框架**:GC 解决三件事——判活、算法、收集器
2. **判活**:可达性分析 + GC Roots 举例(局部变量/静态引用/常量/JNI),顺带说引用计数为什么不行(循环引用)
3. **算法**:标记-清除(碎片)/ 标记-复制(半区浪费)/ 标记-整理(移动开销),对应分代:新生代复制、老年代标记类
4. **收集器演进**:Serial → Parallel(JDK8 默认)→ CMS(低停顿)→ G1(JDK9+ 默认,Region + 可预测停顿)→ ZGC(亚毫秒)
5. **补充**:STW 概念 + GC 日志实战解读,体现工程经验

### 重点得分点

- 准确说出**可达性分析从哪些 GC Roots 出发**(至少 4 个:栈引用/静态引用/常量/JNI)
- 准确说出**三种算法及各自的缺点**(碎片/空间浪费/移动开销)
- 准确说出**分代对应算法**:新生代复制、老年代标记-清除/整理,并解释原因(存活率)
- 准确说出 **JDK8 默认 Parallel、JDK9+ 默认 G1**
- 说出 STW 是什么 + 为什么必须停(引用关系在运动中无法统计)
- 说出四种引用类型(强/软/弱/虚)与回收时机

### 常见误区

- ❌ 说"用引用计数判断存活"——主流 JVM 用可达性分析,引用计数有循环引用缺陷
- ❌ 说"新生代用标记-清除"——新生代是复制算法
- ❌ 说"CMS 是 JDK9 默认"——JDK9 起默认 G1,CMS 已废弃(JDK14 移除)
- ❌ 说"G1 是老年代收集器"——G1 是整堆收集器,靠 Region 分代
- ❌ 说"GC 只回收堆"——元空间(方法区)类卸载也是 GC 的职责

### 过渡话术

- 开场:"GC 全貌是三件事:怎么判断对象该死、用什么算法收、用哪个收集器执行。我按这个顺序讲……"
- 从算法到收集器:"算法是理论,收集器是工程实现——不同收集器就是在停顿时长、吞吐量、碎片之间做取舍……"
- 收尾:"实践中最常用的是看 GC 日志判断问题,比如 Allocation Failure 说明新生代不足,Full GC 频繁就要查老年代和泄漏。"
