# 类加载器加载过程

## 联想记忆法

### 记忆口诀/联想

**口诀:"加验准解初——加载、验证、准备、解析、初始化"**

把类加载想成**新员工入职流程**:

1. **加载**:人事把简历扫描进系统,建档案(把 .class 字节码读进内存,生成 Class 对象)
2. **验证**:审核简历真实性(检查字节码格式、合法性,防止伪造)
3. **准备**:先给新员工预分配工位和初始薪资(为静态变量分配内存并赋默认值)
4. **解析**:把名片上的"职位名"翻译成实际"工位号"(符号引用 → 直接引用)
5. **初始化**:正式开工,执行静态代码块、静态变量真正赋值(执行 `clinit`)

### 记忆原理

用**入职流程**这条故事线把五个阶段串起来:每个阶段对应一个具体动作(建档案/审核/分工位/翻名片/开工),"加载-验证-准备-解析-初始化"五个动词按流程顺序记,不易遗漏。重点区分**准备**(默认值,如 int=0)和**初始化**(真实赋值,如 int=5)——这是最常被问错的点,用"预发工资 vs 正式发工资"的对比锚住。

### 关联知识

- **与双亲委派关联**:加载阶段由类加载器完成,而类加载器遵循双亲委派——"由谁去建档案"是个层层上报的过程
- **与 JVM 内存结构关联**:加载后的类元信息进**方法区(元空间)**,Class 对象在**堆**上,静态变量也归方法区
- **与 JIT 关联**:初始化之后类才算真正"可用",字节码才能被解释执行或即时编译
- **与 OOM 关联**:动态生成类过多(反射/CGLIB)导致元空间溢出,对应加载阶段过于频繁

## 深度解答

### 第一层:核心概念

#### 是什么

类加载(Class Loading)是 JVM 把 `.class` 字节码文件**变成可执行的类**的全过程,分为 **加载、验证、准备、解析、初始化** 五个阶段。前四个阶段统称"连接(Linking)",其中**加载、验证、准备**是 JVM 规范**必须严格按顺序开始**的,解析和初始化可以交叉(解析可在初始化后再触发,即"动态绑定"场景)。

```
.class 字节码
   │
   ▼
① 加载 (Loading)     — 读字节码 → 生成 Class 对象
② 验证 (Verification) — 检查字节码合法性
③ 准备 (Preparation)  — 静态变量分配内存 + 默认值
④ 解析 (Resolution)   — 符号引用 → 直接引用
⑤ 初始化 (Initialization) — 执行 clinit,静态变量真实赋值
```

#### 各阶段职责

| 阶段 | 做什么 | 关键产物/动作 |
|---|---|---|
| 加载 | 通过类的全限定名获取字节码,存入方法区,堆中生成 `java.lang.Class` 对象 | 类加载器(ClassLoader)参与 |
| 验证 | 文件格式、元数据、字节码、符号引用四重校验 | 防止恶意/损坏字节码 |
| 准备 | 为静态变量分配内存并赋**零值**(默认值) | int → 0,对象引用 → null |
| 解析 | 把常量池中的符号引用(Symbolic Reference)替换为直接引用(Direct Reference) | 类/字段/方法/接口解析 |
| 初始化 | 执行 `<clinit>()` 方法:静态变量赋值语句、静态代码块 | **类真正可用**的起点 |

---

### 第二层:底层原理

#### ① 加载(Loading)

- 触发条件:使用 `new`、反射 `Class.forName()`、访问静态成员等**主动使用**场景
- 核心动作:类加载器根据**全限定名**找到并读取二进制字节流(可来自 .class 文件、JAR、网络、动态生成),把字节流**静态结构转化为方法区的运行时数据结构**,最后在堆中生成代表该类的 `java.lang.Class` 对象,作为方法区类信息的访问入口
- 注意:加载阶段**可以自定义**(重写 `loadClass` 或 `findClass`),是"打破双亲委派"的切入点

#### ② 验证(Verification)

保证字节码**不会危害 JVM**,四重校验:

- **文件格式验证**:魔数 `0xCAFEBABE`、版本号是否受支持
- **元数据验证**:类是否有父类、父类是否允许被继承(如 final 类)
- **字节码验证**:栈帧的操作数栈与局部变量表类型是否匹配、跳转指令目标是否合法——最复杂的一步
- **符号引用验证**:引用的类/方法/字段是否存在、访问权限是否允许

#### ③ 准备(Preparation)

- 为**静态变量**分配内存(方法区/元空间)并赋**默认零值**
- 例:`static int count = 5;` 在准备阶段 count 的值是 **0**(不是 5!);`static final String NAME = "a";` 这种 **ConstantValue**(编译期常量)例外,准备阶段直接赋 5/"a"
- 实例变量不在此阶段(随对象分配在堆)

#### ④ 解析(Resolution)

- 把常量池中的**符号引用**(以字符串形式描述的目标,如 `Ljava/lang/String;`)替换为**直接引用**(指向内存中的具体地址/句柄)
- 大部分解析在**使用到时才触发**(惰性解析),支持**动态绑定**:如方法调用 `invokevirtual` 在运行期才确定实际目标方法

#### ⑤ 初始化(Initialization)

- 执行 `<clinit>()` 类构造器:由静态变量赋值语句 + 静态代码块**按源码顺序**合并而成
- 触发条件(6 种**主动使用**):`new` 实例、访问静态成员(非编译期常量)、反射、初始化子类(父类先初始化)、作为 JVM 启动入口(main 方法所在类)、JDK7+ 的动态语言支持
- **被动使用不触发初始化**:通过子类引用父类静态字段、定义类数组、引用编译期常量(常量折叠)、用 `Class.forName(x, false, loader)` 等

```java
class Parent { static int x = 1; }
class Child extends Parent {}

System.out.println(Child.x);  // 只初始化 Parent,不初始化 Child(被动引用)
System.out.println(Sub.b);    // b 是编译期常量,连 Parent 都不会初始化
```

#### 为什么需要这些阶段

五阶段是**安全 + 性能**的平衡:验证防恶意字节码破坏 JVM(这是 JVM 安全沙箱的基石);准备把内存操作与业务逻辑解耦;解析惰性化避免启动即全量解析的开销;初始化才真正执行用户代码,所以只有"真正要用"才走到最后一步。

### 第三层:实践应用

#### 什么时候用自定义类加载器

- **热部署**:重新加载类(同全限定名不同 ClassLoader,实现"类的隔离与替换")
- **字节码加密**:加载时解密 `.class`
- **资源隔离**:如 Tomcat 每个 Web 应用一个 WebAppClassLoader,避免类冲突;JDBC 的 `DriverManager` 通过 SPI 加载不同数据库驱动

```java
// 自定义类加载器核心:重写 findClass(而非 loadClass,保留双亲委派)
class MyClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = loadFromCustomSource(name);   // 自定来源
        return defineClass(name, bytes, 0, bytes.length);
    }
}
```

#### 经典排查场景

- **NoClassDefFoundError**:类**存在但初始化失败**(前一次初始化抛异常),区别于 ClassNotFoundException(加载阶段找不到)
- **初始化死锁**:`<clinit>` 内线程互相等待——静态初始化期间 JVM 会给类加初始化锁
- **元空间 OOM**:频繁反射/动态代理生成类,加载阶段过载

### 第四层:深入思考

#### 追问 1:加载、验证、准备三个阶段"按顺序开始"是什么意思?

意味着这三阶段是**串行开启**的,但**完成时间不保证**——规范允许它们交叉/重叠完成,HotSpot 的"快速验证"还会合并部分校验。所以面试时不要说"严格按顺序执行完毕",说"按顺序**开始**"。

#### 追问 2:接口的初始化时机和类一样吗?

接口初始化**不要求父接口先初始化**(除非用到父接口的默认方法),而类的初始化要求**父类先初始化**。`static final` 常量在准备阶段就赋值,接口的初始化锁(初始化接口实例)也与类不同。

#### 追问 3:初始化失败会怎样?

`<clinit>` 抛异常 → JVM 捕获并抛 `ExceptionInInitializerError`(Error 级别,不是 Exception),且该类会被标记为"初始化失败",**后续再次触发时直接抛 NoClassDefFoundError,不会重试**。经典连环坑。

#### 追问 4:加载阶段获取字节流的途径有哪些?

文件系统 .class、JAR/ZIP、网络(远程加载)、动态生成(代理类)、数据库、加密文件等——加载阶段给 JVM 极高的灵活性,这也是"插件化架构"的基础。

## 回答思路

### 答题逻辑框架(约 2 分钟)

1. **先背五阶段口诀**:加载、验证、准备、解析、初始化
2. **每个阶段一句话职责**:加载读字节码、验证查合法性、准备分内存赋零值、解析换引用、初始化执行 clinit
3. **重点区分准备 vs 初始化**:0 vs 真实值,举 `static int count = 5` 的例子
4. **说触发条件**:6 种主动使用 + 被动引用不初始化(举子类引用父类字段的例子)
5. **落到实践**:自定义类加载器重写 findClass、热部署场景

### 重点得分点

- 五个阶段名称及顺序**一字不差**
- "准备阶段赋**零值**、初始化阶段才真正赋值"——高频考点,必答
- 主动使用/被动引用判断(子类引用父类静态字段不初始化子类)
- 验证阶段的四重校验(至少说出格式/字节码)
- 类加载器参与的是**加载阶段**,`loadClass` vs `findClass` 的区别(加分)

### 常见误区

- ❌ 说"加载就是 new 出对象"——加载产生的是 Class 对象,实例化是初始化阶段 `new` 之后的动作
- ❌ 说"准备阶段把 static int count = 5 赋成 5"——那是初始化阶段
- ❌ 说"初始化是 JVM 做的,不需要执行代码"——初始化会执行静态代码块和赋值语句(用户代码)
- ❌ 把 `ClassNotFoundException` 和 `NoClassDefFoundError` 混为一谈——前者加载阶段找不到,后者初始化失败后的"历史遗留"

### 过渡话术

- 开场:"类加载分为五个阶段,我按顺序讲:加载、验证、准备、解析、初始化,其中最容易混淆的是准备和初始化……"
- 从加载引到双亲委派:"加载阶段是由类加载器完成的,这里就引出了双亲委派机制——加载请求会先交给父加载器……"
- 从初始化引到实践:"理解了五个阶段,就能明白为什么动态代理会撑爆元空间,以及热部署是怎么做到的——本质都是加载阶段的可定制性。"
