# Gateway网关的特性？

## 联想记忆法

### 记忆口诀/联想

**口诀：统一入口、动态路由、过滤增强、限流熔断、响应式高并发。**

把 Gateway 想成小区总门岗：

- **统一入口**：所有请求先过门岗。
- **动态路由**：门岗决定该把人带到哪栋楼。
- **过滤增强**：门口先查证件、登记、改写信息。
- **限流熔断**：人太多先拦，后面楼出故障先别放行。
- **响应式处理**：门岗用异步方式接待更多人。

### 记忆原理

Gateway 的价值不在“转发”这一个动作，而在“**统一入口后的流量治理**”。所以记忆时不要只记“它是网关”，而要记住它在入口层能做的 5 件事：路由、过滤、安全、治理、观测。

### 关联知识

- Spring Cloud Gateway 建立在 **Spring WebFlux** 和 **Project Reactor** 之上，天然偏响应式。
- 它通常和 **Nacos/Eureka**、**OpenFeign**、**Sentinel/Resilience4j** 配合使用。
- 网关不等于注册中心。注册中心解决“服务在哪”，网关解决“请求怎么进、怎么转、怎么控”。

## 深度解答

### 第一层：核心概念

Spring Cloud Gateway 是 Spring Cloud 体系里的 API 网关组件，主要作用是把所有外部请求统一接入，然后根据路由规则、断言和过滤器把请求转发到对应下游服务。

它本质上解决的是三件事：

1. **统一入口**
2. **统一治理**
3. **统一转发**

所以在微服务里，Gateway 不只是“代理服务器”，更像“流量总调度中心”。

### 第二层：Gateway 的主要特性

#### 1. 统一入口

客户端不再直接调用每个服务，而是统一访问网关：

```text
客户端 -> Gateway -> 用户服务 / 订单服务 / 库存服务 / 支付服务
```

这样做的好处是：

- 对外只暴露一个入口
- 下游服务地址变化不会直接影响客户端
- 登录、鉴权、日志、限流等横切逻辑可以集中处理

#### 2. 动态路由

Gateway 的核心能力就是 **Route（路由）**。每条路由通常由三部分组成：

- `id`：路由唯一标识
- `uri`：目标服务地址
- `predicates`：路由断言，决定请求是否匹配
- `filters`：过滤器，对请求或响应做增强

示例：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/orders/**
          filters:
            - StripPrefix=1
```

这里表示：访问 `/orders/**` 的请求，经过匹配后转发到注册中心里的 `order-service`。

#### 3. 丰富的断言与过滤机制

Gateway 不是只看 URL。它可以根据：

- 路径
- Host
- Header
- Query 参数
- Method
- Cookie
- 时间窗口
- 客户端 IP

来决定是否匹配某条路由。

过滤器则可以做：

- 修改请求头、响应头
- 改写路径
- Token 鉴权
- 日志埋点
- 黑白名单
- 限流
- 重试
- 熔断

这意味着 Gateway 把“请求是否能进”和“请求进来后怎么处理”拆成了两套能力：**断言负责选路，过滤器负责加工**。

#### 4. 与注册中心整合

Gateway 常通过 `lb://服务名` 的方式和注册中心协作：

```yaml
uri: lb://user-service
```

这表示它不是把请求写死转发到某个 IP，而是先通过注册中心拿到 `user-service` 的实例列表，再由负载均衡组件选一个实例转发。

因此网关的转发链路通常是：

```text
请求 -> Gateway
     -> 根据断言命中路由
     -> 通过服务名找实例
     -> 负载均衡选节点
     -> 转发到下游
```

#### 5. 过滤器链模型

Gateway 有两类常见过滤器：

- **GlobalFilter**：全局过滤器，作用于所有路由
- **GatewayFilter**：路由级过滤器，只作用于某条路由

请求会经过“前置过滤 -> 路由转发 -> 后置过滤”的责任链。常见场景：

- 前置：鉴权、签名校验、限流、日志
- 后置：统一响应头、统计耗时、审计

#### 6. 响应式与高并发

Gateway 基于 Netty + WebFlux，使用的是响应式非阻塞模型，而不是传统 Servlet 同步阻塞模型。优点是：

- 线程利用率高
- 更适合 IO 密集型场景
- 更适合做大量短连接转发

但这不代表所有场景都天然更快。如果过滤链里做了大量阻塞操作，比如阻塞式数据库访问、同步远程调用，响应式优势也会被抵消。

#### 7. 流量治理能力

Gateway 常承载的治理能力包括：

- 限流
- 熔断
- 重试
- 灰度发布
- 金丝雀发布
- 权重路由
- 跨域处理（CORS）

因此网关经常是“系统第一道防线”。

### 第三层：实践应用

实际项目中，Gateway 常见职责是：

1. 做统一鉴权
2. 统一处理跨域
3. 根据路径转发到不同微服务
4. 在入口层做限流和黑白名单
5. 记录访问日志和 TraceId
6. 做灰度路由和版本路由

例如：

```text
/api/user/**    -> user-service
/api/order/**   -> order-service
/api/pay/**     -> pay-service
```

### 第四层：深入思考

#### Gateway 和 Nginx 的区别

- **Nginx** 更偏通用反向代理和静态资源服务器
- **Gateway** 更偏微服务场景下的业务网关

Gateway 对 Spring 生态集成更深，适合做服务发现、断言、过滤、鉴权和灰度路由；Nginx 更擅长高性能反向代理、静态资源和 TLS 终止。很多线上系统会两者配合使用，而不是二选一。

#### Gateway 和 Zuul 的区别

- Zuul 1 基于 Servlet，同步阻塞
- Gateway 基于 WebFlux，响应式非阻塞
- Gateway 在断言和过滤器模型上更现代，也更适合当前 Spring Cloud 生态

### 答题逻辑框架

1. 先给出一句话定义：Gateway 是微服务统一入口。
2. 再讲五个核心特性：路由、断言、过滤、治理、响应式。
3. 补充它和注册中心、负载均衡的协作关系。
4. 最后对比 Nginx 或 Zuul，加分。

### 重点得分点

- 说清 Gateway 不只是转发，还负责统一治理。
- 说清“断言选路、过滤加工”的职责分工。
- 说清它与注册中心和负载均衡的协作。
- 说清它基于 WebFlux 和 Netty。

### 常见误区

- 把 Gateway 说成注册中心。
- 只说“能转发请求”，忽略限流、熔断、灰度、鉴权。
- 以为用了响应式就一定无脑高性能。

### 面试话术

“Gateway 是微服务的统一入口，核心特性可以概括为动态路由、路由断言、过滤器链、限流熔断和响应式高并发。它通常和注册中心配合，通过 `lb://服务名` 找到下游实例，再结合过滤器完成鉴权、日志、限流和灰度发布，所以它不只是代理转发，而是入口层的流量治理中心。”
