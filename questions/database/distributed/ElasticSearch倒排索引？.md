# ElasticSearch倒排索引？

## 联想记忆法

### 记忆口诀/联想

**口诀：正排看文档，倒排看单词；先分词建表，再按词找文档。**

把倒排索引想成书后的“关键词目录”：

- 普通目录是“第几页有什么内容”。
- 倒排索引是“某个关键词出现在哪些文档、哪些位置”。

### 记忆原理

倒排索引的核心不是把文档倒过来存，而是把查询方向倒过来：**从输入文档的顺序查找，变成从关键词反查文档**。记住“词 -> 文档列表”这条映射，就抓住了它的本质。

### 关联知识

- Elasticsearch 的 `text` 字段通常要经过 analyzer 分词、规范化和建立索引。
- 倒排索引主要由词典（Term Dictionary）和倒排表（Posting List）组成。
- BM25 等相关性算法会结合词频、文档频率和字段长度计算匹配分数。
- 倒排索引适合全文检索；精确过滤通常依赖 `keyword` 字段和 Doc Values。

## 深度解答

### 第一层：核心概念

倒排索引（Inverted Index）是一种从**词项（Term）反向查找文档**的数据结构。

假设有 3 篇文档：

```text
文档 1：Java 分布式系统
文档 2：Java 微服务
文档 3：分布式事务
```

正排视角是：

```text
文档 1 -> Java、分布式、系统
文档 2 -> Java、微服务
文档 3 -> 分布式、事务
```

倒排视角是：

```text
Java    -> 文档 1、文档 2
分布式  -> 文档 1、文档 3
系统    -> 文档 1
微服务  -> 文档 2
事务    -> 文档 3
```

用户搜索“Java 分布式”时，搜索引擎只需要取两个词对应的文档列表，再做集合运算和相关性计算，而不必逐篇扫描所有文档。

### 第二层：倒排索引是怎么建立的

#### 1. 文本分析

文档写入 Elasticsearch 后，字段会按照 Mapping 指定的 analyzer 进行分析。典型过程包括：

- 字符过滤（Character Filter）
- 分词（Tokenizer）
- 词项过滤（Token Filter）

例如英文文本可以被切成多个单词并统一大小写；中文则需要选择合适的中文分词器。分词结果直接影响后续能否搜索到目标内容。

#### 2. 建立词典

把所有文档分析出的词项去重、排序并建立词典。词典负责回答“这个词存不存在”，并通过 FST 等结构提高词项查找效率。

#### 3. 建立倒排表

每个词项对应一个 Posting List，记录包含该词的文档信息：

- 文档 ID
- 词频
- 词项在文档中的位置
- 可能还有偏移量、Payload 等信息

Posting List 通常会使用压缩和跳表等结构，减少存储空间并加快多个词项列表的合并。

#### 4. 写入 Segment

Elasticsearch 底层基于 Lucene。写入的数据会形成不可变的 Segment，后台再通过合并减少 Segment 数量。新数据要先进入内存缓冲和事务日志，刷新后才能被搜索到，合并则会重写更大的 Segment。

### 第三层：查询时发生什么

用户执行全文查询时，Elasticsearch 大致经历：

```text
查询文本
  -> 使用搜索 analyzer 分析
  -> 得到查询词项
  -> 查找每个词项的 Posting List
  -> 合并文档列表
  -> 计算相关性得分
  -> 返回排序后的文档
```

搜索 analyzer 不一定必须和索引 analyzer 完全相同，但实际设计中通常保持兼容，否则可能出现“写入时拆成一种词，查询时拆成另一种词”的召回问题。

### 第四层：为什么倒排索引查询快

#### 1. 避免全表扫描

查询从词典直接定位词项，再读取对应 Posting List，不必逐个文档检查全文。

#### 2. Posting List 适合集合运算

多个关键词查询可以对文档 ID 列表做交集、并集和差集。倒排表通常经过排序和压缩，适合快速合并。

#### 3. 相关性计算有专门结构

倒排索引可以提供词频、文档频率和位置等信息，支持 TF-IDF、BM25、短语匹配和高亮等全文检索能力。

### 第五层：倒排索引和正排索引的区别

| 对比项 | 正排索引 | 倒排索引 |
|---|---|---|
| 方向 | 文档 -> 词项 | 词项 -> 文档 |
| 擅长 | 根据文档读取字段 | 根据关键词查文档 |
| 典型场景 | 文档详情、字段读取 | 全文检索、关键词搜索 |
| 查询代价 | 搜索关键词时可能要扫描 | 直接定位词项并合并列表 |

Elasticsearch 并不是只有倒排索引。`text` 字段主要依靠倒排索引做全文检索，`keyword` 字段常配合 Doc Values 做排序、聚合和精确过滤，两者解决的问题不同。

### 第六层：倒排索引的局限

- 写入时需要分词和建索引，写入成本高于简单存储。
- 索引会额外占用磁盘和内存。
- 分词器选错会导致召回率或准确率下降。
- 近实时搜索意味着刚写入的数据不一定立即可见。
- 大量 Segment 会影响查询和合并性能，需要合理设置刷新和分片策略。

### 第七层：实践应用

一个简单的全文字段通常这样设计：

```json
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "standard",
        "fields": {
          "keyword": {
            "type": "keyword"
          }
        }
      }
    }
  }
}
```

这里：

- `title` 用于全文检索
- `title.keyword` 用于精确匹配、排序和聚合

### 常见误区

- 认为倒排索引就是把字符串倒序存储。
- 认为所有字段都按同一种方式建立倒排索引。
- 认为写入后立即就能搜索到。
- 只说查询快，不说词典、Posting List 和集合运算。

### 面试话术

“Elasticsearch 的倒排索引就是把文档中的词项作为 key，反向记录包含这个词的文档列表。写入时先经过 analyzer 分词，再建立词典和 Posting List；查询时把搜索词分析后直接定位倒排表，做列表合并并计算相关性，所以不需要扫描全部文档。`text` 主要用于全文检索，`keyword` 更适合精确匹配、排序和聚合。”
