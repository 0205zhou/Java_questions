# RabbitMQ消息可靠性保证？

## 联想记忆法

### 记忆口诀/联想

**口诀：发不丢、存不丢、收不丢、处理不重、异常可补。**

RabbitMQ 消息可靠性通常围绕 5 个问题展开：

1. **生产者发出去会不会丢**
2. **Broker 存储时会不会丢**
3. **消费者收到前会不会丢**
4. **消费者处理时会不会重复**
5. **异常场景怎么兜底**

### 记忆原理

可靠性不是一个开关，而是一整条链路的保证：**生产端确认 + Broker 持久化 + 消费端确认 + 幂等处理 + 失败补偿**。只讲其中一个点，比如只讲消息持久化，是不够的。

### 关联知识

- 可靠性和高吞吐通常是权衡关系。
- “不丢消息”与“绝不重复”很难同时零成本实现，因此业务上通常要做幂等。
- RabbitMQ 更常见的是“至少一次（at least once）”语义，而不是天然“恰好一次”。

## 深度解答

### 第一层：核心概念

RabbitMQ 消息可靠性保证，指的是尽可能确保消息在 **生产、存储、投递、消费** 这条链路上不丢失，并且出现失败时能被重试、补偿或幂等处理。

完整来看，一般要从 5 个层面保证：

1. 生产者确认
2. 交换机和队列持久化
3. 消费者手动确认
4. 失败重试与死信队列
5. 业务幂等与补偿机制

### 第二层：生产端如何保证不丢

#### 1. Producer Confirm（发送确认）

生产者把消息发给 Broker 后，Broker 会通过 confirm 机制告诉生产者消息是否成功到达。

如果没有 confirm，生产者发出去以后就不知道 RabbitMQ 到底收没收到。

#### 2. Return 机制

消息可能到达了 Exchange，但因为没有匹配的队列，最终没法投递。此时可配合：

- `mandatory`
- `ReturnCallback`

来让不可路由消息回到生产者侧，避免“到了交换机但没人接”这种隐性丢失。

#### 3. 生产端重试与落库

对高价值消息，常见做法是：

- 本地消息表
- 发送失败重试
- 定时补发

这样即使 RabbitMQ 或网络短暂异常，也能后补。

### 第三层：Broker 端如何保证不丢

#### 1. 队列持久化

把队列声明为 durable，RabbitMQ 重启后队列定义仍在。

#### 2. 消息持久化

发送消息时把投递模式设为持久化，这样消息不会只存在内存里。

#### 3. 交换机持久化

交换机也可以声明为 durable，避免 Broker 重启后交换机丢失。

需要注意：**只持久化队列，不持久化消息，不等于消息可靠；只持久化消息，不持久化交换机和队列，也不完整。**

### 第四层：消费端如何保证不丢

#### 1. 手动 ACK

消费者处理完业务后再手动确认：

- 处理成功 -> `ack`
- 处理失败 -> `nack` / `reject`

如果用自动确认，Broker 刚把消息推给消费者就认为“你已经处理好了”，一旦消费者业务执行失败或宕机，消息就可能丢。

#### 2. 失败重回队列

消费失败时可以选择重新入队，让后续重新消费。但要防止无限重试打爆系统。

#### 3. 死信队列（DLQ）

多次失败、过期、被拒绝的消息，可以进入死信队列，交给专门流程排查或补偿。

### 第五层：为什么还要幂等

RabbitMQ 很多可靠性策略实现的是 **至少一次**：

- 消息可能重复投递
- 消费者可能重复处理

所以业务必须考虑幂等，例如：

- 订单状态更新前先判断状态机
- 用唯一业务单号防重
- 用 Redis / 数据库唯一约束控制重复消费

如果没有幂等，你虽然保证了“不丢”，却可能带来“重复扣款、重复发券、重复下单”。

### 第六层：典型可靠性方案

一个较完整的可靠性链路通常是：

```text
生产者
  -> 本地消息表/重试
  -> Confirm 确认
  -> Return 回退
RabbitMQ
  -> durable Exchange
  -> durable Queue
  -> persistent Message
消费者
  -> 手动 ACK
  -> 失败重试
  -> 死信队列
业务层
  -> 幂等校验
  -> 补偿机制
```

### 第七层：深入思考

#### 1. 为什么不能只靠 RabbitMQ 本身

中间件只能尽量保证“消息到达和投递”，但业务成功与否最终还是应用自己负责。所以完整可靠性一定要包含 **业务补偿** 和 **幂等设计**。

#### 2. 为什么可靠性和性能要权衡

开启 confirm、持久化、手动 ack、重试、死信后，可靠性更高，但吞吐和延迟都会有成本。不能所有消息一刀切都用最重方案，通常要按业务价值分级。

## 回答思路

### 答题逻辑框架

1. 先说可靠性要覆盖生产端、Broker、消费端和业务端。
2. 再分层讲：Confirm/Return、持久化、手动 ACK、死信、幂等。
3. 最后强调 RabbitMQ 常见是至少一次语义，业务上必须防重。

### 重点得分点

- 能说出 Confirm 和 Return 的作用。
- 能说出交换机、队列、消息都要考虑持久化。
- 能说出手动 ACK 比自动 ACK 更稳。
- 能说出死信队列和幂等处理。

### 常见误区

- 认为消息持久化就等于绝对不丢。
- 认为 MQ 保证可靠性后业务就不用幂等。
- 只说消费确认，不说生产确认。

### 面试话术

“RabbitMQ 的消息可靠性要分链路看：生产端用 Confirm 和 Return 保证发得出去且可路由，Broker 端用 durable exchange、durable queue 和 persistent message 保证重启后尽量不丢，消费端用手动 ACK、失败重试和死信队列保证处理前不丢，业务层再用幂等和补偿解决重复消费与最终一致性问题。它通常保证的是至少一次，所以防重不能省。”
